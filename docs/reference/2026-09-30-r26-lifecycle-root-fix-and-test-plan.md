## 1. 结论与适用范围

当前的目标、知识、规划、执行、身体监督和输入出口分工可以继续保留。需要修正的是：共同规则只有数据表达，部分调用者仍能绕过规则；状态归属已经分开，但决定下一步的权限还没有完全分开；测试替正式代码提前提供了正确身份和时间，遗漏了实际创建与使用这些数据的路径。

本方案把“根治”定义为：修过的错误有明确的责任入口，同类错误会被自动检查发现，并且合法事件不会再从另一条调用路径绕开规则。它不承诺有限测试能证明整个项目永远没有缺陷。

本次只处理身份、期限、结果接纳、信息批次、证据撤销和相关身体责任。物理、几何、视觉权限、路径评分和新运动能力不在修改范围内。

与现有方案的关系：

- [R26 原方案](../motion_navigation/stages/navigation-async-work-lifecycle-r26-plan.md)中的稳定身份、固定期限、当前事实接纳和完整退场要求继续成立；
- [D046](../motion_navigation/decisions/0046-reopen-s5-for-asynchronous-work-lifecycle.md)解释为什么需要这些规则；本方案补足执行方式和测试方式；
- [协调架构](../motion_navigation/architecture/navigation-coordination-v1.md)和[协调验收](../motion_navigation/acceptance/navigation-coordination-refactor.md)仍是正式入口；
- [下一阶段验收门槛](2026-09-28-next-stage-gates.md)中的检测前移、同类搜索和缺陷台账要求继续保留。

本文件基于只读代码核对及主对话传来的复现反馈。这里没有重新运行那些复现，也没有取得完整的独立审查报告。下列问题在实施前都必须转为仓库内可重复的失败检查，不能把参考方案写成已完成证据。

## 3. 先固定谁有权决定什么

“owner”指长期保存某类状态，并决定这类状态何时开始、更新和结束的模块。其他模块通过接口向它提供事实或请求。

| 内容 | 唯一决定者 | 其他模块可以做什么 |
|---|---|---|
| 执行实例身份 | 创建执行实例的父级 | 保存和传递，不能按路线几何重新生成 |
| 一项异步工作的身份、期限和终结 | 对应领域 owner，通过共用的小型生命周期实现 | 交付结果或申请取消，不能改期限或清内部字段 |
| 信息是否取得、是否到期、是否可重开规划 | `PlanningCoordinator` | Session 提交观察和传感器结果，处理返回的完整结果 |
| 路线和动作证明是否能用于当前任务 | 现有接纳入口及其 owner | 提供当前身体、目标、知识和输入账本 |
| 放置是否确认、证据是否失效 | `BlockPlacementTransaction` | driver 提供真实派发记录和后续观察 |
| 谁继续控制身体、何时能交接 | 现有 `ExecutionSupervisor` 及身体控制契约 | 请求停止或接管，不能因计算失败直接释放身体 |
| 最终输入提交 | Runtime 的唯一输入出口 | 提交带约束的意图 |

Session 可以汇总这些结果并路由事件，但不得重新解释为“看起来有进展，所以再试一次”。真正的新尝试要由相应 owner 取得现有账本许可后创建。

## 4. 四项具体修正

### 4.1 实例身份由父级分配，路线字段只描述路线

一条几何路线可以被执行多次。两次执行必须有不同的实例身份，即使任务、目标、请求编号和动作编号都一样。

准备这样做：

1. 先核对 Runtime 已有的 `scope / slot / generation` 分配能否提供所需实例身份。能复用就复用，不建立第二套全局注册表。
2. 路线执行实例由 Session 分配实例号。分配必须包含不会因 successor 创建而重置的父级范围，以及该范围内的递增代次。
3. `MotionRouteCoordinator` 构造时必须接收这个身份，删除按 `route_id / route_revision / planning_generation` 自行推导身份的默认路径。
4. successor 继承共享 worker 和邮箱时，要取得新的会话实例身份。旧 identity 已退场，不会在新会话中被再次注册。
5. 工作修订仍使用一个权威计数。不要让 solver、邮箱和 executor 各自递增同一个 revision。
6. 邮箱、窗口历史和退场索引使用完整 `AsyncWorkIdentity` 作为键。文本 key 只用于显示和日志。

同时核对规划、动作求解和放置的字段来源：`task_id` 来自任务 owner，不能用可能变化的 `goal_id` 顶替；`owner_instance_id` 标识本次执行实例，不能只填可重复的 interaction 名称。沿用同一任务的重试和改目标，保留任务身份，但创建新的执行实例或工作修订。

如果实例会在输入源注册之前创建，应使用已有的父级会话实例范围分配；不能为了取得身份提前注册真实输入，也不能从可重复的用户 session 名推导唯一性。

完成条件：通过正式接口连续创建原会话和 successor，执行相同任务与相同路线，两项工作仍有不同 identity。旧成功、旧失败、旧取消回执都只能增加迟到诊断，不能改变新 pending、许可、额度、路线或任务状态。

### 4.2 生命周期规则增加行为，期限只由 owner 的时钟判断

现有值对象继续保留。增加一段三个领域共用的小型行为实现，负责活动 identity、固定窗口、接纳资格和一次终结。它不理解路线、方块、动作证明或身体控制，也不创建线程、队列和调度框架。

建议接口如下。名称可以根据仓库约定调整，职责不能改变：

```python
class AsyncWorkLifecycle:
    def __init__(self, clock_ns): ...

    def begin(
        self, identity, movement_tick, budget_ns,
        owner_deadline_ns=None,
    ) -> AsyncWorkWindow: ...

    def check_result(self, identity) -> WorkCheck: ...

    def finish(self, identity, outcome) -> WorkFinishResult: ...

    def retire(self, identity, cause) -> WorkRetirementSummary: ...
```

该对象只拥有本项工作的身份、窗口和是否终结。领域 owner 保留业务状态。迁移后删除领域中重复维护的活动 identity、窗口和终结标志，不把它们复制一份再声称归属统一。

`WorkCheck` 至少区分：可以继续接纳、身份不匹配、已终结、已到期。它不是一个真假值。领域还要继续核对当前任务和事实。

时序必须固定为：

1. 从产生需求时读取 owner 的单调时钟，创建窗口。
2. 结果返回时由生命周期对象再次读取同一时钟。
3. 身份通过后，领域核对当前事实，准备下一步处置。
4. 真正生效前再次核对期限和活动身份；只有通过后才能提交成功结果或安装候选。到期则形成超时终结，不能继续等。

第四步只需复用同一控制帧内仍有效的事实核对结果；不要求机械重复昂贵的几何计算。若事实版本已变化，则重核对应依赖。

`check_result` 只是检查，不授予生效权限。每个领域只保留一个内部接纳入口，完成事实核对、最终期限核对、业务写入和接纳记录。该入口由 owner 串行执行，中间不调用可能切换任务的外部回调。路线安装、证明接纳和放置 COMPLETE 都必须从这个入口产生，其他分支不能直接写成功状态。这样才能防止增加公共类型后，调用者仍绕过它自行决定。

特别约束：

- `received_monotonic_ns` 说明观察有多旧，不能代替现在的接纳时刻。
- 后台计算时长、排队时长、运动 tick 和观察序列也不能代替接纳时刻。
- 到期检查必须先于“这不是新观察，所以继续等”。旧观察反复轮询也不能绕过期限。
- 调用暂停期间不新增看门狗线程；恢复调用后先处理到期。暂停期间的真实输入仍受现有客户端租约保护。
- `finish` 和 `retire` 都要按指定 identity 操作。重复终结返回已有结论，旧 identity 不触碰新工作。
- 成功和事实取得受期限约束；超时、取消及 owner 主动失败仍能在期限后结束工作。不能因为已经到期，反而禁止终结。
- 退场摘要保持有界。摘要淘汰后的旧调用可以返回“旧工作已不活动”，无需永久保存所有历史，但不能重新接纳旧结果或生成权限。
- 期限到达结束的是计算或确认许可，身体安全收尾继续由监督者负责。

放置确认的起点是 Runtime 实际提交交互输入的时刻。输入出口记录该次提交的单调时间、控制序号和客户端 tick 关联，事务据此建立固定窗口；不能等后续轮询收到回执时，才从那一刻重新计时。没有赢得仲裁、没有真正发送的提案，不启动确认窗口。准备阶段仍使用自己的原期限。

不要把准备提案的旧观察时间当作提交时间。日志分别记录观察、提交和接纳时刻。只在同一时钟范围内相减；worker 自己的计算时长和客户端 tick 单独关联，不能未经对齐混算。如果领域还有更早的 tick 失效条件，可以保留，但它不能延长单调时钟期限。

完成条件：只推进 owner 的单调时钟、保持观察和客户端 tick 不变，所有 owner 仍能按固定期限拒绝结果或形成准确超时。到期边界使用 `now >= deadline`，不因证据先进入队列而放行。

### 4.3 信息批次由协调器一次处理，Session 完整消费结果

当前逐个上报 blocker 的循环存在一个风险：处理第一个 blocker 时，工作可能已经结束或换批；循环还继续使用旧选择。仅在循环中加 `break` 可以修一个位置，但不能防住其他调用者继续报告旧选择。

准备收口为一个正式入口：

```python
PlanningCoordinator.reconcile_information(
    selection_identity,
    frame,
    sensor_outcomes,
) -> PlanningUpdate
```

这是建议新增的入口，当前代码还没有它。返回值继续复用 `PlanningUpdate`；不增加一套与现有规划状态平行的状态机。

入口内部完成：

1. 检查选择 identity、是否活动和固定期限。
2. 到期时一次终结整项信息工作，不再逐个上报同一批次超时。
3. 在有效期内重新运行类型化事实查询。确定为阻塞也算取得知识，不表示路线可行。
4. 处理不可获取事实和后续批次选择。
5. 取得事实后记录一次真实进展、结束旧信息工作，并由协调器使用一次性许可创建下一次规划尝试。
6. 返回完整的当前处置；重复或旧批次报告只丢弃并记录，不能让正常异步迟到变成公开接口异常。

格式错误和非法参数仍可以抛契约异常。合法取消、过期或旧结果应成为有类型处置，两者不能混为一谈。

Session 使用一个处理入口消费所有规划结果：

| `PlanningUpdate.kind` | Session 行为 |
|---|---|
| `RUNNING` | 保留工作与必要身体责任，等待当前尝试；不自行重发 |
| `NEEDS_INFORMATION` | 使用返回的当前批次提出观察请求 |
| `ROUTE_READY` | 按现有接纳和监督规则安装路线 |
| `REQUIRES_INTERACTION` | 交给现有世界交互流程 |
| `FAILED` | 处理准确失败及安全收尾；不能落入通用“信息更新”重规划 |

协调器允许重试时，先向现有 `RetryLedger` 取得许可，再返回新的活动尝试。Session 不得使用 `outcome is None`、`information_updated` 或 reason 字符串替代这个决定。

完成条件：一个、三个和 64 个自然 blocker 在同帧到期，都只产生一个信息工作终结。期限后取得事实不会生成进展许可或额外请求；旧批次重复报告不会抛异常，也不会回到规划中。

### 4.4 放置保留证据记录，后续反证能够使其失效

世界方块和库存数量可以在不同观察中到达。但“曾经确认过”与“现在仍可据此确认事务”必须分开。

准备这样做：

- 保存部分证据对应的事务 identity、观察序列和具体值，不只保存两个永久为真的布尔标志。
- 新观察缺少一个字段时，表示暂时没有新证据；不能直接解释为方块消失或库存恢复。
- 新观察明确目标格为空、方块变成错误材质、库存计数恢复或选槽改变时，旧对应证据失去接纳资格。
- 在 COMPLETE 前，确认两项证据仍属于当前事务、没有被更新观察推翻，并且 owner 当前接纳时刻仍在期限内。
- 生命周期结束后，迟到证据只进入诊断，不复活旧事务。

举例：序列 10 看见目标格出现土块，但库存字段缺失；序列 11 明确看见土块已被挖掉，同时库存减少了一块。这能说明发生过放置迹象，却不能说明目标格仍具备搭桥支撑。不能把它报告为可继续过桥的 COMPLETE。

这类结果使用现有失败或重新评估出口，并保留实际库存消耗证据。不能因确认失败就假装没有消耗物品，也不能自动再点一次掩盖世界变化。若以后需要区分“操作发生过”与“支撑仍可用”，应在当时的领域契约中明确；本轮不新增通用证据框架。

完成条件：两类证据的先后、缺失、重复、撤销和迟到都得到唯一准确结果。证据撤销不能误报成功，字段缺失也不能被误判为撤销。

## 5. 邮箱与身体责任必须一起核对

### 5.1 活动工作先登记，再允许结果占用邮箱

共享邮箱增加活动 identity 的有界登记。只有已登记且未退场的 identity 可以占用结果槽。没有接收者、已退场和重复的结果先丢弃，再判断容量。

同一控制帧仍由共享 owner 排空 worker 一次。incumbent、待接替路线和 successor 通过同一分发器领取自己的结果，不各自轮询 worker。

容量检查至少验证两件事：

- 大量旧结果不能挤掉当前必要结果。
- 满载时提供准确的有类型处置或背压，不阻塞控制线程，也不无限保存无人接收的结果。

不要仅依靠有限的退场历史挡旧结果。退场历史淘汰后，旧 identity 仍然不是活动工作，不能再次进入邮箱。

### 5.2 业务终结与身体退场分别验证

这轮必须继续保留：计算超时、信息失败和放置失效不能直接清空身体控制者。

B11 已验证的着地位移重锚不能外推为空中恢复。需要通过正式路径验证：放置接近时取消、改目标、输入迟到和外力离地，是否仍有明确身体负责人。

若离地场景复现无负责人释放，必须通过现有身体控制契约和 `ExecutionSupervisor` 修正交接。不能仅在文档里写“交给 C1”，却没有真实的请求、接管确认和原控制者退出记录。

可以暂不发布“空中恢复后继续放置”，但必须准确报告能力范围，并保留必要的身体收尾责任。功能未授权不等于可以丢掉已经持有的身体。

## 6. 真正有效的测试怎样设计

### 6.1 测试自己的替身是否掩盖错误

正式闭环继续使用：

```text
Runtime
  → 正式导航或世界交互 driver
  → NavigationSession / PlanningCoordinator
  → 正式规划、接纳、动作执行和 motion 分发
  → Runtime 仲裁和输入账本
  → 测试后端
```

可以替换游戏、时钟和后台结果交付时间。不能替换待审查的 identity 分配、结果接纳、重试许可、Session 分支或身体交接。

测试不允许：

- 给原会话和 successor 手工填入不同 owner，然后只验证邮箱路由；
- 给观察时间自动加上墙钟延迟，使错误的时间来源看起来正确；
- 手工创建 progress permit，让本来不该重开的尝试成功；
- 写 Session 私有字段制造或修复所需状态；
- 只设置 `identity_valid=True` 等诊断布尔值就认定规则成立；
- 只看最终落地或有界失败，忽略中途异常、错误额度或身体失主。

已有隔离单元测试仍可保留，但必须配一条正式入口测试来证明生产者会生成正确数据。

### 6.2 三类时间独立推进

测试时钟必须分别控制：

1. owner 的单调时钟；
2. 客户端运动 tick；
3. 观察采样、接收和当前处理时刻。

至少覆盖：

| 时间排列 | 预期 |
|---|---|
| 三类时间正常推进 | 原正常路线和放置完成 |
| owner 时钟已到期，tick 和观察时间不变 | 过期结果被拒绝；等待有类型结束 |
| 结果在截止前入队，owner 在截止后领取 | 仍按过期处理 |
| 客户端一次补跑多个 tick | 按动作窗口局部处理，Runtime 不被重建 |
| 截止前 1 ns、正好截止、截止后 1 ns | 分别验证接纳和拒绝边界 |
| 新观察已到，包含的方块或库存事实不同步 | 按证据关联处理，不把到达顺序当成因果证明 |

使用可注入时钟，不通过 `sleep()` 制造多数时序测试。另保留实际 worker 的小型进程测试，检查排队、背压和迟到分发。

### 6.3 必须加入的正式场景族

以下编号是本方案的测试场景编号，不替代正式缺陷台账。

| 场景族 | 必须由正式入口产生的条件 | 必须断言的结果 |
|---|---|---|
| T1 实例复用 | 同任务、目标和路线：原会话取消并退场，再创建 successor | identity 不同；旧成功、失败和重复结果不改变当前工作或额度 |
| T2 身份隔离 | 同 subject 和 revision，分别改变世界会话或执行实例 | 结果只交给匹配 owner；退场历史淘汰后旧结果仍拒绝 |
| T3 同帧终结 | 自然规划产生 1／3／64 个 blocker，到期后同帧轮询 | 一次终结、无公开异常、无活动旧批次、无新许可 |
| T4 期限后事实 | 信息到期后，当前观察第一次确定 blocker | 不产生 ACQUIRED、不增加规划代次；失败被 Session 正确消费 |
| T5 放置时间 | 正式 Runtime 派发后，确认观察先到、owner 后处理 | 按处理时刻拒绝到期证据；记录真实派发和接纳时刻 |
| T6 证据撤销 | 世界先确认后变空气；库存先减少后恢复；对照为字段缺失 | 明确反证撤销证据，字段缺失不伪造反证；不错误 COMPLETE |
| T7 邮箱饱和 | 当前请求与大量旧／未知／重复结果交错 | 当前结果不被无关结果挤出；满载有类型且非阻塞 |
| T8 生命周期交错 | 准备、背压、已提交、待接纳、部分证据阶段分别取消／关闭／改目标 | 每项工作最多一次终结；旧 identity 退场不清理新工作 |
| T9 身体责任 | 求解或确认失败时身体仍有惯性、仍在空中或有在途输入 | 身体由明确控制者继续收尾，释放需证据，尾迹无新增可避免违规 |

每个场景要有正常对照。例如 T5 同一证据在期限内处理必须完成；否则实现可以用“永远失败”通过所有过期检查。

### 6.4 自动检查结果之间的关系

除逐个期望值，还增加以下成对运行：

- **有无旧结果对照：**同一正常任务加入任意旧结果，任务状态、当前工作和额度与未加入时一致，允许诊断计数不同。
- **重复交付对照：**同一有效结果交付一次或多次，业务生效次数和额度消费相同。
- **证据顺序对照：**只改变世界和库存证据顺序、且没有撤销或过期，确认结果一致。
- **身份字段对照：**保持任务和路线相同，只改变执行实例或世界会话，旧结果必须失去接纳资格。
- **观察时间对照：**保持事实和旧观察时间相同，只延迟 owner 的处理时刻，跨过截止后结果必须改变为拒绝。

这些关系有助于发现测试没有预先列出的相邻问题。它们验证公共行为，不重复求解器或控制器算法。

### 6.5 每次生效都要有可核对的记录

公开只读诊断或结构化事件至少包含：

- identity、subject、revision 和当前活动 owner；
- 工作开始时间、固定截止、实际派发、结果入队和接纳时刻；
- 事实核对用到的观察序列、依赖版本和部分证据值；
- 终结、退场、一次性许可消费、请求创建；
- 身体负责人、停止请求、交接证据和最终输入来源。

监视器将日志事件与实际状态对照，检查 I18—I22：

1. 同 identity 的截止不变；不同活动实例不能重名。
2. 每次 APPLIED 对应一个当前身份、期限内的接纳及有效事实依据。
3. 已退场 identity 不再拥有 pending、候选、局部等待或邮箱结果。
4. 信息进展要有类型化查询结果；失败结果不能无许可产生新尝试。
5. 每条 worker 结果只有一个接收者或明确丢弃原因。

缺少观察字段或记录时应报告覆盖缺口，不能用默认真值补齐。“没有 APPLIED 事件”时，不能因为没有违规就宣称接纳门槛得到覆盖。

### 6.6 证明门禁确实能发现错误

在独立临时测试目录中故意恢复四种错误，逐项运行对应门禁：

- 执行实例身份改回按路线字段生成；
- 接纳时间改回观察接收时间；
- 忽略信息确认的 FAILED；
- 让部分放置证据不能撤销。

每项都必须由对应的正式场景稳定失败。恢复正确实现后全部通过。另向监视器喂入已退场工作再次 APPLIED、超期 APPLIED 和无许可重开的合成事件，确认它会报错。

测试目录不改当前生产工作区。无需引入全库变异测试框架；只验证这几个已经发生过的错误，确实有能挡住它们的自动门禁。

## 7. 随机序列怎样补强

继续复用 `tests/sim`，扩展现有事件生成器与可控 worker，不创建另一套模拟器。

新增可组合事件：原会话退场后创建同任务 successor、旧结果迟到或重复、队列背压、只推进 owner 时钟、旧观察延迟处理、信息批次同帧到期、部分证据出现后撤销、世界会话变化。

事件可以重复，触发时刻围绕真实阶段和截止边界选择。不能只在固定全局 tick 触发，否则动作变慢后可能根本没有测到目标阶段。

冻结的 1000 个种子继续作为回归。另保留扩展种子，避免只记住固定序列。结果必须分别报告：

- 任务成功、有界失败、有界取消和意外结果；
- 每种事件的生成、派发、生效和跳过次数；
- 每条关键分支的实际覆盖次数；
- 首次违规及自动缩减后的最短事件序列。

每个场景事前声明可接受结果。正常输入正例必须完成；旧结果扰动不应增加任务失败；超出窗口的输入扰动可以得到事前允许的有界结果。不能把“全部有界失败”写成能力通过，也不能运行后再扩大白名单。

缺陷缩减时必须保留触发所需的时间顺序、旧结果 identity 和证据反转；否则缩减出的脚本可能不再复现原问题。

## 10. Fabric 怎么测，怎样关闭门槛

模拟首先关闭代码和时序反例；Fabric 用来确认模拟没有遗漏真实输入、观察和世界事件的关系。

至少补以下窄范围对照：

1. 正式导航驱动跨隙：同任务 successor 及旧结果交错；仍检查输入应用窗口和落地责任。
2. profile 4 搜索前沿：自然产生多个缺失事实，确认取得、不可获取和到期处置的真实调用路径。
3. B11：正常放置、确认处理延迟、部分证据撤销及放置准备阶段的取消／改目标。
4. 若修正了 B11 身体接入：叠加有控制的外力，记录原 owner 停止、恢复 owner 接管和安全落地。未跑到接管分支不能写成通过。

测试世界事件只能走独立测试入口。不能直接修改正式 WorldKnowledge、库存或事务状态，伪造世界变化已经发生。真实的证据撤销要进入正式观察链。

不自动重复 800 场连续高度。若修改实际运动输入、动作交接或身体释放时序，则按受影响的场景族扩大回归，并写清证据仍适用的范围。

S5 再次关闭需要同时满足：

- 审查报告中的确定问题有基线失败和修复后通过证据；
- T1—T9 的适用场景均覆盖正式入口，正常对照也完成；
- 四种故意恢复错误都被自动门禁发现；
- I18—I22 能从真实记录检查，关键分支无未说明覆盖缺口；
- 旧结果不改变新工作，无许可重开、重复终结和期限后生效均为零；
- 固定和随机结果符合事前口径，任务成功率不因“有界”而被隐藏；
- 已承担的身体责任在业务失败后仍有明确收尾和交接；
- 针对性 Fabric、独立导出和四类正式文档与源码一致。

测试数量、文件缩短或实机正常样本通过都不能单独作为关闭理由。每条共同规则要同时有正常路径、反例、正式创建入口和可独立复核的证据。
