# R26：异步工作生命周期与结果接纳整改方案

历史状态：R26 当时完成既有门槛。后续审查发现接纳入口仍可被绕过，按 [R27](navigation-async-work-r27-root-fix-plan.md) 处理。2026-10-01，R27 复审整改完成，S5 按其冻结范围重新关闭；下文只保留 R26 历史结果，当前结论见协调验收第 20 节。

## 1. 要解决什么

R25 把规划行为收进了 `PlanningCoordinator`，但后续审查证明，多个模块仍把异步工作看成几个彼此独立的阶段：先准备，再提交，再等待结果。期限、身份核对和退场只覆盖其中一部分。

这会产生同一种错误：工作已经开始，但当前阶段没有期限；旧结果返回时，系统只确认“这是哪个任务的结果”，没有确认“它现在是否仍然成立”；任务结束时，只清理了部分阶段状态。

已经通过正式组件复现的问题包括：

1. 快照构建因范围外变化持续重启，200 秒后仍停在规划中；
2. 后台返回信息需求前，所需格已经变成已知方块，系统仍等待同一格直到超时；
3. 旧地图上的“无路线”在道路已经补齐后仍直接判定任务失败；
4. 动作求解超时后提交了新修订，旧修订的迟到失败会终结新修订；
5. 动作求解 worker 持续拒绝提交时，1000 tick 后仍无限等待；
6. 放置目标格已经确认、库存证据持续缺失时，确认期限被绕过；
7. 取消和关闭只清理后台提交，没有结束快照、候选和信息选择；
8. R25 的 profile 4 场景实际经过终点解析，没有验证搜索前沿信息选择。

这些问题不是八个独立补丁。本轮建立三条共享规则，并让规划、动作求解和世界交互分别遵守：

- 一项工作从产生需求时开始计时，阶段变化和部分进展不能续期；
- 任何异步结果都要先核对工作身份，再核对当前事实；
- 工作所有者统一负责开始、终结和完整退场，调用者不能选择性清理内部字段。

## 2. 不在本轮做什么

- 不修改物理计算器、支撑面几何、视觉空气规则、路径评分或唯一输入出口；
- 不新增 Swim、Climb、SprintJump、探索移动或战斗策略；
- 不建立通用任务框架、插件系统或新的线程池；
- 不为了缩短文件而拆分 planner、Session 或 controller；
- 不把所有同步计算包装成异步工作；
- 不重跑连续高度 800 场，除非整改实际改变运动输入、动作交接或身体释放时序。

本轮只抽取已经在规划、动作求解和放置确认中重复出现的三条规则。每个领域仍保留自己的结果类型和事实验证方法。

## 3. 公共契约

### 3.1 工作身份

每项可能跨帧或跨线程完成的工作，都要有稳定且不会在同一任务内重名的身份。公共部分建议使用不可变值对象：

```python
@dataclass(frozen=True, slots=True)
class AsyncWorkIdentity:
    world_session_id: str
    task_id: str
    owner_instance_id: str
    work_kind: AsyncWorkKind
    subject_id: str
    revision: int
```

字段含义：

- `owner_instance_id` 区分同一任务内的原会话、successor、旧路线执行器和新路线执行器；
- `subject_id` 由领域决定，例如规划请求、路线动作连接或放置事务；
- `revision` 只在同一个 owner 和 subject 内递增；不能用几何路线 hash 代替执行实例；
- planner worker 和 motion worker 返回结果时，必须原样带回完整身份。

各领域可以在这个身份外保留自己的 `request_id`、`goal_revision`、`candidate_revision` 和动作索引。公共身份不能替代领域身份，但负责判断迟到结果是否仍属于当前活动工作。

`owner_instance_id` 由创建该长期 owner 的上一级分配，并在 owner 重建时更换，不能由 coordinator 从零计数后独立生成。`revision` 与现有 `candidate_revision`、规划尝试序号只有一个权威映射；迁移后不能保留两套各自递增的修订号。

### 3.2 固定期限

工作在第一次产生需求时同时记录：

```python
@dataclass(frozen=True, slots=True)
class AsyncWorkWindow:
    started_movement_tick: int
    started_monotonic_ns: int
    deadline_monotonic_ns: int
```

约束：

- 快照构建、排队、提交、后台计算、结果接纳和等待补充证据共用同一个外层期限；
- 阶段内部可以有更短期限，但不得超过或刷新外层期限；
- 正常增加知识、部分确认和重建内部对象不能延长期限；
- 真实任务更新应结束旧工作并创建新身份，不得偷偷延长旧工作；
- 单调墙钟是正式期限。运动 tick 用于证据关联和确定性测试，不能在客户端停 tick 时替代墙钟；
- 到期先形成一次有类型终结，再决定是否由 `RetryLedger` 产生下一次许可。

不同工作的边界固定如下：

| 工作 | 从何时开始 | 何时终结 | 期限来源 |
|---|---|---|---|
| 规划计算尝试 | 创建快照需求 | 路线、信息需求、交互要求、否定结论或失败完成接纳 | `min(规划预算, 调用方仍有效的期限)` |
| 信息取得 | 接纳一批仍然缺失的 blocker | 某项事实确定、整批不可获取或信息期限到达 | 现有信息获取期限；不能刷新产生它的任务期限或恢复任务总额度 |
| 动作求解 | 执行器首次发现当前动作缺少证明 | 证明或有类型失败完成接纳 | `min(动作求解预算, 调用方仍有效的期限)` |
| 放置准备 | driver 开始走位、选槽或瞄准 | 实际提交交互输入，或准备失败／取消 | 现有准备期限 |
| 放置确认 | 实际提交交互输入 | 成功、证据不完整超时、失败或取消 | 固定确认期限 |

因此，规划返回 `NEEDS_INFORMATION` 时，规划计算尝试已经终结。信息取得是与该尝试关联的新工作。取得事实后再用一次性进展许可创建新的规划尝试，不能续用旧规划期限。

现行导航没有一个可以替代所有局部期限的统一任务墙钟。上层 owner lease 或明确任务期限存在时，各工作期限必须取更早者；任务级重试额度是次数边界，不能称为“任务总期限”。结果是否到期按 owner 实际接纳时的单调时钟判断。即使结果在期限前进入进程队列，期限后才被 owner 轮询，也按过期处理。

工作期限只限制计算和确认。期限到达后，安全停稳、在途输入确认和身体责任转交继续由 `ExecutionSupervisor` 完成，不要求身体在计算期限到达的同一帧立即释放。

### 3.3 结果接纳

所有异步结果统一按下面顺序处理：

1. 当前 owner 是否仍存在；
2. 完整工作身份是否与当前活动工作相同；
3. 该工作是否已经终结过一次；
4. owner 接纳时刻是否仍在固定期限内；
5. 当前任务、目标和世界会话是否仍匹配；
6. 该类结果需要的事实依据在当前状态下是否仍成立；
7. 通过后才允许安装路线、宣布信息完成、登记失败或消费额度。

身份不匹配或已经终结的迟到结果只记录诊断并丢弃，不能：

- 清空当前 pending；
- 安装证明或路线；
- 登记当前工作的失败；
- 消费重试、伤害或放置额度；
- 改变任务状态。

“当前事实核对”由领域实现：

| 结果 | 当前事实核对 |
|---|---|
| 完整路线 | 继续使用 `RouteAdmitter` 核对身体、目标、依赖、资源和窗口 |
| 信息需求 | 使用 blocker 携带的类型化事实要求重新查询；坐标变化或存在记录不等于取得事实 |
| 无路线／不支持 | 核对搜索实际使用的有限快照体积或能力配置依据；相关范围变化后旧否定结论失效 |
| 动作证明 | 核对执行实例、动作位置、入口状态、世界依赖、输入账本和候选修订 |
| 放置确认 | 同时核对目标格、库存差额、事务身份和固定期限；部分证据不能绕过期限 |

不同结果不会假装拥有相同的事实依据：

| 结果类别 | 接纳规则 |
|---|---|
| 成功路线、信息需求、无路线等世界结论 | 身份、终结和期限通过后，再核对领域事实 |
| 动作不可解等依赖入口的否定结论 | 继续核对当前入口状态、动作依赖和规则版本 |
| worker 死亡、内部错误 | 按当前工作身份和期限接纳，不伪造世界事实依据 |
| owner 发出的取消 | 立即终结指定工作；后台取消回执只确认同一身份，不决定是否取消 |
| 期限到达 | 由 owner 独立形成终结，不能等待 worker 返回超时结果 |

事实核对不能通过时，领域接纳入口必须明确返回“按当前事实重算”“继续等待其他证据”或“有类型终结”，不能只丢弃结果并留下一个没有 pending 的活动工作。

每次结果生效都保存一条只读接纳记录，至少包含完整身份、owner 接纳时刻、固定期限、事实核对结果和最终动作。门禁据此判断结果是否真正经过接纳，不能只看结果对象上有 deadline 字段。

### 3.4 一次终结与完整退场

每项工作最多产生一个终结结果：成功、需要上层决定、有类型失败、被替换或取消。工作所有者提供一个幂等的完整退场入口，例如：

```python
retire(identity, cause) -> WorkRetirementSummary
```

`retire(identity)` 只结束指定 identity 拥有的活动状态。旧 identity 重复调用时返回原退场摘要，不能触碰同一 owner 当前的新工作。退场必须结束该 identity 拥有的：

- builder、不可变快照和变化记录；
- 已提交作业、排队意图和 pending 身份；
- 候选、信息批次、一次性许可和局部等待；
- 只能用于本次工作的临时额度保留；
- 领域控制器或身体责任的后续处置请求。

已经转交给接收者的不可变路线、信息要求和责任记录不再属于旧工作的活动状态。任务级已消费许可、`RetryLedger`、`TaskRiskLedger` 和 Runtime 在途输入账本不因工作退场而清空。

身体仍在运动或空中时，任务终结也不能直接释放控制者。工作退场只发送有身份的停止或交接请求，由 `ExecutionSupervisor` 保持唯一身体责任；退场摘要明确身体责任已经释放、已经转交，或仍由哪个控制者负责。

## 4. 领域边界

### 4.1 规划

`PlanningCoordinator` 继续拥有规划行为，但一次尝试从开始构建快照时建立身份和期限。范围外变化不能使快照失效；范围内正常新增知识可以重建内部快照，但不能刷新尝试期限。

所有 planner 结果都经过接纳：

- 完整路线核对明确依赖；
- 信息需求逐个重做类型化事实要求；已经变成确定事实的 blocker 从结果中删除，不要求该事实证明路线可行；全部确定时直接产生一次进展许可并重新规划；
- `NO_ROUTE_WITHIN_COMPLETE_SCOPE` 绑定本次尝试已经保留的有限快照体积，包括支撑面下探和顶部净空。接纳时用完整变化记录过滤到这个体积；分区版本变化但缺少完整变化记录时，按预算重新核对受影响范围，不能直接接受旧结论；
- `UNSUPPORTED` 区分能力配置导致和世界事实导致两类，分别核对规则版本或有限快照依据；
- 范围外变化不能废弃旧否定结论，也不能产生进展许可；
- 迟到结果不能复活已取消、已替换或已关闭的尝试。

worker 只需回传身份和依据引用，不复制整个世界。协调器在候选接纳完成前保留对应不可变快照及其有限体积描述。

终态、取消和关闭使用协调器的完整退场入口，不再由 Session 调用 `clear_submission()` 猜测要清哪些字段。

### 4.2 信息取得

信息流程返回经过验证的事实结果，而不是“某坐标发生过变化”。最小结果应包含：

```python
@dataclass(frozen=True, slots=True)
class InformationFactResult:
    work_identity: AsyncWorkIdentity
    selection_revision: int
    blocker_key: str
    requirement: PlanningFactRequirement
    outcome: InformationOutcome
    evidence_stamp: ObservationStamp | None
    query_result: PlanningFactQueryResult | None
```

`PlanningBlocker` 继续保留用于稳定排序和去重的 `blocker_key`，同时携带有限种类的类型化 `PlanningFactRequirement` 及其必要参数。首版只覆盖当前已经产生 blocker 的支撑事实、净空事实、扫掠事实和动作前置事实；不能从 `ground-sweep:1.800000` 或 `frontier_key` 的字符串表示反向拼回查询。

信息取得表示原来的未知已经变成确定事实，不表示路线一定可行。对知识要求，重新查询得到明确 `BLOCKED` 也算事实已经取得，后续是否存在路线由新一轮规划判断；只有查询仍返回未知时才继续等待。对动作专用证据，则必须满足该证据自己的明确条件。

`ACQUIRED` 只能由当前类型化要求的查询得到确定结果。`changed_cells` 和 `visible_air` 只是触发重新查询的信号，`ObservationStamp` 也不能单独证明原要求成立。不可获取、超出范围、完全遮挡和超时继续分别表达。

本轮不建立完整 `InformationAcquisitionCoordinator`，但要把“验证事实后才能报告取得”收进一个唯一入口，禁止 Session 直接根据坐标宣布进展。

### 4.3 动作求解

动作求解工作从执行器第一次发现“当前动作缺少证明”时开始，不等 `worker.submit()` 成功后才开始。

- 固定期限覆盖背压、提交、后台计算和结果接纳；
- `MotionSolveJob` 携带完整工作身份；
- 旧 revision 和旧执行实例的结果只能丢弃；
- 共享 motion worker 只能有一个结果消费入口。首版由现有 `NavigationSession` 在同一控制帧统一排空，再通过一个有界的小邮箱按身份分发给 coordinator；不能由多个 coordinator 分别 `poll_available()` 后丢弃别人的结果；
- successor 与 incumbent 同时存在时，要有测试证明结果不会串线；
- 到期或背压耗尽后，通过现有重试和 `ExecutionSupervisor` 安全退场，不把身体留给一个已经失败的动作。

邮箱有固定容量，工作退场时注销对应 identity；未知 identity 和已经退场的迟到结果直接记录并丢弃。若未来 motion worker 跨多个 Session 共享，再把同一个薄分发器上移到创建 worker 的 Runtime owner，不另建调度服务。

### 4.4 放置事务

`BlockPlacementTransaction` 从提交交互输入时建立固定确认期限。世界证据和库存证据无论以什么顺序到达，都先检查期限，再组合证据。

- 目标格正确但库存缺失，不能无限等待；
- 库存随后恢复但事务已经超时，不能复活成功；
- 已提交、目标格变化、库存变化和成功分别保留现有语义；
- 取消和目标修订要完整结束确认工作。

`RuntimeBlockPlacementDriver` 使用 `FixedRouteController` 接近边缘时，必须明确谁拥有身体责任。先用正式物理闭环验证取消、改目标和外力时是否可能带速度释放；若能复现，再把这段控制纳入 `ExecutionSupervisor` 或等价的已有交接入口。本轮不先假定一定需要新增控制者类型。

## 5. 实施顺序

### R26-0：重新打开 S5，冻结反例和状态

先把审查中的最小复现转成仓库测试，禁止先改实现：

- 快照持续重启仍受原尝试期限；
- 旧信息需求返回前事实已经取得；
- 旧无路线返回前道路已经补齐；
- motion revision 2 已提交后 revision 1 迟到失败；
- motion worker 持续拒绝提交；
- 放置世界确认后库存持续缺失；
- 取消／关闭后的 `planning_work_owned` 必须为假；
- 信息坐标发生变化但原查询仍不成立；
- 同一 Session 的旧路线与待接替路线同时等待不同 motion 结果；
- 已终态 Session 创建 successor 后，旧 Session 的迟到结果到达共享 worker。

同时把四个待确认风险做成测试或闭环实验：共享 worker 串线、successor 身份重名、B11 接近时取消的身体交接、信息变化误报取得。未复现的项目标为验证缺口，不能直接写成已修缺陷。

完成条件：每个确定问题在当前实现上稳定失败；测试记录实际状态和身份，不通过手工篡改诊断布尔值制造失败。

### R26-1：建立最小公共值对象与渐进门禁

新增工作身份和期限值对象，以及只读诊断字段。不建立统一基类，不要求 planner、motion 和 placement 返回同一种业务结果。

新增不变量：

| 编号 | 不变量 |
|---|---|
| I18 | 活动异步工作都有稳定身份、开始时间和不能续期的固定期限 |
| I19 | 每次结果生效都有接纳记录；过期、已终结、身份不匹配或事实依据失效的结果不能改变当前工作、额度或任务状态 |
| I20 | 每项工作最多产生一个终结结果；退场后没有该 identity 的活动内部状态 |
| I21 | 信息取得必须附带当前查询成功的证据，坐标变化不能单独形成 `ACQUIRED` |
| I22 | 共享 worker 的每个结果只由一个分发入口消费；匹配活动 owner 时只交给该 owner，无活动 owner 时有界丢弃 |

静态门禁检查旧入口，但正确性门禁必须读取真实工作字段、接纳记录和事实查询结果，不能只检查方法名或诊断布尔值。公共值对象可以先加入；严格门禁在对应领域完成原子迁移后逐项启用，避免半迁移代码同时维护两套权威状态。

### R26-2：原子迁移规划与信息取得

一次完成规划领域的身份、期限、接纳和退场：

1. 尝试身份由 Session／任务的唯一 owner instance 派生；
2. 固定期限覆盖快照构建至规划结果接纳，范围外变化不重启；
3. 路线、信息需求、无路线和不支持都经过对应的当前事实接纳；
4. 信息 blocker 改为类型化事实要求，信息工作使用独立期限；
5. 协调器增加按 identity 完整、幂等的 retire，终态、取消、替换和关闭统一调用。

完成条件：规划和信息的所有阶段组合都在各自固定期限内得到有类型结果；规划进入信息阶段时旧尝试已经终结；终态诊断不再报告旧 identity 的 builder、pending、候选或信息批次仍活动。

### R26-3：原子迁移动作求解

一次完成 motion 领域的身份、期限、结果分发和接纳：

- 从执行器第一次需要证明时创建身份和固定期限；
- 背压、提交、后台计算和接纳共用期限；
- `MotionSolveJob` 与结果携带执行实例、动作位置和唯一修订；
- `NavigationSession` 每帧只排空一次共享 worker，并通过有界邮箱按身份分发；
- 旧 revision、旧路线和旧 Session 的结果只记录迟到诊断；
- 到期、worker 故障和当前求解否定经过动作领域接纳，再通过现有重试与身体退场路径处理。

分别冻结两种场景：

- 同一 Session 中 incumbent 与待接替路线同时存在；
- 原 Session 已终态并释放后创建 successor，随后旧结果才到达。

完成条件：旧结果只增加迟到诊断，不改变当前 pending、执行器、额度、失败计数或任务状态；两个 coordinator 并存时，各自只收到自己的结果。

### R26-4：原子迁移放置事务

一次完成放置确认身份、期限、证据组合和退场：

- 准备阶段继续使用现有 driver 期限；
- 实际交互提交时创建确认 identity 和固定期限；
- 世界与库存证据以任意顺序到达时，先检查身份、终结和期限，再组合证据；
- 部分确认、迟到库存、重复观察和取消都只能产生一次终结；
- 退场不清空已提交输入和任务级搭桥额度历史。

完成条件：目标格与库存证据的全部到达顺序都能有界结束；到期后的证据不能复活事务；导航恢复只消费一次事务结果。

### R26-5：核对身体责任和跨模块组合

用正式闭环覆盖：

- B11 边缘接近期间取消、改目标、外力和输入迟到；
- 同一 Session 中旧路线与待接替路线并存时的 motion 结果和身体交接；
- 原 Session 退场后 successor 接续任务时的迟到规划与 motion 结果；
- 放置确认超时后恢复导航；
- motion 背压或旧结果被丢弃后，原控制者的安全退场；
- 任务终结但身体仍在空中或仍有在途输入。

只有确认 B11 现有退出会带速度释放时，才修改其身体控制接入。任何修正继续复用 `ExecutionSupervisor`，不另建放置专用监督者。未复现时只保留验证结果和证据边界，不把风险写成已修缺陷。

5. 分段证据、Java 门禁、公开证据、三版参照和独立导出；
6. profile 4 代表场景：起点和终点已知，路线中部缺少净空，侧面保留持续不可获取的未知格。记录 planner blocker、协调器选择、传感器结果、事实取得和开始移动时刻；
7. 若 motion 期限、停止或交接修正改变实际输入时序，增加对应 air-action 窄范围 Fabric 场景；若 R26-5 改变 B11 的身体交接，再增加放置交接场景。其他情况保留组件和物理闭环证据边界。

## 6. 交错测试矩阵

单独测试“迟到”或“取消”已经不足。每个领域至少覆盖：

| 维度 | 取值 |
|---|---|
| 阶段 | 准备、排队、已提交、部分结果、待接纳、退场中 |
| 外部事件 | 世界变化、目标修订、取消、successor、输入迟到、worker 背压 |
| 返回顺序 | 当前结果、旧结果先到、重复结果、结果永不到 |
| 证据状态 | 无进展、部分进展、事实已满足、事实被推翻 |

不要求机械做全部笛卡尔积。每条共享规则至少选择一个能证明它跨阶段成立的组合，并继续用随机事件序列寻找未列出的相邻组合。随机门禁要记录事件生成、派发、应用和跳过；`navigation_internal_contract_failure` 永远不能进入允许结果。

## 10. 完成结果

R26 按计划完成了三个领域的原子迁移，没有引入通用任务框架：

- 规划尝试从创建快照需求时建立身份与固定期限。路线、信息需求和否定结论都在生效前复核当前事实；
- 信息取得使用独立 identity。只有重新运行类型化查询并取得确定结果，才会形成 `ACQUIRED`；
- motion 求解从首次缺少证明时开始计时。共享 worker 由一个有界邮箱排空并按完整 identity 分发；
- 放置确认从实际交互提交时开始计时。世界与库存证据无论先后到达，都不能越过固定期限；
- 三类 owner 都保留有界接纳记录。旧 identity 的迟到结果只能记录并丢弃，不能清理当前工作；
- B11 边缘准备期间的着地位移会从当前位置重新建立短路线，且不刷新准备期限。空中外力仍是任务组合的证据边界。
