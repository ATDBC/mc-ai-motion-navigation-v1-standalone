## 1. 本轮要解决什么

R26 的规则仍能被调用者绕过。相同路线会重用执行身份；检查返回失败后仍可能重开规划；放置证据只增加而不能撤销；部分退出路径没有清理动作求解。原有测试又替正式代码准备了正确的身份、时间和停止状态。

本轮让规则成为结果生效的必经入口，并验证正式代码实际创建的身份、期限和交接。保留物理、几何、视觉、路径代价、输入仲裁和领域结果类型，不新增运动能力，不建立通用调度框架。

## 2. 责任与接口

- 上级 owner 分配实例身份；successor 共享 worker 时也取得不同身份。邮箱直接使用完整 `AsyncWorkIdentity`，显示字符串不能作权威键。
- `AsyncWorkLifecycle` 拥有一项活动工作的 identity、固定窗口及有界终结记录。`begin(identity, window)`、`check(identity, now_ns)`、`finish(identity, cause)` 是唯一入口。`check` 返回就绪、身份不符、已结束或到期，不能替领域判断事实。
- 规划、motion、放置各自验证当前事实。验证完成后、生效之前再次检查生命周期；不能用观察接收时间替代处理时间。
- `PlanningCoordinator.reconcile_information(selection, frame, outcomes)` 一次处理一个批次。旧批次有类型丢弃；期限失败不得被 Session 当作进展。
- 放置确认以 Runtime 真实派发记录起算。观察缺字段保留已有证据；明确空气、错误方块或库存反证撤销对应证据。宣布成功前复查两项当前证据。
- 求解退场清理 pending、候选和邮箱登记。身体仍由监督者负责；取消计算不等于释放身体。

## 9. 复审整改方案：停止、迟到结果与验证门禁

日期：2026-10-01。状态：方案已批准，A0—A5 已依次实施并完成检查。对应 NC-027-12 至 NC-027-15 均已关闭；不修改物理、几何、视觉权限、路线评分或原允许结果。

### 9.1 根因

四项发现来自两组没有贯彻到接口的约束。

第一组是清理后的合法调用。放置业务结束后，driver 仍可能负责身体收尾，但 `cancel()` 继续要求事务处于活动状态。信息工作已经清理后，丢弃旧结果仍通过需要活动尝试的 `_update()` 构造返回值。这两个入口都把“接收请求”错误地绑在“业务仍活动”上。

第二组是验证所需的记录。监视器能检查收到的事件，但空 tuple 不会触发缺记录检查。矩阵、种子、中断和随机序列各自判通过，未统一执行覆盖门槛。接收者又被先转换成集合，检查唯一性所需的数量被提前丢掉。因此记录为空或身份重复时，检查也可能保持通过。

以前没找到这些问题，有三个具体原因：取消测试主要在事务 READY 时触发；迟到批次主要在超时失败后触发，此时尝试身份还没清理；四类旧错误恢复没有删除诊断或制造双接收者。旧随机生成器还是同步 worker，也不组合这些新的异步事件。增加原九类事件的种子数量不能补足这几处遗漏。

这不是重新划分全部模块的理由。需要让停止接口接受业务已结束的状态，让旧结果能独立报告被丢弃，再把所需证据变成验收入口的实际条件。

### 9.2 放置停止的公共语义

保留 `RuntimeBlockPlacementDriver.cancel(reason: str) -> None` 和 `release() -> bool`，由 driver 收口停止行为：

| 业务与身体状态 | `cancel()` 应做什么 |
|---|---|
| READY／AWAITING_CONFIRMATION | 业务取消一次；请求已有接近控制器停止；检查身体是否可释放 |
| COMPLETE／FAILED／CANCELLED，来源仍保留 | 业务结果保持原值；继续请求身体停止并检查释放 |
| 来源已释放 | 重复停止不产生输入、不重新注册来源、不改变业务结果 |

`BlockPlacementTransaction.cancel()` 仍保留严格的业务状态检查。不能通过放宽它、把 COMPLETE 改成 CANCELLED 来解决 driver 的问题。`reason` 只记录原因，分支使用类型化业务状态和现有身体判据。

外层世界变化 driver 保存任务取消请求，清掉尚未提交的新目标，并持续推进已有 placement driver。外层可以最终报告任务取消，内部已经发生的放置及库存消耗仍保留。取消后不得再点击，也不得因为 placement 已终态就停止调用身体收尾。

退场前还要记录已经确认的业务效果。外层确认数量与库存消耗不能因为走了取消分支就丢失，也不能因重复停止而计两次；不要求重新启动导航才记账。业务失败、取消或连接失效时，不能把缺收尾依据解释为安全释放。发布范围内的有限外力和有限输入迟到若仍不能完成收尾，本轮保持未完成，不靠延长期限或停止监视器掩盖。

这里保存事务已有报告以及 Runtime 对应的派发、库存与世界观察记录，不新增跨任务的副作用账本。库存没有确认时如实报告未确认，不能根据点击或超时推测已消耗。

释放继续使用 `ExecutionSupervisor.evaluate_quiescence()` 和 Runtime 输入账本，不增加一套速度阈值或落地判据。准备帧仍须先 discard 未提交提案，或 adopt 已真实提交的回执；不能用幂等停止掩盖 prepare/adopt 配对错误。连接失效仍按现有控制不可用规则处理，不声称已经证明身体安全。

### 9.3 旧信息通知自己携带身份

保留 `PlanningInformationNeed` 作为规划器返回的事实需求，不让后台规划器分配 owner 身份。协调器发出的现有 `PlanningUpdate` 增加 `information_identity: AsyncWorkIdentity | None`：NEEDS_INFORMATION 必须携带真实 INFORMATION 身份；丢弃通知保留被交付通知的原身份和 `attempt_id`。

已实施的正式入口为：

```python
PlanningCoordinator.current_information_update -> PlanningUpdate | None
PlanningCoordinator.reconcile_information(
    selection: PlanningUpdate,
    frame: NavigationFrame,
    *,
    edge_probe: LandingEdgeProbe | None = None,
    outcomes: tuple = (),
) -> PlanningUpdate
```

`current_information_update` 读取协调器已经拥有的通知，不新增一份活动状态。Session 从它取得不可变通知，再交回协调器。正常通知必须是 NEEDS_INFORMATION，且带事实需求与正式身份；格式错误仍是契约错误。

旧通知的丢弃从传入通知构造，不调用需要活动尝试的 `_update()`，不查当前请求来补旧身份。完整身份、世界、请求、目标修订、快照和批次不匹配，或原工作已清理时，返回 DISCARDED。不得重建尝试、伪造 `attempt_id`、取得进展许可或修改新工作的期限。

这样，取消、关闭、替换和退场历史淘汰后的迟到通知，都不再依赖旧状态仍在内存里。正式生产者、两个 Session 消费入口、测试与实机脚本一起迁移；旧单事实组件接口继续明确隔离，不作为新异步调用入口。

### 9.4 先核对接收者，再去重历史

每次检查先按完整活动 identity 统计接收者。活动邮箱必须恰好有一个匹配的活动接收者；同时核对诊断 owner 与 identity 的 owner。没有接收者、多个接收者和 foreign owner 分别报告。

活动接收者检查发生在集合化或事件去重之前。正式采集器每帧只提交每个活动 owner 一份诊断；同一份诊断跨帧重复读取由事件去重处理。已退场的历史记录不算活动接收者，也不能因为保留历史而误报。

不增加生产环境的全局 owner 注册表。身份仍由既有分配器产生；本步修的是测试监视器及诊断采集约束。

### 9.5 让缺证据阻止验收通过

区分任务结果和验证结果。机器人到达目标是任务成功；若没有所需记录，验证结论仍是证据不足。不得把证据不足改成允许的有界任务失败，也不得从任务统计分母删掉该样本。

在测试工具中增加小型覆盖要求与评估：按工作类别声明所需的 begin／apply／finish 样本，使用真实记录计算缺口。未提供评估不能默认通过。合法没有异步工作的场景在运行前明确声明，不适用不等于自动豁免。

覆盖不能只靠同一个 `async_work_diagnostics` 推断。测试 worker 在真实 submit／poll 时记录正式代码生成的 identity；信息通知和实际接纳、放置派发及输入记录作为独立依据。只记录和控制交付时间，不替生产代码创建身份或许可。对指定正常对照，还要求至少一个真实生效样本，避免所有结果都被丢弃也判通过。

在既有 `Result` 中保存结构化验证结论，未给结论时为未验证。`Result.verdict`、固定矩阵、种子扫描、中断矩阵、`SequenceOutcome` 和随机序列入口共同消费这一结论，不分别复制缺口规则。缺记录、遗漏 apply 或缺某类 owner 必须使本轮关闭检查失败并返回非零进程退出码。任务结果及原有伤害、输入、权限违规分别保留。

测试侧拟定的接口如下，名称可以按仓库约定调整，返回含义不能改变：

```python
InvariantMonitor.finalize(
    required_coverage,
    observed_activity,
) -> VerificationAssessment
Result.verification: VerificationAssessment | None
Result.verification_complete -> bool
```

`VerificationAssessment` 保存 VERIFIED／INCOMPLETE／UNASSESSED 结论、按工作类别统计的实际事件数，以及含规则编号的缺口。它由共同监视器计算，actor 不填“已验证”标志。`None` 和 UNASSESSED 都不能通过关闭门槛。无异步工作的声明须与独立调用记录一致；有实际活动却没有诊断时，不能落入无工作对照。

I18—I22 是本轮必须验证的范围。I7／I8 既有逐帧诊断缺口继续单独报告，不静默改成通过，也不声称本轮完成其全链证据。需要使用结构化规则编号，不解析 `reason` 或缺口描述字符串决定权限。

### 9.7 实施中补足的边界

新增计算器闭环通过完整世界变化 driver 后，发现成功放置的身体仍处于潜行姿态。直接交给要求站立的普通路线，会返回 `ground_mode_invalid_entry`。旧测试后端立即回报站立，没覆盖这条边界。

放置 driver 现在仍使用同一监督者证明释放中性输入是安全的。成功后准备恢复导航时，它先解除潜行，等真实观察确认站立再释放来源。取消使用有类型的 `StopCause.CANCELLED`，不强迫已经停止的任务恢复站立，也不修改业务结果。没有新增速度阈值或碰撞规则。正常放置和 18 个停止组合一起验收，并扩回完整 B11 Fabric 正反例。

新增 256 个序列使用独立清单，旧四个清单没有改种子或允许结果。放置证据撤销与超时之后，着地状态可以经过新的正式派发完成重试；有限离地则拒绝重新接近。两者都必须证明被撤销的旧 identity 没有生效，不能根据最终失败就跳过这项核对。

最初两次扩展 Fabric 批次在第一个正常对照的释放后尾迹中超时。检查派发记录后发现，测试脚本没有调用外层 driver 的 `release()`，旧中性意图重复使用直至过期。延长诊断窗口没有解决原因，已撤回。脚本现完整调用公开释放入口，活动控制和尾迹窗口均保留 500 ms。两次失败证据不会删除。
