# 表面深度主线修正计划

日期：2026-09-26

状态：正式入口和旧射线专用逻辑已完成整改；正在处理 B10 端到端时序

## 要解决的问题

核查时发现，正式主线的方块视觉仍在使用已经淘汰的 profile 3 稀疏射线。数据契约虽然支持 profile 4，真正的表面深度提供器却仍放在诊断模组中，由环境变量临时启用。正式启动器没有安装它，也没有检查观察源。

本轮修正要把已经验证过的表面深度算法变成正式、必需、可复现的观察能力，并让旧射线无法再次成为默认值。

## 根因

问题由三处共同造成：

1. 2026-09-11 的表面深度计划明确保留 profile 3 为默认，因为当时只做隔离实验。
2. B02 后来的设计只约束“可见方块”，没有约束这些方块必须由 profile 4 产生。
3. 自动测试大多验证方块进入世界知识后的行为，没有验证正式启动器实际选择了哪一种传感器。

因此，表面深度代码、profile 4 契约和专项测试都存在，但正式 B10—B12 运行仍稳定地产生 profile 3。它不是偶发配置错误。

## 已核实的影响范围

### 直接受影响

| 范围 | 核查时的情况 | 影响 |
|---|---|---|
| 正式 Fabric 方块观察 | 默认 profile 3，1431 条首命中射线 | 会漏掉射线之间实际可见的方块 |
| B02 观察验收 | 验证了三态知识和空气查询，没有冻结 profile 4 | 观察源门槛需要重新打开 |
| B03 及后续实机运行 | 都通过同一正式观察入口 | 路线取得时间和已知地图范围可能变化 |
| B10、B11、C1、B12 公开证据 | 9 个归档均没有 `surface_depth`；可检查的正式帧使用 profile 3 | 只能作为旧射线历史证据 |
| 公开独立仓库 | 没有导出表面深度 Java、C++、固定依赖和构建门禁 | 外部无法复现目标视觉配置 |

profile 3 容易少看方块，通常表现为更多未知、规划开始较晚或路线不存在。未知目前会保守拒绝通行，所以现有问题主要是能力和响应退化；这不能被解释成安全证明。

### 仍然有效

以下结果不依赖可见方块由哪种传感器产生，可以继续保留：

- 世界会话、已知方块／空气／未知三态；
- 按需空气正例、身体接触和脚下支撑；
- 扫掠、支撑面、A*、动作求解和物理计算器的纯组件检查；
- 输入账本、动作生效窗口、取消、失联和空中落地责任；
- 攻击准星、伤害来源、仲裁和任务结果分类。

这些组件仍要参加回归，但无需按“逻辑全部作废”处理。

### 需要重新取得实机证据

最低重跑集合如下：

1. B02：表面深度、按需空气、身体接触、世界变化和新世界会话。
2. B03：长距离直行、转弯、停止和取消，检查新增观察成本是否影响输入时限。
3. B10：固定路线、跨隙、台阶、上升和下降的代表组合。
4. B11：放置前观察、放置确认和确认后的重新规划。
5. C1-A／B／C：固定目标、移动目标和受击恢复。
6. B12-A／B：攻击证据、遮挡、活动目标持续追击和边瞄准边移动。

B04—B09 的纯逻辑结果由统一组件检查回归；它们的动作实机连接由 B10 组合矩阵覆盖。若 B10 没有覆盖某个已声明能力，再补该能力自己的实机场景。

## 实施顺序

### 第一步：先建立会失败的门禁

- 正式后端收到 profile 3 时拒绝建立运行帧。
- 正式客户端缺少表面深度提供器时，在任务开始前失败。
- 正式轨迹出现 `first_hit_ray` 时，验收失败。
- 公开证据索引不能把旧射线归档登记为当前通过证据。
- 包边界检查只允许历史读取器和冻结旧快照出现 profile 3 名称。

这一步先写测试并确认在当前代码上失败，再修改实现。

### 第二步：把表面深度从诊断模组提升为正式依赖

复用现有增量分区、动态形状更新和原生遮挡计算，不另写第二套算法。需要把职责拆开：

- 正式提供器只维护几何缓存并返回本帧可见方块；
- 全量外形审计、逐帧 JSON 和磁盘日志保留为显式诊断功能；
- 正式运行不做全量审计，也不逐帧写诊断文件；
- 世界对象变化、区块加载／卸载和方块变化必须使相关缓存失效；
- 原生库加载失败和容量超限都明确失败，不能退回射线。

现有诊断器遇到任何流体都会抛错，不能原样提升为常驻正式能力。本轮至少要保证普通流体不会导致整个客户端失效：能够表达的流体按独立介质事实导出；尚未支持的水浸形状只把相关格标为缺少信息并给出明确原因。完整的游泳和流体运动仍属于 B13。

正式 Fabric 包必须声明表面深度模组为必需依赖，保证安装顺序。启动清单保存 Java、原生库和固定第三方几何依赖的哈希。

当前 CMake 文件写死了 Windows JNI 路径和 MSVC 参数。Windows 是本轮实机门槛；同时要把源码和构建条件整理为可移植结构。macOS 或 Linux 没有通过构建与实机检查前，启动器应报告平台未支持，不能悄悄使用旧射线。

### 第三步：删除正式射线入口

- 从正式 `ClientBlockObservationV3` 中删除 1431 条射线的发现分支和环境变量选择。
- 正式采集固定输出 profile 4、零行列和 `surface_depth`。
- `ClientBlockParityDiagnostics` 不再进入正式客户端构建。
- 如需读取旧轨迹，在单独的历史兼容模块中保留 profile 3 解码；名称、包路径和测试都必须带有 `legacy`。
- Observation V3 的正式对象不再用 profile 3 作为字段默认值。

攻击和方块交互继续调用原版中心准星命中检测。这条射线不进入世界知识，也不受本次删除影响。

### 第四步：统一消费者与测试夹具

- `NavigationObservationAdapter` 继续消费统一的可见方块，不复制表面深度算法。
- 正式测试夹具默认生成 profile 4 和 `surface_depth`。
- 只有历史兼容测试可以构造 `first_hit_ray`。
- 按需空气、身体接触和当前交互目标继续使用原来源，并验证它们能与 `surface_depth` 同格合并。
- 明确玻璃、玻璃板、植物、蜘蛛网和其他非遮挡形状的规则。可见外形和“是否遮挡后方”分开记录，不能仅凭碰撞箱决定视觉遮挡。

第一轮消费者审计另外确认：旧策略会为一个缺失支撑生成多组与 159×9 射线网格对齐的转头候选。该逻辑已改为一个连续视野区域。已知障碍的线段相交、实体视线和准星命中仍保留，但已在代码和文档中与方块视觉分开命名。

### 第五步：先做感知验收，再恢复动作验收

感知专项至少覆盖：

- 平视、抬头、低头和连续转头；
- 完整墙、墙边开口、细缝、悬浮墙、坑、半砖和楼梯；
- 玻璃或玻璃板前后的方块；
- 植物和蜘蛛网不遮挡后方，但自身仍可见；
- 门、活塞或放置方块造成的动态变化；
- 区块加载／卸载和世界会话切换；
- 未加载区域和被遮挡区域保持未知；
- 表面深度结果与冻结的独立几何参考一致。

热态表面计算 P95 不得超过 8 ms；必须另外报告冷启动、完整客户端采样、序列化、传输和 Python 接收的 P50／P95／P99。控制帧和输入实际生效继续使用原有门槛，不能用感知耗时单独达标代替端到端达标。

感知门槛通过后，按前述最小重跑集合恢复端到端证据。任何正式帧出现 profile 3、`first_hit_ray` 或静默回退，整批运行无效。

## 公开仓库与历史证据

公开独立仓库需要加入：

- 正式表面深度 Java 与 C++ 源码；
- 固定第三方依赖及许可证；
- 可重复构建命令和最小 Java／原生门禁；
- 感知专项测试和新的代表性实机证据；
- 旧射线证据的历史标签。

旧归档不删除，也不改写原字节。新的索引把它们与当前通过证据分开，避免外部审查者把旧射线成绩当成现行结果。

## 完成条件

同时满足以下条件后，才能关闭修正门槛：

1. 正式客户端没有可达的 profile 3 采集路径。
2. 缺少表面深度依赖会在任务开始前明确失败。
3. 感知专项和最小动作重跑集合全部通过。
4. 公开仓库能从源码构建并验证同一 profile 4 行为。
5. 新公开轨迹只有 profile 4 和 `surface_depth`，旧证据有明确历史标签。
6. AGENTS、架构、阶段、验收和决定文档使用同一个观察定义。

## 当前进度

- 正式 Fabric 已固定 profile 4，缺少表面深度提供器会在启动前失败。
- 正式采集器已删除 159×9 方块扫描；历史实现移动到 `legacy_ray_profile3`，正式 JAR 门禁检查它不存在。
- 导航证据拒绝 profile 3 和 `first_hit_ray`。
- 当前测试夹具默认使用 `surface_depth`；旧射线夹具只保留给兼容测试。
- 旧主动观察和 Follow Playground 脚本已标为历史 profile 3，并从当前独立仓库导出中移除。
- 公开导出只收录正式 Java 覆盖层，包边界检查明确禁止 `legacy_ray_profile3`。
- 公开导出不再整目录收录 `skills`。正式入口的依赖闭包中已经移除旧 Follow Playground、旧 V2 导航证据恢复和 CraftGround Java 测试。
- 正式 V3 轨迹恢复、进程树管理、导航视图和观察方块转换已经拆成中性模块，不再借用旧射线／CraftGround 工具。
- 当前控制能力数据契约已经与旧 J3 证明读取器分开。正式 C1 不再因为读取一个允许输入集合，就把旧 CraftGround／profile 3 源码清单带入公开包。
- 旧策略中按 159×9 采样网格生成观察角度的分支已经删除。已知几何线段、实体遮挡和准星命中继续保留，它们不会产生方块视觉证据。
- 公开旧归档已标为 `historical_legacy_ray_profile3`，不能登记为当前验收。
- B02、B03 的 profile 4 实机回归通过。
- B10 的自然滑行和落地稳定段已经改为沿用同一份动作证明，不再虚构逐 tick 命令身份。
- B10 关闭额外诊断后连续完成 33 次，随后仍有一条活动命令晚 1 tick；执行器安全落地。问题现已收窄到偶发的控制调度与传输时序，不能再笼统归因于表面深度计算。
- 下一步测量观察年龄、控制处理和客户端实际生效 tick，修正严格活动命令的交付链，再重跑 B10。B10 关闭前不恢复 B11、C1 和 B12 的当前视觉配置验收。
