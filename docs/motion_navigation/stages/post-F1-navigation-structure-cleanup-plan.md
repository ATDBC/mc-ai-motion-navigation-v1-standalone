# F1 后导航结构整理计划

日期：2026-10-06。状态：S0 已完成，下一步为 S1；尚未修改生产导航代码。时间盒截止 2026-10-08，最多四个工作批次；日期和批次先到者触发冻结。

## 1. 要解决的问题

正式跟随已经通过产品验收，薄跟随层也没有复制规划和恢复状态。但 F1 暴露的共享缺口让 6 个核心协调文件继续增长。原“十二个核心文件零修改”门槛失败，F1 整体因此没有全部关闭。

本阶段只整理已经验证过的代码。目标是减少共享协调面的重复，不改变机器人行为。

## 2. 范围

只处理下面三类已有代码：

1. 已经没有正式调用入口的死路径；
2. 同一身份或状态在相邻层重复检查、重复转发的代码；
3. 只为了旧迁移过程保留、当前 owner 已经能够直接表达的适配分支。

明确不做：

- 不新增跟随、终点贴墙、探索或运动能力；
- 不修改物理、几何、感知权限、路径评分和动作窗口；
- 不新增状态类、账本、线程、缓存或兼容开关；
- 不因为代码难删而移动文件、压缩写法或改变公开接口来制造行数下降；
- 不修复完整检查中冻结的五项历史失败。它们另按各自阶段处理。

## 3. 实施顺序

### S0：冻结可删除清单

先用静态调用关系和现有测试入口列出候选。每项必须说明：

- 当前生产调用者；
- 当前状态 owner；
- 删除后由哪个现有入口承担职责；
- 哪组正式链检查能发现误删。

找不到明确替代者的代码不删。S0 只产出清单，不改生产代码。

S0 还要从整理前的干净提交生成三组确定性基线：

- v7 产品清单 2,000 项；
- 协调清单 1,448 项；
- 四个补充故障场景。

轨迹比较使用 `r28-structure-trajectory-v1` 归一化规则：递归保留字段、顺序和类型，只把有限浮点数四舍五入到小数点后 9 位。它只用于新旧行为对照，不改旧归档、旧哈希或生产数据。归一化器本身必须有版本字段和组件检查；整理前基线与每个候选使用同一版本。

S0 已在干净提交 `a1649c2` 上完成。这个提交只增加只读量尺和组件检查，生产代码与父提交 `2f0e46b` 相同。冻结结果为：v7 产品 2,000 项、协调 1,448 项和补充故障 4 项。候选只有 3 个；`_wait_for_active_terminal` 等有正式职责或证据不足的入口明确保留。具体结果见[结构整理验收](../acceptance/post-F1-navigation-structure-cleanup.md)和[冻结清单](../../../evidence/motion_navigation/post-f1-structure-s0/deletion-inventory.json)。

### S1：先删除零调用死路径

每次只删一组同一职责的函数。先跑直接测试；通过后再跑受影响模块。任何行为差异立即停止，不把它改成“新预期”。

### S2：合并重复身份检查和转发

只把已经由同一 owner 判断的身份结果传给调用方。不能让 Session 重新推断 owner 的结论，也不能把 typed 结果改成 reason 字符串判断。

### S3：复核薄跟随边界

再次检查：

- `KnownWorldFollowDriver` 只调用 `start`、`replace_goal` 和 `release`；
- 没有规划、路线、恢复、交接、重试或输入账本字段；
- 十二个核心文件没有跟随专用状态和分支；
- 旧跟随实现没有进入正式调用链。

### S4：完整回归和结构签署

运行完整运动导航检查。结果必须仍为同 5 项冻结失败，不得新增失败或改变失败断言。

随后用 S0 的同一输入、同一模拟器和同一 `r28-structure-trajectory-v1` 规则重新生成 v7 2,000 项、协调 1,448 项和四个补充故障。结果、原因、实际输入、身体轨迹、风险、交接、工作数和监视器结论必须逐项一致。任一差异立即判定该整理批次失败；不通过解释差异来改写基线，也不继续运行 Fabric。

五个已签署 Fabric 目录只做哈希和摘要复核；只要正式输入、动作窗口、感知或运行入口没有改变，就不重跑游戏。

## 4. 门槛

本阶段同时满足下面条件才通过：

- 核心协调文件总物理行数下降；
- 决定分支数量下降；
- 没有新增生产状态字段或公共接口；
- 跟随结构审计保持通过；
- 五个产品摘要和哈希不变；
- 完整运动导航仍只有冻结的同 5 项失败；
- v7 2,000 项、协调 1,448 项和四个补充故障经版本化取整后逐项一致；
- `git diff --check` 通过。

行数和分支只是防止整理继续膨胀的量尺。它们不能替代正式链行为检查。

## 5. 工作方式

采用 fail fast：先审一个候选、删一个小组、跑直接检查。直接检查失败就恢复该组，不继续扩大。只有多个小组分别稳定后，才运行完整集合。

本阶段不设置“必须删到某个文件少于多少行”的目标。若 S0 证明没有足够安全的删除项，就以“结构门槛仍未通过”结束，不为达到数字而改写架构。

## 6. 时间盒

S0 不修改生产代码，不计工作批次。S1 和 S2 合计最多使用三个批次；S3 与 S4 共用最后一个收口批次。2026-10-08 或第四个批次先到时，冻结已经通过的提交并停止继续整理。

时间盒到期时，若行数、分支或确定性行为门槛没有全部通过，就如实记为整理未通过。不得通过延期、合并批次或降低对照范围来关闭阶段。
