# F1 后导航结构整理计划

日期：2026-10-06。状态：S0-R 已在正式 Windows 环境完成；S1 可以开始但尚未实施。原时间盒仍在 2026-10-08 截止，S0-R 不占四个结构整理批次。平台范围见 [D071](../decisions/0071-windows-is-the-formal-project-platform.md)。

## 1. 要解决的问题

F1 正式跟随已经通过产品验收。薄跟随层只调用导航的开始、目标修订和释放接口，没有复制规划、路线、恢复或身体交接状态。

结构门槛仍然失败。F1 开始后，接纳、复核和会话协调代码明显增长。原 S0 建立了可靠的确定性签名，却只找到三个零引用函数，共 34 行。它没有覆盖 F1 新增的地面直走接纳、正式跟随和行走中世界变化路径。按原门槛执行，只删这 34 行也可能被写成“结构通过”。

三方复核还发现，当前完整检查包含真实恢复缺陷、测试场景污染、测试前提失效和墙钟相关失败。整理正要触及的恢复与接纳代码因此没有可靠保护。

所以顺序改为：

1. 先修正测试和两项正式行为缺陷；
2. 再冻结覆盖正式跟随和世界变化的五组行为基线；
3. 再补齐重复检查与迁移适配清单；
4. 最后才开始逐项删除或合并。

## 2. 不改变的原则

- S0 已发布的索引保留为历史，不覆盖、不改写。
- S0-R 只让后续整理有可靠量尺。它不新增运动、探索或战斗能力。
- 每个生产缺陷单独提交。缺陷修复完成后再取 S0-R 结构基线，缺陷修复的代码变化不算结构整理成果。
- 行为签名与路径覆盖分开采集。路径探针会增加调用开销，只用于证明代码被走到，不能代替产品行为量尺。
- 路径中出现相同条件，只说明值得检查。只有同一个事实、同一个 owner、同一个生命周期时点，才能合并。
- 一项候选一次提交。直接检查或行为签名出现差异，立即回退该项，不扩大修改范围。

## 3. 范围

S0-R 只处理四类工作：

1. 修复测试隔离、失效前提和墙钟依赖；
2. 修复后端 I/O 失败后的状态覆盖，以及 `seed 163` 暴露的空中过早失败；
3. 扩充确定性基线和路径矩阵；
4. 补齐结构候选清单和逐项关闭规则。

S1—S4 只处理三类已有代码：

1. 没有正式调用入口的死路径；
2. 相邻层对同一事实的重复检查或重复转发；
3. 旧迁移过程遗留、当前 owner 已能直接表达的适配分支。

明确不做：

- 不新增跟随、终点贴墙、探索或运动能力；
- 不修改物理、几何、感知权限、路径评分和动作窗口；
- 不新增状态类、账本、线程、缓存、插件系统或兼容开关；
- 不通过搬文件、压缩写法或包装状态制造行数下降；
- 不为了合并校验再建一层通用校验框架；
- 不把已有失败改成新预期，也不删除失败证据。

## 4. S0 历史结果

S0 在干净提交 `a1649c2` 上完成。它只增加 `r28-structure-trajectory-v1` 量尺和组件检查，生产代码与父提交 `2f0e46b` 相同。

冻结结果为：

- v7 产品清单 2,000 项；
- 协调集合 1,448 项；
- 补充故障 4 项；
- 三个零引用候选：`_admit_async_event`、`_cell_fact_id`、`_upcoming_air_index`。

三方已在 Linux 上复跑这三组集合，签名与 Windows 索引逐项一致。量尺本身可以继续使用。S0 的问题是覆盖和清单不足，不是签名算法失效。

## 5. S0-R：修正基线

### R0：固定起点和失败清单

开始修改前，从当前干净提交重新运行完整运动导航检查，并记录实际失败项。公开审查中的“五项失败”只作为问题来源，不作为永远固定的数量。

需要保存：

- 当前提交、Python 版本和平台；
- 正序与逆序的失败项；
- S0 三组索引的复核结果；
- 生产源码指纹；
- 共享场景运行前的深度哈希。

只有明确当前起点，后续才不会把已经修正的公开打包问题重新写进计划。

### R1：先让测试真正保护目标路径

#### R1-1 隔离模拟场景

`tests/sim/runner.py` 在每次运行开始时复制 `Perturbations`。测试不得修改 `tests/sim/scenarios.py` 中的共享对象。

新增检查应证明：

- 运行会修改 `late_ticks` 的场景后，共享场景深度哈希不变；
- 同一套测试以正序和逆序运行，I3 落点安全检查结果相同；
- 连续运行两个任务时，前一任务的扰动不会进入后一任务。

#### R1-2 恢复失效的世界变化前提

下面两条检查目前用“石头与草方块交替”触发变化，但这两种材料对普通行走没有差异：

- `tests/motion_nav/test_r28_shared_recovery.py`；
- `tests/motion_nav/test_r28_migration_faults.py` 和 `tests/sim/migration_faults.py`。

将触发条件改为石头与下半砖交替。下半砖改变支撑高度，但不直接移除支撑。

测试还必须断言目标路径真的被走到：

- C-02 至少出现一次路线复核停止和一次新规划提交；
- `active_route_dependency_retry` 至少进入一次任务恢复入口；
- 换回石头与草方块时，前提断言必须失败。

#### R1-3 移除墙钟成败条件

单元测试只验证格式、字段、覆盖拒绝和类型化结论。真实性能门槛继续由正式性能证据承担。

优先检查：

- D058 CLI 与运行时复核测试；
- D061 长会话基准测试；
- R28 持续预算测试；
- 其他直接用 `perf_counter`、`monotonic` 或固定毫秒数决定通过与否的运动导航检查。

涉及期限和预算的行为测试改用注入的模拟时钟。并行高负载运行只用于诊断，不作为确定性发布门槛。

### R1-B：两个正式行为缺陷

这两项不是结构整理。各自单独提交，补缺陷记录和正式链回归。

#### R1-B1 后端 I/O 失败后的状态归属

R0 起点的一次后端 I/O 失败会先把驱动器写成 `failed/control_unavailable`，随后又被调用方覆盖成 `stopping`。下一拍复用旧观察，最终抛出 `fixed route frame did not advance`。

修正目标：

- `_release_if_quiescent` 返回有类型结果，不用一个布尔值同时表示“等待交接”和“控制已失效”；
- `RuntimeNavigationDriver` 只有一处可以决定自身终态；
- 会话同步进入 `control_unavailable` 一类的类型化终态；
- 运行时不再 READY 时，`release()` 不重新取消会话；
- 第一次 `propose` 发现帧未推进后，不使用同一帧再次 `propose`；
- 点任务和跟随外层循环都在终态后停止调用驱动器。

故障族覆盖行走中、制动中、跨隙空中，可重试与不可重试 I/O 失败。验收要求没有异常逃出、终态一致、失败后不再写输入，处置分别为 `recreate_runtime` 或 `end_episode`。

#### R1-B2 `seed 163` 的空中过早失败

R0 起点的身体仍在空中时，地面动作准备返回 `needs_state`，会话把它当成“运动无解”并提前失败。身体随后安全落地，但任务没有从新状态继续。

修正目标：

- 空中收到 `needs_state` 时保留现有落地责任；
- 落地后从正式观察重新锚定并继续求解；
- 只有落地后仍明确无解，才能结束任务；
- R28-C-05 的朝向复核检查改为条件触发一次迟到，不依赖某个种子恰好产生特定时序；
- `seed 163` 继续作为恢复回归场景。

这项不能标成 `expectedFailure` 后继续 S1。若在 S0-R 截止前不能修好，S0-R 记为未通过，S1 不开始。

### R2：冻结五组行为集合

S0-R 最终提交上重新生成以下五组索引：

| 集合 | 内容 | 主要保护路径 |
|---|---|---|
| 产品 | v7 2,000 项 | 普通路线、连续高度和严格下降的现有行为 |
| 协调 | 1,448 项 | 中断、异步交付、目标修订和身体交接 |

世界变化集合先使用模拟器已支持的整块障碍，并保留 R1-2 的下半砖恢复场景。每项场景必须记录它实际走到的入口，不能只根据最终结果推测覆盖。

### R2-2：单独生成路径矩阵

新增只读的路径计数脚本，输出：

`候选 × {产品、协调、补充故障、跟随、世界变化} → 调用次数`

路径探针不得和行为签名同进程采集。它只回答“哪组场景走到了这段代码”，不能改变产品结果或参与性能门槛。

候选在五组集合中均为 0 次时，只能：

1. 补一个正式路径场景；
2. 证明静态和动态都不可达后删除；
3. 标记为 `retained:unprotected`，本阶段不修改。

已知需要处理的入口包括：

- `RouteAdmitter.admit`；
- `RouteAdmitter.admit_local_direct`；
- `NavigationSession._wait_for_active_terminal`；
- 行走复核的停止分支。

### R3：清单升级为 v2

每个候选增加以下字段：

| 字段 | 含义 |
|---|---|
| `category` | `dead_path`、`duplicate_check` 或 `legacy_adapter` |
| `duplicate_of` / `legacy_of` | 重复或替代关系 |
| `kept_owner` | 最终保留该判断的状态 owner |
| `entering_sets` | 五组路径矩阵的调用次数 |
| `detecting_check` | 临时移除保留检查后，会失败的测试或集合 |
| `expected_delta` | 预计减少的行数和决定分支 |
| `risk` | 涉及的安全、恢复或交接路径 |
| `closure` | 删除、合并或保留理由 |

保留理由只允许：

- `retained:independent_responsibility`：同样的条件出现在不同 owner 或不同时点，必须各自检查；
- `retained:unprotected`：现有集合无法走到，本阶段不修改；
- `retained:merge_changes_behavior`：合并后行为签名发生变化；
- `retained:out_of_time`：时间盒到期。

S0-R 要逐项核实这些线索：

| 编号 | 线索 | 判断重点 |
|---|---|---|
| K1 | `admit` 与 `admit_surface` 有九条相同条件 | 是否处在同一接纳时点；早期脚本是否仍有独立职责 |
| K2 | `admit_local_direct` 与 `admit_ground_direct` 有六条相同条件 | 补同支撑跟随场景后，再决定共同检查由谁保留 |
| K3 | Session 两个直走资格函数有五个相同条件 | 能否由一次类型化分类代替两次推断 |
| K4 | 接纳与路线复核都判断行走边可行性 | 区分首次构造与运行时复查；只有同一事实才能复用 |
| K5 | 接纳与复核记录类有相同构造校验 | 判断是同一事实的副本，还是两个边界各自保护不变量 |
| K6 | 两个大型接纳函数持续增长 | 只检查其中的重复；不以函数较大为由重写 |

此外，按 F1 差异检查 `navigation_session.py` 和 `execution_supervisor.py` 的新增代码。新能力和共享缺陷修复不进入删除清单；重复检查和旧适配逐项登记。

## 7. S1—S4：行为不变整理

### S1：零调用死路径

先处理原有三个第一类候选。删除前把函数体临时改为抛出断言；完整检查与五组集合仍应通过，且静态扫描没有生产调用者。每项单独提交。

### S2：重复检查与转发

只合并已经证明属于同一个 owner、同一个事实和同一个生命周期时点的判断。合并前临时去掉计划保留的那处检查，至少一项直接测试或基线必须失败。否则说明缺少保护，先补场景，不能直接合并。

### S3：跟随边界复核

再次确认：

- `KnownWorldFollowDriver` 只调用开始、目标修订和释放；
- 不保存规划、路线、恢复、交接、重试或输入账本状态；
- 核心协调代码没有跟随专用状态或分支；
- 旧跟随实现没有进入正式调用链。

### S4：逐项关闭和签署

每项候选必须成为：

- `deleted`；
- `merged`；
- `retained:<允许理由>`。

完整签署条件：

1. 清单闭合率 100%；
2. K1—K5 中没有 `retained:unprotected` 或 `retained:out_of_time`；
3. 十二个核心协调文件加 `route_validation.py`，相对 S0-R 的总行数和决定分支均减少；
4. 报告相对 F1 开始前的净变化、接纳入口数量和重复条件数量；这些只用于说明，不能靠搬代码改善；
5. 五组行为签名逐项一致，完整检查正序和逆序均为零失败；
6. 没有新增生产状态字段、公共接口或文件搬迁；
7. 五个已签署 Fabric 目录的摘要和哈希不变；
8. 新证据只保存索引、摘要和差异，单个文件小于 1 MB。

## 8. 每个候选的 fail-fast 流程

1. 先运行直接测试；
2. 再运行正序和逆序完整检查；
3. 再对照五组行为索引；
4. 再更新路径矩阵与清单关闭状态；
5. 任一步失败，回退该候选，记为 `retained:merge_changes_behavior`；
6. 不为解释差异而修改基线，不把相邻问题带进当前提交。

路径矩阵和变异检查只需针对当前候选，不必每次重跑全部静态分析。多个候选分别稳定后，再做一次完整 S4 复核。

## 9. 提交顺序

S0-R 建议按下面顺序保存：

1. 测试隔离、世界变化前提和模拟时钟；
2. 后端 I/O 失败终态修复；
3. `seed 163` 空中恢复修复；
4. 五组行为量尺、路径矩阵和 S0-R 索引；
5. v2 清单、验收记录和阶段入口更新。

第 2、3 项是行为修复，不计入结构整理的净变化。S1—S4 从第 5 项后的提交开始计量。

## 10. 时间盒

- S0-R 不占原四个结构批次，但必须在 2026-10-07 结束前满足 A1—A9。
- S1 和 S2 合计最多三个批次；S3 与 S4 共用最后一个批次。
- 2026-10-08 或第四个结构批次先到时，立即停止。
- S0-R 未按时完成，或 S4 任一门槛未通过，都如实记为本次整理未通过。
- 若之后继续，必须新增决定并重新设时间盒。不得延长旧时间盒，也不得在基线不完整时开始 S1。
