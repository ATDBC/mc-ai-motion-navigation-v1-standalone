# D041：事件先准入，动作收尾必须有界

日期：2026-09-29

状态：已决定、完成实现并通过专项 Fabric 对照。

## 要解决的问题

第二十轮复审发现，受控下降在执行中改目标或取消后，如果下一帧输入又晚到，任务可能永久停在执行或收尾状态。原事件表只记录发生了什么，没有阻止事件进入不适用的业务分支。动作执行者等待输入回执时也没有自己的期限。身体持续运动还会绕过只检查“原地不动”的监视器。

## 决定

1. 生命周期使用两张表。事件准入表只决定处理、忽略或拒绝；状态转移表继续独占状态写入。
2. 终态收到旧规划、旧接纳、旧控制器或旧信息结果时直接忽略。表外事件明确拒绝，不能先修改路线、账本或控制者再报错。
3. 已验证动作等待命令生效、处理歧义回执和负责空中落地时，都使用自己的运动 tick 期限。期限到达后返回有类型结果，不依赖任务总超时。
4. 从停止恢复执行必须有当前控制者的 `TRANSFERABLE` 证据；从停止恢复规划必须有 `QUIESCENT` 证据。旧帧、旧世界或旧控制者的证据无效。
5. 监视器同时检查身体位置和动作阶段。身体来回移动但动作序号、已确认输入和阶段修订没有前进，仍算无进展。
6. 执行监督者只依赖统一的 `BodyController` 协议。路线和探边通过薄适配器接入；监督者不读取它们的内部状态类型。

## 为什么这样做

事件表和转移表解决的是两个不同问题。事件表防止过期或不适用的输入进入业务逻辑；转移表防止业务分支随意写状态。只做后者，旧结果仍可能先改动路线和账本。只做前者，合法事件仍可能把状态写到不允许的位置。

同样，任务总超时不能替代动作收尾期限。机器人在空中时，等待几十秒才发现回执永远不会来并不安全。动作执行者最清楚自己等待哪条命令、当前是否离地以及何时必须转入保护收尾，因此期限归动作执行者所有。
