# D001：先验证基础层，再逐步接入规划和新动作

日期：2026-09-18  
状态：已接受

## 要解决的问题

架构文档列出了完整模块和建议目录。如果把这些内容直接理解成“第一批生成全部架构代码”，会出现大量尚未被真实行为需要的空壳。接口和状态会在没有运行证据时提前固化，旧版中已经验证过的能力也容易在重写过程中丢失。

## 决定

新主线按以下顺序交付，前一阶段通过后才进入下一阶段：

1. 固定三个用途不同的旧实现参照，并冻结空地、转角走廊、悬浮墙和坑边四类代表地图。已有和后续运行使用统一的控制输入、身体轨迹和分时钟计时格式。
2. 统一时间、世界会话、三维支撑、未知／已知空空间、扫掠查询和普通地面预测。此时不做自动导航。
3. 只实现固定路线步行，独立证明直行、转弯、停止、取消和输入失联处理正确。此时不加入搜索、探索或跳跃。
4. 固定路线步行通过后，接入已知地图 A*、路线接纳和真正独立的后台进程。
5. 规划边界成立后，尽早加入一个小型跨高度动作，检查动作能力能否通过现有地图、规划、安全和输入接口接入。

第一批不生成完整架构的全部代码文件。每个阶段只创建当前交付真正使用的最小模块。

## 为什么这样决定

固定路线步行把运动控制与搜索问题分开。机器人直线或转弯表现异常时，可以先在执行层定位，不需要同时怀疑检查点、探索评分和后台搜索。

先统一数据和几何，能让规划、局部跟踪和安全检查使用相同的支撑、净空、扫掠与动力学结论。这样不会再次出现规划认为能走、执行层却用另一套口径拒绝的问题。

跨高度动作放在 A* 之后尽早验证，可以及时发现架构是否把“位置决定全部状态”“任何节点都能立即停止”等平地假设写死，又不必一开始承担完整跳跃系统的范围。

## 对后续扩展的约束

- 跟随主要扩展目标管理。
- 跳跃主要扩展移动能力和动作执行。
- 新地形主要扩展世界知识、几何和能力判断。
- 更换寻路算法主要替换后台规划内部。
- 转弯优化主要修改局部跟踪。

这些变化允许通过稳定接口影响其他模块，但不应要求重写整个导航系统。如果新增一项能力必须同步复制目标、地图、路线和输入状态，说明职责边界仍有问题。

## 影响

新架构的初期代码量会较少，完整能力出现得更晚，但每个阶段都有可运行成果和清晰的失败归属。三个参照继续承担各自的比较用途，不因新分支存在而被删除、覆盖或合并成一套实现。
