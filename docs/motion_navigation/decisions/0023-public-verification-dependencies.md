# D023：公开仓库补齐 Java 输入门禁和真实运行样本

日期：2026-09-25
状态：采用

## 要解决的问题

公开仓库原有 Java 门禁只编译纯 Java 类。负责输入租约和采样账本的 `ClientBehaviorInput` 依赖 Minecraft 的 `Input` 基类，因此只能在主项目已有游戏依赖时检查。

公开验收文档还引用了多次 Fabric 正式运行，但仓库没有任何真实轨迹。外部审查者只能验证合成夹具，无法核对文档中的批次汇总是否确实来自对应运行。

## 决定

1. 在 `tests/java/stubs/` 中维护 Minecraft `Input` 的最小编译桩。它只声明 `ClientBehaviorInput` 实际使用的字段和方法。
2. 公开 Java 门禁同时编译这个桩、`ClientRequestGate`、`ClientBehaviorInput` 和现有测试程序。桩不进入 Fabric 构建，也不替代真实 Minecraft 1.21 JAR 的兼容性检查。
3. 公开证据保留七个完整批次：B10-C 跨隙、C1-B 移动近战和 C1-C 外力恢复各一个通过批次、一个失败批次，再加入 B11 放置与有限搭桥的最新通过批次。
4. 每个批次只保存结构化结果、完整试次清单和结构化轨迹。JAR、世界、普通日志、画面、缓存和本机路径不进入公开包。
5. 归档使用确定性的 `tar.gz`。外层清单和归档内清单都记录 SHA-256。验证器拒绝越界路径、符号链接、未登记成员、状态不一致和超过上限的内容。
6. 七个归档的总压缩体积不得超过 30 MiB。这个上限在生成和验证时同时检查。B10-C 通过批次不复制近 500 MB 的整条 trace；改为保留 210 个协调控制帧、协调试次、完整求解汇总和物理 tick 片段。
7. 历史运行结果与当前代码重放分开记录。旧失败批次后来可以被新代码正确处理，但公开包仍保持它当时的失败状态和失败原因。

## 为什么这样做

最小桩能让没有 Minecraft JAR 的审查环境检查我们的输入逻辑，同时不会伪装成游戏接口兼容性证明。真实 JAR 集成检查继续留在主项目和 Fabric 验收中。

完整批次比单条试次更有价值。审查者可以重新统计 20／20、19／20 等结果，也能沿着结构化轨迹检查失败发生在哪一层。每类只保留一正一反，既覆盖实际数据，又避免把数百兆世界和运行目录复制到源码仓库。

## 证据边界

- Java 最小桩只能证明 `ClientBehaviorInput` 的自有逻辑和当前所需接口能独立编译。它不能证明 Mojang/Fabric 的二进制接口没有变化。
- 七个样本证明的是这些历史批次的内容、结果和读取链没有被改写。它们不是新的实机实验，也不能替代当前代码的单元测试与 Fabric 回归。
- 失败样本用于保留问题及其归因。不得从正例成功率中删除失败，也不得用修复后的重放结果覆盖历史失败。
