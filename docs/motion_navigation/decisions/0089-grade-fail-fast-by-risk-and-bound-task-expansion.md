# D089：按风险使用 fail-fast，并限制任务自动扩张

日期：2026-10-08。状态：决定有效。

## 要解决的问题

fail-fast 原本用于尽早发现问题，避免带着已知错误运行昂贵矩阵。但 F2-S 之后的工作出现了另一种失控：每个子阶段都及时停止，整个任务却在发现新问题后继续自动开下一阶段。

后续必须同时限制验收成本和任务范围。

## 决定

### 1. 先按风险分类

| 类别 | 例子 | 处理 |
|---|---|---|
| 硬停止 | 安全不变量违反、身体无人负责、旧结果获得执行资格、真实控制期限错过、无界等待 | 立即停止实施和扩大验收 |
| 当前交付阻塞 | 冻结旧成功退步、当前目标未完成、正式路径与声明不一致 | 当前能力不能签署，最多做两轮限定修正 |
| 性能或体验债 | 内部余量未达，但没有真实期限失败、安全事件或产品退步 | 保存数据并登记，不自动阻塞无关工作 |

动作名称不能决定风险。坑边普通步行可能属于硬停止；后台计算较慢但仍赶上执行窗口，可以只是性能债。

### 2. 同一任务最多做两轮限定修正

第一轮修正直接根因。第二轮只处理该修正带来的相邻回归。

出现以下任一情况时，结束当前任务并报告：

- 需要改变新的公共契约或状态所有者；
- 需要更换规划、求解或控制方法；
- 需要建立新阶段或新验收集合；
- 第二轮后仍有交付阻塞；
- 新问题与冻结目标没有直接关系。

只有用户明确授权，才能重新冻结范围并开始新阶段。

### 3. 验证按成本扩大

默认顺序为：

1. 最小复现或组件检查；
2. 少量正式调用链；
3. 受影响的冻结集合；
4. 完整矩阵；
5. Fabric 实机。

前一层出现硬停止或交付阻塞时，不继续运行更昂贵的层。小范围诊断修改只复跑直接受影响的检查。没有代码、输入、环境或验收变化时，可以复用仍然有效的证据。

### 4. 区分真实期限和容量目标

真实期限回答“输入是否还能及时生效”。容量目标回答“是否给未来负载留有余量”。

输入错过动作窗口、后台过期结果获得资格、完整控制帧超过冻结真实期限，属于硬停止。单独的内部 P95／P99 余量不足属于性能债。

### 5. 历史记录不回写

旧阶段的失败、停止和未运行项目继续保留。新口径只决定后续如何安排工作，不会把旧失败改成通过。
