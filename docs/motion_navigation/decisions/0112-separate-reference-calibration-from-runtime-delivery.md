# D112：把参考机校准与运行时交付期限分开

日期：2026-10-16。状态：**FAILED／STOPPED。**

## 1. 要解决的问题

D111 证明了 GC 不是那次 B10 整体超限的主因，但不能证明求解器稳定在 30 ms 左右。D110 与 D111 使用相同求解代码和输入，求解线程 CPU 平均值仍从 19.6 ms 变成 26.5 ms。用户确认 D111 正式运行时还有其他程序在工作。

因此，单次后台求解的墙钟时间会受机器状态影响。它不适合作为机器人能力的唯一门槛。项目也不能把当前开发机的空闲速度写成设备要求。

## 2. 决定

### 2.1 空闲校准只判断性能证据能否用于比较

正式性能运行前后，使用同一份固定输入运行短基准。校准只回答“本次运行期间机器是否足够稳定”，不回答“这台设备能不能运行机器人”。

校准不合格时：

- 功能、安全和类型化结果仍然有效；
- 本次墙钟结果不用于签署性能结论；
- 不通过反复重跑挑选最好结果。

D112-0 在当前 Windows 上取得四轮独立短采样，固定输入、求解结果和工作量签名逐项相同，wall P50 的自然波动约 0.5%。正式运行前后校准要求同一工作负载签名一致，wall P50 与 P95 的成对漂移分别不超过 10%。这个阈值明显高于本次短采样波动，又能识别 D110 到 D111 约三成的整轮差异。

记录 CPU、逻辑核数、电源计划和用户声明的重负载程序；不扫描程序命令行。10% 只决定性能证据能否用于比较，不是设备准入线。

### 2.2 正式行为按 tick 和输入实际生效判断

后台工作是否及时，以客户端回执确认输入在候选窗口内实际生效为准。正式证据按同一 computation identity 关联：

1. worker 提交；
2. worker 完成；
3. receiver 看见并登记；
4. 控制线程首次取用；
5. 动作获准；
6. 客户端实际应用输入。

新动作首次取用候选时，至少领先首条输入最早许可 tick 一格。首条输入必须不晚于最晚许可 tick。后续命令允许在精确的最晚 tick 生效，不能强制每条命令都保留一 tick 余量。

### 2.3 控制线程保留实时门槛

控制准备继续使用既有门槛：P95 不超过 8 ms，P99 不超过 15 ms，最大值小于 30 ms。测量从观察已交付到动作派发，不包含等待下一次游戏观察的后端阻塞。

D112-0 已用 D111 原始 trace 核对当前口径。5,399 个控制准备样本的 P95／P99／最大值为 3.5100／29.6744／42.3297 ms。该运行没有前后校准，而且用户确认当时还有其他程序在工作，所以这里只把口径和原始结果冻结为基线，不签署性能通过。D112 正式运行必须在校准合格时重新判断完整门槛。

### 2.4 同步探针不再充当生产求解门槛

B10 的 142 次同步求解只属于测量探针。它们继续报告墙钟、CPU、GC、候选数和物理步数；30 ms 保留为非阻断警戒，不再决定正式 B10 是否通过。

候选数、命令 tick、队列容量和证据字节上限仍是硬门槛。D109—D111 的历史结论不回写。

正式控制线程不得在缺少后台结果时临时求解。`prepare_planned_gap_motion()` 和 `prepare_planned_air_transition()` 缺少 `precomputed` 时返回有类型的 `PRECOMPUTED_REQUIRED`，不调用求解器。

### 2.5 较慢设备必须有界降级

设备较慢时，机器人可以提前准备、延后严格动作、换路或执行安全尾段。一次后台结果较慢不能让 Runtime 失败，也不能阻断普通地面控制。

D112 使用 movement tick 注入延迟：

- 延迟 2 或 5 tick：正式动作应完成；
- 延迟 10 tick：允许完成，或得到有类型的安全有界结果；
- worker 存活但永不返回：不得盲目起跳或离边，必须零伤害、有界结束并释放 owner。

固定矩阵只能表述为“这些场景零错过”。没有约 300 个独立随机零失败样本时，不宣称错过率的 95% 上界低于 1%。

D112-3 的 RED 证明，旧的 4-tick 中性地面准备上限会让固定 5-tick worker 每轮都少一 tick 启动余量，并在三次复核后失败。该上限扩为 5 tick；新增的一 tick 仍由计算器和复核证明，不放宽入口、落点、UNKNOWN 或伤害条件。10-tick 延迟继续走安全有界降级，不继续扩大前缀。

## 3. 正式结果

D112 的组件矩阵和 Windows 门禁已通过。第一次 Fabric 尝试在完成 82 个既有 B10 求解试次后，读取 receiver 汇总时把 `deliveries` 写成 `delivery`，于第一个 D112 coordinator 试次的证据组装阶段触发 `KeyError`。没有形成 D112 coordinator 试次记录，因此只记为 `INVALID_HARNESS_RUN`。

字段修正后，第二次尝试完成 20／20 基线和 8／8 的 2-tick 延迟场景。随后客户端在固定 5-tick 延迟的第一场附近以脱敏 `IllegalStateException` 退出，Python 等待下一帧观察超时。调查发现部署客户端确有独立期限配置，外层 600 秒没有传入客户端；该缺口已修，但最终运行仍复现后续客户端异常，所以不能把第二次失败归因于期限。该次尝试同样不能覆盖冻结矩阵，原始记录保留为 `INVALID_HARNESS_RUN`。这次已经形成的 28 个可执行场景全部安全完成，证据链完整，窗口错过和伤害均为 0。

修正期限传递后运行最终正式批次。20／20 基线和 8／8 的 2-tick 延迟场景再次全部完成。固定 5-tick 延迟的第一场在三次结果交付后仍没有启动余量，以 `motion_retry_exhausted:new_motion_grant_has_no_start_slack` 安全失败。机器人保持着地、零伤害并显式释放来源，但这违反“5 tick 必须完成”的冻结门槛。控制准备的正式 trace P95／P99／最大值为 4.8791／22.4488／29.9488 ms，P99 也超过 15 ms 门槛。运行前后校准 P50／P95 只变化 +0.09%／−0.14%，性能结果可比较。

在上述两个阻断结果之后，后续等待观察又以客户端脱敏的 `IllegalStateException` 和 Python `deadline_exceeded` 结束。它作为独立夹具缺陷登记，不改写已经形成的 D112 失败。10-tick 与 worker 永不返回的 Fabric 场景没有运行，不能宣称实机通过。

D111 保持原结论；D112 为 **FAILED／STOPPED**，不再重跑。D110-SOLVE-01 继续打开。旧记录保持原字节和原结论。

## 4. 范围外

- 不优化求解器或删除安全尾段证明；
- 不开始连续两跳、零等待交接或新动作；
- 不新增生产状态机；
- 不把同步探针的 142 次样本冒充正式 worker 链；
- 不把当前开发机的速度设为设备准入条件。
