## 1. 要解决的问题

Task 5A 停止后，Windows 复现确认了两类问题。

第一类是证明错误：未恢复的风险区间可能从证明中消失，条件资源也可能被当成已经证明。

第二类是搜索结构错误：逐 tick 贪心搜索会长时间停留在一条从首个输入起就不可能通过验证的分支里。给输入集增加疾跑或新朝向后，原来能找到的路线反而可能找不到。

因此，本决定只授权一轮 Task 5A-R。它先修证明，再把搜索前端换成有界动作元枚举，最后在 Windows 上判断计算成本是否值得继续。

## 3. R1：证明只保留一套安全含义

支撑与停车拆成两个判断。

安全支撑要求：

- 已着地；
- 公开支撑查询为 `FEASIBLE`；
- 支撑比例至少为 0.15。

安全停住在安全支撑的基础上继续要求：

- 水平速度为零；
- 没有低于允许高度；
- 预计伤害没有超过任务余额。

停车尾迹、风险区间恢复和等待分支使用安全停住。目标检查只使用安全支撑，再把实际速度交给 `GoalState.accepts()` 和原型最小终速下限。循环结束时仍未关闭的风险区间必须拒绝候选，不能发出证明。

当前 1.21 计算器没有完整服务端饥饿时钟。请求只要带非空资源下限，就返回 `NEEDS_INFORMATION/unproven_resources`，不使用旧的 `food_points` 假装完成证明。

单个候选在停车尾迹上限内停不住，只淘汰该候选。整个请求的共同物理 step 预算耗尽，才返回请求级预算结果。

## 4. R2：动作元必须稳定扩展

### 4.1 候选结构

候选由以下短段组成：

1. 地面推进 G，0—20 tick；
2. 可选的一次起跳 J；
3. 起跳后的控制 A，0—16 tick；
4. 可选的正常制动 B。

每个网格点先检查“当前状态能否作为正常终态”。尚未满足时，对所有目标枚举正常制动段 `B(k)`，`k` 从 1 增加到剩余轨迹长度；每个前缀都用实际速度检查是否进入目标允许的最小／最大终速带。B 不要求最终完全静止。安全停车尾迹仍由承诺扫描器独立计算，不能因为存在停车尾迹，就把整条停车尾迹强行加入正常路线。

这样可以同时支持：

- 需要停住的普通目标；
- 以非零速度进入下一段的连续目标；
- 取消时仍能安全停车的证明。

`TrajectorySearchRequest` 增加原型专用的最小终速下限。它不得超过 `GoalState.maximum_terminal_speed_blocks_per_second`。搜索与逐支目标检查都必须同时满足最小和最大终速。

请求还要明确声明 `stop_input`。它必须是零移动、非跳跃、非潜行、非疾跑输入，并存在于每个输入层。扫描器使用它生成安全停车尾迹，不能自行制造一条未声明的中性输入。

### 4.2 输入集单调性由构造保证

增加输入不能修改旧动作元已经生成的输入序列，也不能挤占旧输入的冻结预算。

请求把输入登记为累计层：A3 是第一层；A5 必须完整保留 A3 的有序输入，再追加疾跑；A15 必须完整保留 A5，再追加新朝向。所有层与承诺扫描共用同一个 `CountedPhysics` 和同一份请求总预算。搜索先完整运行旧层；旧层找到后立即返回，不进入新层。旧层确认没有结果后，才进入下一层。共同预算先耗尽时立即返回请求级预算结果。

动作元以稳定身份登记：输入层、步态、转向策略和保持 tick 数共同组成身份。层内转向可以根据目标中心选择该层已有的朝向；增加下一层不会重新生成上一层的命令。

同一动作元的准时和晚一 tick 分支执行完全相同的输入。搜索使用共享前缀树，不再按单一准时状态合并节点。结果记录获胜输入层、完成尝试次数和完整扫描次数。

### 4.3 R2 冻结场景

冻结正例为：

- Task 5A 三个代表；
- 直线跨隙：起点 `start=1`、宽 1—2，分别使用 A3／A5／A15；起点 `start=4`、宽 1—2，分别使用 A3／A5／A15；起点 `start=4`、宽 3，使用 A5／A15；
- `flat_sprint`、`turn_90`、`jump_up_after_turn`；
- 两项连续终态：

- `jump_gap_continue`：落地后仍以冻结速度带继续前进；
- `jump_up_after_turn_continue`：转弯上跳后以冻结速度带进入下一段。

这两项必须证明正常终态非零速，同时最后边界仍有安全停车尾迹。它们不能靠先完全停住再重新起步通过。

冻结负例为：

- `start=4`、宽 3、A3 的网格耗尽；
- 1／12 支撑；
- 非空资源目标；
- UNKNOWN 落点；
- 极小预算；
- 只有碰撞候选。

输入集单调门槛同时检查 A3、A5、A15：扩大请求时，进入新层之前产生的候选、输入、逐支终态和计数与单独运行旧层一致；旧层能找到时，扩大请求仍由同一旧层返回同一执行输入。请求身份不同，因此不要求整个结果哈希相等。不可行网格必须有界结束，并与预算耗尽区分记录。

## 5. R3：性能门槛

Windows 是正式性能平台。墙钟只用于测量，不参与候选顺序或停止条件。

每个正例和负例分别预热 3 次，再测量 20 次。逐场报告 P50、P95、最大值、节点、物理 step、完成尝试、扫描次数和缓存命中。P95 使用 nearest-rank，即排序后第 19 个样本。

通过条件：

- 所有 R2 正例在 P0 计数预算内找到；
- 每个正例的稳态 P95 不超过 150 ms，最大值不超过 400 ms；
- 每个负例的稳态 P95 不超过 150 ms，最大值不超过 400 ms；
- 同一请求在不同 `PYTHONHASHSEED` 下结果、证明哈希和计数一致。

超过上述门槛不允许“带债进入 5B”。R3 内只允许一轮限定性能修正，仍未通过就结束 TP。

150 ms 只表示后台原型值得继续制作 5B 的完整 P0 量尺。现行 P1 的后台搜索 50／100 ms、正式控制线程 8／15／30 ms 和至少提前一个 movement tick 可用的门槛都不在本决定中放宽。P2 后续还要单独测量承诺余量和等待后台结果是否造成停步。

## 6. 允许的性能优化

允许：

- 调整不删除候选的枚举顺序；
- 有证明且有变异检查的前缀剪枝；
- 请求内按“全部时序分支完整状态＋输入”缓存 `step()`；
- 复用同一状态和同一输入的真实停车尾迹；
- 在进入完整扫描前做便宜、保守的目标和支撑检查。

不允许：

- 复制运动公式替代 `step()`；
- 用墙钟决定结果；
- 放宽 R1 安全判断；
- 为了过矩阵修改某个场景的目标或输入；
- 把安全停车尾迹冒充正常执行路线的一部分。

## 7. 退出规则

出现任一情况就结束 TP，不再追加修正轮：

- R1 后仍发现证明遗漏、UNKNOWN 当 FREE、未验证输入获得证明或资源误证；
- R2 正例、输入集单调性或非零终速场景不通过；
- R3 一轮性能修正后仍超过门槛；
- 原型生产代码超过约 2500 行且不能逐项说明；
- 时间盒到期。

结束时保留 TP-0 对照、扫描器、合同、全部失败和测量，不接入正式导航。

## 8. 实际结果与终结

R1 修正了安全支撑、未关闭风险、条件资源、停车尾迹和最小终速分类，专项检查与既有回归通过，R1 签署。

R2 候选 `cfd36acd` 在绑定式动作元下通过当时的22项正例、6项负例、层单调、非零终态和哈希种子检查。但独立审查发现，候选要求 G、J、A 使用相同 forward／sprint／yaw，因而不会枚举合法的 `Walk×1 → SprintJump×1 → Walk×5 → Neutral×14`。这违反第4.1节中 G、J、A 各自独立选择控制的含义；原全绿结果不能签署 R2。

唯一限定修正把 G、J、A 身份和枚举拆开。审查反例随后由 A5 找到同一21 tick输入，并通过完整 scanner 和两支目标检查，计数为859 nodes、23,900 physics steps、384 tail ticks、11,565 completed candidates和1次完整扫描。随后重跑冻结矩阵时，`turn_90`、`jump_up_after_turn`、`jump_up_after_turn_continue` 均在1,375 nodes、65,536 physics steps、32,769 completed candidates处返回 `NO_TRAJECTORY_IN_BUDGET/physics_step_budget`，没有进入完整扫描。

这触发“R2 正例不通过就结束 TP”的退出规则。没有调整 `4096／65536／40／2` 预算，没有修改场景或用枚举顺序掩盖失败。限定修正未提交，完整 diff 与计数保存在 `evidence/motion_navigation/trajectory-proto-5ar-v1/`。`cfd36acd` 保留为候选，不回写成 R2 通过；R3、5B、完整18族、runner、闭环、Fabric 和 worker 均未开始。
