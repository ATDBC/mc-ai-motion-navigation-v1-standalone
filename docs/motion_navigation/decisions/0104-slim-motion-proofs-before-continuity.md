# D104：先缩小运动证明，再恢复连续动作试验

> 2026-10-13 后注：本决定止于 K1，失败结论和证据保持不变。后续工作改由 [D105](0105-restart-sound-proof-slimming-and-decouple-tracks.md) 重新定义。

日期：2026-10-13。状态：**K0 已验证；K1 完整性门槛失败，后续停止。**

本决定接续 [D103](0103-repair-g2-window-and-control-hot-path.md)。D103 的 G2-F2 仍保持 `FAILED／STOPPED`，历史证据不改写。新的实施方案见[关键边界证明与连续动作计划](../stages/key-boundary-motion-proof-and-continuity-plan.md)，结果记录见[对应验收文档](../acceptance/key-boundary-motion-proof-and-continuity.md)。

## 要解决什么问题

D101 已经证明“短开环输入＋逐 tick 廉价比较＋关键节点严格检查”的方向可行，但动作开始时仍为每个边界生成停车尾迹。以 `jump_gap_1` 为例，完整证明需要 451 次物理推进，其中停车尾迹约占九成。

D102／D103 没有先减少这部分工作，而是把整份证明搬到后台。worker 返回约 775 KiB 的对象图，receiver 又逐格复核快照、重跑所有构造器并重算规范摘要。一次接收的工作量因此比物理证明本身大很多。G2 后来又用“控制线程任何物理调用都必须为 0”作门槛，与正式 `FixedRouteController` 的有界短预测相冲突。

这三个问题必须分开处理：

1. 证明只保存真正影响安全决定的节点；
2. 本地 receiver 只核对当前权威事实，不重复执行离线审计；
3. 控制线程允许有步数上限的短预测，禁止无界搜索和整份证明。

## 决定

### 1. 运动证明只保存动态关键节点

关键节点不能按动作名称或固定 tick 写死。每条时序分支先回放一次主输入，再根据真实支撑和停车尾迹求出：

- 动作入口；
- 每个风险区间的最后可放弃边界；
- 越过该边界后的承诺边界；
- 重新落地并恢复安全停车能力的边界；
- 动作终点。

只有入口、最后可放弃边界、恢复边界和终点需要保存安全尾迹。承诺区间内不再声称“随时能停”；它保存必须继续执行的输入和恢复边界。普通无风险动作只保留入口和终点。

第一次实现只支持一个风险区间。UNKNOWN、未支持材料和多个风险区间继续有类型地拒绝。冻结的 18 个动作样本必须与旧逐边界扫描器逐项比较风险区间；新实现不能凭动作名称猜测承诺点。`jump_gap_1` 在按下跳跃前已经可能越过最后可放弃点，这一场景必须进入门禁。

### 2. 主轨迹继续用于廉价逐 tick 比较

本轮保留主轨迹。正式执行每 tick 只比较当前状态是否仍落在已证明范围内，不重新计算停车尾迹。安全尾迹只保存输入、起点、终点、伤害和依赖，不再保存全部中间状态。

真正执行尾迹前，从当前真实状态做一次有界回放。尾迹长度由证明自己声明并受模板上限约束，不能统一假定为 9 tick；现有样本最长达到 21 tick。

输入流第一条回执到达后，只保留实际发生的时序分支。中段输入晚到或缺失属于偏离，不能重新选择“整体晚一 tick”分支。

### 3. receiver 采用受信任本地 worker 的可靠性边界

当前 worker 是同一发行物启动的本地特权子进程。pickle 只用于这个受信任边界。消息摘要用于发现传输损坏和程序错误，不构成发送方认证。

receiver 继续检查消息类型、schema、作业身份、大小和摘要，并独立核对 request、generation、owner、路线／动作修订、账本、世界会话、规则版本、预期输入摘要、生效窗口、期限、伤害余额、当前依赖版本和发布竞态。

递归遍历整份不可变对象图、重跑所有嵌套构造器、重算整份 proof／bundle 规范摘要、逐格重建和复核快照，移到构造端测试和离线审计。

如果以后允许外部或插件 worker，必须改用非可执行 wire 格式并重新定义认证边界，不能继续用 pickle 后再增加递归检查。

### 4. 局部快照是独立值，不建立长期租约

父侧按动作模板的最大可达包络、入口身体范围、落地区域和扫掠余量生成 detached 局部快照。边界统一向外多取一格。worker 查询超出快照时返回 `NEEDS_WORLD`，不能把缺格当空气。

结果只返回实际依赖的版本。父侧登记和执行前仍以当前正式世界核对这些版本。局部快照由普通对象引用和垃圾回收管理，不再为它保存规范 bytes、租约返回队列和独立引用计数线程。

这不删除身体责任。candidate、executing 和 safe-tail 仍是三种明确用途；close 只能撤销尚未生效的 candidate，已经承担的执行和安全收尾必须保留到有证据释放。

### 5. 热路径按时间和物理步数共同约束

控制线程继续满足 Windows 完整决定 P95≤8 ms、P99≤15 ms、最大值<30 ms。

同时记录每 tick 的物理推进数。正式上限在 Windows 上测量 `FixedRouteController`、最长合法关键尾迹和正常收尾后冻结。门槛禁止无界搜索、整份候选证明、整份世界快照复制或规范化，以及 receiver 对完整对象图的递归复核。

有明确上限的地面短预测、关键尾迹回放和必要的安全收尾可以运行。旧 G2 的“任何物理调用均为 0”不再用于新阶段。

### 6. F-TICK 改为 D101 的独立只读试验

真实客户端 tick 顺序在代码上不依赖 G2、G3 或提前证明管线。现有依赖只是 D102 计划和验证器人为规定的流程顺序。

F-TICK 改用已经验收的 B10 Runtime＋Fabric 跨隙路径，四方向各 10 次。它只记录每条输入流首命令的 observation、发送、采样、应用和 movement tick 顺序，并分类为 `NEXT_MOVEMENT_TICK`、`LATER_MOVEMENT_TICK` 或 `INCOMPLETE`。

F-TICK 不改写 D102 的失败，不伪造 G3 predecessor，也不证明连续两跳已经完成。只有 40／40 时间线完整，后续阶段才能决定是否需要客户端按绝对 tick 预排程。

### 7. 零等待连跳的规则

如果两个动作之间没有安全停车点，两个动作属于同一个承诺段。后一个动作声明是否需要“落地即起跳”。它的首条输入必须在看到落地之前准备好，并按 F-TICK 证明可行的协议发送。

落地观察用于事后核对。核对失败后，原 owner 继续负责空中或落地恢复，不能先释放身体再重规划。不同动作之间只交换入口范围、出口范围和承诺边界，不增加动作组合专用分支。

## 实施顺序和止损

顺序固定为：

1. 用旧扫描器冻结关键节点 oracle 和 RED；
2. 在隔离 D101 路径实现关键边界证明；
3. 在 Windows 重跑原 M0 门槛；
4. 通过后把同一紧凑证明迁入正式 worker；
5. 再简化 receiver、局部快照和 registry 载荷，并重测正式提交到可用的完整延迟；
6. 独立运行 F-TICK；
7. F-TICK 通过后，才在现有 B10 worker 链上接连续两跳和零等待交接。

任一步未通过即停止。失败结果保持原样，不通过放宽时间门槛、删除 owner 或减少安全事实来继续后续阶段。

## 历史边界

D098 P3、D101 M0 和 D102／D103 G2 的原失败全部保留。D102 的临时 pipeline 不直接成为第二套生产管线。D103 Task A／B 已通过的窗口转换与观察容量修正继续保留；Task C／D、旧 Task 10、G3 和旧 F-TICK 顺序由本决定停止使用。
