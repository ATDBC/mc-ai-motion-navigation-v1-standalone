# D115：收好 D114 夹具边界，并用现有准备链验证连续两跳

日期：2026-10-17。状态：**PARTIAL／STOPPED。** D114 夹具收尾和按动作更新交付估计已完成；连续两跳在正式闭环代表场景触发预定止损，没有进入矩阵或 Fabric。

## 1. 要解决什么问题

D114 已经证明 B10 单动作链能够在 Fabric 上经过正式导航驱动完成后台求解、等待、降级和来源释放。三方复核同时发现，B10 的传送等待在连续两场起点和朝向相同时可能提前返回。真正的传送随后落进正式场景，会污染带速入口和助跑结果。

连续两跳的基础结构也已经存在。`MotionRouteCoordinator` 能按当前动作的已确认出口准备紧邻严格动作，receiver、registry、执行监督者和 Runtime 激活也已有对应接口。现行生产路径只在 `Walk -> 严格动作` 时自动准备，尚未在 `JumpGap -> JumpGap` 时调用已有入口。

本轮先收好夹具，再接通这一个生产调用点。不得借此新增第二套 worker、状态机、账本或 Session 分支。

## 2. D114 收尾

传送命令发出后，夹具不能因为命令前的旧观察已经处于目标位姿而立即开始场景。等待必须同时满足：

- 至少推进 3 个新的 movement tick；
- 必须先观察到传送命令生效的因果迹象：位置或朝向相对命令前发生变化，或者同位姿传送出现 Fabric 已稳定观测到的 `on_ground=false` 到达帧；固定等待时长不能代替这项证据；
- 随后连续 2 帧位于目标范围、着地、水平速度接近零且朝向满足要求；原版和现有计算器在着地时仍可能保留竖直速度分量，不能把它误判成未稳定；
- 期间任何未着地、位置、速度或朝向超限都会清空连续稳定计数；
- 正式场景在 `driver.start()` 前再次核对起点，失败记为夹具错误，不进入产品安全统计。

组件后端要能延迟应用一次“目标位姿与当前位置相同”的传送。这个场景必须证明旧实现会提前返回，新实现会等到真实传送后的稳定观察。

“等待帧”统一表示：**正式驱动在本帧没有提出移动意图。** `submit_input=false` 不能作为该指标，因为规划帧仍可能有本帧重新提出并获胜的移动意图。

Fabric 和组件必须调用同一个 trial 组装与汇总函数。撞到场景帧数上限始终属于夹具失败，即使当时身体可以立即释放，也不能计作安全终态。

本切片不单独重跑 Fabric。下一次连续两跳正式批次会同时验证修正后的真实传送等待。

## 3. 旧前置条件怎样处理

### 3.1 D110-SOLVE-01

D112 已经把同步探针的 30 ms 门槛改为非阻断警戒，并封住控制线程同步求解入口。因此 D110-SOLVE-01 以“旧门槛已由 D112 取代”退役，不写成求解器性能已经修好。

D110、D111 的失败历史保持不变。D114 同步探针最大 27.9042 ms 只作为一次参考数据。

### 3.2 T1

T1-A0、A1、A2 已验证的安全语义继续有效。完整证明应由现有 motion worker 提前生成和登记。控制线程只做有界比较：身份、generation、真实身体、依赖版本、伤害余额和执行窗口。

控制线程不得临时做完整扫描、摘要、序列化、快照重建或同步求解。控制准备继续满足 P95 不超过 8 ms、P99 不超过 15 ms、最大值小于 30 ms。完整证明本身的耗时只报告；是否及时按“交接前可信可用”判断。

T1 历史性能失败不回写。本轮用连续两跳正式链验证 worker 集成，满足门槛后再签署新的集成结论。

### 3.3 T2-3

删除重复 bundle、bytes、lease 和返回载荷属于性能整理，不再阻塞连续两跳。消息大小、队列容量、快照范围、资源关闭和交付余量仍是硬门槛。真实数据证明载荷妨碍交付时再处理，不提前做删除工程。

### 3.4 T3

T3 用组合证据关闭：D106 的四方向 40／40 `NEXT_MOVEMENT_TICK` 加上 D114 的正式驱动、输入回执、安全终态和来源释放。D105、D106 的原失败保持原样，只新增关闭记录。

## 4. 路线内交付估计

交付估计按当前动作代际维护：

- 一个合法的新 `SOLVE` 首次交付时，用本次实测 tick 重新建立该动作的估计；
- 同一动作代际后续的 `REVALIDATE` 只能把估计上调；
- 无效、过期、重复、旧 scope、旧 connection 或旧 revision 的结果不能改变估计；
- 估计仍限制在现行 1—5 tick，不增加字段、等待、重试或任务状态。

这样，一次较慢的旧动作不会让整条路线后面的每个严格动作都多等约 200 ms。

## 5. 连续两跳的首个正式范围

只验证已知地形、同一路线、同方向的两个相邻 `JumpGap`：

1. 第一跳的首条真实回执确定 0／1 tick 分支；
2. 第一跳仍在空中时，协调器按该分支的已验证出口准备第二跳；
3. 第二跳在落地前已经可信登记且真实入口匹配时，通过现有监督者和 Runtime 激活链交接；
4. 第一跳落地 tick 为 `L` 时，第二跳首条实际输入最迟在 `L+1` 生效；
5. 两跳之间不出现无必要的 neutral、制动、反向输入、完整停车、owner 空档或 route 变化；
6. 第二跳尚未准备好、晚到或永不返回时，第一跳原 owner 执行已经证明的安全尾段，身体停在中间平台，不盲目开始第二跳。

首轮不授权落地同 tick 的预排程，不扩展到不同方向、其他动作组合、新动作族或一般跑酷搜索。

## 6. 门槛与止损

组件矩阵至少覆盖四个方向、中间平台 2／3／4 格、第二跳交付 0／2／5／10 tick 和永不返回。结果分别报告“落地前已准备并连续接续”与“未准备好但安全收尾”，不能把安全失败算作连续成功。

硬门槛：

- 伤害、UNKNOWN 放行、无人负责的身体推进、旧 generation 应用和来源泄漏均为 0；
- 相关依赖变化后旧证明使用为 0；
- 准备及时的样本全部 `L -> L+1`，两跳间完整停车为 0；
- 控制准备和交接 tick 满足 8／15／30 ms；
- 控制线程同步 solve 或完整证明重算为 0；
- pending 作业、已登记 handle、消息字节和资源生命周期保持有界。

出现以下任一情况立即停止，不进入 Fabric：

- 需要新增 Session 状态；
- 需要第二套 worker、inbox、registry、账本或交接协议；
- 需要按 `JumpGap -> JumpGap` 写动作组合状态机；
- 需要扩大入口、UNKNOWN、伤害或依赖门槛；
- 未确认第一跳真实分支就准备第二跳；
- 为赶期限把完整求解搬回控制线程；
- 两轮限定修正后，已准备的候选仍不能在 `L+1` 生效。

组件、Windows 完整检查和公开快照全部通过后，只运行一次 Fabric 批次。正式运行同时验证传送稳定等待、四方向连续两跳和迟到安全收尾。

## 7. 实施结果

D114 夹具收尾已完成组件验证：

- 同位姿传送必须先观察到 `on_ground=false` 到达帧，再累计连续稳定观察；起点的毫米级自然漂移不能冒充传送已生效；
- 不同位姿传送以第一次进入目标位置和朝向范围作为生效证据；
- `driver.start()` 前再次核对起点；
- 组件和 Fabric 共用 trial builder 与汇总函数；等待帧统一为“本帧没有移动意图”；
- frame limit 始终为夹具失败。

交付估计已经按动作 subject 更新。相同 subject 的完整求解重试和复核都只能上调；subject 改变的新完整求解才重新建立估计。D113 抖动矩阵保持通过。

连续两跳的局部自动准备曾在临时正式闭环中接通，随后按计划撤回。代表路线由正式规划器生成 `Walk -> JumpGap -> JumpGap`。第二跳证明在 tick 12 登记，窗口为 21—22；身体在 tick 20 精确进入准备入口，但 Session 在该控制循环先请求交接批准，执行器随后才发布动作边界。tick 21 再批准时，身体已经滑出精确入口；tick 22 证明过期，任务停在 `executing/prepared_action_boundary`。

修复需要调整 Session、ExecutionSupervisor 与 ActionRouteExecutor 的同帧交接顺序，或者增加明确的同帧第二阶段。这超出本决定只允许协调器局部接线的范围，因此触发止损。自动准备生产改动、活动失败测试和临时测试夹具修正均已撤回。紧凑复现记录保存在 `evidence/motion_navigation/d115-two-jump-v1/stop.json`。

本轮没有扩大 0／2／5／10 tick、永不返回、四方向或平台长度矩阵，没有运行完整 Windows／公开快照检查，也没有运行 Fabric。不得写成连续两跳已经交付。
