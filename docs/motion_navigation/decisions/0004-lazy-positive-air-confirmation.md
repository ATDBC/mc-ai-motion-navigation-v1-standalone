# D004：空气采用按需批量确认

日期：2026-09-18
状态：已接受；2026-09-27 已完成单帧视觉空气实现和 Fabric 实测

2026-09-26 补充：本文只决定空气如何按需确认，不再允许实现自行选择方块视觉来源。正式方块视觉必须使用 profile 4 表面深度。profile 3 稀疏射线已经弃用，只能读取历史证据，详见 [D035](0035-formal-surface-depth-only.md)。

2026-09-26 第二次修订：旧实现会在玩家周围 32 格内直接读取 `isAir()`，即使目标格被墙完全挡住。这会让导航知道玩家无法从当前视角获得的空间信息。现行决定改为：空气请求只确认**视觉上完整呈现为空**的格子。它允许与游戏内部的隐藏状态不同；身体接触、当前交互目标或后来真正看到的方块会用更新事实纠正它。实施顺序和验收见 [表面深度合法空气与感知成本整改计划](../stages/B12-surface-depth-remediation-plan.md)。

## 要解决的问题

`pre-floating-7ab0b35f` 能提供真正看见的方块，但“没有看到方块”不能证明该格是空气。逐帧扫描整个视锥会重复检查大量与当前动作无关的格子；逐格跨模块查询又会产生通信和调度开销。

## 决定

新主线使用 D035 固定的 profile 4 表面深度作为方块事实来源。空气由单独的正式观察能力按需确认：

- 调用方一次提交一组位置或一个扫掠体积，不逐格跨模块调用；
- 返回值只列出本帧已经确认“视觉上完整为空”的位置；
- 没有返回的位置仍是未知，调用方不能从中反推出隐藏方块；
- 已确认空气按世界会话缓存；重复查询直接命中缓存；
- 世界会话变化立即清空；后来取得的合法方块、身体接触或交互事实可以覆盖旧空气事实；
- 不主动扫描整个世界，也不因一个格子进入视野就自动查询。
- 角色身体碰撞盒实际占据的空气格不需要查询，随同 `body_contact` 直接确认；脚下支撑仍按实际接触形状确认。
- 协议硬上限为每次 512 格和每个请求 16 KiB；当前适配器默认每帧提交 128 格，把剩余位置留到后续帧；
- 空气确认与 profile 4 使用同一份视锥和遮挡结果。目标整格必须完全位于当前 120° 视野和 16 格范围内，并且整格投影没有被更近的不透明表面遮挡；
- 同一帧中，该格不能存在表面深度已经报告的可见方块。身体接触或当前交互事实发现了实际方块时，也不能同时产出空气正例；
- 屏障、光源方块、结构空位等没有正常可见外形的状态，可以被确认成视觉空气。机器人接触到实际碰撞后，再由接触事实纠正；
- 单帧只看见部分格子时不确认。跨帧八分块累积尚未进入正式契约；它若以后实施，只能作为带观察时间的历史空空间，不能声称八个部分在同一时刻都为空。

视觉方块、视觉空气和未知是三种不同状态。未知不能用于通行授权。视觉空气是机器人依据合法视觉形成的自由空间事实，不是读取隐藏世界得到的绝对真值。

## 为什么这样做

扫掠、支撑和普通地面预测能够提前给出接下来一小段动作需要的格子。按这个集合批量查询，可以在控制器行走当前已确认区域时准备下一段，同时避免每帧重复扫描整个视野。

表面深度已经计算了本帧所有遮挡面的投影。空气确认复用这份结果，计算“目标整格的屏幕投影是否全部可见”，不再发射中心射线或固定数量的采样射线。只有整格都能从当前视角确认为空，才返回正例。

## 边界

空气确认是“视觉为空的正例确认”接口，不是任意方块查询接口。它不能返回隐藏方块的类型、碰撞形状或“确定不是空气”。方块仍须由合法视觉、身体接触或交互事实获得。

确认结果可以像人的观察记忆一样过时。当前阶段不使用隐藏的方块变化通知来提前撤销它；只有世界会话变化或新的合法事实到达时才更新。执行层仍要处理碰撞和接触纠正，不能把视觉空气解释为永远不会碰到东西。
