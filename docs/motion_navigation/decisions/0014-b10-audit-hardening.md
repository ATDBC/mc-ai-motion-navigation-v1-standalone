# D014：收紧 B10 的故障、性能和证明边界

日期：2026-09-23
状态：采用

## 要解决的问题

三方审查发现，B10 的正常场景虽然通过，但还存在四类薄弱点：后台异常可能造成永久等待；A* 的浮点平手会让展开量随终点位置大幅波动；空中动作会为不可能的连接做昂贵查询并复制整张世界；部分安全行为只有实测现象，没有进入候选证明。

## 决定

- 游戏 tick 中的固定容量缓冲采用“丢最旧并报告缺口”，不能因消费者暂时停顿而让客户端崩溃。
- 后台异常、进程死亡和请求过期必须变成控制侧可见的失败。相同上下文中的同因重验最多重试两次。
- 地面规划使用按列代价和稳定整数优先级。基准必须包含偏轴终点和迷宫，不能只测对角平地。
- `JumpGap` 先用支撑事实排除普通地面；真正求解时只传局部物理快照。
- 正式规划入口保留同一连接的多种动作。规划状态只保存当前动作资格真正依赖的差异。
- 空中动作必须声明快照顶部余量。跨隙候选必须记录每个命令时刻松开输入后的安全落地证据。

## 证据边界

本轮整改先通过组件测试、原生 Java 缓冲测试和规划基准，随后重跑 B04、B07、B09、B10，并增加 10.5 秒输入缓冲空闲专项实测。缓冲专项累计产生 212 个运动采样，保留最新 64 个并报告丢弃 147 个；随后前进和释放输入都取得真实应用回执，客户端没有崩溃。

Fabric 复测证明整改后的正式链路能在代表场景中继续工作。后台进程死亡、超时和异常注入仍以组件证据为准；规划性能仍以固定基准为准。B07、B09、B10 的本轮正确性回归同时运行，其耗时只用于发现明显异常，不替换原先单独运行的性能成绩。
