# D030：按问题边界拆分 B12-A 反例证据

日期：2026-09-26
状态：已采用

## 要解决的问题

B12-A 冻结了 12 类反例，每类运行两次。其中一半依赖 Minecraft 的真实观察或客户端门禁，另一半是人为注入的仲裁、输入、会话和重试故障。

若为了后半类故障也启动游戏并在正式后端加入测试开关，JVM 只充当外壳。真正决定结果的仍是注入的控制事件，还会让测试代码进入正式运行链。

## 决定

64 个冻结试次和判定标准保持不变。证据来源按下表固定：

| 证据来源 | 反例 |
|---|---|
| Fabric | 门禁拒绝、确认超时、仅生命下降、未归因死亡、提交后目标修订 |
| 确定性 Runtime 注入 | 仲裁延后、输入失败、提交后观察中断、世界会话切换、门禁额度耗尽、输入额度耗尽、确认额度耗尽 |

40 个正例全部使用 Fabric。两类反例都必须经过正式攻击契约和有类型终态。能够形成单次攻击记录的试次还要经过正式 Runtime、攻击驱动和离线重放。三类额度耗尽使用同一有类型尝试结果和正式额度归并器，核对连续两次失败只耗尽本类额度。区别只在故障事实由真实客户端产生，还是由冻结的 Runtime 夹具注入。

世界会话切换在旧 Runtime 仍有效时先取消旧攻击尝试，再替换会话。若实际运行中会话异常消失，另记为观察中断或运行故障，不能套用正常切换的取消结论。

## 为什么这样处理

客户端门禁、实体生命、死亡和受伤动画需要真实游戏证明。观察中断与仲裁输赢、后端回执失败、会话切换和重试额度一样，是控制链故障；确定性注入能准确控制中断发生在攻击提交后的哪一帧，也能检查 Runtime 是否保持可用。

这项决定不减少试次数，也不放宽结果。它只避免为了给控制故障套上“实机”名称而增加生产测试钩子。

## 影响

- 场景清单为每个试次写明 `evidence_source`。
- 验收结果分别报告 Fabric 和确定性 Runtime 数量，不能合并成“64 个实机试次”。
- 以后若真实运行自然出现同类控制故障，可以追加证据，但不改写本次冻结结果。
