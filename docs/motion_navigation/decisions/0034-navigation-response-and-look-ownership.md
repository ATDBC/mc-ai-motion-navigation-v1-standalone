# D034：记录无路线等待并明确动作视角归属

日期：2026-09-26
状态：已采用并完成验证

## 要解决的问题

活动目标追击有三处边界不清楚。

第一，导航只有在路线已经接纳后才记录动作原因。快照构建、后台规划和等待新信息期间，Runtime 仍会提交中性移动，但回放看不出为什么停下。

第二，每个验收场景都会新建 Windows 后台规划进程。这会重复支付进程启动和模块加载成本，也让首动延迟难以归因。补齐记录后的实测表明，1.39 秒停顿的主要原因不是冷启动，而是攻击站位前的一排地面仍然未知；空气查询不能把被遮挡的实体地面直接判成可走。

第三，普通步行允许战斗先决定视角，但台阶、上升、跨隙和下落也可能产生自己的视角。若两者都用相同优先级，获胜结果会受提交顺序影响。

## 决定

1. 每个导航控制帧都写一条 `navigation_session_decision`。它记录会话状态、原因、请求、目标修订、路线是否存在、是否有动作决定，以及最终移动。已有路线时继续保留 `navigation_route_decision`，用于动作级诊断。
2. 验收统计只读取正式试次内的观察序号。试次结束后的取消和制动不能用来解释试次内的停顿。
3. 同一批连续验收复用一个 `PlannerWorker`。每个 `NavigationSession` 仍独立拥有目标、路线和执行器，只借用后台规划进程。会话关闭时不能关闭借来的进程。
4. 活动目标始终记录“驱动启动到首条非中性命令”的原始时间，以及首动前的控制帧数。若地形信息从一开始就足够，原始时间不得超过 0.5 秒；若会话明确等待未知地形，则从最后一帧“信息不足”结束后计算，必须在 10 个控制帧内开始移动。未知空间不能为了通过反应门槛被改写成空气或可走地面。
5. 普通 `WalkSegment` 可以按当帧战斗视角重新计算移动。台阶、上升、跨隙和下落保留路线视角；这些动作执行时，战斗层不再提交竞争视角。
6. 追击达到任务期限时，先让导航安全停止或完成落地，再返回 `NEEDS_TASK_DECISION`。任务期限不是程序契约错误，不能因此重建 Runtime。

## 为什么这样做

会话状态和动作决定属于不同层。没有路线时，动作执行器无法提供原因，但导航会话知道自己是在复制地图、等待后台结果还是缺信息。分开记录后，回放可以直接定位等待来自哪一步。

后台规划进程是计算资源，不属于某一条路线。连续场景反复启动它只会增加固定开销，不会提高隔离性。目标、请求和接纳检查仍由各自会话保存，因此复用进程不会复用旧路线权限。复用进程也不能消除真实的信息缺口；这两类等待必须分别记录。

视角归属按动作证明划分。普通步行每帧重新预测，可以接受战斗视角；跨高度和空中动作依赖已经验证的朝向与时序，不能被同优先级的战斗视角临时替换。

## 边界

- 一个后台规划进程当前按“最新整项请求”工作。不同会话不能同时把互不替代的必要子任务当成一个单槽队列使用。首版只在顺序执行的验收批次复用。
- 原始首动时间从正式目标驱动启动算到非中性命令提交。只有没有信息缺口时才直接应用 0.5 秒门槛；存在信息缺口时，另核对信息齐备后的 10 帧门槛。实际输入生效和身体开始位移仍由输入回执与轨迹单独检查。
- 非步行动作保留路线视角，不代表已经证明它能在战斗中完成。仍需对应动作的 Fabric 场景。
