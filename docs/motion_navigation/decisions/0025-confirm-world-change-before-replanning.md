# D025：确认世界变化后再重算路线

日期：2026-09-25
状态：已采用

## 要解决的问题

放方块会改变后续路线是否存在。客户端发出一次使用动作，只能证明操作已经交给原版游戏处理，不能证明服务器已经放置方块。若规划器提前把方块当成存在，机器人可能走向仍然是坑的位置。

## 决定

世界修改按一次一个的事务执行：

1. 导航只能提出有类型的 `RequiredInteraction`，不能直接修改世界知识；
2. 交互执行器使用正式观察核对站位、准星、支撑面、目标空气和主手物品；
3. 动作仍通过唯一 `Runtime`、仲裁器和 Fabric 的原版使用入口发出；
4. `pending_confirmation` 只表示已经尝试，不表示成功；
5. 后续正式观察确认目标格出现预期方块，并在生存模式下确认物品数量减少后，事务才完成；
6. 完成后让 `WorldKnowledge` 接收自然观察，并从真实新状态重新规划；
7. 未确认、目标变化、世界会话变化或依赖变化时，不采用假想地图继续移动。

首版只授权普通完整方块。每次只放一块。有限搭桥也逐块确认，不提前承诺后面的方块一定存在。

## 为什么这样做

这条边界把三件事分开：规划器说明需要改哪里；交互模块完成一次合法操作；观察系统确认世界实际变成了什么。以后增加门、按钮、挖掘或其他建筑动作时，可以复用相同事务边界，不必把每种交互写进寻路算法。

## 影响

- `InteractBlockV1` 继续表示一次原版方块交互。放置的预期结果由更高一层的放置事务保存，不新增绕过原版逻辑的写世界接口。
- 路线中的移动段和交互要求分别表达。交互要求不是一种移动模式。
- B11 的成功必须由动作前后的正式观察证明，不能用发送回执替代。
- 未经授权的世界修改边不可用，不能靠增加一个很大的有限代价偷偷进入路线。
