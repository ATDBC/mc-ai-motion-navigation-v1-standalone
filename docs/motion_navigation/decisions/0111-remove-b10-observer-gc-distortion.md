# D111：去掉 B10 证据缓冲造成的 GC 扰动

日期：2026-10-15。状态：**FAILED／STOPPED；已完成授权实现和唯一一次正式 B10，原始墙钟门槛未通过。**

## 1. 要解决的问题

D110 的 142 个求解样本只有一个墙钟超过 30 ms。该样本也是唯一与二代垃圾回收重叠的样本。Linux 补充实验还表明，B10 探针长期保存解析后的字典树和另一份诊断字典，会额外保留约三万个受 GC 跟踪的对象。

现有证据足以优先调查探针自身，但不能证明 Windows 那次 39.2484 ms 全部来自垃圾回收。Windows 线程 CPU 计时主要以 15.625 ms 为步进，不能承担精确归因。

## 2. 决定

### 2.1 原始墙钟门槛保持不变

`b10b_solver_is_bounded` 继续要求：

- 每次最多检查 12 个候选；
- 142 个求解样本的原始墙钟最大值小于 30 ms。

扣除垃圾回收停顿后的时间只用于归因，不参与 D111 的通过判定。如果原始墙钟仍超限，D111 仍失败；是否改变长期口径必须另写决定。

这条 B10 门槛测量同步探针路径的求解返回墙钟。正式后台求解还必须继续报告提交、交付、消费和输入实际生效期限，不能用本门槛代替完整控制链。

### 2.2 全程记录 GC 停顿，运行结束后统一归因

探针使用自己的 `gc.callbacks` 回调记录每次垃圾回收的代、开始时间和结束时间。每次求解保存开始和结束时刻。所有试次完成后，再计算求解区间与 GC 区间的交集。

不能在每次求解返回时立即结算。其他线程触发的 GC 结束回调可能稍后才取得 GIL，立即结算会漏掉本次停顿。

回调只追加有界的小元组，不改变求解、候选、输入或安全判断。无论成功或异常，都必须只移除自己的回调，不能覆盖进程中已有的回调。

### 2.3 证据缓冲只保留规范 JSON 字符串

控制路径已经生成规范 JSON。缓冲区直接保存这个字符串，不再立即 `json.loads()` 成字典树。需要汇总或最终写盘时才解析。

诊断 `rows` 也只保存字符串，避免同一记录在内存中保留两棵对象树。修改后必须证明：

- 行数、容量和字节预算不变；
- 调用方后续修改原对象不会改变缓冲值；
- 正常 JSONL 输出逐字节不变；
- 溢出和 flush 失败语义不变。

### 2.4 修正测试时序，不增加生产等待接口

Linux 清理场景由收到信号的父进程记录新 fork 子进程的 PID，避免正确的快速清理抢在子进程第一次调度前。

动作交接测试最多等待五个 receiver 周期，直到正式 `PreparedMotionJob` 出现。这个循环只存在于测试中，不增加生产接口或等待状态。

### 2.5 补齐 D110 历史语义哈希

D110 精简证据增加运行提交 `67f4f1d8` 的生产文件 LF 归一化 SHA-256，并写明对应公开提交 `f663586`。该文件用于核对历史运行，不声称 D111 修改后的最新脚本仍与 D110 运行字节相同。

## 3. 范围外

- 不优化 `solve_one_cell_gap()`；
- 不改变候选顺序、动作证明、输入窗口或路线；
- 不引入手动 `gc.collect()`、`gc.freeze()` 或关闭 GC；
- 不修改 30 ms 门槛；
- 不开始连续两跳、零等待交接或新动作。

## 4. 实施结果与停止结论

实现提交为 `01afa1212214e8f985c547641a30a052a062be9a`。测试时序、D110 历史语义哈希、字符串缓冲和全程 GC 区间归因均已完成。GC 派生结果写入最终汇总，已接纳的 trial JSONL 保留同钟起止时刻，不回写派生字段。新增 `b10b_gc_pause_timeline_complete` 只检查新证据完整性，原始求解门槛保持原样。

前置 Windows 门禁通过后，只运行了一次 600 秒 B10：`20261015T151355333152Z-0f9aee96`。142 个样本的 raw wall P95／P99／最大值为 **31.8873／33.4408／39.9605 ms**，19 个样本达到或超过 30 ms；扣除已记录 GC 停顿后的诊断值为 **31.4963／32.1705／33.1761 ms**，仍有 17 个样本超限。

功能、安全、来源释放、trace 和时间归因通过。GC 的 656 个事件完整配成 328 个区间，零丢弃、未配对或测量错误。这说明本轮测量完整，不能据此把剩余墙钟进一步归因为求解工作或调度，也不能证明 D110 的超限全部由 GC 引起。

按冻结判定停止，不改门槛、不重跑 B10、不追加求解器优化。D110-SOLVE-01 保持未关闭。完整数字和来源见[验收](../acceptance/d111-b10-gc-attribution-and-buffer.md)及[精简证据](../../../evidence/motion_navigation/d111-b10-gc-attribution-v1/README.md)。

## 5. 2026-10-16 审查后注

三方在 Linux 上复核了 GC 时间线、字符串缓冲和两处测试时序修正，结论成立。D110 与 D111 的求解代码和输入相同，但 D111 的求解线程 CPU 平均值及同进程 trace 投影都明显变慢。用户确认 D111 正式运行时还有其他程序在工作。

因此，本决定只证明 D111 当次运行在旧门槛下失败，以及 GC 不是整体超限的主因。它不证明求解器稳定在 30 ms 左右，也不把该次速度当作设备要求。长期门槛由 [D112](0112-separate-reference-calibration-from-runtime-delivery.md) 重新放到控制线程、后台交付和输入实际生效上；本决定的历史状态不改写。
