# D110：先修关闭证据链，再测量求解离群

日期：2026-10-15。状态：**已实施；关闭归因通过，求解墙钟门槛未通过，阶段停止。**

## 1. 要解决的问题

D109 的 B10 功能与安全场景已经完成，但阶段仍未通过：

- `close_release` 的诊断由异步线程在后端关闭后读取，最终得到 `null`，时间归因无法完成；
- 142 个求解样本中有一个墙钟耗时为 41.0339 ms，现有证据没有线程 CPU 时间和垃圾回收信息，不能判断是求解工作增加，还是线程调度或垃圾回收造成的离群；
- Linux 补充验收发现 settle 阶段反复发送 `SIGTERM` 时，信号处理器可以持续 fork 新进程；另有两处测试断言与计数时点错误。

## 2. 决定

### 2.1 关闭诊断与 trace 使用同一条接纳记录

调用线程必须在后端关闭前抓取 close 诊断。诊断快照随 `close_release` 一起进入异步队列。只有该记录被接纳并写出时，`diagnostics.jsonl` 才写对应行。

不能先单独写诊断、再尝试提交 trace。否则队列满或 writer 失败时，两个文件会再次错位。

归因读取器遇到缺失或 `null` 诊断时，返回带上下文的 `ValueError`，不再泄漏无说明的 `TypeError`。

### 2.2 先补测量，不修改 30 ms 门槛

每次 B10 求解同时记录：

- 墙钟耗时；
- 当前线程 CPU 耗时；
- 各代垃圾回收完成次数的变化；
- 试次名称和入口参数。

D110 不优化求解器，也不改变 `maximum < 30 ms`。取得新的逐样本数据后，再用后续决定确定长期门槛。墙钟仍代表真实输入延迟，不能仅因为线程 CPU 较低就忽略。

### 2.3 Linux settle 阶段不再重复给异常处理器运行机会

第一次进程树清理仍先发送 `SIGTERM`。进入 subreaper settle 阶段后，对身份仍匹配的已登记非 root 进程直接发送 `SIGKILL`，再完成回收与稳定扫描。

只有父进程已经退出、后代确实成为孤儿的场景才要求 `adopted_processes` 证据。提前作为登记后代被清理的进程，只要求出现在清理尝试中且最终不存在。

文件描述符门禁必须在测试自己的 stderr 副本关闭后计数。

## 3. 验收边界

- 真实 `PlayerRuntimeV1.close()` 顺序下，后端关闭会清空诊断，close 行仍保存调用线程抓取的值；
- trace 和 close 诊断同生同灭，不允许出现额外诊断行；
- 求解新增字段不改变候选、输入、轨迹、试次结果和现有门槛判定；
- Windows 正式检查先通过，之后只运行一次 600 秒 B10；
- Linux 专属动态结果由 Linux 环境补充复核，Windows 不冒充 POSIX 验收；
- 连续两跳、零等待交接、新动作和求解器优化均不在 D110 范围内。

## 4. 实施结论

关闭诊断已改为随同一条异步 trace 记录接纳和写出。正式 B10 的 `complete_time_event_attribution` 通过，原 `NoneType` 证据缺口关闭。

正式 B10 的 142 个求解样本中，只有一个墙钟超过 30 ms，最大值为 39.2484 ms。该样本也是唯一与二代垃圾回收重叠的样本。Windows 线程 CPU 计时只有约 15.625 ms 的主要步进，只能提供相关性，不能精确归因。现行墙钟门槛保持失败；后续若要调整测量或门槛，必须另写决定。

Linux settle 代码已经修正，但 POSIX 动态结果仍需 Linux 对最终字节补跑。D110 不据此声称 Linux 门槛关闭。
