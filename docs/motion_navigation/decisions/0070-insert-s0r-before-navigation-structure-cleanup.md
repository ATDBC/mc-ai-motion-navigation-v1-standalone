# D070：在导航结构整理前插入 S0-R

日期：2026-10-06。状态：已完成；平台门槛由 [D071](0071-windows-is-the-formal-project-platform.md) 修正。

## 1. 决定

F1 后导航结构整理不直接进入 S1。先插入 S0-R，修正测试基线、正式缺陷、覆盖集合和删除清单。

S0-R 不计入四个结构整理批次。原时间盒仍在 2026-10-08 截止；S0-R 必须在 2026-10-07 结束前满足全部门槛。做不完就把本次整理记为未通过。若要继续，另写决定并重新设时间盒。

## 2. 原因

S0 的确定性签名可跨 Windows 和 Linux 复现，可以继续使用。但它只有三个零引用候选，没有覆盖 F1 新增最多的路线接纳和复核代码。

原三组集合也没有充分走到正式跟随的地面直走入口和行走中世界变化路径。与此同时，当前完整检查包含共享场景污染、失效测试前提、真实墙钟依赖和两个正式行为缺陷。

在这些路径没有可靠保护前删除或合并代码，无法证明行为没有变化。

## 3. S0-R 的边界

S0-R 包含：

- 复制每次运行的扰动设置，消除测试间污染；
- 让世界变化测试使用确实会改变行走条件的下半砖，并断言目标路径已进入；
- 把真实墙钟从单元测试的通过条件中移出；
- 修复后端 I/O 失败后的驱动器状态覆盖；
- 修复 `seed 163` 暴露的空中过早失败；
- 冻结产品、协调、故障、跟随和世界变化五组行为集合；
- 生成候选路径矩阵和 v2 清单。

S0-R 不新增伙伴能力，不修改物理、几何、感知权限或路径收益。

## 4. 两项正式缺陷单独计量

I/O 失败和 `seed 163` 是产品行为修复，不是结构整理。它们必须单独提交，完成后再冻结 S0-R。

后续结构变化只从 S0-R 最终提交开始计算。不能把修缺陷带来的代码增减算作结构整理成果。

`seed 163` 不允许标成预期失败后继续 S1。它位于本轮准备整理的恢复链中；未修复意味着量尺仍不可靠。

## 5. 墙钟与平台

单元测试使用模拟或注入时钟来验证期限、预算和退场行为。真实墙钟只用于正式性能证据和诊断，不直接决定功能测试通过与否。

S0-R 行为集合要在正式 Windows 环境连续运行两次并逐项一致。Linux 复跑是补充的可移植性检查，不影响阶段关闭。路径覆盖另行采集，不能把探针开销混入产品行为量尺。

## 6. 重复代码的判断标准

文本相同只是一条线索。只有下面三项都相同，才可以合并：

1. 判断的是同一个事实；
2. 由同一个长期状态 owner 负责；
3. 发生在同一个生命周期时点。

例如，首次接纳和运行时复查即使检查相同字段，也可能承担不同职责。此时应记录 `retained:independent_responsibility`，不能为减少行数而合并。
