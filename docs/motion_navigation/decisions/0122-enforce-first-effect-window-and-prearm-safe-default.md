# D122：在客户端限制首效时刻，并提前放好安全默认输入

日期：2026-10-20。状态：**D122-0—D122-3 已完成；D122-4 为 PARTIAL／STOPPED**。

关联：[架构规格](../architecture/client-first-effect-window-and-safe-default-v2.md)、[实施计划](../stages/d122-client-timing-and-safe-default-plan.md)、[D121](0121-prove-fallback-backed-momentum-handoff.md)。

## 1. 要解决什么问题

D121 Task 5 已证实：Python 在落地观察 `L` 提交的第二跳，本应只在 `L+1` 生效。现行客户端收到它时不知道这个窗口，晚到 `L+2` 仍会起跳。若后继一直没有送到，第一跳的租约耗尽后又会变成不按键，身体凭余速滑出平台。

两件事必须同时修：过期后继不能进入物理计算；后继未到时，客户端也必须已经持有安全输入。Python 在 `L` 之后再补发潜行来不及。D120 的 972 个冻结入口重放中，`L+1` 潜行并保持至少 8 tick 全部停住；`L+1` 不按键、`L+2` 才潜行则全部掉落。这是有限样本证据，不是连续安全包络。

D121 发布修复已经通过完整 Windows、独立公开快照和最终独立审查。D121 仍为 `PARTIAL／STOPPED`，历史传输失败不改写。D122 处理该阶段明确排除的 action contract、wire 和 Java 改动。

## 2. 本轮决定

在现有 action 请求上增加两个可选值：

1. **首效窗口**：客户端只允许在给定 movement tick 范围内第一次采样这条请求。窗口用现有客户端 movement tick，不能用观察交换次数代替。
2. **预排安全默认输入**：在证明给定的绝对 tick、父动作输入结束后，客户端自动执行请求携带的一个有界 movement 快照。它来自已有证明，不由 Java 推测安全动作。

默认只属于第一跳最后一条 incumbent 请求，即最后一条继续执行第一跳的请求。客户端必须在采样 `L` 之前安装它，正常 lease 覆盖到 `L`，默认绝对激活 tick 是 `L+1`。`L` 返回的 receipt 确认 `fallback_armed`；后面不再发普通输入续租。第二跳在 `L` 决定，首效窗口严格为 `[L+1,L+1]`。按时接纳并成功采样才替换默认；早到只等候，晚到或被拒绝都保留默认。默认结束并确认安全后，身体责任才按现有流程释放。

本阶段只保证父请求已到位之后的后继传输迟到和失联。父请求自身迟到或丢失继续由现有动作的 input-loss 责任处理，D122 不声明覆盖。当前每 tick 一条请求的轨迹在边界 15 后已不可放弃，最后请求 sequence 25 到 tick 26（`L`）才应用，因此不能要求 Python 在最后可放弃点前确认 armed；本阶段不为此新增续租或 heartbeat。

## 3. 时序和身体责任

客户端最多保留一个待生效请求。早到的后继不能改变当前按键、租约、视角、操作或安全默认。过期检查位于真实 movement 输入采样前；先应用再报告 `applied_outside_window` 不算通过。

默认的 tick 和墙钟额度从默认真正激活时开始，不能在父请求到达时倒计时。默认 wall budget 至少覆盖 `duration × 50 ms`；安装时父 wall deadline 必须覆盖到激活点的名义时间和默认 wall budget，额度不足就 arm 失败。已成功 arm 的默认必须完成真实采样的证明时长。机器暂停导致 wall 或父响应期限先到，不能提前把 missed／未激活的 future 响应交还 Python，也不能把默认提前变成中性。默认完成后才允许普通控制继续；无 movement tick 时物理也不推进。外层硬终止只能走既有 reset／许可撤销边界，不能当作普通响应继续控制。这是 D122-1 审查后的安全修正：原文“不得越过父总期限”与“必须执行完整证明时长”在慢 tick 下冲突，现以完整证明时长和持有响应为准，不再允许墙钟先到后用普通请求截短默认。

默认持续时长由证明和当前 profile 给出。本次 D120 profile 至少覆盖 8 tick；Java 不硬编码“潜行 8 tick”。默认只含 movement，不含跳转视角或一次性操作。它沿用父请求身份，状态为 `default_active`，不是无 owner 的输入。

Runtime 收到任务取消或换目标时，身体责任仍按 D117 收尾，不能在承诺后直接发普通 cancel 清掉安全输入。真正送到客户端的普通更新、cancel、reset、episode 切换和强制失去控制许可，都会清空旧的整份安排，避免旧默认以后误触发；这种清空不自动算安全收尾。窗口化后继被拒或过期只清它自己，不清当前默认。传输失联则继续已预排默认到其有界结束，不无限延长。

更高 sequence 的窗口化后继到达不等于已经接管。它先经过现有身份、episode、许可和期限检查；只有在自己的窗口内成功激活，才替换默认。其他合法普通请求按原替换语义清除整份旧安排。被拒请求仍按现有规则消费 sequence，防止它被重放为另一种副作用。

pending 的 sequence 和 observation 只在接纳时检查、消费一次。激活时只复核已登记 pending、episode／reset、许可、wall deadline 和首效窗口，不重复完整 `validate`。排队期间观察已推进，不能让已接纳请求变成 duplicate 或 stale。

沿用现有一问一答和 pending 响应。未来窗口的后继已到达时，`receiptReady` 保持 false，客户端自主推进到窗口后才返回响应；不能为了等窗口先让 Python 发下一帧。后继 late／missed 后也暂不返回本次响应，直到默认有界结束，再返回最终观察，避免紧接着的普通请求清掉默认。never 场由客户端 trace 或延后释放观察验证，不伪造逐 tick 同步观察。

输入选择必须发生在 `prepareForPlayerTick` 内、原版读取 sneak 之前。这里选择 `L+1` 默认或窗口内后继，并同步更新本拍 sneak；`Input.tick` 只消费一次，不重复切换或扣减 lease。同拍从潜行切到跳跃时不能残留上一拍的 sneak 投影。

## 4. 兼容和回执

通过会话握手明确选择 `mc2p.client_action.v2`。只有双方确认 v2，Python 才发送新字段。旧客户端维持 v1 的精确键集合；v1 会话不允许使用本阶段的动量交接，不静默删除安全字段继续执行。CalculatorBackend 和 Java 使用同一张时序转换表。

回执区分 `fallback_armed`、`window_pending`、`window_applied`、`window_missed`、`default_active`、`default_exhausted`。每项都关联 episode、request sequence 和实际 movement tick。`fallback_armed` 只确认预排，不能充当默认已应用；`window_pending` 只表示排队，不算已经应用；`window_missed` 必须证明物理采样前已拒绝；`default_exhausted` 也不自动表示身体已经安全。

## 5. 零等待连跳的边界

本次“零等待”指两跳之间没有额外停稳：第一跳在 `L` 落地，第二跳必须在 `L+1` 首效。不能先执行一拍默认，再把迟到跳跃放到 `L+2`。未就绪就持续潜行并安全结束本次组合。

本阶段不承诺在观察到落地之前排好第二跳，也不新增产品规划能力。若最远跳距需要另一种客户端 tick 顺序，须用实机证据另行决定，不能修改本窗口来迁就。

## 6. 范围、门槛和停止条件

按 D122-0—D122-4 推进：只读最小时序 probe、合同与 RED → Python 投影 → Java 采样门禁 → 正式组件三态 → Fabric 受控延迟。D122-0 先确认现行正式循环能保持 pending 响应、自主推进，以及在原版读取 sneak 前选择输入；不能成立就停止，不先改代码再解释时序。每步先用代表场景检查合同，前一步通过再扩大。完整回归在代码冻结后集中运行，避免每改一段诊断就重复全量。

安全门槛：及时后继完成；过期后继零物理应用；未送达、被拒绝和过期后继全部使用已预排默认，安全停在中间平台；零伤害、单一 movement winner、owner 无空档、无界等待为 0。全过程回执与真实采样逐项对应。

Python 同步控制计算继续使用已有生产 P95 ≤ 8 ms、P99 ≤ 15 ms、最大值 < 30 ms，同步提交计算 < 50 ms。默认至少 8 tick 期间合法持有 missed 响应的等待单列，不混入这些同步计算门槛；端到端响应时长照常完整报告并有界。计数和计时分开运行。Java 采样只做有界比较、一次待生效替换和默认倒计时，不做证明、摘要、搜索或同步 I/O；额外成本单列报告。action 16 KiB 和 worker 2 MiB 上限不变。

需要通用排程器、多个默认、wire generation、新 Session 状态、第二条 worker 管线或放宽证明时停止。出现旧成功退步、安全违规、父请求在采样 `L` 前不能安装默认、正式一问一答不能有界持有响应并自主推进、真实采样顺序与组件不一致，或两轮限定修正后仍有清单外阻塞，也停止并保存证据。

不恢复 D121，不修改 D120 物理规则或有限入口，不增加路线组合边或正式四格 profile。本阶段结束后再决定产品规划接入。

## 8. D122-3 的可达状态修正

正式 producer 只有看到 `L` 的落地观察后才创建后继。它无法在不改变 proof 和产品时序的情况下制造“后继在 `L` 以前已经 pending”的 formal early 场景。因此 D122-3 的正式矩阵改为四方向各覆盖按时、晚到、失联、明确拒绝和任务取消；early 继续由正式链共用的客户端 sampler、v4 receipt 和 ledger 转换表覆盖。

## 9. D122-4 的真实观察边界

D122-4 的组件外层及时、`L+2` 和 never 三场为 3／3 通过。正式 Fabric 前置也通过 95／95 个定向检查和 overlay 编译。v1—v7 的环境、缓存、装配和导入失败全部保留，不能计为协议样本。

v8 真正进入服务器和客户端后，在执行第一场协议试验前停止。冻结 proof 需要 67 个格子；actor 只确认了 55 个，另有 12 个仍为 `UNKNOWN`。客户端查询表明其中 10 个被方块遮挡，2 个位于视野外。夹具虽然把这些位置放成了空气，但 actor 没有观察证据，不能把它们当作 `AIR`。因此及时、`L+2`、never 的真实协议样本是 0／3，四方向 36 场矩阵没有运行。D122-3 的通过结论不受影响；D122-4 记为 `PARTIAL／STOPPED`。

后续有两条可选路线：

1. 只改夹具和观察准备。调整观察点或分阶段获取事实，让这 12 个格子在 trial 前真正变成已知，再重做 D122-4。
2. 另立 proof 语义决定。若能证明“外围支撑已经已知时，这些下层格子不影响该动作”，再缩小 proof 查询范围。这会改变证明语义，不属于 D122-4 的夹具修正。

两条路线都不允许把 `UNKNOWN` 当作 `AIR`。在新决定完成前，不继续运行 D122-4 Fabric。

## 10. D122-4 复核补充：失联不是一种情况

D122-4 收尾复核又确认了一条生命周期边界。后端抛出 `TimeoutError` 时，`PlayerRuntimeV1.step()` 不会把异常交给外层夹具；它会返回 typed `DEADLINE_EXCEEDED`，并把 Runtime 置为 `failed`。此后 driver 停在 `stopping`，source 仍由原 owner 持有。客户端虽然已经执行父请求预排的潜行默认，但旧 Runtime 观察早于这段默认，不能拿来证明身体终态或健康。

因此后续必须区分两种语义：

1. 单个后继请求丢失，但客户端通道仍然可用。后端应返回正式 typed rejection 和新的观察，driver 再按现有身体责任流程收尾。
2. 客户端通道失联。客户端继续执行安全默认；Python 只能报告 `BODY_RESPONSIBILITY_UNRESOLVED` 或相应 typed 终态，不能伪造新观察、健康或 source 已释放。

当前 D122-4 validator 会拒绝缺失的新健康证据、未完成的 driver 生命周期或未释放的 source。这个拒绝是正确结果，不能通过修改结果行绕过。选择上述哪一种语义、怎样取得失联后的正式健康证据，需另立决定。D122-4 不扩实现，也不再运行 Fabric。
