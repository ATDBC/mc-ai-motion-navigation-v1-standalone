# D073：接受动作接口迁移，撤回体积门槛

日期：2026-10-07。状态：已决定，整改已按本轮 Windows 验收完成。历史 M1 的原结论不变。

## 1. 决定

M1 仍按当时冻结的门槛记为“不通过”。原验收、失败项和证据不改写。

M1 已完成的受控下降迁移予以保留。它证明动作自己的风险、入口、求解和执行规则可以从 Session、接纳器和执行器中收回。

从本决定开始，撤回下面这些未来门槛：

- Session 必须减少指定行数；
- Session 最终必须低于指定总行数；
- 协调层必须低于指定代码占比。

这些数字继续报告，用来发现异常增长，但不再决定阶段成败。

## 2. 为什么撤回

M1 把受控下降在 Session 中的专用判断全部移走，Session 只减少 52 行。剩余代码负责信息等待、采集许可、入口快照和身体责任，本来就不属于动作规格。

动作接口的价值应按新增动作要修改哪些调用方来判断，不能按 Session 缩短多少行判断。

## 3. 当前需要补的边界

M1 仍有两个需要立即修正的问题：

1. 执行器用 `ControllerFamily` 选择实现。它是动作类型判断的另一种写法；
2. `actions/controlled_drop.py` 在运行时反向导入接纳模块和私有帮助函数，形成循环依赖。

此外，`RuntimeNavigationDriver` 仍使用字符串生命周期，并在多个位置直接写状态。S0R-C-02 和 M0-C-01 都与此有关，应在恢复产品开发前改成枚举并收口写入。

## 4. 新的扩展门槛

动作接口以后按下面的行为验收：

- 新动作使用已有控制方式时，只增加自己的实现和固定登记；
- 新动作使用新控制器时，执行器、Session、执行监督者和规划协调器不增加动作专用分支；
- 动作实现不反向导入接纳、Session 或协调 owner；
- 量尺同时统计直接类型判断和通过封闭枚举选择实现的代理分支；
- 通用能力判断可以保留。例如 `BodyCommitment` 只表达身体责任，不要求调用者知道具体动作。

## 5. 后续顺序

1. 修复控制器代理分支、量尺缺口和反向依赖；
2. 将 `RuntimeNavigationDriver` 生命周期改成枚举，并只保留一个写入入口；
3. 单独设计终点接近产品阶段；
4. 统一复核只在终点接近确实需要计算器重放时启动；
5. 统一异步作业只在出现第三种后台作业，或再次出现身份、迟到结果缺陷时启动。

不再单独实施 M2。迁移其余动作时，以产品或真实缺陷为入口，并要求动作分支量尺不倒退。

实施范围见[动作接口加固与驱动器生命周期方案](../stages/action-spec-hardening-driver-lifecycle-plan.md)。

整改结果见[加固验收](../acceptance/action-spec-hardening-driver-lifecycle.md)。后续只设计终点接近，不自动扩大实施范围。
