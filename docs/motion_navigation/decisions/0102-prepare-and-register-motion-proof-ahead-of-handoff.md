# D102：在交接前准备并可信注册运动证明

日期：2026-10-12。状态：**设计冻结；尚未实施正式链。**

规格见[提前准备与可信注册运动证明架构](../architecture/prepared-motion-proof-pipeline-v1.md)，依据见[D102／D103 隔离试验验收](../acceptance/prepared-motion-proof-spikes-d102-d103.md)。本决定只冻结职责与契约，不授权代码实施、实施计划、正式链接入或 Fabric。

## 要解决什么问题

D101 M0 的正常关键节点已经只做比较，但动作开始仍同步生成完整证明，完整决定 P99／最大值为 48.6079／57.5597 ms，超过 15／30 ms 门槛。**D101 M0 整体未通过，M1／M2 未实施、未运行。** 本决定保留这项失败，也保留 D098 P3 的原结果。

D102 隔离单跳试验说明，完整证明和父侧接纳都提前完成后，动作开始热路径可以满足预算。400 个开始决定的 P95／P99／最大值为 0.4061／0.4257／0.4525 ms。不过，worker 提交至可信可用的 P99／最大值仍为 107.5297／108.5532 ms。父侧摘要、反序列化、完整校验和登记的 P99／最大值为 34.6822／35.4011 ms。仅移走证明扫描，仍会让接纳工作阻塞控制线程。

D103 把具体模拟世界快照送入 worker，并在父侧 receiver 线程完成完整校验与登记。固定朝南的 2／3／4 格平台、精确预测入口、Windows 20 Hz 模拟下，无积压 A 组和一项积压 B 组各 120／120 完成两跳，落地后 1 movement tick 接续。它还暴露了新的重工作：246 次快照构造的 P95／P99／最大值为 39.1137／42.7386／45.0731 ms。正式链如果在控制 tick 临时复制世界，仍可能超时。

因此需要提前完成整个准备过程：取得快照、封装请求、计算证明、接收完整结果、核验并注册。交接时只读取已经登记的证明引用，再核对当前事实。

## 决定

### 1. 扩展现有 motion worker，不建立第三套异步管线

复用现有 `MotionSolverWorker`／`MotionWorkerPort`、`MotionResultInbox`、`AsyncWorkIdentity` 和运动协调生命周期。下一动作由现有协调器提前请求，结果仍沿同一请求登记、接收、退场和关闭路径流动。

receiver 指这个既有结果接收环节中的后台完整校验职责。它可以有自己的执行线程，但不能拥有另一套任务、generation、重试账本、pending 队列或资源管理者。D102／D103 的临时 worker、pipeline 和 registry 只作证据来源，不直接成为生产代码底座。

计算作业结束与执行证明结束分开。成功接纳先把不可变 bundle 转为候选引用，再退场原 `AsyncWorkIdentity`／inbox job token。registry 在同一结果服务内唯一记录 candidate、executing、safe-tail 的使用与释放；协调器／执行器发送这些事实。开始下一动作的准备不能撤掉当前动作引用。未使用候选取消、过期或作废时释放；执行引用只有在安全交接、真实命令终态齐全、监督者确认释放最后相关身体责任后注销。

### 2. Runtime 拥有世界，后台计算只借用不可变事实

Runtime／正式世界知识是世界事实的唯一拥有者。它提供有版本、局部、不可变的快照，或保证读取期间内容不变的快照租约。世界会话、来源 revision、快照摘要、逐格事实版本和 ruleset 必须随请求一起绑定。

快照构造、规范序列化和摘要计算不能在约 20 Hz 控制热路径从头执行。优先由正式知识持续维护局部不可变版本，或按变化增量导出。控制线程只读取已发布版本和准备好的请求。后台不能重新构造 fixture、读取测试全知世界，或把 UNKNOWN 补成 AIR。

已发布 handle 持续引用该不可变版本。lease 释放只减少存储引用，不能充当世界依赖变化或执行取消。Runtime 发布相关依赖变化后，受影响资格在下次热比较失效，但执行 owner 仍保留安全收尾责任。最后候选、执行、尾迹及在途校验引用释放后，才能归还 snapshot lease 和回收仍被引用的大对象 bytes。服务关闭时也保留已执行安全尾迹所需事实到责任解决。

### 3. 完整检查完成后才发布 handle

`PreparedMotionBundle` 是不可变的完整准备结果。它绑定请求、generation、owner、路线和动作、父侧 expected inputs 与摘要、入口范围、出口／落地区、世界与依赖、规则、伤害额度、完整 proof 与摘要、欠载安全尾段、许可和时序分支。

motion worker 只计算。receiver 先核对消息摘要，再反序列化；随后检查三向 ruleset、不可变对象图、完整 proof、父侧 expected inputs、请求／账本／generation／世界／依赖。全部成立后，才登记并原子发布 handle。handle 是登记表给出的只读证明引用，不是 worker 自报的“通过”标记。

父侧预登记字段各有原 owner：expected inputs、入口、安全后缀、输入流身份及 requested start／effect window 由协调器提供；世界与 lease 由 Runtime／正式知识提供；ledger／session identity 和已有输入事实由现有账本 owner 提供。准备阶段不制造或预留实际 control sequence，receiver 不生成、猜测序号，也不从返回结果推回父侧期待。

首条命令真正赢得仲裁并取得实际全局 sequence 时，Runtime 唯一输入出口创建 `StreamActivationBinding`，绑定 generation、ledger identity、实际首序号、请求／允许生效 tick 与实际复合命令身份，在第一条实际应用回执前交给执行器／tracker。只有已登记 handle、匹配激活事实和正式交接条件同时成立，输入流才能开始。首条未赢仲裁则仍是候选；绑定不符或 generation 过期就 typed 拒绝，该 bundle 身体推进为 0。

控制线程只读取本进程登记表发布的 handle，做真实身体、当前相关依赖、许可和时序比较。禁止在该路径执行 scan、搜索、完整 proof 哈希、序列化／反序列化或重新构造快照。

### 4. 准备结果不拥有身体，也不自动取得输入资格

当前 owner 一直承担身体责任，直到 `ExecutionSupervisor` 正式交接。新结果已准备、已登记或已到入口，都不能单独转移控制权。

结果晚到、过期、错配或作废，只退场相应的准备工作，不清空当前仍有效的安全前段。未在交接期限内可信可用时，只能执行预先证明并登记的安全前段、停车尾迹或落地尾迹。不能临时把缺输入解释为 Neutral，也不能等待结果时无限保持旧输入。

例如，第一跳还在空中时准备第二跳。着地后，真实身体在入口范围内、依赖与时序仍匹配且监督者批准交接，才开始第二段。第二段没有及时登记，就继续已有安全尾段。若原 owner 仍在空中，即使任务取消，它也要保留身体责任。

### 5. 沿用 D101 的换代和输入时序

计算身份、身体 owner 与输入流身份分别绑定。`AsyncWorkIdentity.owner_instance_id`／`AsyncComputationScope.generation` 只约束计算接纳；`RouteControl.owner_id` 对应监督者管理的身体责任；D101 `StreamGeneration` 由现有 `MotionRouteCoordinator` 唯一创建和换代。动作执行器消费该身份，Runtime／输入账本记录实际应用事实，receiver 只校验和保存。

目标修订不自动更换输入流 generation。只有输入、入口、许可或安全后缀需要改变时才换代；同一身体 owner 内的动作衔接不制造新身体 owner。旧输入流 generation 的迟回结果不得重新接纳，计算 scope 失效不能撤销已经承担责任且仍有效的安全尾迹。换代不会抹去已经采样或应用的输入事实。

0／1 tick 只属于每条输入流的起点。第一条实际应用回执用 Runtime 激活的实际首序号核对归属，立即上报并剪掉另一分支；后续输入从同一首序号关联流内索引，effect tick 按同一真实起点偏移推导。后续单条晚到、缺失或内容不同按偏离处理。准备身份与实际序号分开不放宽 D101；不能为了满足旧实验字段提前占用 Runtime 全局序号。是否采用有限预排程，要等 Fabric M2 或同等最小 tick 顺序证据，当前不冻结发送方式。

宽阔普通地面继续只使用 `FixedRouteController`。提前准备不建立通用地面输入包执行器。入口范围必须由完整证明覆盖，不能把 D103 的精确入口证据扩写成 ±0.05 范围，也不能事后扩大旧证明来制造余量。

## 为什么采用这一做法

完整 proof 摘要只能发现内容变化，不能证明各字段彼此一致。D102 第二轮漏比 `proof.ruleset`；修改内部规则并重新封存后，旧接纳仍会放行。第三轮补齐 `proof.ruleset == bundle.ruleset == world.ruleset` 后拒绝了该反例。

D103 第一批只比较返回 bundle 与 proof 内部输入。另一条合法输入可以在同 request 下重新完整证明，并被旧 receiver 登记。第二批保留父侧 expected inputs 和提交前摘要，登记前独立比较后，typed `INPUTS` 拒绝且没有身体推进。

因此，信任必须同时来自可信计算代码、父侧独立保留的请求、完整核验、不可变对象和唯一发布路径。SHA-256 不认证外部不可信证明；自行构造一个字段相同的 handle 也不能取得登记资格。

## 证据能够支持到哪里

- D102 支持固定单跳“动作开始至首条回执”的热路径可行，未验证完整连续动作。
- D103 支持三种固定朝南平台、精确预测入口、Windows 模拟、0／1 项积压下的连续两跳；A／B 各 120／120。
- 六项 800 ms 迟交付样本只证明预登记安全尾段能够在中间平台收尾，不计作两跳成功。
- 本批没有覆盖 Fabric、±0.05 落点偏差、多方向、多并发、复杂材料或持续变化世界。它没有交付正式 Runtime／Session、客户端队列、撤销／替换协议。
- D102／D103 预先分配首序号是隔离夹具安排，没有证明生产 Runtime 存在预留 API，也没有验证战斗／视角复合仲裁后的正式激活绑定。

D102 三轮与 D103 两批的旧结果、失败发现及最终 APPROVED 均按原字节保留在本地证据中。Git 只保存紧凑报告、审查、summary、verification 和来源清单，不能仅凭这份紧凑包重放所有 proof 与 tick。

## 后续进入正式链的顺序原则

先冻结契约，再做正式隔离矩阵；通过后，在正式 Python 链中完成单一组合；随后用 Fabric 记录真实 tick 顺序；最后才扩展动作。每一步都要有新的明确授权和相应证据，不能把本决定当成逐任务实施计划。

完整控制决定继续要求 Windows P95≤8 ms、P99≤15 ms、最大值<30 ms。后台总成本、发布后实际可用时间、队列积压、唤醒迟到与交付期限必须独立记录。D102 的“3 tick 覆盖本批最大值”和 D103 的提前量都不是通用交付保证。
