# D028：过期动作窗口只触发局部恢复

日期：2026-09-25
状态：已采用

## 要解决的问题

D027 把动作证明的生效窗口带进了正式 Runtime。这样可以正确接纳晚一个 tick 生效的首条命令，但也暴露出另一个边界：空中动作执行期间，客户端可能在两次观察之间多推进一个玩家运动 tick。

此时，下一条证明命令已经错过合法 tick。旧实现仍提交这条命令，Runtime 随后把窗口与当前观察不一致判为契约损坏，并要求重建整个 Runtime。导航输入源因此被释放，但原执行器仍认为自己正在负责空中的身体。

## 决定

1. 已验证动作执行器在提交每条命令前，用当前状态锚点检查下一次可能生效的 tick。
2. 若命令窗口已经过去，执行器不再提交该命令，并把动作结果转为输入丢失。
3. 身体仍在空中时，原执行器进入恢复状态，发送中性移动并继续负责落地。接地后再结束这次动作。
4. Runtime 在仲裁后再做一次最后检查。获胜移动意图的窗口已经过期时，只压掉这一帧的移动，并记录 `movement_window_expired`；Runtime 保持可用，同帧其他控制不受影响。
5. 若当前 tick 仍在首条命令已经证明的启动窗口内，Runtime 可以把登记窗口收窄到当前 tick，而不把它误判为过期。
6. 未来组合移动、攻击和放置时，每个动作来源都先处理自己的过期约束。Runtime 的检查只负责隔离遗漏，不能代替动作执行器维护生命周期。

## 为什么这样处理

错过一个动作窗口，说明这一条动作证明不能继续使用。它不表示世界会话、观察协议或输入出口已经损坏，因此不应该重建整个 Runtime。

例如，跨隙第 2 条命令只能在 tick 103 生效。客户端卡顿后，下一次观察已经是 tick 103，最早只能在 tick 104 接收新命令。执行器应放弃第 2 条命令并保持落地责任。Runtime 仍可继续处理转头、攻击或其他没有过期的输入。

## 验证范围

- 执行器组件检查覆盖“首条命令已正确应用，空中观察随后多推进一个 tick”；结果为中性移动和落地责任，不再提交过期命令。
- 正式 `RuntimeNavigationDriver` 集成检查使用与三方复现相同的 `lease_exhausted` 额外 tick；Runtime 保持 `READY`，导航来源不释放。
- Runtime 单独检查过期的获胜移动意图只被压掉，不产生 `observation_invariant`。
- 本轮没有人为制造 Fabric 客户端补跑 tick，因此这项结论属于确定性正式路径证据，不新增实机成功率。

## 影响

这项规则直接适用于后续同帧组合控制。某个来源的时序约束失效时，系统先隔离该来源，再由它自己的执行器完成恢复。只有观察、世界会话或输入出口本身失去可信度时，才允许升级为 Runtime 重建。
