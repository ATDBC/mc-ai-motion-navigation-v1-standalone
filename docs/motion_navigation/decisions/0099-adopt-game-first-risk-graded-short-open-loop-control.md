# D099：按游戏实际风险使用短开环控制

日期：2026-10-11。状态：决定有效；只确定后续方向，尚未授权实现或正式链适配。

## 要解决什么问题

D098 的隔离闭环尝试在逐边界证明的基础上处理每次偏离，并要求需要时在当前决定内同步重证。复审表明，输入时序、证明分支比较和恢复目标仍有混用。继续沿这条路径补例外，容易把普通环境中的小变化也当成高风险事件，计算成本和恢复分支都会继续增加。

Minecraft 与现实世界不同。它是规则明确、状态维度有限、绝大多数时间稳定的虚拟环境。项目可以借鉴机器人学中的闭环控制、模型预测和安全边界，但不能照搬现实机器人面对传感器噪声、连续材料变化和未知动力学时的全部防御措施。客户端事件、方块状态、输入应用记录和确定性运动计算器都是游戏提供的可靠捷径，应当直接使用。

大多数移动发生在宽阔地面、普通台阶和已知路线中。系统首先要把这些常见场景做得及时、连续和自然。极端高危场景不要求底层运动代码强行通过。例如，下界岩浆池上只有一格宽道路，同时还有恶魂攻击时，合理选择可能是先消除危险、换路、等待或改变地形。以后由任务和策略层决定采用哪种办法；运动层负责报告风险和现有能力，不能假装安全，也不需要为所有极端组合预建恢复分支。

## 决定

后续连续运动采用以下方向：

> 短开环输入包＋逐 tick 廉价监视＋事件触发重算＋关键节点严格检查。

这里的“开环”只表示输入包在几个 tick 内按已验证序列执行，不表示停止观察。客户端仍逐 tick 记录真实输入和身体状态，便宜的监视也持续运行。

### 1. 短开环输入包

运动控制器生成一段有限的输入，例如未来 3—6 tick。输入包至少绑定：

- 绝对 movement tick 与输入序列；
- 可接受的位置、速度、朝向、姿态和支撑范围；
- 相关地形与物理条件的版本；
- 最后可安全停车点；
- 起跳、离边或下落等承诺点；
- 允许落地区域；
- 安全停止或安全落地的办法。

输入包必须留有明确余量。路线不能只在唯一 tick、唯一落点或容差边缘成立。具体包长度和余量由下一阶段用 Windows 量尺确定，不在本决定中预设成正式参数。

输入时序的首选候选契约是：整包按时开始，或整体晚一 tick 开始。第一条命令的实际回执到达后，删除不再可能的时序分支；后续命令按绝对 tick 执行。中间某一条命令单独晚到或缺失属于偏离，不能继续冒充原证明仍然成立。该契约必须在下一阶段单独冻结并验证，当前正式 Runtime 的许可窗口不因此改变。

### 2. 每 tick 只做廉价监视

每个客户端 tick 继续检查：

- tick 是否连续，输入是否仍由正确 owner 持有；
- 实际应用输入是否符合当前输入包及已确定的时序分支；
- 身体是否仍在输入包允许的状态范围内；
- 是否收到伤害、爆炸、活塞、流体、碰撞、属性或姿态变化等直接事件；
- 实际位置和速度是否出现当前输入无法解释的明显残差；
- 与本动作相关的方块或物理条件版本是否变化；
- 是否到达下一个关键节点。

这些检查应以字段比较、版本比较和集合相交为主，不在每个 tick 重新搜索整条动作，也不重复计算所有停车尾迹。

逐 tick 监视必须与仍然存活的证明分支比较。不能只比较“上一观察加实际输入”的一步预测，否则确定性模拟中两边天然相同，无法发现身体已经走出原证明范围。

### 3. 只有相关事件才重算

规划和证明只登记实际依赖的区域与条件。发生变化时先判断是否相关：

- 无关位置的方块变化不触发重算；
- 将要通行的支撑、净空、起跳边缘或落地区变化时，作废受影响部分；
- 方块状态和形状版本不变时，不重复解析碰撞形状；碰撞形状或物理属性变化时，再复核相关动作；
- 姿态、流体、速度属性或运动规则变化时，只作废依赖这些条件的证明；
- 伤害、爆炸、活塞等明确信号会触发外力处理；没有直接事件但运动残差超限时，也触发重锚；
- 输入晚到、缺失或实际内容不同，会使当前包的原时序证明失效；
- 目标修订只作废不再满足当前目标的工作，不取消已经承担的身体责任。

事件发生后从真实观察重新锚定。能够复用仍覆盖当前状态的安全后缀时可以复用；否则重新查表、求解或规划。所有重算仍需有明确期限和次数上限。

### 4. 关键节点严格检查

严格检查集中在可能让动作难以撤销的位置：

- 进入助跑或动作入口；
- 最后可安全停车点；
- 起跳、离边或下落命令提交前；
- 承诺命令实际生效后；
- 进入预计落地区；
- 确认着地；
- 向下一动作交接。

关键节点检查真实状态、输入回执、依赖事实、伤害额度和安全收尾。越过承诺点前拿不到所需证据，就不提交该命令。普通宽阔地面不因此采用空中动作同等强度的逐 tick 完整证明。

### 5. 输入回执保留事实，降低传输成本

客户端仍逐 tick 维护权威输入账本。正常连续记录可以压缩或批量交给 Python，例如报告一个输入包整体从哪个 tick 开始、是否连续、是否遗漏。以下情况立即上报：

- 输入晚于允许窗口；
- 回执缺失；
- 实际输入与提交内容不同；
- 即将越过严格节点；
- 身体状态出现异常。

降低的是跨进程通信和上层处理频率，不能降低客户端记录事实的频率，也不能把缺失回执解释成中性输入。

### 6. 恢复身体安全与完成任务分开

承诺后发生偏离时，当前 owner 首先负责安全停住、安全落地或保持在已知支撑区域。恢复轨迹不必同时到达任务最终目标。

身体重新进入可交接状态后，Session 再从真实位置规划任务目标。任务失败、取消或目标变化不会自动结束身体责任；同样，安全落地也不会自动算作任务成功。

## 按风险决定是否执行

这项决定补充 D048 的风险分级和 D089 的范围控制，不降低已有安全不变量：

- 宽阔、稳定、可停车的普通移动优先使用短开环包和廉价监视；
- 坑边、窄桥、未知落点、预计伤害和承诺后的空中阶段继续使用严格门槛；
- 上层可以拒绝高危动作，改走安全路线，先处理威胁，等待条件变化或改变地形；
- 底层如实返回风险、缺信息或能力不足，不为“必须从这里过去”自动放宽安全条件。

“大多数场景比较安全”是产品和工程取舍，不是把 UNKNOWN 当空气，也不是允许已承担责任的控制者直接退出。

## 控制开发范围

新增防御逻辑必须至少对应一项：

1. 现行已授权能力；
2. 真实失败或可信复现；
3. 已冻结的验收场景；
4. 已决定要支持的明确风险。

仅凭假想的极端组合，不能继续增加状态、等待、重试、恢复分支或完整矩阵。先把它记录为边界，由上层避险或后续阶段决定是否支持。防御措施如果让常见安全场景明显变慢、停顿或无法完成，必须用同条件证据证明收益大于代价。

开发仍遵守 fail-fast：先用最小正式路径验证核心假设，失败就停止扩大矩阵。不能为了追求“任何情况下都不出错”而持续加固一个尚未证明有产品价值的局部分支。

## 与 D098 的关系

D098 的 P3 失败、性能数字和原始证据保持不变。三方复审指出旧闭环存在证明分支比较、输入时序和恢复目标混用等问题，这些结果只能用于定位下一步，不能回写 P3 为通过。

D099 不授权 P4，不修改 `mc2p`，不运行新的 Fabric，也不宣称短开环输入包已经实现。下一阶段开始前还要冻结：

- 输入包长度及整体 0／1 tick 起始偏移契约；
- 关键节点的生成方式；
- 廉价监视的状态范围和容差；
- 事件订阅、依赖版本和批量回执格式；
- 安全停止、着地重规划和空中恢复的验收矩阵；
- Windows 性能门槛和正式 Runtime 接入顺序。
