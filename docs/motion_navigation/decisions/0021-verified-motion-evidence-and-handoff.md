# D021：缺少运动证据时仍保留身体责任

日期：2026-09-25
状态：采用

## 要解决的问题

已验证的跨隙或带速动作开始后，下一帧可能暂时拿不到状态锚点。常见原因是输入采样缺失，或身体进入尚未确认的空间，导致运动残差暂时无法计算。旧实现会抛出异常并封存 Runtime。

同一类责任丢失还会出现在路线替换时。目标修订、路线依赖变化和新路线接管原来走不同分支。旧执行器可能已经提交命令，但身体在观察中仍然着地。此时若直接换成新执行器，下一帧便可能没人继续照管助跑或起跳。

受击检测也有相同缺口。伤害事实等待运动残差超过八个运动 tick 后，旧实现会把它静默清除。

## 决定

1. 已验证动作开始后，状态锚点暂时不可用时不得抛出异常，也不得释放身体责任。执行器停止提交新的证明命令，保持中性输入并请求缺少的世界或输入证据，直到重新取得锚点并确认落地或进入明确终态。
2. 目标修订、路线依赖变化和新路线接管共用同一条安全交接规则。以下任一条件成立时，新路线必须等待旧执行器结束：
   - 身体仍在空中；
   - 已验证命令已经提交但尚未收到确定的应用结果；
   - 当前动作不是普通地面步行；
   - 执行器正在完成取消或落地恢复。
3. “身体仍在地面”不能单独证明可以接管。刚提交的起跳命令可能在下一运动 tick 才生效。取消后至少要看到更新的一帧正式观察，才能确认命令没有把身体带入空中。
4. 路线依赖变化会立即使原证明失效。执行器不再继续使用证明中的后续输入，但仍负责保持中性输入并等待落地。落地后该动作以失败结束，由会话从最新状态重新规划。
5. 伤害事实等待 `NEEDS_WORLD` 或 `NEEDS_INPUT` 超过八个运动 tick 后，转成 `DAMAGE_WITH_UNVERIFIED_MOTION`。恢复模块按保守外力处理，但记录中必须保留“运动未验证”，不能写成已经证明发生击退。
6. `RuntimeNavigationDriver` 只有在导航意图实际赢得移动仲裁后，才把 Runtime 的真实请求序号登记给已验证动作执行器。未胜出的候选不能伪造输入应用记录。

## 为什么这样做

动作证明失效和身体责任结束是两件事。证明失效后不能再声称后续命令安全，但角色可能已经起跳，也可能即将在下一 tick 起跳。此时直接删除执行器会制造无人负责的时间段。

保持中性输入是一种保守恢复，不代表跨隙动作仍按原证明成功。它保留唯一输入所有者，并让后续观察决定机器人已经落地、需要恢复，还是可以重新锚定。

伤害事实同样不能无限等待，也不能无声消失。八个 tick 是现有残差重放上限。超过上限后已无法补出原区间的完整证明，因此应明确进入保守恢复。

## 验证范围

- 确定性测试覆盖跨隙命令在途时缺一帧锚点、空中路线依赖变化、地面上在途命令遇到新路线，以及伤害残差持续缺少世界信息。
- 集成测试通过 `RuntimeNavigationDriver`、真实 `NavigationSession`、Runtime 仲裁和输入账本执行跨隙，并分别注入缺锚点和落地区域变化。
- 本轮没有新增 Fabric 实机场景。跨隙物理能力仍只沿用 B10-R4 已冻结的实机范围；新增证据证明的是责任不会丢失，不是所有受扰跨隙都能成功到达对岸。
