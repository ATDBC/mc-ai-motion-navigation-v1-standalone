# D035：正式方块视觉只允许表面深度

日期：2026-09-26

状态：已接受；正式感知入口和旧射线专用逻辑已完成整改，动作重跑尚未完成

## 要解决的问题

早期观察系统使用 `159 × 9` 条射线，只记录每条射线首先击中的方块。表面深度方案完成后，这套射线观察本应退出正式主线。

B02 重构只写了“沿用 `pre-floating-7ab0b35f` 的合法可见方块”，没有把表面深度的协议版本写成强制条件。正式启动器因此继续走 Observation V3 的默认 profile 3。B10、B11、C1 和 B12 最近的实机记录也都来自 `first_hit_ray`，没有使用 `surface_depth`。

## 决定

正式方块视觉只接受 `sensor_profile_revision=4`：

- 水平和垂直视场仍为 120°，最远 16 格；
- `ray_columns=0`、`ray_rows=0`；
- 可见方块来源为 `surface_depth`；
- 前方实体方块仍会遮挡后方，不能透视；
- 方块类型和碰撞形状只在方块实际可见时进入世界知识；
- 身体接触、脚下支撑和按需空气确认继续使用各自独立的合法来源；
- 交互与攻击继续使用 Minecraft 原版准星命中检测。它只回答本次操作能否命中，不作为环境视觉。

profile 3 从正式运行中删除。若为了读取历史轨迹而保留解码能力，代码和名称必须明确标为 `legacy_ray_profile3`，并满足以下限制：

- 正式启动器不能选择它；
- 环境变量和配置不能让正式运行退回它；
- 缺少表面深度提供器时，客户端在任务开始前明确失败；
- profile 3 不能生成新的正式验收和公开通过证据；
- profile 3 的实现不进入正式客户端构建，只能存在于历史快照、历史证据读取器或专门的兼容测试中。

## 空气与未知

D004 的按需空气确认继续有效。它与表面深度承担不同职责：

- 表面深度确认哪些实体方块真正可见；
- 按需空气查询只确认规划当前需要的空气正例；
- 没有看到方块，也没有得到空气正例的位置，仍是未知。

切换到表面深度不能把未返回的位置当成空气，也不能借此读取被遮挡方块的类型。

## 证据处理

公开代表证据中的 9 个归档都包含 profile 3 或 `first_hit_ray`。这些文件继续保留，作为历史行为和失败复现材料；索引必须把它们标为旧射线证据，不能再把它们列为当前视觉配置的正式通过记录。

规划、物理计算、控制器、输入账本和动作恢复的组件证据不会因为观察源变化而自动失效。依赖真实观察取得地图，再完成导航或战斗的端到端结论，需要在 profile 4 下重新验证。

## 防止再次回退

正式门禁同时检查启动、协议和证据：

1. 客户端没有表面深度提供器时不能开始正式会话。
2. Python 后端拒绝正式会话中的 profile 3。
3. 正式轨迹中不得出现 `first_hit_ray`。
4. 公开证据校验器拒绝把 profile 3 归档登记为当前通过证据。
5. 包边界检查阻止旧射线采集器重新进入正式客户端构建。

只改文档、只改默认值或只在脚本里补一个环境变量，都不能关闭这项修正。

## 旧射线逻辑审计

切换观察源时，不能只替换客户端采集器。旧策略中还有一些逻辑是为了弥补 159×9 采样间隙而存在的。审计后的处理如下：

| 逻辑 | 处理 | 原因 |
|---|---|---|
| 把待观察方块对齐到九个固定俯仰行和某一条水平射线 | 删除 | 表面深度覆盖连续视野，不再需要寻找“恰好穿过方块”的采样姿态 |
| 正式导航接受 `first_hit_ray` | 拒绝 | 旧来源不能进入当前世界知识和路线判断 |
| 正式客户端同时编译旧 159×9 采集器 | 删除 | 缺少表面深度时必须失败，不能存在隐式回退 |
| 已知碰撞箱与观察线段的相交计算 | 保留并改名 | 它只判断已知障碍是否挡住几何线段，不采样视觉，也不会产生新证据 |
| 缺信息时原地转头、等待下一帧再确认 | 保留，但候选改为连续视野区域 | 表面深度消除了离散射线之间的漏采样，仍不能消除遮挡、视野边缘和观察传输时序；现行逻辑不再枚举 9 个俯仰行 |
| 实体视线遮挡检查 | 保留 | 实体是否被墙挡住仍需原版视线判断，与方块地图的表面深度采集不同 |
| 攻击和方块交互的准星命中 | 保留 | 它验证一次动作能否命中目标，不负责观察环境 |
| 转头后等待新的正式观察再授权移动 | 保留 | 表面深度仍可能受视野边界和遮挡影响，预测朝向不能替代真实观察 |

旧主动观察脚本和旧 Follow Playground 证据脚本不再进入当前独立仓库导出。若主仓库继续保留它们，文件说明必须明确写出“历史 profile 3”，并且正式 Fabric 的构建和启动清单不能引用它们。

本轮进一步检查了现行 Python 策略、测试入口和公开导出。结果如下：

- 当前策略中已经没有按 `159 × 9` 射线行列挑选转头角度的分支；
- 当前通用测试夹具默认生成 profile 4，构造 profile 3 只用于证明正式入口会拒绝旧记录；
- 仍复现旧射线几何的夹具和脚本已经标为历史测试，不进入现行验收入口；
- 公开导出不再使用“导出所有 Java 文件”的宽泛规则，`legacy_ray_profile3` 不会出现在独立仓库；
- 当前独立仓库也不再导出 CraftGround 适配和它的 V2 兼容桥；这些文件只留在主仓库复现历史结果；
- 正式 Fabric 后端的默认观察协议已经改为 V3。仍需测试 V2 传输时，测试夹具必须显式声明旧协议；
- Observation V3 仍能解码历史 profile 3 文件，但正式后端和导航证据入口会立即拒绝它。保留解码能力只为了读取既有失败证据，不代表运行时兼容或回退。
- 当前证据恢复器已经与旧 `navigation_motion_evidence` 分开。正式 V3 轨迹读取不会再连带加载旧 Follow Playground、V2 导航审计和目标搜索重放。
- 当前导航视图已经移到中性的 `navigation_views`。`follow_playground_types` 只保留旧导入名的兼容转发，不再是现行模块的依赖方向。
- 把观察方块写入世界知识的通用转换已经移到 `observed_block_adapter`。它只接受显式方块或空气证据；没有返回某格不能推导为空气。旧 `pre_floating_adapter` 只保留兼容导入名。
- 正式独立包改为从现行入口递归收集 Python 依赖，不再把整个 `skills` 目录一并导出。旧 Follow Playground、旧导航证据、CraftGround 测试和 profile 3 采集器均不在当前文件集合中。
- 当前 C1 只依赖中性的 `control_capabilities` 数据契约。旧 `normal_control_capabilities` 会读取 J3 封存证明，并连带引用当时的 CraftGround／profile 3 源码清单，因此只保留给历史证明复核，不再进入正式运行的依赖闭包。旧 J3 证明仍能说明当时测过哪些输入，但不能证明修改后的当前客户端仍与当时字节一致。

协议中继续出现 `ray_columns=0`、`ray_rows=0`，是为了让接收端能够明确识别 profile 4，并拒绝伪装成新协议的旧记录。它们不是现行采样参数。`ClientObservationCollector` 中保留的原版方块射线只判断实体是否被墙遮挡；它不会把射线命中的方块写入导航地图。
