# D072：结束 S1—S4，先验证动作扩展边界

日期：2026-10-06。状态：决定有效；M0 通过，M1 结构止损，不通过。

## 1. 决定

S0-R 已在正式 Windows 环境通过。原 F1 后结构整理的 S1—S4 不再实施，由运动导航中层重构取代。

这不是否定 S0-R。S0-R 修好了正式缺陷，建立了五组确定性行为基线和路径矩阵。停止的是收益已经很低的逐项删减方案。

当前只批准两个阶段：

1. M0：补齐结构量尺和不变量保护，删除三个已经证明的死路径；
2. M1：只迁移受控下降，用它验证动作规则能否从 Session、接纳器和执行器中收回。

M2—M5 只作为后续方向。M1 完成后必须重新判断，不因本决定自动开始。

## 2. 为什么改变顺序

S0-R 的清单表明，原 S1—S4 最多能删除三个死路径，并检查少量重复条件。它无法解决下面这些长期问题：

- 动作类型判断散落在 Session、路线接纳、运动协调和执行器中；
- 步行和空中动作各有一套复核入口；
- 规划与动作求解重复维护作业身份、窗口和迟到结果；
- `NavigationSession` 继续接收其他模块没有明确拥有的行为；
- 驱动器仍用字符串维护自己的生命周期。

继续按原清单删减，容易减少少量行数，却保留新增动作需要修改多个核心模块的问题。

## 3. M1 的责任边界

`ActionSpec` 只描述动作自己知道的事实：

- 入口前提和所需观察；
- 身体承诺和安全停止方式；
- 风险与伤害；
- 是否需要后台运动求解，以及如何构造该动作的求解请求；
- 如何创建执行控制器，怎样判断动作完成。

它不拥有：

- 作业世代、请求身份和接纳窗口；
- 当前身体由谁负责；
- 等待落地、重新锚定、重试和任务终态；
- Session 生命周期和世界变化后的调度。

特别是 S0R-C-01 的“身体已在空中时保留落地责任，落地后重新锚定”继续属于通用运动协调。动作只声明自己需要的入口状态，不能把这条通用恢复规则塞进 `ControlledDropSpec`。

## 4. 安全默认值

每种登记动作必须显式声明：

- 身体承诺；
- 是否需要经过验证的运动；
- 风险和预计伤害；
- 安全停止方式。

缺少声明时拒绝登记。不能默认成“在地面”“零伤害”或“不需要验证”。真正可选的能力可以显式返回 `None`，例如某动作不需要后台求解。

登记表是固定、可枚举且启动时可检查的类型映射，不是动态插件系统。

## 5. 后续方向的限制

后续如继续推进：

- 复核统一的是入口和类型化结果，不强制所有动作使用同一种算法；
- 普通步行可以继续使用同步几何配方，空中动作可以使用计算器重放；
- 规划与动作求解共享作业身份和接纳协议，但可以保留不同的有界 worker，避免互相阻塞；
- 版本快照由一个 owner 构造和检查。已接纳许可在依赖变化、窗口过期或入口变化时失效，不能理解成整个执行期间只检查一次；
- 现有 `NavigationLifecycle` 是唯一 Session 状态转移表。后续只让它成为完整权威，不再创建第二张表。

## 6. 平台、证据和止损

- 正式开发、自动验收和 Fabric 环境仍是 Windows；Linux 只作补充复核。
- M0、M1 不改变产品行为，不需要新的 Fabric 结论。
- 每个小提交先跑直接检查和受影响场景；批次末再跑完整检查和五组集合，遵循 fail fast。
- M1 若不能减少 Session 和调用方的动作特判，或需要两个以上只服务受控下降的公共接口成员，就停止后续重构。
- 行数和分支数只是辅助量尺。把代码搬进 `actions/` 不能算作结构改善。
