# D117：收口 prepared 后继交接，再恢复连续运动扩展

日期：2026-10-18。状态：**COMPLETED／SIGNED OFF（组件范围）。**

## 1. 要解决什么问题

D116 修正了 prepared proof 的语义依赖判断。第二跳证明现在可以获批，首条输入也会实际生效，但整条 prepared 后继链仍不能完成。

当前已经确认五个缺口：

1. prepared 结果登记为 `APPLIED` 前，没有经过异步生命周期的 `try_apply()`；
2. prepared 提交只推进执行器下标，没有同步完成 tracker、伤害记账和候选清理；
3. prepared 入口和运行中状态使用浮点逐位相等，1 ULP 的表示差异就会进入恢复；
4. receiver 借快照遇到锁忙时，会把瞬时竞争写成永久的“缺少信息”；
5. prepared 准备失败或激活后无法继续时，没有回到普通 `SOLVE` 或有界终态的出口。

这五项只属于 prepared 后继链。D115 撤回自动准备后，现行生产路线不会调用这条链。同一条两跳路线会用两次普通 `SOLVE` 完成。因此本阶段修复的是未来连续运动需要的基础设施，不把它宣传为当前玩家能力的新增交付。

## 2. 处理原则

### 2.1 一个结果只从一个生命周期入口应用

普通结果和 prepared 结果共用同一个顺序：

`try_apply -> 安装 -> 记录 APPLIED -> 退役`

只有 `try_apply()` 成功，结果才可以安装。登记记录必须带同一次调用得到的 `accepted_monotonic_ns`。

### 2.2 完成当前动作是一项完整提交

prepared 交接不能只写 `action_index += 1`。它必须复用普通动作完成时的完整语义：

- 结算已经开始的动作伤害；
- 丢弃已完成动作的 prepared 候选；
- 清除动作边界；
- 推进执行器动作下标；
- 推进 `ActiveRouteTracker`；
- 安装后继控制器。

这不是线程锁问题。正式控制链在同一个调用中同步执行。正确做法是先检查所有参与者是否接受这次交接，随后一次提交；检查失败时不能留下半提交状态。

### 2.3 数值等价只吸收表示误差

prepared 入口和执行中的状态比较共用一个公开的数值等价函数。它继续要求 movement tick、姿态、碰撞条件和离地状态一致，只允许已有规则覆盖的位置、速度和朝向浮点误差。

本阶段必须证明：

- 1 ULP 的已知差异能够继续；
- 超出允许范围的真实偏离仍被拒绝；
- 不扩大动作入口、落点和安全证明范围。

这项组件结论不能代替 Fabric 上的真实数值边界。

### 2.4 快照锁忙不是缺少世界信息

快照借用必须区分：

- `READY`：取得不可变快照；
- `BUSY`：当前有观察写入，下一 receiver 周期重试；
- `CAPACITY`：请求范围不受支持；
- `INTERNAL_ERROR`：封存过程出错。

receiver 不在锁忙时 `sleep`，也不吞异常。`BUSY` 保持 pending，下一 receiver 周期继续尝试；最终上限由现有 `AsyncWorkWindow` 和 movement tick 期限决定，不能由线程碰巧运行了几轮决定。

### 2.5 prepared 失败必须回到现有安全路径

后继尚未激活时，如果准备被拒、过期或重试用尽，协调器撤销 prepared 要求，执行器继续使用普通 `SOLVE`。

撤销必须同时清理 coordinator 保存的 prepared stream、submission、signature、selection 和候选引用。只从执行器的下标集合删除要求，会让下一次准备复用已经失败的旧结果。

后继已经激活时，如果真实状态偏离证明：

- 身体仍在空中时，prepared 控制器继续持有身体责任；
- 身体安全着地后，把任务交给现有普通恢复或重新规划；
- prepared 控制器在稳定着地后转成现有 `INPUT_LOST` 路径，不另建恢复状态；
- 无法安全交接时，在既有预算内返回类型化终态。

不能因为 prepared 失败而直接释放空中身体，也不能无限保持 `prepared_action_boundary` 或 `RECOVERING`。当前 prepared 控制器尚未证明任意外力下都有安全尾迹，因此本阶段只承诺代表链在已经安全着地后的有界退出，不扩展为通用空中恢复能力。

## 3. 非目标

本阶段不做以下工作：

- 不恢复正式生产中的自动后继准备调用；
- 不新增动作类型、扩大跨隙距离或修改规划能力；
- 不修改 Session 状态集、WorldModel 语义版本或伤害规则；
- 不运行 Fabric；
- 不把一格连续两跳的 1 tick 攁善写成产品能力提升；
- 不治理历史文件行尾。D117 的提交禁止夹带无关行尾变化。

## 4. 进入和退出条件

进入条件是 D116 的 RED、Windows 只读复现和三方对照能够稳定说明五个缺口。

退出条件：

- 五项检查和各自 mutation 通过；
- 空闲和受控同核负载下各 30／30 完成；
- 快照持续 `BUSY` 时回退普通 `SOLVE` 并完成；
- 代表链进入 `RECOVERING` 并已安全着地后，在有界 tick 内恢复或返回类型化终态；
- I18—I22 零违规；
- 边界等待和 `RECOVERING` 有按控制 tick 计算的上限；
- D102、D113、D114、动作连续性和完整 Windows 分片不退步。

如果五项修完后出现第六个新的 prepared 链阻塞，本阶段停止。自动准备继续保持撤回，不进入扩大矩阵或 Fabric。

## 5. 后续能力安排

D117 通过后，也不单独为一格两跳运行 Fabric。下一次实机验证应与第一个真正依赖落地动量的能力一起安排；如果仍只验证一格两跳，验收必须明确它是基础设施验证。

## 6. 最终结论

R0—R5 已按范围完成。五个已知缺口都由共享规则关闭，没有新增 Session 状态、等待类型或第二套身体责任协议。D116 代表链在空闲和受控同核负载下各重复 30 次，全部完成；持续快照竞争、容量拒绝、内部错误、prepared 过期和安全着地后的恢复都有类型化、有上界的出口。

本决定只签署组件基础设施。生产默认路径仍不会自动准备后继动作，Fabric 也没有在本阶段运行。下一阶段只有在实现真正依赖落地动量的能力时，才可以另写决定启用这条路径并安排实机验证。
