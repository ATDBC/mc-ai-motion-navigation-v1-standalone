# R28 下降退步的根因调查

日期：2026-10-03。调查对象是 v4 成功、v5 未完成的六个下降任务：种子 9、14、56、72、97、146。调查沿用 v5 的生产字节，即 `1a67050` 加 D054 的修正；本轮未修改正式运动代码、原基线或失败证据。调查不等于修复通过，也没有新增 Fabric 结果。

## 1. 结论

六个任务的新增退步来自同一处时序衔接缺口：启动证明只覆盖两个相邻 tick，后台交付已经用掉其中一个，真正发送首条动作输入时便没有迟到余量。

旧版在接纳时按当前身体同步复核动作，会重新证明“下一 tick 启动”和“再晚一 tick 启动”。D052 把复核移到后台，并要求执行器只使用已经发布的启动分支，这个职责方向应保留。但普通等待路径仍把启动窗口放在发起求解的观察之后。它没有为后台交付和输入传输分别留下时间。

执行器按证明拒绝过期命令，随后恢复、重新准备。重新准备又重复同样的时间安排。六个任务最终都消耗完允许的两次恢复重试，以 `input_lost` 结束；身体仍在原上层，伤害为零。D054 修好了种子 56 的安全退回，却没有修复这处启动时间安排。

这不是六个独立的下降几何问题。四百个下降任务中，398 个进入了首条已验证动作提交：v4 的这些首次提交全部还剩一 tick 余量，v5 全部剩零。其余两个没有进入该阶段。正常输入二百场仍全部完成，因此仅看无扰动结果会漏掉这处缺口。

## 2. 一条实际时间线

种子 72 为向南两格下降，身体在准备时已停住。

| 环节 | 当前 v5 的运动 tick |
|---|---:|
| 用真实观察发起后台求解 | 37 |
| 求解器证明的两个启动时刻 | 38、39 |
| 控制层收到结果并核对当前观察 | 38 |
| 首条动作输入准备生效 | 39 |
| 注入的一 tick 迟到使其到达 | 40 |

第 39 tick 尚未消耗首条动作输入。第 40 tick 控制层发现已超过最后一个已证明的启动时刻，于是提交中性收尾输入。原动作请求被该输入替代，身体仍留在上层，进入恢复。

v4 在收到结果后同步复核，将当前观察后的 39、40 两种启动都重新证明。第 40 tick 可以在该窗口内重发同一首条命令，随后继续下降。

种子 9、56 的第一次失联还包含后续有效按键迟到；旧版也会对这类失联恢复。新增退步发生在重新起步时仍没有首条输入的迟到余量。不能把所有 `input_lost` 都解释为错误报警，也不能放宽整段有效输入的检查来解决首条启动问题。

## 3. 小范围因果对照

使用正式模拟链 `Runtime → 导航驱动 → 会话 → 求解／接纳／执行器`。观察器只记录后台任务、证明窗口和执行器启动；没有修改求解结果。原六场保存的 v5 结果也均为失联失败。

| 条件 | 六场完成 | 安全违规 |
|---|---:|---:|
| 当前源码、原晚到序列、只加只读观察器 | 0/6 | 0 |
| 仅去掉输入迟到 | 6/6 | 0 |
| 保留原晚到序列，诊断中按当前状态重新证明同一命令序列，并恢复一 tick 启动余量 | 6/6 | 0 |

第三组没有重新搜索输入，没有更改动作命令、落点范围、伤害额度或释放门槛；重放计算仍验证轨迹、停止尾迹和延迟启动分支。六个任务因此恢复，支持“后台交付耗尽启动余量”的归因。

第三组是隔离原因的模拟对照，不能直接作为正式补丁。同步复核会把运动推演重新放回控制线程，违背 D052 的性能边界。本轮没有测它的正式在线成本，也没有跑完整矩阵。十八场诊断的原记录保留在本地 `.tmp/r28-drop-root-cause-20261003/`；原 v4、v5 的完整正式记录仍在各自冻结归档中。

### 为什么只新增六场失败

输入迟到按各任务冻结的运动 tick 注入。起点、速度、观察准备和下降高度不同，动作起步及恢复重试就会落在不同的帧。相同的 20% 晚到率，并不意味着晚到会命中相同的有效输入。

当前二百场晚到下降中，185 场完成。按共同重试账本的累计失败计数分组：113 场为零次，48 场为一次，24 场为两次。出现过失败的七十二场仍完成，是因为后面的尝试赶上了有效时刻，或者身体已经满足出口、可以按原出口证据确认动作。余下十五场未完成，其中九场在 v4 也未完成。

新增六场都在初次执行及两次重试中再次碰到失联，最终达到重试上限。例如，种子 97 的三次首条输入分别安排在第 40、43、46 tick，这三个时刻都在该任务的晚到清单中；种子 146 则是第 43、46、49 tick。种子 9、14、56、72 还包含后续有效按键迟到，不能把它们简化为三次首条输入都晚到。

六场是本次固定清单中把共同缺口触发到业务失败的组合。其余任务完成，不表示它们仍有首条输入容错。六场新增失败、两场原失败改善，合计净少完成四场。

## 4. 代码中的责任位置

- `motion_coordination.py` 的 `_submit_action`：无准备前缀时，从求解源观察之后的第一、第二 tick 定义启动窗口。
- `motion_candidate.py` 的接纳与启动：结果交付时只选择仍可用、且与真实输入和身体匹配的启动分支。上述窗口交付后只剩最后一个分支。
- `motion_candidate.py` 的 `_latest_tick` 与过期收尾：首条命令最晚生效时刻仍是该证明的最后启动 tick。它不能自行增加未验证时刻。
- `motion_coordination.py` 的着地恢复：恢复后重新提交动作，使用同样的窗口安排，所以重试不会补回这项容错。

提交 `11b8f50` 移除了 `RouteAdmitter` 中的同步复核，并改为按真实输入验证原证明或请求后台重验证。旧版接纳时刷新窗口的行为由此消失。这个性能和权限修正需要同时迁移“交付后仍有多少启动余量”的保证；当前没有迁完整。

## 5. 修正应达到的行为

求解结果到达并准备提交首条输入时，应仍有明确、经过证明的输入迟到余量。后台准备期间实际保持了什么输入，也必须进入同一次预测与真实账本核对。

现有的准备前缀、延迟启动分支和输入账本可以承担这项工作。应先用同一规则补齐普通等待路径与提前准备路径，不为六个种子分别增加分支，也不只增加重试上限。若实际身体或输入偏离准备依据，仍应重新求证或有界恢复。

不能直接把最晚生效时刻加一：新的等待可能改变位置、速度、姿态或是否离边，必须把等待和后续命令一起推演。不能恢复无条件同步复核，也不能把“已接纳”当作“交付和传输已经赶上期限”。

后续低成本检查先覆盖原六场、首条迟到、后续有效输入迟到、实际等待输入不符、后台更晚交付和带速入口。专项稳定后，再扩大到原四百场下降和受影响的跨隙／上升路径。调查结论不关闭现有产品非退步门槛。
