# 动作转换 v1

日期：2026-09-19
适用阶段：B06 起

## 要解决的问题

规划器过去只知道边的起点、终点和时间。这样无法表达“必须低速起跳”“落地后才能交给 Walk”“取消后要先安全落地”以及整条路线的资源消耗。

## 契约

每条能力边可以携带一个 `MovementTransition`：

| 字段 | 含义 |
|---|---|
| `transition_id` | 动作转换身份 |
| `environment_id` | 适用的固定运行环境 |
| `mode` | 本段使用的运动模式 |
| `entry` | 入口模式、姿态和速度区间 |
| `exits` | 可交给后续动作的出口状态集合 |
| `duration_seconds` | 预计耗时 |
| `dependencies` | 轨迹成立所依赖的世界格 |
| `trajectory_profile_id` | 生成和检查整段轨迹的版本化 Profile |
| `resource_change` | 对已启用资源的变化；负数表示消耗 |
| `minimum_entry_resources` | 动作开始前必须仍然具备的最低资源 |
| `risk_tags` | 本段引入的风险标签 |
| `cancellation` | 明确取消时的安全终态 |
| `input_loss` | 输入失联时的安全终态 |

数值轨迹仍由具体能力 Profile 拥有。通用转换只引用 Profile，并保存经过几何查询得到的依赖，避免在规划边和执行器之间复制两份轨迹参数。

## 当前动作

- Walk：入口和出口都是站立 Walk，允许的速度上限来自普通地面 Profile；取消和失联都要求地面停稳。
- JumpUp：入口是低速、站立的一格上升；出口是已经落地且进入 Walk 接管速度；空中取消和失联都要求安全落地。

规划边创建转换，候选路线保存这些边，路线接纳把转换带入 `WalkSegment` 或 `JumpUpSegment`。执行器仍由具体动作控制器推进阶段，通用路线层不解释跳跃细节。

## 资源标签

`ResourceState` 保存剩余能力，数值越大表示越有余量，任何维度都不能为负。规划请求的初始资源同时是本次路线的容量上限，恢复不能超过这个上限。`ResourceChange` 只更新已经启用的维度。动作引用未知资源或一次消耗会使余额低于零时，该动作不可用。

资源变化和入口门槛是两件事。例如跨隙动作当前不估算一次跳跃消耗多少饥饿值，但使用冲刺输入前仍要求至少 7 点饥饿值。搜索在应用资源变化前先检查入口门槛，路线接纳和具体动作控制器再用最新观测复核。

搜索在同一站位保留互不支配的“时间 + 剩余资源”标签。只有一个前缀时间不更差、所有相关资源也不更少时，才能丢弃另一个前缀。因此，快但耗尽资源的路线不会覆盖慢但能到达的路线。

资源变化必须保持动作顺序。带非零资源变化的 Walk 边不能通过简单求和合并；路线接纳把这些边保留为独立动作段。这样“先恢复再消耗”和“先消耗再恢复”不会被误认为同一件事，恢复容量上限也不会在合并时丢失。

## 后续扩展

B08–B13 新增动作时，应新增自己的 Profile、入口／出口和执行器，再通过本契约接入。B10 可以利用出口与下一入口的兼容关系做带速交接，但不能另建一套动作协议。
