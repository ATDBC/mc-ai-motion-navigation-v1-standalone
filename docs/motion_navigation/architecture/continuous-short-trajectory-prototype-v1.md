# 连续短轨迹原型架构 v1

状态：隔离实验设计。它不属于正式 actor 接口。

## 1. 要解决的问题

现有路线把 Walk、JumpUp 和 JumpGap 分成独立动作。每段都有自己的入口和结束条件。连续运动因此容易在交界处停车、反复调整，或因为预计入口稍有变化而重新求解。

TP 原型不再为每一种动作组合写接续规则。它在一个短时间窗内直接搜索逐 tick 输入，并让速度、方向和落点从计算结果自然延续。

## 2. 边界

原型复用：

- `PhysicsState`、`TickInput` 和 Minecraft 1.21 运动计算器；
- `PhysicsWorldView` 与 UNKNOWN 语义；
- 现有任务目标、伤害额度和输入账本事实；
- 现有支撑图给出的全局走向，只把它当作引导，不把格心当作必经点。

原型不得导入到 `mc2p`。反向依赖也禁止：生产代码不能引用 `experiments/motion_navigation/trajectory_proto`。

## 3. 输入与输出

`TrajectorySearchRequest` 至少绑定：

- 入口 `PhysicsState` 或有界入口状态集合；
- 状态锚点、输入账本摘要和允许的生效 tick；
- 局部世界快照及依赖版本；
- 当前目标区域和全局路线引导；
- 任务伤害余额；
- 最大搜索节点、最大物理 step 和最大轨迹 tick；
- 支持的输入集合与时序分支。

### 3.1 准时与真实晚一 tick

两支以同一个观察状态 `S_t` 为来源。第一支入口保存这个共同锚点。扫描器负责重放已知等待输入，不能靠调用者手工偏移位置或只修改 tick 来制造第二支。

| 分支 | 已知等待输入 | 候选入口 | 首条候选生效 tick |
|---|---|---|---|
| ON_TIME | 空 | `S_t` | `t+1` |
| LATE_ONE_TICK | 明确的一 tick 输入 `p` | `step(S_t,p).next_state` | `t+2` |

`branch_preludes` 保存每支等待过程的应用事实；`None` 表示缺少证据，返回 `NEEDS_INFORMATION/MISSING_INPUT_APPLICATION`。扫描器不默认补中性。每支必须满足 `entry_state.movement_tick_id+1 == allowed_effect_tick`，并把完整重放状态与请求声明的入口比较。两支随后执行同一候选，输入值、长度、顺序和 yaw 均一致。

应用事实绑定 session、control sequence、输入值、生效 tick 和证据身份。`conditional_prediction` 表示在已知输入安排下的条件预测，不能伪称收到实际回执；`observed_application` 才能带 actual movement tick，且必须与绑定的生效 tick 相同。请求保存共同候选的起始 control sequence，候选第 k 条输入在两支中都使用同一提交序号。

本轮限定等待前后仍在同一高度的已知安全支撑上，不能横向碰撞、改变高度或离地。除计算器接触标记外，扫描器用现有公开支撑查询检查等待前后的真实身体投影，支撑比例不得低于正式执行的 0.15 下限。超出条件返回 `CANDIDATE_REJECTED/prelude_outside_same_safe_support`，不宣称该分支不可达。等待期间进入空中或越过风险区间的模型未交付，不能丢掉等待过程后再从较低入口继续授予证明。

非空等待结束后，即使支撑仍满足 0.15，也必须在候选边界 0 得到安全停车尾迹。惯性已经使该边界不能停车时，同样返回 `CANDIDATE_REJECTED/PRELUDE_UNSAFE` 且不发证明；未知事实和尾迹预算耗尽保留各自结果类型。此限制只适用于等待分支，不禁止普通单支从已有承诺状态继续完成安全动作，也不新增等待风险区间模型。

`BranchScan` 保存等待状态、等待依赖、候选入口、首条生效 tick 和从共同锚点到退出的总 tick。候选边界 k 的绝对 tick 是 `entry.tick+k`；`BoundaryInputs` 把每项不可撤回输入同时绑定到绝对生效 tick 和 control sequence。风险区间保留相对边界、边界的绝对 tick，以及开始承诺的候选命令生效 tick。

证明哈希绑定全部等待与时间安排。提交校验只核对各支本次边界的事实，未来无关缺回执不能阻塞当前提交；明确过期的身份、时间安排或世界依赖优先返回 `STALE`，当前必要事实缺失才返回 `NEEDS_INFORMATION`。实际观察是否仍处于提交窗口由后续 P2 驱动检查，此处没有正式控制消费者。

缺少等待证据也不能抢先遮盖当前边界已知矛盾。先比较各支当前已知的输入值、绝对 tick 和应用安排，再统一处理等待或当前必要事实缺失；任一已知当前差异返回 `STALE/INPUT_LEDGER`。

### 3.2 2026-10-10 时序证据更正

旧 Task 3／4 组件结果和审查保留。专项审查确认它们曾把两个同 tick 入口标成准时与晚一 tick，因此旧双支检查只证明“给定入口使用同一候选”，没有证明真实迟到。上述共同锚点与扫描器等待重放是在 Task 5 前完成的限定修正。新组件结果不替代参考搜索、闭环或 Fabric。

`VerifiedShortTrajectory` 保存：

- 每 tick 输入和预测状态；
- 名义分支与允许的晚一 tick 分支；
- 每个风险区间的最后可放弃状态、承诺点和安全停车尾迹；
- 落地、安全收尾和任务目标判定；
- 世界依赖、入口身份、目标修订和输入账本身份；
- 预计伤害与实际可恢复扰动包络。

## 4. 搜索层次

### 4.1 P0 参考搜索

P0 使用小场景和明确上限的参考搜索。它用于测量可达性、承诺边界、节点规模和计算成本，不声称在 40 tick 输入空间上完全穷举。

参考搜索报告：

- 实际展开节点数与物理 step 数；
- 找到的最好用时；
- 未搜索到的输入类别；
- 在当前上限内是否具有完整性；
- 每个场景的最后可放弃 tick 和承诺 tick。

### 4.2 P1 有界在线搜索

P1 使用固定顺序的 RUN、TURN、BRAKE、JUMP 和 WALK_OFF 短输入段扩展状态。扩展最终仍调用真实逐 tick 计算器。缓存键必须包含规则版本、完整物理状态、输入和依赖世界身份。

第一版不生成离线运动表。只有 P0 数据证明计算器调用占主要成本，才允许新增表格实验。

### 4.3 P2 滚动执行

P2 每次只提交已经验证且仍处于当前生效窗口内的短前缀。收到新观察后，从真实状态继续搜索剩余轨迹。

如果输入账本存在有限歧义，原型同时验证按时和晚一 tick 两个入口分支。两支必须验证同一条待提交输入前缀及同一提交顺序，不能各自挑选不同命令取得安全。两支不能同时安全时，该候选不得执行。缺少应用证据时返回 `NEEDS_INFORMATION` 等待重锚；固定分支预算用尽时返回 `NO_TRAJECTORY_IN_BUDGET`。`STALE` 只表示请求身份、世界依赖、目标或锚点已经过期。

## 5. 安全检查

候选至少检查：

- 每个已声明时序分支的碰撞、支撑和伤害；
- UNKNOWN 依赖；
- 停车尾迹；
- 承诺点前是否仍能安全放弃；
- 承诺点后的落地与身体责任；
- 目标变化、依赖变化和输入落选后的结果；
- 任务累计伤害额度。

承诺扫描按每个风险区间分别进行。停车尾迹先消费已经提交且无法撤回的输入，然后才追加制动或中性输入。落地后重新安全可停会关闭当前区间，但不能把本次承诺点移动到落地之后。

外力零伤害只对验收中冻结的可恢复扰动包络成立。超出包络时，原型仍必须保留身体责任、遵守伤害额度，并返回有类型结果。

## 6. 性能与确定性

Windows 是正式性能平台。分别记录：

- 请求准备耗时；
- 搜索与物理计算耗时；
- 后台交付耗时；
- 控制线程消费与提交耗时；
- 节点数、物理 step 数和缓存命中率。

墙钟不参与候选排序和行为决定。搜索由节点数、物理 step 数和轨迹长度上限终止。相同输入必须得到相同结果和轨迹哈希。

P0 的 `max_trajectory_ticks` 限制共同候选长度，最高 40 tick。等待额外占一 tick，晚支从锚点到候选退出最长 41 tick，单独记录，不能隐藏在候选长度中。等待的每次真实 `step()` 与候选、停车尾迹共用 `max_physics_steps`，支撑查询依赖也进入同一证明。

## 7. worker 生命周期

原型 worker 由原型驱动拥有。驱动负责创建、取消、关闭和有界等待。重复创建／关闭、取消中的关闭、异常结果和无人消费结果都必须有测试。不能依赖 `Runtime.close()` 代收资源。
