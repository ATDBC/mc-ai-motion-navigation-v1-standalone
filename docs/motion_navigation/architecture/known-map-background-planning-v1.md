# 已知图规划与后台隔离 V1

日期：2026-09-19

## 职责边界

B04 把 B03 的“外部固定路线”分成四个新步骤：

1. 控制侧把指定范围的世界事实按固定格数复制为不可变快照；
2. 后台进程用 B02 的支撑、净空和扫掠查询按需生成普通地面节点和边，再运行 A*；
3. 后台只发布候选路线；
4. 控制线程核对候选身份、变化依赖和身体接入条件，接纳后才交给 B03 控制器。

候选路线没有动作权限。后台进程不能持有当前路线、当前进度或游戏输入，也不能调用运行时。B03 控制器不感知 A*、Dijkstra 或后台进程。

## 世界快照

`KnownMapSnapshotBuilder` 只复制规划棱柱中的脚下支撑层和两格身体空间。调用方决定每次最多复制多少格，因此实时控制不需要一次复制整个范围。复制期间若世界会话或几何修订变化，构建器返回 `STALE`；调用方必须用新版本重新开始，不能拼接多个版本。

每个事实在分批复制时完成校验。最后一批直接把构建器独占的事实表交给只读快照，不再遍历并复制整张表。因此最后一步仍受调用方给定的格数预算约束，不会在大范围上突然占满一个控制周期。

完成复制只表示工作结束。`complete_scope` 另外表示范围内是否仍有未知格。这两个状态不能混用。后台快照与实时 `WorldKnowledge` 脱离，后者继续更新不会修改正在计算的候选。

## Walk 图

首版节点是同一高度、完整已知的站立位置。节点使用 `(x, feet_y, z)` 标识，连续位置位于格子中心。节点成立需要：

- 身体占据空间的净空查询为 `FEASIBLE`；
- 脚下支撑查询为 `FEASIBLE`；
- 支撑材质属于当前普通地面动力学配置。

首版只生成四邻接边。边成立需要：

- 起终点节点均成立；
- 身体从起点到终点的连续扫掠为 `FEASIBLE`；
- 沿边的支撑检查成立。

因此端点都能站立仍不保证有边。薄障碍、坑和悬浮净空都由同一套 B02 查询处理。图构建器不复制方块类型判断。

明确阻塞、缺少信息和当前实现不支持分开保留。未知碰撞形状、流体或未经校准的支撑材质会让失败结果成为 `UNSUPPORTED`，不能因为范围内没有未知格就报告“已经证明无路”。

正式后台请求按 A* 实际展开范围生成节点和边，不预先构造全部边。完整构图接口仍用于小图验证和独立 Dijkstra。首版边代价相同，搜索队列使用整数步数排序，得到路线后再换算为预计时间。这样既保留正确的最短步数，也避免浮点累计误差让开放地图展开大量同代价节点。

## 规划请求和结果

`PlanningRequest` 包含请求序号与 ID、目标 ID 与修订号、世界会话、起点、终点和展开预算。

`RouteCandidate` 保存相同身份、规划使用的几何修订、节点和边序列、总代价、依赖格以及展开数。结果状态分别表达完成、已知范围暂时无路、完整范围确定无路、超时和未支持。

A* 的启发式使用全图最小边代价乘曼哈顿距离。首版边代价为预计步行时间且始终为正。独立 Dijkstra 不复用 A* 的启发式和前驱逻辑，用于随机图验收。

## 后台进程

`PlannerWorker` 使用 `spawn` 启动一个独立进程。不可变世界快照、动力学配置和请求一起交给后台。控制侧最多保留一个尚未交付的最新请求；后台结果也只保留最新项。提交和轮询不等待构图或搜索结束。

旧结果仍可能在新请求提交后到达，因此最新槽不能代替身份检查。路线接纳必须再次核对 `request_id`。后台发布结果时若结果槽中的旧项仍停留在 `multiprocessing.Queue` 的发送线程，会在后台等待它变得可替换并重试；这个等待不会发生在控制线程。后台退出时控制侧不会合成路线，也不会把进程失败变成无路结论。

500 ms 延迟注入只用于验收，不参与正式算法。它验证控制线程调用提交和轮询时不会等待后台。

## 路线接纳和走廊

接纳顺序如下：

1. 候选必须完整；
2. 请求 ID、目标 ID、目标修订和世界会话仍为当前值；
3. 若地图修订已变化，必须提供这段时间的变化格；
4. 变化不能与候选依赖相交；
5. 当前身体必须能通过 B02 查询安全接到候选起点。

接纳后的 `route_id` 由世界、目标和完整节点序列计算，不包含当前身体位置。若身体没有正好位于首个图节点，执行路线会先加入已经通过扫掠和支撑检查的短接入段。走廊进度和长度都会先计入尚未走完的接入段，避免身体尚在接入时提前推进图走廊。接入段独有依赖在接入完成前参与变化撤销，完成后退出当前走廊。连续同方向图边在交给 B03 前合并成一条直线，避免一格一个网格点制造不必要减速。图路径、接入段和依赖仍完整保留，不因几何简化丢失安全证据。

`NavigationFrame.changed_cells` 只列出本帧中导航语义真正变化的格子，不把同一事实的重复观察当成变化。Fabric 运行入口在每个动作结果进入世界知识后，立即把这些变化交给 `ActiveRouteTracker`。

`ActiveRouteTracker` 单独维护有限走廊。它记住所有与路线相关的变化；远处变化暂不撤销当前走廊，但走廊推进到受影响区域前必须停止授权并请求新路线。调用方必须先得到 `READY`，才能让 B03 控制器继续提交动作。

## 与局部跟踪的边界

A* 只保证静态身体沿一格边扫掠时成立。实际角色带有速度，接近直角拐弯时还需要局部控制器提前管理速度。B03 因此只用完整停止尾迹判断动作失联后是否安全，用输入租约结束时的短期状态评价动作是否沿路线前进。全局搜索不写转弯按键，也不把动力学制动过程塞进图搜索。

## 当前边界

V1 还没有正式未知探索、动态实体绕行、路线平滑、对角边或增量搜索。四邻接只约束后台图，不约束 B03 在连续空间里怎样组合前进与横移。后续更换搜索算法时，应保持请求、候选和接纳接口不变。
