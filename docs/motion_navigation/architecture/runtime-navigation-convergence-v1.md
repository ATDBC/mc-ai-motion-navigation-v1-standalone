# 运行时与导航收敛架构 V1

日期：2026-09-24
状态：现行实施架构；R0、R1 已采用，R2 至 R5 依次实施

## 1. 要解决的问题

当前系统已经有可靠的正式观察、动作仲裁、唯一输入出口、输入账本、世界知识、运动计算器和后台规划。但这些组件还没有形成一条可由战斗、跟随和其他任务共同调用的在线导航入口。

C1 的父驱动器会在不同子驱动器之间交接，并由每个子驱动器调用 `Runtime.step()`。战斗接近使用旧 `PointGoalPolicy("D")`。这种结构带来四个直接问题：

1. 一帧只能由一个子技能推进，移动、转头和攻击难以合法组合；
2. 战斗无法使用台阶、跨隙、支撑面和 B10 动作证明；
3. 旧导航记忆与 `WorldKnowledge` 同时保存地形事实；
4. 日志、观察或输入出现可恢复缺口时，验收用的封存行为会关闭常驻会话。

本方案先统一这些公共边界，再扩大动作和战斗策略。

## 2. 完成后的主流程

```text
正式观察和输入回执
  → Runtime 更新输入账本并广播同一帧观察
  → 世界知识、目标状态、交战记忆和外力检测各自更新
  → 当前任务选择本帧需要运行的技能
  → 导航、战斗、恢复和视角技能只提交意图
  → 仲裁按控制组和操作兼容表合并
  → MotorGateway 只提交一个完整动作快照
  → 客户端记录真实应用 tick
  → 下一帧确认结果、重新锚定或报告失败
```

一帧只读取一次正式观察，只调用一次后端推进。观察可以被多个只读消费者使用，但不能由某个子驱动器私自消费后让其他模块看不到。

R1 已把这条流程接入 Runtime。技能通过 `ControlFrameProposalV1` 返回有序意图和观察请求，Runtime 合并后只执行一次仲裁和后端提交。正式驱动器不得再直接调用 `Runtime.step()`。

## 3. Runtime 是唯一逐帧推进者

### 3.1 技能输出

技能每帧返回以下内容：

- 零个或多个现有 `OrderedIntentV1`；
- 一个有类型的技能状态和结果；
- 下一帧需要的 `ObservationRequestV3`；
- 是否仍拥有空中落地、制动或一次性操作收尾责任。

技能可以更新自己的有限状态，但不能：

- 直接调用后端；
- 自行增加 Runtime 的观察序号；
- 清空其他技能的意图；
- 在没有显式交接时接管仍在空中的身体。

首版不新建通用插件系统。现有驱动器逐个改成“观察／提议／收尾”三步即可。

### 3.2 操作兼容表

兼容关系按最终动作快照中的操作种类判断：

| 操作 | 移动 | 转头 | 首版处理 |
|---|---:|---:|---|
| `attack_entity` | 允许 | 允许 | 客户端继续核验准星、距离、目标身份和当前能力条件 |
| `neutral` | 允许 | 允许 | 保持现状 |
| `open_inventory`、`click_slot` | 拒绝 | 按现有界面规则 | 防止界面输入与身体控制混用 |
| `interact_block`、`mine_block` | 保持现有限制 | 保持现有限制 | 等实际能力需要时分别设计 |

攻击冷却是否必须满属于攻击能力条件。客户端仍可核验本次候选声明的条件，但通用协议不能永久规定所有攻击都必须等到满冷却。C1 现有“满冷却近战”能力继续使用该条件。

组合攻击不会在请求刚到达时提前点击。客户端先暂存这一条攻击，在下一次玩家输入采样前重新核验世界、界面、目标身份、准星、距离和冷却，然后分发攻击；紧接着由原版玩家运动读取同一请求的移动输入。回执要等这两个动作进入同一个客户端运动 tick 后才能返回。若复核失败，客户端会先撤销这次输入，再返回拒绝，避免只移动却没有执行攻击。

目标受伤动画只用于确认一次攻击可能命中，不能反过来阻止下一次合法攻击。队友攻击、着火或其他伤害可能让动画持续存在。攻击能力应根据自身冷却、目标身份、距离、遮挡和本次任务条件决定是否提交；命中确认继续按攻击命令身份独立归因。

持续使用物品仍是后续能力。本轮不增加 `UseItemV1`，但 Runtime 的唯一控制帧和兼容表不能假定操作都在一帧内结束。以后增加吃东西、举盾或拉弓时，只扩展操作生命周期和兼容项，不再改逐帧所有权。

## 4. 正式导航会话

### 4.1 职责

`NavigationSession` 是任务层调用新运动主线的唯一入口。它负责：

- 当前目标 ID、修订和满足条件；
- 规划请求代次；
- 当前已接纳路线、动作位置和进度；
- 后台结果接纳；
- 取消、替换、等待路线和有界恢复；
- 对任务返回有类型导航报告。

它不拥有世界事实、正式身体状态、输入账本和后端连接。

### 4.2 首版接口

首版提供以下操作，名称在实现中保持一致：

```text
start(request, frame)
observe(frame, changed_cells)
update_goal(goal_id, goal_revision, goal_state)
propose(frame, state_anchor, deadline_ns) -> navigation intents + report
cancel(reason)
close()
```

`request` 复用现有 `PlanningRequest` 的身份和预算字段，并引用现有 `GoalState`。会话不再建立第二套点目标几何。动态战斗站位通过更新同一个目标 ID 的修订和 `GoalState.region` 表达。

### 4.3 与现有组件的连接

`NavigationSession` 依次复用：

1. `NavigationObservationAdapter` 形成 `NavigationFrame`；
2. `PlannerWorker` 生成已知地形路线；
3. `RouteAdmitter` 检查请求、目标、世界和当前身体；
4. `MotionRouteCoordinator` 准备需要求解的局部动作；
5. `ActionRouteExecutor` 产生短期移动和视角决定；
6. Runtime 将决定转换为正式意图并统一仲裁。

现有 B10 脚本中的手工编排先迁入会话。脚本只负责场景准备、启动会话和收集报告。

## 5. 世界知识只有一个正式拥有者

新正式链只读取 `WorldKnowledge`。旧 `NavigationMemory`、地形信念和 A–E 策略只服务参照与历史回放，不再给新任务提供正式通行事实。

为支持常驻运行，`WorldKnowledge` 按 16×16×16 区段保存事实。每个区段有独立的几何修订和证据修订。一次远处更新只让引用该区段的视图和候选失效。

首版内存策略为：

- 玩家 32 格球形范围内的事实受保护；
- 当前接纳路线、在途候选和恢复包络引用的区段受保护；
- 其余区段按最后使用顺序回收；
- 正式 actor 最多保留 262,144 个已知格；
- 如果受保护事实本身达到上限，拒绝扩大规划范围并返回 `world_knowledge_capacity_exhausted`，不能静默删除活动路线依赖。

32 格球形范围最多包含约 13.7 万个格。262,144 的首版上限可以完整容纳这一范围，并为当前路线和恢复依赖保留接近一倍余量。正式容量试验若证明对象开销仍不合格，应优化表示方式，不能在运行后提高上限来掩盖增长。

这项限制只管理内存工作集。以后若需要跨很远区域的长期地图，另行增加持久化存储，不让持久化逻辑进入控制帧。

## 6. 伤害事实与外部运动分开

### 6.1 伤害事实

伤害检测读取同一采样边界上的：

- 生命；
- 吸收心；
- 受击动画；
- 已知状态效果和明确来源证据。

它只报告角色受到伤害或可能受到伤害，不直接宣称发生击退。

### 6.2 运动残差

外部运动检测从最近可信状态锚点出发，按输入账本中真实应用的命令调用 B09-R。然后比较预测位置／速度与下一正式观察。

误差阈值来自固定静止、行走、冲刺、转弯、跳跃和网络纠正样本。阈值冻结前，残差检测只能以影子模式记录，不能接管身体。

残差超过已验证范围时产生有类型结果：

- 有伤害证据且运动残差成立：`DAMAGE_KNOCKBACK`；
- 有实体接触证据且残差成立：以后可增加 `ENTITY_PUSH`；
- 有活塞接触证据且残差成立：以后可增加 `PISTON_PUSH`；
- 只有残差：`UNATTRIBUTED_EXTERNAL_MOTION`；
- 只有伤害：记录伤害，不启动位移恢复。

恢复仍由一个控制器负责。单次恢复保留 tick 上限。重复事件耗尽后返回有类型结果，战斗任务决定撤退、继续观察或失败。

恢复不再默认等于“先刹到静止”。外力发生后，导航会话从新状态锚点重新判断：若当前支撑、速度和已知走廊仍落在已验证范围内，可以直接生成后续动作；只有空中责任未完成、路线已经不安全或当前速度超出能力入口时，才进入落地、制动或其他声明过的恢复。

## 7. 失败和证据完整性

运行时使用四类处理结果：

| 类别 | 例子 | 处理 |
|---|---|---|
| 会话必须封存 | 世界身份倒退、输入所有权冲突、无法安全收尾的契约破坏 | 中性化可控输入后关闭当前会话 |
| 需要重新锚定 | 输入应用缺口、观察序号缺口、预测分支过多 | 保留当前动作责任，取得新观察并重新建立锚点 |
| 证据降级 | 异步日志线程失败、非关键记录被丢弃 | 控制继续；本次运行不得作为完整成功证据 |
| 任务结果 | 无路、目标取消、能力不支持、恢复预算耗尽 | 向上层报告，不直接关闭后端 |

交战记忆不再因为全局观察序号跳过一帧而永久撤销。它根据自己依赖的目标事实判断是否还能使用；缺少必要连续证据时变为等待重新观察。实体明确死亡、卸载、换世界或目标修订仍立即失效。

## 8. 带速度局部求解试点

本轮只扩展同高一格跨隙。语义动作仍是 `JumpGap`，全局图仍保存入口、落地和风险条件。局部求解器使用当前连续速度，从有限命令模板中寻找 8–20 tick 输入并交给 B09-R 验证。

试点覆盖与跳跃方向基本一致的三个入口速度带：

- 0.5–1.0 格／秒；
- 1.0–2.0 格／秒；
- 2.0–3.0 格／秒。

首版不支持途中大角度转向、斜向跨隙和疾跑极限跳。找不到经过证明的候选时返回求解失败，不能退回未经验证的固定轨迹。这个试点用于证明入口速度可以成为求解条件，不宣称所有动作已经丝滑衔接。

## 9. 旧代码处理

- `skills/navigation_*`、`PointGoalPolicy` 和 A–E 策略在迁移期间保持可读、可回放；
- 新功能不得再导入这些模块；
- C1 和现行任务迁移完成后，在包边界测试中禁止正式入口依赖旧导航；
- 旧证据仍有调用时，移动到明确的 `legacy` 或参照目录并保留薄兼容入口；
- 未完成依赖清理前不删除源码。

## 10. 不变量

1. 一个客户端运动 tick 最多提交一个完整动作快照。
2. Runtime 是唯一后端推进者；技能不能调用后端 step。
3. 只有 `WorldKnowledge` 保存正式地形事实。
4. 导航会话拥有目标和路线生命周期，不拥有世界和输入账本。
5. 动作兼容由有类型规则决定，不能比较 `reason` 字符串取得权限。
6. 空中动作在完成、失败或显式交接前始终有唯一责任方。
7. 伤害不自动等于击退；运动残差不自动证明来源。
8. 日志失败会影响证据资格，不应自动关闭仍可安全控制的客户端。
9. 旧阶段结果保留原范围，不因本轮重构改写历史证据。
10. 本地完整验收通过前，不更新公开仓库的完成声明。
