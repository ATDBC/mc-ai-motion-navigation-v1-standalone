# B10 动作求解与连续执行架构

日期：2026-09-21
状态：已实现；B10-A、B10-B、B10-C 已通过当前冻结范围的验收

## 1. 要解决的问题

B09-R 已能计算“给定状态和给定输入之后会发生什么”，但它不会寻找输入，也不会授权真实执行。B10 要补齐这段连接：从正式观察得到可信的运动起点，搜索真实输入链能够产生的命令，验证完整轨迹，再把仍适用于当前状态的短期方案交给唯一输入出口。

B10 不重写 B09-R，不复制地图、身体状态、路线或输入出口。正式范围继续限定为已知地形、玩家自身、不使用载具或消耗型道具、不主动改变世界。未知探索、动态实体避让和跟随仍不属于本阶段。

## 2. 长期职责

| 责任 | 拥有者 | 不负责什么 |
|---|---|---|
| 世界方块、形状和会话事实 | 现有世界知识层 | 不保存第二份供求解器私用的地图 |
| 当前正式身体状态 | 现有观察／身体状态层 | 不接受诊断 sidecar 作为 actor 真值 |
| 真实输入应用记录和有界输入账本 | 唯一 `MotorGateway`／客户端输入出口 | 不由求解器或观察适配器各自维护一份权威进度 |
| 正式状态锚点 | 状态锚定组件 | 只读正式观察和输入应用账本，输出不可变锚点，不写按键 |
| 给定状态和采样后输入的运动后果 | B09-R 计算器 | 不搜索命令，不决定是否值得执行 |
| 合法命令到逐 tick `TickInput` 的投影 | 输入投影边界 | 不写入游戏，不拥有按键租约 |
| 候选连接和已验证结果查找 | 动作可达性查询 | 查不到不能宣称现实绝对不可达 |
| 合法命令和时序搜索 | 动作求解器 | 不直接写按键，不自行实现物理 |
| 给定轨迹是否满足任务约束 | 轨迹验证器 | 不重新寻找另一条输入，不复制物理规则 |
| 候选现在是否仍可使用 | `RouteAdmitter` | 不求新解，不把版本相同当作充分条件 |
| 短时执行、阶段推进和反馈 | 现有动作执行层 | 不拥有全局路线，不绕过最终仲裁 |
| 真实输入写入、租约和失联回退 | 唯一 `MotorGateway` | 不接受第二个写入者 |

可达性、求解、验证和接纳按职责单向连接，但不要求每个组件只调用一次。求解器会逐 tick 交替调用输入投影、计算器和验证器；接纳器也可以使用同一个验证器复核已变化的短期部分。

## 3. 三种精度的状态

### 3.1 具体模拟状态

`PhysicsState` 表示某个确定 tick 边界上的具体身体状态，用于逐 tick 计算。它包含连续位置、速度、朝向、姿态、接触、必要内部状态和规则身份。

它不负责定义哪些状态可以在搜索中合并。

### 3.2 动作入口和出口范围

动作范围表达一个动作方案允许从哪些连续状态开始，以及执行特定命令后会到达哪些状态。文档中称为 `MotionStateEnvelope`；这是概念名称，不要求在 B10-A 立即建立同名通用类。

入口与出口必须保留关联：

```text
入口子域
  + 命令序列
  + 规则和世界依赖
  → 预测轨迹
  → 对应出口范围
```

不能分别合并入口和出口，再假设任意入口都能到达任意出口。若一个动作从平台偏左和偏右开始会产生不同落点，就应形成不同结果，或由同一结果中的条件关系明确区分。

### 3.3 规划状态键

`PlannerStateKey` 只保存本次搜索必须区分的有限信息。它可以包含支撑区域、模式、姿态、速度范围、方向类别、接触类别和当前能力实际依赖的内部状态。

同一个键只表示便于组织搜索，不自动表示其中所有具体状态可以互相替代。只要方向会改变下一动作是否可行，规划器就必须采用一种明确做法：

- 把方向纳入键；
- 在同一键下保留互不支配的方向标签；
- 或把不同状态都转换到一个已验证的共同入口，并计入时间和资源。

现有 `MovementStateClass` 继续作为已发布转换的粗粒度契约。B10 不向其中无条件塞入所有连续字段。只有确认一个字段长期属于共享粗分类时，才修改该公共类型。

当前表面规划已经使用 `PlannerStateKey`。首版键包含支撑面、移动模式、姿态和速度区间。现有已发布动作没有根据来向改变下一动作资格，因此不保存方向，避免同一位置按来向重复展开。以后新增确实依赖来向的动作时，再按前述三种办法之一保留方向差异，不能提前把所有节点乘成四份。

动作边的身份同时包含起点、终点、动作类型和转换／Profile 身份。两个动作连接即使连接同一对支撑面，也可以并存。搜索返回的每一步都保留对应的规划状态键，后续路线组装仍须验证前一出口是否满足后一入口。状态键负责避免错误去重，不能代替动作交接验证。

## 4. 正式状态锚点和输入账本

### 4.1 状态锚点

在线预测必须从一个可追溯的正式状态开始。锚点至少绑定：

- 世界会话；
- 正式观察序号；
- 客户端玩家运动 tick；
- 该状态处于输入采样前、运动更新前或运动更新后的哪个边界；
- 最近已确认应用的控制序号及作用区间；
- 规则、状态 schema 和输入投影版本。

局部 rollout 的第 0 步表示“从该锚点开始模拟”，不冒充客户端真实 tick 0。

### 4.2 输入应用账本

未收到回执的输入不能直接当作未执行。每条在途记录至少保存：

- 命令内容和控制序号；
- 请求生效 tick 或窗口；
- 租约和到期条件；
- 已知应用信息与确认状态；
- 可用来消除歧义的后续观察。

真实应用记录由唯一输入出口产生并维护。状态锚定组件读取正式观察和应用账本，产生不可变锚点；求解器只读取锚点，不修改账本。首版只维护数量有上限的账本。若少量可能结果都能枚举，候选必须对所有仍可能的结果成立；若分支过多或差异过大，就等待新观察重新锚定，不建立无界的状态分支树。

经过 Runtime 提交的已验证命令，要把求解器给出的最早和最晚生效 tick 绑定在对应的移动意图上。仲裁器只把获胜移动意图的窗口交给 Runtime；其他来源获胜时，不能误用导航窗口。Runtime 在唯一账本中登记获胜意图的窗口，再用客户端回执核对实际生效 tick。带证明窗口的移动意图只允许仲裁一次，不能像普通持续前进意图一样在下一帧重复使用。探针、技能和导航会话不得另外维护一份本地账本；中性落地帧也由 Runtime 记录，但它不需要伪造动作证明编号。

等待只暂停新的求解或执行授权。已接纳且仍有效的前段继续由原动作执行器负责；没有有效前段时，进入当前模式已经声明的恢复。空中动作不会因为暂时无法构造新锚点而失去落地责任。

### 4.3 两种期限

必须分开记录：

- **状态／预测有效范围**：在给定输入历史、世界依赖和不确定性下，可以继续推演到哪里；
- **候选执行窗口**：某条已经验证的方案最迟何时开始或继续执行仍满足约束。

预测有效不代表执行安全。世界变化、服务器纠正、输入历史不确定性或资源条件变化后，应按依赖重新核对候选。

后台求解期间，客户端玩家 tick 可能继续前进。首条命令可以在候选已经验证的启动窗口内生效；输入出口必须记录真实生效 tick，执行器以它重新锚定剩余命令。动作一旦开始，后续命令仍按重新锚定后的连续 tick 精确核对。这个规则只吸收求解交付延迟，不能掩盖动作执行中途的漏帧。

执行窗口中的每一个允许开始 tick 都必须有完整证明。若允许首条命令晚一 tick 生效，求解器要先模拟这一 tick 实际会保持的输入，再从得到的新状态重放不可变命令，重新检查完整轨迹、落点、世界依赖和每个释放时刻。不能只证明最早开始分支，再把同一出口套给较晚分支。后台任务可以等待多久属于协调器期限，与候选首条命令可以在哪些 tick 生效是两件事，不能用扩大执行窗口代替刷新观察和重新接纳。

## 5. 命令、输入和动作证明

### 5.1 求解真实命令

求解器搜索机器人能够实际提交的命令和时序，例如前进、冲刺、跳跃、释放、朝向变化及其生效窗口。它不能直接搜索任意连续轴值，再把模拟器专用 `TickInput` 当作真实按键。

输入投影按 tick 工作：

```text
命令 k + 预测状态 k + 输入相位
  → TickInput k
  → B09-R 计算状态 k+1
  → 再投影下一 tick
```

姿态缩放、实际运动 yaw、冲刺资格、释放语义和输入相位都在这条链中处理一次。不得提前用初始状态生成整段输入后忽略途中状态变化。

### 5.2 可复用运动结果和任务候选

可缓存的运动结果至少绑定：

- 状态锚点或适用入口范围；
- 可发送的不可变命令序列；
- 同次计算得到的不可变 `TickInput` 轨迹；
- 完整预测轨迹、接触和姿态变化；
- 对应出口范围和必要恢复范围；
- 规则、输入投影和求解器身份；
- 世界依赖；
- 资源完整性和适用风险策略；
- 成本和计算预算结果。

三类记录必须来自同一次计算，不能分别修改。大轨迹可以通过不可变引用保存，规划节点不复制完整数组。

准备交给路线接纳的任务候选在可复用运动结果之上再绑定：

- 所属规划请求和请求代次；
- 目标 ID 和目标修订；
- 所属路线、动作位置和前后动作关系；
- 当前候选修订、替代关系和执行窗口。

这些任务字段不强塞进所有可复用物理结果。目标取消或修订后，即使世界、身体和运动结果都没有变化，旧任务候选也必须失去执行资格。

### 5.3 失败结果

至少区分：

- 已知条件明确冲突；
- 缺少世界事实；
- 缺少身体或资源条件；
- 规则尚未支持；
- 有候选但尚未求解；
- 搜索预算耗尽；
- 找到输入但轨迹不满足任务；
- 候选已经过期；
- 接纳时相关事实已经变化。

有限搜索没有找到解，不等于物理上绝对无解。

## 6. 求解、验证和接纳

### 6.1 可达性查询

先用支撑面、途中净空、已知能力边界和硬条件做便宜排除，再查找适用的已验证结果。地图中所有位置不做两两求解。

已知表面规划按搜索需要查询支撑列和相邻动作边，不再预先物化完整地图图。普通无资源路线使用可证明不高估的曼哈顿距离下界；存在资源约束时使用保守搜索口径。物化图和独立 Dijkstra 只保留为小图等价性检查，不进入大地图正式热路径。

### 6.2 后台求解

重搜索复用现有后台隔离或一个明确有界的工作队列。控制循环不等待完整求解。“保留最新有效项”只在对象确实互相替代时成立：

| 对象 | 覆盖规则 |
|---|---|
| 已被新目标或新请求取代的整项规划 | 可以取消旧代次 |
| 同一动作连接、同一用途的新修订 | 可以替代旧修订 |
| 同一规划中的不同必要连接 | 不能按完成或到达顺序互相覆盖 |
| 已接纳且仍有效的执行前段 | 不因新求解尚未完成而清空 |

首版可以在一个后台规划任务内部有界地顺序计算多个连接，不为此预先增加新队列。只有确需并发调度时，才引入明确的请求代次、连接身份、用途和取消传播。

后台进程抛出异常时，必须把异常转换成带类型的失败结果。协调器还要检查进程是否存活和请求是否过期。它不能在工作进程死亡后永久停在“等待结果”。同一连接在身体状态、世界修订和失败原因都没有实质变化时，最多重新提交两次重验；继续失败就结束这次动作准备。

优先减少重复工作：复用共同命令前缀、稳定世界查询、候选初值和仍有效的控制余段。只有实测证明必要时才增加新进程、共享内存或原生实现。

### 6.3 轨迹验证

验证器检查完整运动，而不是只检查终点：途中碰撞、支撑、姿态、落点、资源、恢复范围和任务出口都必须成立。`CalculationStatus.OK` 只说明计算完成，不能直接转换成动作许可。

### 6.4 路线接纳

`RouteAdmitter` 不求新解，但至少核验：

- 规划请求和请求代次仍有效；
- 目标 ID 和目标修订仍一致；
- 路线身份、动作位置和候选修订没有被替代；
- 当前身体能否进入候选；
- 命令是否仍在执行窗口内；
- 世界、能力、规则和资源身份是否一致；
- 相关事实是否变化；
- 恢复条件是否仍成立。

有限变化可以调用同一验证器复核受影响部分。需要重新搜索命令或重验整条长路线时，提交后台任务；不能把这项工作放入控制帧。只有目标变化、世界和身体完全不变的反例，也必须拒绝旧候选。

## 7. 资源范围

B10 不提前实现完整服务端饥饿时钟。它可以在已证明的动作数、持续时间、入口资源余量和条件化资源界内授权短路线。

路线短不是证据。若接近资格阈值、内部消耗可能改变动作资格，或发生未覆盖事件，依赖该资格的候选应返回条件不足或等待更新。每条边不能重复读取同一个初始食物值后宣称整条路线安全。

完整饥饿和呼吸同步在实际依赖它们的后续能力中交付。

## 8. 连续接续与执行

连续执行以事前冻结的接续矩阵为准，不要求所有动作两两组合。每个声明支持的组合都记录入口域、中间状态、出口、减速要求、时序和证据。

停稳是合法控制结果，但不是接口交接的默认动作。局部执行每次只发送当前已接纳方案的短期前段，然后根据新观察更新锚点、进度和剩余执行窗口。

执行中的世界依赖仍要逐帧检查。相关格子变化时，接地动作立即按有类型失败收尾；空中动作继续承担落地责任，但不再宣称原证明仍有效，并在落地后失败收尾。无关格子变化不撤销候选。

偏差仍在已验证恢复范围内时，可以有限修正。输入、入口状态或中间出口一旦超出原结果的适用范围，就生成新的候选修订，并重新验证受影响的剩余轨迹、落点、恢复范围和下一动作入口。只有仍明确满足原契约的部分可以继续复用，不能因为眼前几帧没有碰撞就保留原来的全部落地结论。

空中能力只能使用包含足够顶部空间的地图快照。能力的参考轨迹会给出相对脚点的最高上升量；快照的 `extra_top_clearance_cells` 小于该值时，规划返回 `insufficient_top_clearance`，不能把缺少查询范围写成普通无路。

跨隙求解器会从每个待执行命令的起点额外模拟一次“立即松开全部输入”。只有所有命令时刻都能在无水平碰撞的情况下回到同高度已知支撑，候选才会发布。这个证明只表示中断后能安全落地，不表示仍会落进正常完成所要求的恢复区。当前执行仍逐 tick 核对真实输入回执，没有因为这项证明压缩后半段空输入。以后若要改为“观察自由下落”，必须先声明动作拥有者、落地确认、最大观察期限和失联处理，并单独验收。

默认业务运行、只读影子和受控实机验收必须分开：

- 默认业务运行只使用已经发布的命令生产者；
- 只读影子可以计算和记录，不能提交输入；
- B10-B/B10-C 的受控验收会话可以明确授权新命令生产者通过既有 `MotorGateway` 执行。

切换期间只有一个有效命令来源，旧控制器暂停产生输入。试验结束或取消后按现有恢复和交接规则退出。当前空中动作的拥有者持续负责落地或进入经过接纳的显式交接状态，不能为了恢复默认控制器而直接替换动作拥有者。

## 9. 与 B11–B13 的关系

- B11 扩展接触和材质规则，继续使用同一计算器、求解器和动作证明结构。
- B12 增加攀爬模式和进出动作，不伪造脚下支撑。
- B13 的流体规则提供水体接触、浮沉、流动和呼吸条件；姿态规则仍由运动计算体系统一拥有。
- 水只是 Crawl 姿态转换的一种条件来源。流体模块不维护第二份 Crawl 状态。
- 每种 Crawl 入口仍需要固定版本的合法机制和证据。看到一格高通道不自动代表站立角色能够进入。

## 10. 不变量

1. 只有一个正式世界事实拥有者、一个正式身体状态拥有者和一个真实输入出口。
2. 诊断数据只用于对照，不进入正式 actor 决策。
3. 求解器输出真实命令；`TickInput` 是投影和计算产物。
4. 入口、命令、轨迹和出口保持关联。
