# D097 M0 Windows 证据

日期：2026-10-10。结论：M0 未通过，M1 未开始。

本目录保存 D097 的仓库内只读探针结果。量尺直接调用 `trajectory_proto` 的冻结夹具、Java 1.21 计算器、目标检查和完整承诺扫描器，没有从三方 `reviews/` 导入代码。

正式口径关闭尚未证明正确的模板高度截断，并且只在两支时序都着地时尝试起跳。`floor_diagnostic` 只帮助观察模板限制的成本，不能参与正式安全结论。每个场景预热 3 轮，再正式运行 20 轮。JSON 保存每轮原始耗时，并用 nearest-rank 计算 P50、P95、P99 和最大值。

文件：

- `windows-m0-first-run.json`：第一轮正式采集；正例最大 587.9058 ms，M0 未通过。
- `windows-m0-second-run.json`：补齐每轮原始耗时后的第二次采集；正例最大 591.1611 ms，M0 未通过。
- `windows-m0.json`：以最终实验模块入口复跑；正例最大 736.8842 ms，M0 未通过。
- `red-green.md`：测试驱动过程。
- `verification.md`：最终检查和证据边界。
- `manifest.json`：命令、来源和文件哈希。

失败集中在新增的混合动作元反例。三轮中该反例都使用 10,056 次 physics step。最终模块入口复跑的 P50／P95／最大值为 733.5156／735.3165／736.8842 ms；机器较快时的前两轮最大值仍为 587.9058／591.1611 ms。不能删除新增反例后签署 M0。

`controller_ms` 包含每次重新构造冻结夹具和世界快照的约 26—31 ms。独立复核缓存夹具后，混合反例仍约为 556—695 ms，继续超过 400 ms。原始 JSON 保留完整调用耗时，不事后扣除夹具成本；停止结论不变。

`tiny_budget` 由 M0 探针直接分类，没有独立重放真实计数器耗尽。真正的 `PHYSICS_STEP_BUDGET` 路径由旧 TP 94 项冻结回归覆盖。M0 只能说明极小预算被正确排除在无解成本之外。

lazy 成本是从同一份完整扫描结果拆出的 step 估算。它没有实现 M2 的逐次证明，也不构成执行许可或正式控制性能证据。
