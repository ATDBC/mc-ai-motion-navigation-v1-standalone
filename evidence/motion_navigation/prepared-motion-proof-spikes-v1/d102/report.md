# D102：完整证明提前准备的 Windows 可行性试验

2026-10-11。第三轮结果：对 D101 固定单跳，完整初始证明及父侧接纳校验都提前完成后，动作开始热路径可行。400 个热决定 P95／P99／最大为 0.4061／0.4257／0.4525 ms，通过沿用的 P95≤8 ms、P99≤15 ms、最大值<30 ms 门槛。

只把 `scan_commitment` 移走还不够。现有 `validate_commitment` 的 P95／P99 是 17.4525／17.7467 ms，仍超控制预算。它虽不重新跑物理，却会将整份 proof 转为 JSON 并算 SHA-256。后台结果必须先完成这次完整检查，再交给动作开始路径使用。

**语义可行性。** 证明指计算器保存的主轨迹、每个边界的停止办法及其依赖，不只是一个“通过”标记。`PreparedProofBundle` 把这些证据封成一份准备结果，绑定完整请求、输入、`CommitmentProof`、每条分支的主轨迹和停止尾迹、各边界输入事实、世界会话与版本、逐格依赖、物理规则、输入账本与第一条序号、输入流世代与 owner，以及确定性摘要。输入流世代（generation）用于区分新旧输入流，owner 表示谁承担身体责任。每个新请求都调用原 `scan_commitment` 准备；没有复制物理公式，没有搜索新动作。400 份准备证明同时以同一请求重新 scan；分类、完整证明摘要、等待段与分支状态、停止尾迹、风险区间、依赖和完整数据对象都是 400／400 逐项一致。

准备调用完整证明 400 次、物理 162,800 步；独立 fresh scan 再用 162,800 步。准备和接纳时间均单独记账，没有当成免费工作。

**热路径性能。** 按时和整体晚一 tick 各 200 个样本，均完成第一条命令的实际应用并立即剪枝。按时推进 1 个物理 tick；晚一分支先执行已证明的 prelude，再推进首条命令，共 2 tick。合计 600 物理步，完整证明和搜索调用都是 0。阻断器会在热路径尝试完整证明或冻结输入搜索时直接失败。热决定包含完整性／identity／dependency／ledger 校验、generation／tracker／账本创建、物理推进、首条实际应用回执、剪枝和结果构造。

信任来自准备／接纳阶段对所有内部对象的完整检查及精确对象注册。这里的不可变对象图，指所有内部字段都由冻结对象、元组或不可变值组成，准备结束后不再修改。热路径只消费已经注册的同一个对象，并核对封存 bytes 摘要、当前请求、generation、owner、物理规则、输入账本和逐格依赖。未注册对象、即使字段完全相同的 `dataclass.replace` 新对象、篡改后沿用旧摘要的证明，都拒绝。25 类负例覆盖请求 id、锚点与入口、目标与版本、账本与第一条序号、世界与版本、依赖格、输入、物理规则、证明摘要与状态、generation 和 owner；全部拒绝，身体推进为 0。

第二轮独立审查发现接纳检查漏比了证明内部规则集：修改 `proof.ruleset` 后重新生成所有摘要，原脚本仍会登记并在热路径推进 1 tick，而现有 `validate_commitment` 返回 STALE。第三轮要求 `proof.ruleset`、`bundle.ruleset`、`world.ruleset` 三者一致，并在热检查中保留同一约束。新增负例使用普通 `dataclass.replace` 修改内部规则集，重新封存所有摘要；登记阶段以有类型的 `RULESET` 原因拒绝，身体推进为 0。完整 proof 的规范序列化字节包含内部规则集，封存和父侧完整摘要核验继续覆盖这一字段。此修正没有优化性能，也没有改变其他执行语义。

这依赖项目内部可信准备代码及冻结 dataclass 的正常不可变契约。SHA-256 用于发现数据错误，不能验证外部不可信证明的真实性；不把绕过冻结契约的进程内任意内存修改纳入该试验。来自 worker 的 pickle 只在自己的可信进程之间传递。父侧先检查消息 bytes 摘要，再反序列化、重新完整绑定和比较依赖，最后注册，不凭 worker 自报 proof hash 接纳。

**后台交付性能。** 使用 Windows `multiprocessing.get_context('spawn')`，一个持久 worker、容量 1 的请求队列和结果队列；预热 10 次，顺序测量 200 个新 request。worker 在子进程内自行构建固定 fixture。请求只传递结构化请求、冻结输入、generation 和 owner，没有传输真实世界快照。因此本轮没有测量真实世界快照的构建、序列化与传输成本。worker 返回输入及完整 proof bundle 的 bytes 和摘要。冷启动至 ready 为 344.5348 ms；返回结果的序列化、传输与父侧接纳均计入已报告的端到端时间。

容量 1 队列按顺序提交：上一个作业收到并完成接纳后，才提交下一个作业，没有队列积压。本轮未叠加持续 20 Hz 控制负载，也未叠加接纳与控制线程争用 Python 解释器执行权的 GIL 竞争。这里测量的是固定 fixture 下逐个准备作业的成本，不能外推为真实世界快照与并行控制负载下的交付期限。

提交至收到 bytes 的 ≤50／≤100 ms 比例为 0.0%／100.0%；提交至可信可用的比例为 0.0%／87.5%。这些比例仅报告，不设置未预登记的 worker 硬门槛。

正常完成、构造器失败、父侧异常及 worker 内部准备失败四条路径均调用 close，退出码均为 0；结束时活进程为 0。close 支持重复调用。构造器在 ready 前异常时也会清理已经创建的队列与进程。行为只消费计数、输入和有类型事实；墙钟仅测量，等待只用于作业轮询节拍及有界退出，不根据耗时选择输入或接纳旧结果。
