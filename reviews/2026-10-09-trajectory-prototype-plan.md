# 原型方案：连续短轨迹搜索（TP）

日期：2026-10-09。状态：三方建议，供项目方决定是否立项。达标后的完整方案见 [连续轨迹架构方案](2026-10-09-trajectory-architecture.md)。

## 1. 结论

用一个隔离的原型回答一个问题：

> 把“走进去、起跳、空中、落地、继续跑”当作一条完整的短轨迹来搜索，能不能在成功率不降的前提下，消除动作衔接处的停顿和交接失败，并且满足控制期限？

原型不接入正式导航链，不修改 Session、Runtime 和现有动作代码。时间盒为两周，代码量上限约 2,500 行。达标后再按完整方案分阶段接入；不达标就记录原因，主线继续按 F2-REC 推进。

## 2. 背景

现在的结构是：规划器在格心之间找路，每种动作有自己的控制器和严格的入口窗口，例如 JumpUp 要求速度 ≤ 0.1 b/s、朝向误差 ≤ 2°。前一个动作要把身体送进下一个动作的入口窗口，衔接点就成了缝。最近的问题几乎都出在这些缝上：

- 终点停不准，墙角卡住；
- 走跳交接：走路不会转头（D1），预计入口求解被拒后取消整条路线（D2）；
- 入口要求接近停稳，所以每次跳跃之前都必须先停下。

原型要验证的思路是：不再切成动作再拼接，而是从当前真实运动状态出发，搜索一条连续的短轨迹。速度延续和落地接续都是搜索结果的一部分，不需要专门的交接规则。

## 3. 范围

### 3.1 包含

- 能力：Walk、Sprint、转向、上一格（JumpUp）、跨 1—3 格坑（JumpGap）、半砖或台阶上下，以及它们的连续组合；
- 已知世界：使用 Runtime 的正式观察世界模型，UNKNOWN 不能当 AIR；
- 运行环境：仿真 Runtime 链（`tests/sim`，带输入账本和晚到模型），最后用少量 Fabric 实机抽查；
- 全局路线：调用现有支撑面规划器取得节点路径，作为局部搜索的引导。

### 3.2 不包含

- 受控下降超过 1 格、潜行、爬行、游泳、攀爬、疾跑跳以外的特殊动作；
- 未知探索、动态避障、战斗中的移动；
- 修改 NavigationSession、ExecutionSupervisor、PlanningCoordinator、Runtime 生命周期或输入仲裁；
- 替换任何正式代码路径。

## 4. 设计

### 4.1 核心概念

| 概念 | 含义 |
|---|---|
| 轨迹 | 每 tick 一条命令（`MovementV1` 加目标朝向），以及计算器预测的每 tick `PhysicsState` |
| 地面段 | 身体在已知支撑上，随时可以松键并安全停下 |
| 承诺段 | 从起跳那一 tick 到落地后稳定在支撑上，中途不能放弃 |
| 承诺点 | 承诺段的第一个 tick，也就是起跳或离开支撑面的那一 tick |
| 可恢复终态 | 落在已知支撑上，并且从这里开始的中性停止尾迹安全 |
| 引导 | 全局路线给出的支撑面节点序列，以及沿路线的剩余代价 |

### 4.2 不变式（替代入口窗口）

1. 选出的轨迹，结束状态必须是可恢复终态。
2. 地面段中的每个 tick，如果此刻松键，中性停止尾迹都必须安全。这就是 F2 已有的停止尾迹检查。
3. 承诺段必须在两种输入时序下都安全落到已知支撑上：按时生效，以及晚一 tick 生效。
4. 承诺点那一 tick，用当前真实状态重新验证整段承诺轨迹。验证失败就不起跳，按地面段的停止尾迹安全减速。
5. 轨迹经过的格子，以及停止尾迹扫过的格子，都不能是 UNKNOWN、危险材质、流体或未支持形状。
6. 任何影响选择的逻辑都不读墙钟。预算只按节点数和物理步数计算。

这几条保证的效果，与现在的入口窗口加动作证明相同：不可逆的动作开始前，身体已经有安全的退路。区别在于它不再要求“停稳再跳”。

### 4.3 运动基元

搜索空间不是逐 tick 的按键组合，而是少量带参数的基元：

| 基元 | 参数 | 说明 |
|---|---|---|
| RUN | 朝向、是否疾跑、持续 tick 数 1—12 | 沿一个方向加速或保持 |
| TURN | 目标朝向、转向 tick 数 | 跑动中改变朝向和移动方向 |
| BRAKE | 持续 tick 数 | 松键减速，可带少量反向键 |
| JUMP | 起跳前保持 tick 数、空中是否保持前进或疾跑、空中侧移 −1/0/1 | 跨坑和上一格都用它 |
| WALK_OFF | 朝向 | 走下 1 格以内的边 |

**预计算。** 在完整方块构成的平地上，Minecraft 的运动对平移不变，只取决于速度、朝向和输入。所以可以对“起始速度档 × 朝向档 × 基元参数”离线算出无碰撞时的相对轨迹，存成表。

在线使用时，把相对轨迹平移到当前位置，用扫掠盒对照世界做碰撞和支撑检查，代价远低于逐 tick 调用计算器。

**不能查表的情况必须在线计算。** 半砖、台阶，以及扫掠检查发现身体会接触碰撞体的位置，都改用 1.21 计算器在线计算。

### 4.4 局部搜索

- **起点**：后台 worker 从“当前状态往后推 L tick 的预测状态”开始搜索。L 是输入延迟估计，初值为 2。
- **时域**：取 40 tick，或者到越过下一个承诺段、落地后再跑 10 tick为止，两者取较长。
- **算法**：在基元序列上做束搜索，束宽和展开节点数都有固定上限，例如束宽 32、最多 2,000 个节点。
- **热启动**：先把上一条轨迹剩余部分平移重放，作为初始最优解；后续候选只有在代价更低时才能替换它。
- **代价**：
  - 时间：以 tick 计；
  - 剩余代价：取终态最近的引导节点，用其“剩余路线长度 ÷ 疾跑速度”计算；
  - 安全余量惩罚：离边缘和危险方块越近惩罚越大；
  - 停顿惩罚：每出现一次速度低于 0.5 b/s 就加罚。
- **剪枝**：先用便宜的几何规则排除候选，例如坑宽超过 4 格、落点没有支撑、头顶净空不足，再调用计算器。
- **输出**：最优轨迹，附带承诺点位置、两种时序的验证结果、依赖格子和搜索统计。

### 4.5 控制线程（每 tick）

1. 读取 `StateAnchor`，与当前轨迹在本 tick 的预测状态比较。
2. 偏差在容差内（地面上位置 ≤ 0.05、速度 ≤ 0.05 b/t）：发出轨迹在本 tick 的命令和朝向。
3. 地面上偏差超过容差：
   - 如果有新到达的后台轨迹，并且它的起点与当前状态一致，就切换到新轨迹；
   - 否则发出安全减速命令，即停止尾迹已验证的中性或刹车输入，并请求重新搜索。
4. 即将进入承诺点：用当前真实状态，按两种时序重新验证承诺段。这次验证约 25—35 个计算器 tick。通过才起跳，否则按第 3 步减速。
5. 处于承诺段中：继续执行承诺命令，并按现有方式承担落地责任。偏差超出模型时，按现有空中恢复规则处理。
6. 每一帧控制线程最多调用 20 个计算器 tick，承诺点验证那一帧除外。

### 4.6 与现有代码的关系

**复用：**

- 1.21 计算器 `physics_1_21.step`；
- `PhysicsWorldView`、`WorldQueryCache`；
- `StateAnchor` 和 `InputApplicationLedger`；
- 晚到模型；
- 支撑面规划器，只用来取节点路径；
- Motion worker 的进程和身份机制。如果在原型里接入成本太高，就先在模拟中按真实延迟交付；但必须记录 tick 延迟，不能同步计算后当作零延迟。

**新增（只放在原型目录 `mc2p/motion_nav/proto_trajectory/` 和对应测试中）：**

- `primitives.py`：基元定义和离线表生成；
- `trajectory.py`：轨迹和验证结果类型；
- `local_search.py`：束搜索；
- `tracker.py`：控制线程跟踪与承诺点验证；
- `driver.py`：一个按 Runtime 有序输入源接入的原型驱动，结构参照 follow 和 melee 驱动的接入方式。

**不修改：** `mc2p/motion_nav/` 下的现有文件、Session、Runtime。

## 5. 场景

每个场景族都覆盖四个方向、三种时序（正常、首条晚一 tick、每条命令 20% 概率晚一 tick），以及两种起始速度（静止、已在疾跑）。第三种时序是项目连续高度矩阵和 v7 产品集已经使用的口径；[交接修复审查](2026-10-09-handoff-repair-review.md) 发现只取前两种会漏掉动作缝上的问题，所以补上。

| 编号 | 场景 | 目的 |
|---|---|---|
| S1 | 跑上半砖后跨 1 格坑，落地继续跑 3 格 | 你举的例子：高度变化加跨坑，速度延续 |
| S2 | 转 90° 后上一格，转弯点在入口前 1、2、3 格 | 覆盖 D1 |
| S3 | 助跑 3 格、5 格后跨 2 格和 3 格坑 | 疾跑跳和起跳时机 |
| S4 | 上一格后紧接着跨 1 格坑 | 两个承诺段相邻 |
| S5 | 下楼梯后接着跨坑 | 下降与起跳衔接 |
| S6 | v9 柱顶 24 项 | 与 F2-REC 直接对比 |
| S7 | 杂乱地形长路线（v8 杂乱层中含高差的子集，约 100 项） | 一般情况下不退步 |
| N1 | 4 格宽坑（跳不过去） | 必须拒绝 |
| N2 | 落点是岩浆块，或落点 UNKNOWN | 必须拒绝 |
| N3 | 坑上方净空不足 | 必须拒绝或改走别的路线 |
| N4 | 承诺点前一 tick 落点被移除 | 必须放弃起跳并安全停下 |
| N5 | 承诺段中被外力推偏 | 按现有空中恢复处理，零伤害 |

**对照组：** 同一组场景，用现有正式链（`02bc4c4` 或 F2-REC 最新签署版本）各跑一遍。

**参照时间：** 对每个正例，用不受时间限制的离线穷举（全知世界，仅用于评分）求出最短完成时间，作为“理想用时”。

## 6. 指标

| 指标 | 定义 |
|---|---|
| 成功率 | 完成原 `GoalState`，零安全事件 |
| 衔接停顿 | 从出发到终点前 10 tick，水平速度低于 0.5 b/s 的连续段数 |
| 用时比 | 实际完成 tick ÷ 理想用时 |
| 控制线程耗时 | 每帧 production 耗时的 P50、P95、P99、最大值，单独报告承诺点验证帧 |
| 后台搜索耗时 | 每次搜索的 P50、P95、最大值，以及展开节点数、计算器 tick 数 |
| 交付延迟 | 后台轨迹从请求到可用的 tick 数 |
| 重规划次数 | 地面偏差触发的重搜，以及承诺前放弃起跳的次数 |
| 确定性 | 同一输入重复 3 次，命令序列逐 tick 相同 |
| 安全 | 掉落、伤害、危险接触、UNKNOWN 接触、终态潜行均为 0 |

## 7. 阶段

| 阶段 | 内容 | 产出 | 预计 |
|---|---|---|---|
| P0 | 冻结场景、对照组结果和理想用时；在 Windows 测量计算器单 tick 耗时 | 场景清单、基线表 | 1—2 天 |
| P1 | 开环：在全知世界里，只用计算器验证局部搜索能否找到轨迹，不涉及执行 | 每个正例的轨迹、搜索耗时 | 3—4 天 |
| P2 | 闭环：原型驱动接入仿真 Runtime，带输入账本、晚到和后台延迟 | 第 6 节全部指标 | 4—5 天 |
| P3 | Fabric 抽查：S1、S2、S3 各四个方向，正常和晚一 tick 各一次，共 24 次 | 实机结果 | 1—2 天 |
| P4 | 汇总报告和是否立项的建议 | 报告 | 1 天 |

每个阶段结束都检查止损条件（第 9 节）。

## 8. 达标标准

| 类别 | 门槛 |
|---|---|
| 正例成功率 | S1—S6 的冻结正例全部完成；S7 不低于对照组，旧成功退步为 0 |
| 负例 | N1—N5 全部安全拒绝或有界结束，零安全事件 |
| 衔接停顿 | S1、S3、S4 为 0；S2 只允许转弯处 1 段 |
| 用时比 | S1、S3、S4 的中位数 ≤ 1.15，P95 ≤ 1.30 |
| 控制线程 | Windows production P95 ≤ 8 ms、P99 ≤ 15 ms、最大值 < 30 ms，承诺点验证帧也包括在内 |
| 后台搜索 | P95 ≤ 150 ms，最大值 ≤ 400 ms；需要承诺的轨迹，交付时距承诺点至少还有 3 tick |
| 晚一 tick | 首条晚一 tick 与正常时序成功率相同；20% 随机迟到下不低于对照组，零安全事件 |
| 确定性 | 全部场景的命令序列逐 tick 一致 |
| 规模 | 原型代码 ≤ 2,500 行，不含测试 |
| Fabric | P3 的 24 次全部完成，零安全事件 |

## 9. 止损

出现以下任一情况，就停止原型并写报告：

- P1 结束时，S1—S4 有任何一族开环找不到轨迹，并且原因不是场景本身不可行；
- P2 的控制线程耗时，在两轮优化后仍超过门槛；
- 后台搜索的 P95 两轮优化后仍超过 300 ms；
- 必须修改 Session、Runtime 或现有动作代码才能继续；
- 代码量超过 3,500 行；
- 两周时间盒用完。

停止不等于失败：报告要写清楚卡在哪一步，这本身就能为“现有结构是否必要”提供证据。

## 10. 与 F2-REC 的关系

- F2-REC 继续推进。R2 按“不劣于 R0 基线”的口径签署，R3、R4 照常进行，主线保持全绿。
- 原型隔离开发，不进入主线，不影响 F2-REC 的量尺。
- 走跳交接的 D1 和 D2 先不在旧结构里修。原型达标，就由新结构解决；原型不达标，再按 [F2-REC 分析](2026-10-09-f2rec-review.md) 第 4 节的局部修复处理。
- 如果产品上急需柱顶类目标，可以只做 D1（接近时转头）。它的代价很小，不影响原型的结论。

## 11. 证据边界

- 计算器单 tick 约 130 µs 是 Linux 上的测量结果，Windows 需要在 P0 重测。
- 平移不变只对完整方块的平地和空中段成立。半砖、台阶和接触碰撞体的情况必须在线计算。
- 原型通过只说明这条路线可行，不等于正式能力已经交付。
