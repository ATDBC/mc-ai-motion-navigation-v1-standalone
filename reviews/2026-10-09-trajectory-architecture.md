# 方案：原型达标后的连续轨迹架构

日期：2026-10-09。状态：三方建议。本方案只在 [连续短轨迹原型](2026-10-09-trajectory-prototype-plan.md) 达标后才生效；原型未达标时，本文只作为参考，主线继续按 F2-REC 和 [F2-REC 分析](2026-10-09-f2rec-review.md) 第 4 节推进。

## 1. 结论

如果原型达标，建议把运动导航的执行部分从“按动作拼接”改为“全局拓扑加局部连续轨迹”，分三层：

| 层 | 职责 | 频率 | 位置 |
|---|---|---|---|
| 全局路线 | 在支撑面图上找拓扑路线，给出经过哪些支撑面、剩余代价 | 目标或世界变化时 | 后台规划 worker（现有） |
| 局部轨迹 | 从当前真实状态出发，搜索 1—3 秒内的连续短轨迹，跨越动作边界 | 偏差或新信息时，通常每几 tick 一次 | 后台运动 worker（现有进程，新内容） |
| 跟踪与承诺 | 每 tick 跟踪轨迹，起跳前用真实状态验证，偏差时安全减速 | 每 tick | 控制线程 |

原则只有三条：

1. **动作不再是执行单位。** 规划图上的边仍然有动作类型，用来判断拓扑上走不走得通。但执行的是轨迹，不是动作。入口窗口、交接规则和每种动作单独的控制器逐步退役。
2. **安全靠承诺点，不靠停稳。** 起跳之前，身体随时可以安全停下；起跳那一刻，用真实状态验证整段空中轨迹，必须落在已知支撑上，而且落地后仍可安全停下。
3. **只有一种轨迹表示。** 搜索、跟踪、承诺验证、证据记录都使用同一条“逐 tick 命令加预测状态”的轨迹。

不变的部分：Runtime、输入仲裁、`StateAnchor`、输入账本、晚到模型、1.21 计算器、支撑面图、`GoalState` 与完成区域、观察世界模型与 UNKNOWN 规则、外部运动检测。

迁移分四个阶段（T1—T4），每个阶段都保持主线全绿、旧成功零退步；新旧链在 T3 之前并存，由同一组量尺比较。

## 2. 为什么是这个形状

现在的困难大多不是任务本身带来的，而是结构带来的：

- **入口窗口要求近乎停稳。** 速度 ≤ 0.1 b/s、朝向误差 ≤ 2°，所以每次跳跃前都要停，衔接点就是一条缝；
- **三种表示。** 规划器的格心路线、动作控制器的局部目标、运动求解的物理状态，三者之间需要翻译，每次翻译都可能不一致；
- **每一步都要证明。** 每个动作单独证明，证明之间的衔接又要额外证明。

连续轨迹把这三个问题合成一个：从当前状态出发，找一条安全、连续、能接上全局路线的轨迹。速度延续、转头、起跳时机都成为搜索变量，不再需要规则。

这和成熟机器人系统的做法一致：全局规划管拓扑，局部规划管动力学，控制器只管跟踪。

## 3. 模块与状态归属

```text
GoalState ─→ NavigationSession ─→ 全局路线（支撑面路径 + 剩余代价场）
                    │                       │
                    │                       ▼
                    │            TrajectoryPlanner（后台）
                    │              输入：预测起点、引导、世界快照、视角约束
                    │              输出：TrajectoryV1
                    ▼                       │
            TrajectoryExecutor（控制线程）◀─┘
              跟踪 / 承诺验证 / 安全减速
                    │
                    ▼
            ActionArbiterV1（唯一输入出口）
```

| 状态 | 唯一拥有者 | 其他模块怎样使用 |
|---|---|---|
| 目标、任务生命周期、完成判断 | NavigationSession | 只读 |
| 全局路线和剩余代价场 | 规划协调（现有 PlanningCoordinator） | 局部搜索只读快照 |
| 当前轨迹、承诺状态、跟踪偏差 | TrajectoryExecutor | Session 只收到事件：进行中、已承诺、需要重规划、已完成、失败 |
| 搜索请求和结果身份 | 运动协调（现有 MotionRouteCoordinator 演变而来） | 执行器只收已通过身份检查的结果 |
| 输入应用、晚到记录 | `InputApplicationLedger` | 只读 |
| 视角所有权 | 动作仲裁 | 局部搜索按约束取朝向，不自行占用 |

Session 不增加状态。它看到的执行器接口比现在更简单：不再关心当前执行到第几个动作、入口是否满足，只关心“轨迹层是否还能朝目标前进”。

## 4. 轨迹

### 4.1 表示

`TrajectoryV1` 是不可变值：

- 起点：预测状态 `PhysicsState`、预测起点 tick、所依据的锚点身份；
- 逐 tick 的条目：命令（`MovementV1`）、目标朝向和俯仰、预测状态、该 tick 是地面段还是承诺段；
- 承诺段列表：每段的开始和结束 tick、落地支撑面、两种时序的验证摘要；
- 终态：可恢复终态的证明摘要，即中性停止尾迹；
- 依赖：轨迹和停止尾迹扫过的格子与支撑面身份；
- 引导：本轨迹对应的全局路线身份和终点剩余代价。

### 4.2 不变式

1. **可恢复终态**：轨迹的最后状态在已知支撑上，从这里松键的停止尾迹安全。
2. **地面段可停**：地面段的每个 tick，此刻松键的停止尾迹都安全。
3. **承诺段双时序安全**：每个承诺段在按时和晚一 tick 两种时序下都落在已知支撑上，落地后满足第 2 条。
4. **承诺前重验**：进入承诺段之前，必须用当前真实状态重新验证该段，失败就不进入。
5. **依赖完整**：轨迹依赖的格子都已知，且不是危险、流体或未支持形状。
6. **确定性**：同样的起点、世界快照、引导和预算，得到逐 tick 相同的轨迹。预算只按节点数和计算器 tick 数，不读墙钟。
7. **连续性**：新轨迹替换旧轨迹时，新轨迹的起点必须与当前状态一致（在容差内），承诺段中不允许替换。

第 2、3、4 条合起来，就是现有入口窗口加动作证明所保证的安全性：不可逆的事情发生前，身体总有退路。

### 4.3 动作类型的去向

规划图上的边仍然带动作类型（Walk、JumpUp、JumpGap、ControlledDrop、Step），用于：

- 拓扑可达判断：这条边原则上能不能走；
- 剩余代价估计；
- 局部搜索的提示：在这条边附近优先尝试 JUMP 类基元。

但执行时不再按边切换控制器。一条局部轨迹可以覆盖多条边，也可以选择与全局路线略有不同的落点，只要终态能接上全局路线。

## 5. 局部搜索

### 5.1 输入

- 预测起点：当前锚点按输入账本中已发出但未生效的命令推进 L tick，L 来自晚到模型，通常为 1—2；
- 世界快照：观察世界模型的只读视图，带版本；
- 引导：全局路线和沿路线的剩余代价场；
- 视角约束：朝向是否可由导航决定。战斗占用视角时，朝向固定为当前值或战斗给出的值；
- 热启动：上一条轨迹的剩余部分；
- 预算：最大展开节点数、最大计算器 tick 数。

### 5.2 搜索空间与方法

- 基元：RUN、TURN、BRAKE、JUMP、WALK_OFF，参数见原型方案第 4.3 节；能力扩展时增加基元，而不是增加控制器；
- 完整方块平地和空中段使用离线基元表，平移后做扫掠碰撞；半砖、台阶、接触碰撞体的段落使用计算器在线计算；
- 束搜索，固定束宽和节点上限；先用几何规则剪枝；
- 代价：用时、终点剩余代价、安全余量、停顿惩罚、转向幅度；
- 热启动解作为初始最优，新解必须更好才替换。

原型如果证明其他搜索方法更合适，例如采样加局部优化，只需要替换搜索内部，接口不变。

### 5.3 输出与失败

搜索结果分四类，必须分别表达（对应 AGENTS.md 第 5 节）：

| 结果 | 含义 | 执行器的处理 |
|---|---|---|
| FOUND | 找到满足不变式的轨迹 | 起点一致就替换 |
| NO_TRAJECTORY_IN_BUDGET | 预算内没找到，不代表不可行 | 继续当前轨迹的地面段，到承诺点前仍无新解就安全减速并重搜 |
| BLOCKED | 几何上证明从此起点无法接上引导，例如坑太宽、落点 UNKNOWN | 通知 Session 需要全局重规划 |
| STALE | 起点、世界版本或引导身份已过期 | 丢弃 |

## 6. 跟踪与承诺

每 tick，控制线程：

1. 取得 `StateAnchor`，与当前轨迹在本 tick 的预测状态比较；
2. 若有新的 FOUND 结果，并且起点与当前状态一致、当前不在承诺段中，就替换轨迹；
3. 地面段偏差在容差内：发出本 tick 的命令和视角；偏差超出：发出安全减速命令，并请求重搜；
4. 下一 tick 进入承诺段：用当前真实状态，在两种时序下验证承诺段，通过才发出起跳命令；不通过就减速并重搜；
5. 承诺段中：发出承诺命令；偏差超出模型时，交给外部运动恢复（C1-C 的 `ExternalMotionRecoveryController`）；
6. 记录本 tick 的轨迹身份、偏差和决定，作为证据。

**偏差容差**：取跟踪误差能被下一次重搜吸收的范围，由原型测量后写入配置，不在本方案里拍定。

**控制线程预算**：普通帧计算器调用 ≤ 20 tick；承诺验证帧约 25—35 tick × 2 种时序。原型需要证明后者在 Windows 上也满足 8/15/30 ms；不满足时，承诺验证可以提前 1—2 tick 在后台按预测状态做一次，控制线程只验证“真实状态与预测状态的差在已验证的容差内”。

**快速控制器**：地面段远离边缘时，可以用便宜的比例跟踪代替逐 tick 计算器预测，但它跟踪的必须是同一条轨迹，偏差判断也用同一个容差。不能出现快速控制器和完整验证各自追各自目标的情况。

## 7. 视角

- 朝向是搜索变量，视角是轨迹输出的一部分；
- 地面移动按本帧最终视角计算世界坐标下的移动（B12-B 已有），所以转头和移动可以同时进行；
- 战斗占用视角时：导航提交视角约束（固定朝向或可接受范围），局部搜索在约束内找轨迹。需要特定朝向才能完成的承诺段，例如疾跑跳，必须在约束内找到解，找不到就不承诺；
- 视角仲裁沿用 `ActionArbiterV1` 的优先级，不在导航里新增仲裁。

## 8. 与战斗和跟随

- **跟随**：跟随目标修订时只更新 `GoalState` 和全局路线；局部轨迹按新引导重搜，热启动保留速度。现在“修订帧要同时做跟随更新和导航准备”的时间大头，有一部分是动作路线的重建；轨迹层下，修订只触发一次后台搜索。
- **近战移动目标（C1-B）**：目标在动时，引导是“到目标附近的完成区域”，局部轨迹的终点代价改为到预测目标位置的距离。攻击时机仍由战斗驱动决定，导航只保证移动合法、连续。
- **受击（C1-C）**：外部运动由现有检测器发现；地面段偏差直接触发重搜，承诺段中按现有空中恢复处理。统一外部运动的决定（0017）不变。

## 9. 退役与保留

| 现有部分 | T4 之后 |
|---|---|
| 入口窗口（`_action_entry_window`、`segment_entry._fits`） | 退役，由承诺前重验代替 |
| 交接规则、`handoff_entry_window` | 退役 |
| `FixedRouteController` 的格心跟踪 | 退役，由轨迹跟踪代替 |
| JumpUp、JumpGap、ControlledDrop 各自的控制器 | 退役；它们的物理参数和校准数据转为基元与验证用例 |
| JumpGap 的单动作求解 | 演变为局部搜索：起点从入口窗口扩展到当前运动状态，终点扩展到落地继续跑 |
| `LocalAttemptChain` 和重试预算 | 由“FOUND／NO_TRAJECTORY_IN_BUDGET／BLOCKED／STALE”代替，不再计数取消 |
| `VerifiedMotionExecutor` | 保留其“按已验证命令序列执行、观测确认”的语义，作为承诺段执行的内核 |
| 支撑面图、A*、`RouteAdmitter` | 保留，接纳对象从动作路线改为全局路线 |
| `GoalState`、完成区域 | 保留 |
| 计算器、锚点、账本、晚到模型 | 保留 |
| 外部运动检测与恢复 | 保留 |
| 证据格式 | 新增轨迹身份和偏差字段；旧证据不改写 |

退役只在对应能力的新实现通过全部量尺之后进行，并按 AGENTS.md 先确认没有现行入口和证据依赖。

## 10. 迁移阶段

### T1：轨迹执行器接入，只覆盖地面

- 内容：
  - 正式实现 `TrajectoryV1`、局部搜索（只有 RUN、TURN、BRAKE）、TrajectoryExecutor；
  - 对 Session 提供与现有执行器相同的事件接口，通过 Runtime 配置选择新旧执行链；这是迁移期唯一的选择项，T4 删除。
- 门槛：
  - v7、F2 528、v8 纯地面子集：旧成功零退步；
  - 终点停准：完成区域内的停止成功率不低于旧链；
  - 控制线程 production P95 ≤ 8 ms、P99 ≤ 15 ms、最大值 < 30 ms；full 最大值 < 50 ms，deadline miss 0；
  - 确定性：重复 3 次逐 tick 一致；
  - Fabric：直线、转弯、墙边各四个方向。

### T2：加入承诺段

- 内容：JUMP、WALK_OFF 基元，承诺前重验，双时序验证。
- 门槛：
  - 原型 S1—S6 全部正例，加上 v7 和 F2 528 的全部高度变化用例；
  - N1—N5 全部安全；
  - 衔接停顿和用时比达到原型门槛；
  - 晚一 tick 与正常时序成功率相同；
  - Fabric：S1、S2、S3、S4，四个方向，两种时序。

### T3：跟随和战斗接入

- 内容：跟随和移动目标近战改用轨迹链；视角约束接入。
- 门槛：
  - C1-A、C1-B、C1-C 的正式验收用例全部通过；
  - 跟随修订帧 P95、P99 不劣于 R0 基线，并争取进入 8 ms；
  - 战斗占用视角时零放宽：没有违反朝向约束的承诺段。

### T4：退役旧链

- 内容：删除入口窗口、交接规则、格心跟踪器、各动作控制器和新旧链选择项；更新四类文档。
- 门槛：
  - 全部量尺再跑一遍，结果与 T3 一致；
  - 生产代码净减少，目标是减少的行数不少于新增的行数；
  - Windows 完整正序、逆序全绿。

每个阶段都遵守 D089：两轮内没过门槛就停下来写报告，不在同一阶段叠加子阶段。

## 11. 性能预算

| 项目 | 预算 |
|---|---|
| 控制线程普通帧 | 计算器调用 ≤ 20 tick；production P95 ≤ 8 ms、P99 ≤ 15 ms、最大值 < 30 ms |
| 承诺验证帧 | 同上；超出时改为后台预验加控制线程容差检查（第 6 节） |
| 局部搜索 | 每次 P95 ≤ 150 ms、最大值 ≤ 400 ms；按节点数和计算器 tick 数限额 |
| 搜索频率 | 只在偏差、新信息、引导变化或剩余轨迹不足 20 tick 时触发；平稳跑动时每秒不超过 2 次 |
| 内存 | 基元表 ≤ 20 MB |

所有数字以 Windows 正式机测量为准；Linux 只用于量级判断。

## 12. 风险

| 风险 | 表现 | 应对 |
|---|---|---|
| 搜索不够快 | 承诺点前拿不到新解，频繁减速 | 热启动；提前触发；剩余轨迹不足时优先搜索；仍不够就降低时域 |
| 计算器与游戏不一致 | 承诺段落点偏 | 承诺段已有双时序验证；落地偏差纳入证据，定期与 Fabric 对比；不一致时收紧安全余量而不是放宽验证 |
| 基元表覆盖不足 | 某些地形一直在线计算，变慢 | 统计在线计算比例；对高频形状增加离线表 |
| 局部最优 | 局部轨迹接不上全局路线，来回摆动 | 终点代价来自全局剩余代价；BLOCKED 时让全局重规划；增加摆动检测作为失败类型 |
| 迁移期双链 | 维护成本、行为不一致 | 选择项只在 T1—T3 存在；同一量尺同时跑两条链；T4 必须删除 |
| 再次过度工程化 | 子阶段、证明层层叠加 | 每阶段一个可验收行为；代码量随阶段报告；T4 必须净减少 |

## 13. 需要记录的决定

原型达标、项目方决定采用时，建议新增以下决定：

1. 执行单位从动作改为轨迹，规划图的动作类型只用于拓扑和代价；
2. 安全模型：承诺点、可恢复终态、承诺前用真实状态重验，替代入口窗口；
3. 搜索预算只按节点数和计算器 tick 数，不读墙钟；
4. 视角是轨迹输出，战斗占用时作为约束；
5. 迁移期新旧链并存的期限和删除条件；
6. 0012（B10 分步接入动作求解）和 0014 中与入口窗口相关的条款，标为被新决定取代，正文保留。

## 14. 证据边界

- 本方案依赖原型的结论。原型的指标、容差和预算以原型报告为准；本文的数字是起始建议。
- 本文没有实现，也没有在 Fabric 上验证。
- 对现有代码的描述来自 `02bc4c4` 及之前的阅读；实施前需要按当时主线重新核对。
