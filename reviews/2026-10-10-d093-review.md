# 审查：D093 入口随机迟到小批次（19231c6），以及 H-02 的修正方案

日期：2026-10-10。对象：`main` 上的 `19231c6`。复现脚本、输出和原型补丁在 [2026-10-10-d093-review/](2026-10-10-d093-review/)。

## 1. 结论

**这一批可以接受。**

- H-01 的刹车修正与我上轮的原型一致，又加了完成区域和支撑两项保护。100 种子下，四个正例族的成功分别从 37、47、74、84 提高到 100、100、99、100，旧成功退步为 0。
- H-02 只改了分类，原因用已有的 `StopCause.INPUT_LOST` 传给任务报告，没有新增状态。
- 证据写得诚实：Fabric 新门槛没过，就保留原始失败，没有改夹具凑数。

**H-02 不需要新机制就能修，原型补丁共 3 个文件、净增 31 行。** 需要改两处：

1. **执行器：把“末次动作失联、已着地、未到目标”交给现有的重规划路径。**
   - 执行器已经有类型化状态 `NEEDS_REPLAN`。Session 收到它，会走 `request_recovery(destination=REPLAN)`，受任务级 `RetryLedger` 约束，额度用完就以失败结束。
   - 运动协调器在落地后返回 `NEEDS_REPLAN`（`landed_entry_requires_reanchor`），已经是同样的用法。
   - 只改这一处，落点格两族（8 种子）就从 3/8、3/8 提高到 6/8、4/8。
2. **同面直连：不再要求“已经站着的起点”也满足 0.5 的支撑余量。**
   - 剩下的失败全部是 `same_support_local_path_unavailable`。身体落在 x≈2.82，只有 20% 的脚掌在方块上。
   - 同面直连的连接检查从起点开始，每 0.1 格取一次样，每个样点都要求支撑 ≥ 0.5，起点本身也算在内，所以整条连接被判 `BLOCKED`。
   - 原型只在 `admit_local_direct` 这一处、且身体着地时放宽：支撑低于 0.5 时，只要求沿途不下降；达到 0.5 以后恢复原门槛。终点仍要求 ≥ 0.5。

100 种子结果：

| 族 | `19231c6` | 原型 | 旧成功退步 |
|---|---:|---:|---:|
| 柱顶落点格，需要转弯 | 41 | **99** | 0 |
| 柱顶落点格，已经对准 | 35 | **99** | 0 |
| 柱顶外角，需要转弯 | 100 | 100 | 0 |
| 柱顶外角，已经对准 | 100 | 100 | 0 |
| 转弯后上一格 | 99 | 99 | 0 |
| 转弯后下一格 | 100 | 100 | 0 |

`19231c6` 一列与项目公开的 `round2-random100` 证据一致。落点格两族我在 Linux 上重跑过，200 项的结果、原因和 tick 数与公开的 Windows 证据逐项相同。原型一列来自 Linux，零伤害、零违规；剩下的 3 次失败都是原来就失败的 `motion_unsolvable:needs_state`。

**建议把 H-02 的修正作为一个新的小批次（D094），不要等连续轨迹原型。** 理由：

- 改动小，全部落在现有职责内：执行器只是换用一个已有的状态，Session 和规划器没有新增字段、等待或作业类型；
- 原型要两周，而且可能止损；
- “站到那个方块上”是最常见的指令之一。在 20% 随机迟到下，落点格目标现在约六成失败（41/100、35/100 成功）。

**Fabric 的 HANDOFF-FABRIC-01 是门槛定义的矛盾，不是机器人的问题。**

- Runtime 给没有显式窗口的输入一律记成“只能在请求的那一 tick 生效”。
- 夹具又把任何晚于这一 tick 的生效都算作 `input_deadline_miss`。
- 所以在普通 Walk 上注入晚一 tick，按定义必然失败。

建议见第 5 节。

## 2. D093 代码审查

| 项 | 判断 |
|---|---|
| `stopping_fits_entry` | 与我的原型相同，另加三项保护：身体在完成区域内、支撑合格、速度置零时保留竖直分量。`entry_matches is False` 已经排除了没有入口窗口的情况，所以不会以 `None` 调用入口检查。没有问题 |
| `_final_action_failure_cause` | 只在最后一个动作经 INPUT_LOST 落地推进时设置，其余路径都会清掉。`failure_cause` 只在 `FAILED` 时输出。没有问题 |
| `NavigationSessionReport.failure_cause` | 取自 `_last_decision`。换路线时 `_last_decision` 会被清空（第 3959 行），不会带上旧路线的原因 |
| 第一轮改成 `ActionRouteState.INPUT_LOST` 后撤回 | 判断正确。Session 对 INPUT_LOST 走的是 `destination=FAIL` 的恢复，会多出一次入口恢复 |

一点意见：报告里的失败原因是从“最后一个执行器决策”读出来的，而不是 Session 自己的终态原因。按 D093 的范围，任务一定在这个决策上结束，所以结果正确。但采用第 3 节的修正后，任务可能经重规划额度用完才失败，那时最后一个决策是 `NEEDS_REPLAN`，原因会丢失。建议让报告优先读 Session 自己的终止请求（`_handoff.stop_request.cause`），再回退到执行器决策。

## 3. H-02 的修正

### 3.1 为什么用现有的 `NEEDS_REPLAN`

我考虑过三种做法：

| 做法 | 问题 |
|---|---|
| 规划器在严格动作后总追加一段收尾 Walk | 改动所有以严格动作结尾的路线，v7、F2、v9 的路线签名都会变；正常落地时也要多执行一段 Walk |
| 执行器自己生成一段补走的 Walk | Walk 需要执行契约、依赖和完成区域，这些归规划和接纳所有。执行器自己造路线，就越过了职责边界 |
| **执行器返回 `NEEDS_REPLAN`，由 Session 现有的恢复路径重新规划** | 只换一个已有状态。规划、接纳、执行契约仍由原来的所有者负责；次数由 `RetryLedger` 限定 |

**正常时序也离边界很近。** 柱顶落点格目标的完成区域是 x∈[3.3, 3.7]，正常时序下 JumpUp 落在 x=3.36，只在区域内 0.06 格。所以这个修正不只关乎迟到，任何让落点偏短几厘米的扰动都会走到同一条路径。

### 3.2 第一处：执行器

`_finish_goal()` 中，在 D093 新增的 INPUT_LOST 分支前面加一个条件：

```python
if (self._final_action_failure_cause is StopCause.INPUT_LOST
        and observed.status is ObservedGoalStatus.NOT_SATISFIED
        and frame.body.is_on_ground):
    self.state = ActionRouteState.NEEDS_REPLAN
    return self._result(started, MovementV1(), 1,
                        "input_lost_landing_requires_replan")
```

身体不在地面时，仍保留 D093 的 `FAILED` 加 INPUT_LOST。经 `_landed_on_current_action_destination` 推进时身体已经着地；保留这条分支，是为另一条确认路径（`confirm_observed_exit_after_input_loss`）兜底。

只改这一处时，落点格两族（8 种子）为 6/8、4/8，失败全部是 `same_support_local_path_unavailable`（[输出](2026-10-10-d093-review/h02-output.txt)）。

### 3.3 第二处：同面直连的起点

重新规划从身体当前位置到目标。起点和目标在同一个支撑面上，所以走 `RouteAdmitter.admit_local_direct()`。拒绝原因是：

```text
admit_local_direct (2.824, 65.0, 9.557) rejected current_body_cannot_connect
  phase=exact_connection  exact_status=blocked  selected_position=(3.5, 65, 9.5)
```

`standable_point_in_region()` 的连接检查从 `connection_from` 开始，每 0.1 格取一次样，每个样点都要求 `support_fraction ≥ 0.5`，包括 index 0，也就是身体此刻所在的位置。身体在 x=2.824 时，脚掌在方块上的部分是 (3.124−3.0)/0.6 ≈ 0.21，于是整条腿被拒。

**但这个位置是观察到的事实：身体已经着地站在那里。** 0.5 是规划选点用的余量，不是物理上能否站立的界限。从这里向内走，支撑只会单调增加。

原型规则（[proto-h02-replan.diff](2026-10-10-d093-review/proto-h02-replan.diff)）：

- 新增关键字参数 `observed_grounded_start`，默认 `False`，所以另外十多处调用的行为都不变；
- 只有 `admit_local_direct` 在 `frame.body.is_on_ground` 时传 `True`；
- 开启后，支撑低于 0.5 时只要求每个样点不低于前一个；一旦达到 0.5，之后都按原门槛；
- 终点仍按原规则要求 ≥ 0.5，净空扫掠、未知格和材料检查都不变。

[grounded_start_connection_check.py](2026-10-10-d093-review/grounded_start_connection_check.py) 在一个完全已知的 L 形平台上做组件检查（[输出](2026-10-10-d093-review/grounded-start-connection-output.txt)）：

| 腿 | 原规则 | 新规则 | 预期 |
|---|---|---|---|
| 从 20% 支撑的边缘向内（柱顶短落） | 拒绝 | 接受 | 接受 |
| 沿边缘先平行再向内 | 拒绝 | 接受 | 接受 |
| 从内部走向边缘 | 拒绝 | 拒绝 | 拒绝 |
| 从边缘出发、经过 L 形凹口（支撑先降后升） | 拒绝 | 拒绝 | 拒绝 |

执行层不变：Walk 控制器自己的支撑下限是 `FixedRouteConfig.minimum_support_fraction = 0.15`，候选验证和停止尾迹都照常运行。起点支撑低于 0.15 时，预期 Walk 会按原有停滞上限结束；这一点我没有单独构造场景验证，列入第 3.5 节的负例。

## 4. 是否推广到“正常落地但不在目标里”

D093 有意把正常动作结束后的“目标不满足”单独保留。第 3 节的修正也只覆盖 INPUT_LOST。

但从道理上讲，最后一个严格动作无论因为什么原因落在目标外，只要身体安全着地，都应该允许一次有界的重规划；落点离区域边界只有 0.06 格，本来就容易偏出。

建议 D094 先只做 INPUT_LOST，因为现有证据覆盖的就是这种情况。正常落地偏出登记为下一个问题，先用 Fabric 的落点分布判断它实际发生的频率，再决定要不要推广。推广前要检查 v7、F2 528 中以 `goal_state_not_satisfied` 作为预期结果的负例，确认它们不会因此改为成功或进入循环。

## 5. HANDOFF-FABRIC-01

**原因：**

- `PlayerRuntimeV1._submit_input_record()` 在没有执行窗口时，把 `latest_allowed_first_tick` 设为请求的那一 tick；
- `InputApplicationLedger.submit()` 的默认值也是这样；
- 夹具 `f2_ground_route_runtime.py` 对每一帧检查实际生效 tick 是否晚于 `latest_allowed_first_tick`，晚了就记为 `input_deadline_miss`，并判失败。

所以普通 Walk 输入在记录上被当作“精确到 tick”，而 `late_entry` 条件恰恰是在普通 Walk 上注入晚到。这两条放在一起，结论只能是失败，与机器人表现无关。南、西两个方向的身体行为是正确的：刹车、进入原入口、零伤害。

**这里需要项目方做一个定义上的决定：普通 Walk 是否承诺“晚一 tick 仍然安全”？**

| 选择 | 做法 | 代价 |
|---|---|---|
| A：不承诺（建议现在采用） | 夹具只把执行器声明了生效时刻的输入（严格动作、首条起步）计入 `input_deadline_miss`；普通 Walk 的晚到单独计数并报告，不作为失败 | 只改量尺。账本记录本身区分不了两者，因为严格动作的后续命令也是“精确到 tick”。要按执行器决策区分：`expected_movement_tick` 或 `verified_command_index` 不为空，就是声明了时刻的输入 |
| B：承诺 | 普通 Walk 每个候选的停止尾迹都要再验证“旧命令多执行一 tick”的情况，然后给它显式的 +1 窗口 | 控制线程的候选验证要多算一种时序；`InputApplicationLedger` 现在只允许单 tick 命令放宽窗口，还要改契约 |

仿真中 20% 随机迟到下，普通 Walk 一直靠逐帧重新观察来吸收偏差，大量量尺都是这样通过的。所以 A 符合现在的实际语义。B 等需要严格证明普通 Walk 的场景出现时再做。

**东、北没有注入成功**，是因为夹具要等身体进入完整入口位置才注入，而 H-01 让身体在此之前就开始刹车。建议改为按“离起跳的 tick 数”选择注入点，与仿真里的关键 tick 扫描用同一口径。
