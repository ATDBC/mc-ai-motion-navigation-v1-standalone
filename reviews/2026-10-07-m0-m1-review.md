# M0/M1 审查：M0 通过；M1 止损判定正确，但门槛是我定错的。下一步不单独做 M2

- 日期：2026-10-07
- 对象：`main` 上的 [`5124bd7`][new]（对照 [`e108a32`][old]）
- 对照：[中层重构总方案](2026-10-06-redesign-master-plan.md)、[下一步方案](2026-10-06-redesign-next-step.md)
- 复现材料：[`2026-10-07-m0-m1-review/`](2026-10-07-m0-m1-review/)

## 结论

**M0 合格，而且比计划多做了一件重要的事。** 后台规划不阻塞的检查已经恢复，并用两种变异证明有效；3 个死路径按调用计数变异后删除；量尺升级为 v2，统计范围比我的版本更完整。另外，我在 S0-R 审查中列为"未验证疑点"的问题被确认是真实缺陷（M0-C-01），并已修复：正式后端返回拒绝回执时，运行时仍为 READY，驱动器却单方面写成失败，Session 在地面和空中都还停在执行中。

**M1 的迁移本身做得好，按冻结门槛记为不通过也是对的；但那条门槛是我定错的。**

| 项目 | 结果 |
|---|---|
| Linux 复核 | 完整检查正序、逆序都是 1,531/1,531（比 Windows 记录的 1,528 多 3 项，是发布提交中新增的公开导出检查），共享场景哈希不变；五组集合与 Windows 的 M1 索引逐项一致：产品 2,000、协调 1,448、故障 16、跟随 10、世界变化 19 |
| 量尺：v2 口径 | 动作类型分支 79 → 42，受控下降 30 → 0 |
| 量尺：我的 v1 口径 | 70 → 42，受控下降 21 → 0；`MotionSolveKind` 在求解器外的引用 15 → 1 |
| 行为 | 两轮五组逐项一致，正式性能门槛全部通过 |
| 不达标的一项 | Session 只减少了 52 行，门槛是 100 行 |

那条"Session 至少减少 100 行"是我在方案中估出来的，前提是"Session 的体积主要来自各种动作的特殊处理"。M1 的数据说明这个前提不成立：

- 受控下降在 Session 中的 8 处判断已全部移走，但这些判断周围的代码是通用流程：信息等待、采集许可、入口快照、身体责任。按 D072 第 3 节，它们本来就不该进入动作规格。
- 动作接口改善的是"新增或修改一种动作要动哪些地方"，也就是可扩展性；它不会让 Session 变小。

所以 M1 的结论应该分开写：**扩展性目标基本达成，体积目标不成立。** 项目方没有降低门槛、没有借机拆包装层，处理是正确的。我上一轮方案中与 Session 体积挂钩的目标（M1 减 100 行、M5 降到 3,000 行以内、协调层占比 30%）应当撤回，详见第四节。

**下一步建议：不单独做 M2。**
- 剩下的 42 处分支中，步行占 30 处，其中 15 处属于步行证明和复核，只有统一复核（M3）才能处理；
- 跨隙、一格跳、台阶合计只剩 12 处，单独为它们开一个阶段，产品收益很小。

建议改为：
1. 修掉 M1 留下的三个小问题（第三节）；
2. 回到产品，做终点接近；改到哪种动作就把它迁到接口上，量尺只作为"不倒退"的约束；
3. 驱动器生命周期改为枚举，作为一项独立的小任务尽快完成。驱动器状态已经连续出了两个真实缺陷：S0R-C-02 和 M0-C-01。

## 二、做得比计划好的地方

1. **安全声明不设默认值。** 我的草图给"身体承诺、伤害、验证要求"设了中性默认值（在地面、零伤害、不需要验证）。D072 第 4 节改为必须显式声明，缺失就拒绝登记。这样更安全：新增动作时不会因为漏写一项，就被默认当成"在地面、无伤害"。
2. **通用恢复留在协调层。** 我的方案让受控下降的规格通过 `accept_solution()` 表达"空中先等待落地"。项目方判断这是所有空中动作共有的规则，应继续由运动协调负责。这个判断更准确：动作只声明自己的入口状态，恢复属于协调。
3. **等价比对的证据边界写得清楚。** 459 场、403 个下降实例、约 3 万次查询比较，差异为零。文档也写明：完成条件的判断没有在运行中出现，只有 45 次直接几何比较作证据。没有把它夸大成全量等价。
4. **v2 量尺更完整。** 它覆盖了映射、比较、别名、类名字符串和未知类型。旧口径的结果保留，不与新口径混用。

## 三、M1 留下的三个问题

### 1. 执行器里仍有变相的类型分支，而且量尺没有统计

`proxy_dispatch_check.py` 的输出（`proxy_dispatch_check-5124bd7.txt`）显示，执行器选择控制器和入口参数时，是这样分支的：

```
223  if type(action) is WalkSegment:
265  if type(next_action) is JumpUpSegment:
268  elif action_spec(next_action).controller_family is ControllerFamily.AIR:
371  elif type(action) is JumpUpSegment:
385  elif action_spec(action).controller_family is ControllerFamily.AIR:
397  assert type(action) is StepSegment
1069 if action_spec(action).controller_family is ControllerFamily.AIR:
```

`ControllerFamily` 有 4 个值，几乎与 5 种动作一一对应，只有跨隙和下降共用 AIR。所以 `controller_family is ControllerFamily.AIR` 实际上还是在问"这是哪种动作"。v2 只统计动作段类名，这 3 处没有计入 42 处；运动协调中的 `kind is MotionSolveKind.JUMP_GAP` 也是同样的情况。

**影响：** 新增一种使用新控制器的动作（例如梯子、游泳），仍要修改执行器的这几处。M1 的扩展探针是一个继承 `ControlledDropSegment` 的子类，沿用了下降的几何和 AIR 控制器，所以没有覆盖这种情况。

**建议：**
- 量尺把"在动作实现之外比较动作规格的枚举字段"也计入分支；
- 控制器统一通过 `controller_factory` 创建，使执行器不再需要 `ControllerFamily`。这一步可以在迁移一格跳或台阶时顺带完成；
- 扩展探针改为一个使用新控制器的测试动作，验证新增动作时执行器不需要修改。

### 2. 下降规格反向依赖上层模块

`actions/controlled_drop.py` 的 `precondition()`：
- 在函数内部从 `route_admission` 导入 `direct_drop_visual_evidence_sufficient`；
- 从 `action_preconditions` 导入私有函数 `_acquisition_id`。

动作规格本应位于协调层之下，现在却反过来依赖接纳模块（协调层的一部分）和一个私有函数。放在函数内部导入，是为了绕开循环引用。

**建议：** 把这两个函数移到动作层或更低的模块（例如观察与几何辅助），改为公开函数。`action_preconditions.py` 和 `route_admission.py` 也从那里导入。

### 3. `EntryObservation` 的字段目前只为下降服务

`recheck_started_action`、`can_begin_acquisition`、`needs_acquisition_before_solve` 这三个字段描述的是"下降前采集落点证据"这一流程，其他 4 种动作都返回 `None`。按我在方案中写的 M1-g 判定方式（"其余 4 个实现都只用默认值"），这会被算作只服务下降的成员。

但 M1-g 这条规则本身也写得不好：只有一种动作有采集需求时，任何描述采集的字段都会"只服务它"。更合理的判断是看概念是否通用。"开始执行前需要先采集信息"是通用概念，可以接受。

**建议：** 不改代码。等第二种需要采集的动作出现时，再检查这三个字段是否需要调整为更通用的形式。

## 四、M1 数据对总方案意味着什么

| 我在方案中的假设 | M1 的数据 | 修正 |
|---|---|---|
| Session 的体积主要来自动作特殊处理 | 移走下降的 8 处判断，只减少 52 行；剩下的是通用流程 | 撤回 M1 的 100 行门槛，以及 M2 / M4 / M5 中 Session 行数的目标。Session 体积不再作为验收门槛 |
| 动作接口能显著缩小协调层 | 协调层 16,785 → 16,655，只减少 130 行；运动导航总量相对 M0 增加 152 行 | 撤回"协调层占比 ≤ 30%"的目标 |
| 动作接口能改善扩展性 | 受控下降涉及的文件从 5 个降到 1 个；`MotionSolveKind` 外部引用 15 → 1；分支数下降 40%—47% | 成立，保留这一目标 |
| M2 迁移其余 4 种动作有足够收益 | 剩下的 42 处中，步行占 30 处，其中 15 处要等统一复核；其余三种动作合计 12 处 | 不单独做 M2，改为随产品工作逐步迁移 |
| M3—M5 按顺序推进 | M0、M1 都在驱动器、失败路径和协调边界上发现了真实缺陷 | 改为按缺陷类型触发，而不是按顺序推进（见第五节） |

应该保留的判断：上一轮评估中的 P2（动作知识散落）已经被 M1 证明可以有效改善；P3（两套复核）、P4（两条异步管线）、P7（字符串表示生命周期）仍然存在。

应该修正的判断：P6（Session 过重）不是靠动作接口能解决的。Session 的体积来自通用协调职责：生命周期、目标修订、信息采集和身体交接。要处理它，只能在出现具体缺陷时，针对对应职责的归属来调整。
