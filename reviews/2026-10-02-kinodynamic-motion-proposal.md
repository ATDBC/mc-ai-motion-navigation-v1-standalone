# 带速度的运动规划：让动作衔接从搜索中产生（设计提案）

- 日期：2026-10-02
- 基线：`main` 上的 [`7348b64`][base]
- 问题：要实现丝滑的跑酷式移动，动作衔接是关键，应当用学习，还是靠代码逻辑？
- 性质：外部审查者的设计提案，附可运行的原型。不属于 `docs/motion_navigation/` 的正式文档；采纳后应由项目方改写为正式的 decisions 和 stages。
- 原型与输出：[`2026-10-02-kinodynamic-motion-proposal/`](2026-10-02-kinodynamic-motion-proposal/)

## 结论

**1. 主干用代码，但不是给每对动作写衔接规则，而是用项目现有的 1.21 运动计算器做带速度的搜索，让衔接从搜索中自然产生。学习放在第二步，用来加速和让动作更像玩家，不负责安全判断。**

理由：Minecraft 的玩家运动是确定、低维的，而且项目已经有逐 tick 对齐原版的计算器。在模型精确已知的前提下，"用哪串按键过去"是搜索和优化问题，代码求解更准、可以验证，失败时也能定位原因。学习擅长的是模型未知或规则难以写清的问题，这里的运动部分不属于这一类。

**2. 原型说明，这个方向在能力上明显优于现有方案，但 Python 下的速度是主要风险。**

原型的核心搜索约 250 行：在计算器上做加权 A* 搜索，基元包括疾跑 1 或 3 tick、疾跑跳（跳起后保持按键直到落地）、步行和松键。没有任何"动作 A 接动作 B"的规则。

| 路段 | 现有正式链 | 原型（按路线引导） | 原型搜索耗时 |
|---|---|---|---|
| 平地 20 格 | 99 tick（步行） | 60 tick（疾跑加连跳）；只用步行时 103 tick | 0.6 s；只用步行时 0.1 s |
| 1 格空隙 | 75 tick | 43 tick；只用步行时 75 tick | 0.5 s |
| 2 格空隙 | **找不到路线** | 46 tick；只用步行时 78 tick | 0.5 s |
| 3 格空隙 | **找不到路线** | 49 tick | 0.7 s |
| 4 格空隙（物理极限） | **找不到路线** | 54 tick | 1.4 s |
| 3 格空隙 + 4 格平地 + 3 格空隙 | **找不到路线** | 69 tick，中间不停 | 1.4 s |
| 带速上一格台阶 | 87 tick | 51 tick；只用步行时 84 tick | 2.7 s |
| 先转 90° 再过 3 格空隙 | **找不到路线** | 74 tick | 2.3 s |

- 原型找到的每一条路线，都用真实计算器从头重放过，全部到达目标。
- 只用步行时，原型的用时与现有正式链相当（1 格空隙 75 对 75，台阶 84 对 87），说明差距主要来自"能否带速度衔接、能否疾跑跳"，而不是搜索本身更快。
- **晚一帧鲁棒**：每次起跳同时按"晚 1 tick 起跳"再模拟一遍，晚了也必须安全落地。
  - "3 格 + 平地 + 3 格"：不要求鲁棒时，计划中 4 次起跳只有 1 次能承受晚一帧；要求鲁棒后 4/4 都能承受，只多 3 tick。
  - 4 格空隙：要求鲁棒后需要 54 s 才找到。说明 4 格这类处在物理极限的跳跃，在有输入延迟的服务器上本来就不该尝试；鲁棒检查会自动把它排除，不需要手写规则。
- **速度**：计算器每步约 0.18 ms。一次 15–20 格的规划要做 2,400–17,000 次步进，耗时 0.5–3.3 s。不按路线引导时，转弯路段 30 s 内找不到；证明"走不过去"（只用步行过 3 格空隙）要耗尽 3,000 次扩展、约 57 万次步进，按每步 0.18 ms 估算约 2 分钟。在线使用需要把单次局部规划压到几十毫秒，还差 10–100 倍。

**3. 建议作为 R28 之后的下一个阶段，先做一个性能可行性的小验证，再分步替换现有的动作段。** R28 仍应先完成；这里列出的方案不改变 R28 的范围。

## 一、为什么现在的衔接僵硬

现在的问题不是"没用学习"，而是结构：

1. **按动作类型切段。** Walk、Step、JumpUp、JumpGap、ControlledDrop 各有自己的控制器和入口窗口，衔接处靠静态条件对接，每多一种组合就多一种情况。这和协调层越补越复杂是同一个根源。
2. **状态不带速度。** 规划图的节点是"站在哪个支撑面上"，很多动作要求低速或静止入口，所以每个动作之间会停一下。
3. **不转身。** 疾跑只能配合前进键，跑酷需要边跑边调整朝向，而普通步行目前不转身。
4. **预测时域太短、太保守。** 批次 5 评审中看到的"一次前进至少滑 0.35 格""碰墙即判为不可用"，都是控制器只看眼前、不为下一个动作做准备的表现。
5. **能力上限被动作清单限制。** 现在只支持一格跨隙。2–4 格空隙、连续空隙、转弯接跳跃，都要一个个新增动作类型才能做。

## 二、提案

### 1. 规划状态带速度

规划的状态不是"在哪个方块上"，而是：位置、速度、是否着地、朝向、是否疾跑、跳跃冷却。为了去重，按 0.1 格位置、0.02 格/tick 速度分格。起跳、助跑、落地后继续跑，都通过速度延续，不需要专门的衔接逻辑。

### 2. 运动基元代替动作类型

一个基元是"按某组按键、某个朝向，保持 k 个 tick"，例如：疾跑 1 或 3 tick、疾跑跳并保持到落地、步行、松键、潜行接近边缘。基元的结果一律由 1.21 计算器给出。项目里的 `physics_1_21.step`、`TickInput` 和 `PhysicsState` 可以直接用，原型就是这样做的。

### 3. 两层规划

- **全局：** 继续用现有的表面图规划器求出大致路线。它快，而且已经处理好了未知格、依赖和风险额度。
- **局部：** 只在接下来的几格到十几格范围内，沿全局路线做带速度的搜索。原型的对比说明引导很重要：同一组路段，不引导时 0.4–11 s，转弯路段 30 s 内找不到（要求鲁棒时 4 格空隙也找不到）；按路线引导后 0.5–3.3 s，全部找到（只有 4 格空隙的鲁棒搜索要 54 s）。

### 4. 滚动执行，恢复自然产生

每隔几个 tick，从实际观测到的状态重新做一次局部规划。输入晚到、被推一下、改了目标，都只是"从当前状态再算一次"。R28 想要的统一恢复入口，在这种结构下是自然得到的，不需要为每种失败写分支。

### 5. 晚一帧鲁棒直接写进搜索

评估不可逆的基元（起跳、走下边缘）时，同时按"按时生效"和"晚 1 tick 生效"各模拟一次，两种都安全才采用。原型显示：可行时代价很小（多 3 tick）；处在极限的跳跃会被自动排除。项目的验收一直把"20% 的 tick 晚到一帧"作为标准扰动，跑酷式的跳跃对这一帧最敏感，所以这一条是必需的。

### 6. 严格只留在不可逆的那一刻

与 R28 的风险分级一致：
- 起跳之后、下落途中，保持现有的证明、落点证据和伤害额度；
- 地面部分全部交给"闭环加重规划"，不在每一步都做证明。

### 7. 代价不只是时间

原型只按 tick 计时，结果是平地上也一路连跳，因为在 Minecraft 里疾跑跳确实比疾跑快。伙伴机器人还需要考虑：
- 饥饿消耗：每次疾跑跳消耗 0.2；
- 风格：跟着玩家走时不应一路蹦；
- 风险：离边缘的距离、离岩浆的距离等。

这些都应作为代价项写进搜索，而不是写成规则。

### 8. 与现有模块的对应

| 现有模块 | 在新方案中的位置 |
|---|---|
| `physics_1_21` 计算器 | 状态转移模型，不改 |
| 表面图规划器 | 全局路线，基本不改 |
| `RouteAdmitter` | 接纳局部计划，检查依赖和风险 |
| `FixedRouteController` 与各动作控制器 | 逐步被"跟踪局部计划"加"滚动重规划"取代 |
| `VerifiedMotionExecutor`、落点证据、伤害额度 | 保留，作为不可逆基元的执行和检查 |
| `ExecutionSupervisor`、输入账本、唯一输入出口 | 不改 |

## 三、原型与结果

`kinodynamic_search.py` 是基础搜索，`guided_search.py` 加上路线引导，`current_stack.py` 让同样的路段走现有正式链，`primitive_cache.py` 是一个失败的缓存实验。

### 1. 不引导与引导的对比（疾跑基元，加权 A*，w = 1.5）

不引导（30 s 墙钟上限）与按路线引导（3,000 次扩展上限）：

| 路段 | 不引导：tick / 扩展次数 / 计算器步数 / 耗时 | 引导：tick / 扩展次数 / 计算器步数 / 耗时 |
|---|---|---|
| 平地 20 格 | 60 / 125 / 10,152 / 2.0 s | 60 / 39 / 3,147 / 0.6 s |
| 1 格空隙 | 42 / 28 / 2,243 / 0.4 s | 43 / 29 / 2,439 / 0.5 s |
| 2 格空隙 | 46 / 319 / 27,241 / 5.5 s | 46 / 32 / 2,661 / 0.5 s |
| 3 格空隙 | 49 / 186 / 15,451 / 3.1 s | 49 / 43 / 3,603 / 0.7 s |
| 4 格空隙 | 54 / 466 / 39,498 / 7.9 s | 54 / 82 / 7,242 / 1.4 s |
| 3 格 + 平地 + 3 格 | 69 / 602 / 51,666 / 10.8 s | 69 / 68 / 6,299 / 1.4 s |
| 带速上台阶 | 51 / 442 / 36,445 / 7.5 s | 51 / 138 / 9,855 / 2.7 s |
| 转弯接 3 格空隙 | 30 s 内未找到 | 74 / 104 / 10,241 / 2.3 s |

耗时是本机（4 核容器，单进程）的结果，会随机器变化；tick、扩展次数和步数是确定的。不引导的版本用墙钟上限，"30 s 内找不到"本身会随机器变化，这正是第六节第 4 条要避免的做法，这里只作对照。

### 2. 晚一帧鲁棒

| 路段 | 不要求鲁棒：tick，起跳中能承受晚一帧的比例 | 要求鲁棒：tick，比例，耗时 |
|---|---|---|
| 3 格 + 平地 + 3 格 | 69，1/4 | 72，4/4，3.3 s |
| 4 格空隙 | 54，1/3 | 55，3/3，54 s |
| 转弯接 3 格空隙 | 74，3/4 | 74，3/4 |
| 其余路段 | 全部能承受 | 相同 |

"能承受"的统计方式是：把计划中的某一次起跳推迟 1 tick，其余部分按原计划继续执行，看最终能否到达。鲁棒搜索保证的是"推迟的那一跳本身能安全落地"，不保证后面那段固定计划仍然适用；转弯路段的 3/4 就是这种情况。在滚动重规划下，晚跳之后会从新状态重新规划，所以真正需要保证的只是前者。

### 3. 只用步行

疾跑会改变用时，所以用步行基元再跑一遍，与现有正式链做同口径比较：

| 路段 | 现有正式链 | 原型（只用步行） |
|---|---|---|
| 平地 20 格 | 99 tick | 103 tick（会小跳） |
| 1 格空隙 | 75 tick | 75 tick |
| 2 格空隙 | 找不到路线 | 78 tick |
| 带速上台阶 | 87 tick | 84 tick |
| 3 格及以上空隙 | 找不到路线 | 找不到：步行跳最远约 2.6 格，结论正确；但证明"过不去"耗尽 3,000 次扩展、约 2 分钟 |

最后一行说明：**必须有便宜的可行性上界**（例如"这种速度下最远能跳多远"的表），才能快速放弃不可能的选项，不能靠搜索穷尽来证明。

### 4. 缓存实验：失败了，但验证机制起了作用

我尝试按"起始速度 + 基元"精确缓存平地上的基元结果：在参考平地上用真实计算器算一次，记录相对轨迹；到新位置时先检查沿途地形与参考一致，再平移复用。结果：
- 命中大约一半。未命中时要在参考平地上多算一遍，所以不要求鲁棒的搜索全部变慢（平地 2.0 s → 4.6 s，带速上台阶 7.5 s → 19.5 s），4 格空隙和"3 格 + 平地 + 3 格"在 30 s 内反而找不到了。要求鲁棒的搜索里晚一帧变体可以复用，命中率较高，有几组略快（2 格空隙 7.9 s → 6.0 s）。
- 所谓"精确"缓存并不精确：同一路段的扩展次数与不缓存时不同（"3 格 + 平地 + 3 格"的鲁棒搜索从 139 次变成 987 次仍未找到），说明平移复用的结果与计算器直接算出的结果有差别。
- 在 4 格空隙的鲁棒搜索中，缓存给出的计划用真实计算器重放时没能到达，被拦截了下来。

这说明两点：近似方法（缓存、分格表、学习）只能用来**提出**候选，最终必须由真实计算器**验证**；而缓存要真正有效，需要按速度分格、接受近似，再做验证。

## 四、学习放在哪里

| 阶段 | 学习的作用 | 前提 |
|---|---|---|
| 规划能跑通后 | 学一个"到目标还需多少 tick"的估计，代替直线距离做启发函数 | 有大量规划器生成的数据。原型显示启发函数的好坏决定了速度和能否找到解（转弯路段、步行的不可行证明） |
| 搜索仍然太慢 | 把规划器的结果蒸馏成快速策略（模仿规划器，再由规划器纠错），规划器继续把关安全 | 同上 |
| 追求像人 | 用真人跑酷录像做模仿学习，作为代价项（风格），不替代可行性检查 | 有录像数据和合法的观察接口 |
| 高难技巧 | 在计算器里做强化学习，外层用规划器的安全检查拦截 | 前面三步都已稳定 |

每一步的产出都只是"建议"，最后能不能执行由计算器验证。这与 AGENTS.md"先规则基线、再学习"的原则一致。

## 五、迁移路径

| 步骤 | 内容 | 完成条件 |
|---|---|---|
| P0 性能验证 | 在目标机器上测：局部窗口缩到 8 格；速度分格的基元表加验证；计算器的批量或原生实现 | 一次局部规划 P95 ≤ 50 ms，可在后台运行。达不到就先不进入 P1 |
| P1 转身与地面跟踪 | 朝向作为输入；平地和小高差改为"跟踪局部计划 + 滚动重规划"，取代 `FixedRouteController` | R28 产品清单不退步；玩家站位（贴墙、走廊尽头）改善 |
| P2 带速跳跃 | 疾跑跳、带速上台阶作为不可逆基元，保留证明、落点证据和伤害额度，加晚一帧鲁棒 | 2–3 格空隙、连续空隙、转弯接跳跃加入产品清单，配对比较，Fabric 对照 |
| P3 删除旧动作段 | 逐个用基元替换 JumpGap、JumpUp、Step、ControlledDrop，替换一个删一个 | 代码量净减少，严格层指标不退步 |
| P4 学习 | 启发函数、蒸馏、风格 | 见第四节 |

## 六、风险

1. **性能。** 这是最大的风险。Python 计算器约 0.18 ms/步，原型规划 0.5–3.3 s，在线需要几十毫秒。P0 必须先回答这个问题。
2. **启发函数。** 原型显示，启发函数校准不好时，搜索会退化成接近广度优先，例如步行时的不可行证明。需要上界表或学习得到的估计。
3. **风格。** 只按时间计算，机器人会一路连跳。需要把饥饿和风格写进代价。
4. **墙钟依赖。** 不能重复批次 5 的问题：搜索预算要用扩展次数或步数这类确定的量，不能用墙钟时间决定路线，否则行为会随机器变化。原型的引导版本已经按扩展次数限制。
5. **模拟与实机的差异。** 原型只在计算器中运行，没有跑 Fabric。真实的输入延迟、服务器节奏和视角同步都需要实机对照。

## 七、边界

- 原型不是生产代码：没有处理未知格、依赖登记、风险额度、潜行接近边缘、水和梯子等特殊地形，也没有接入正式运行链。
- 路段都是平整的石头地形，宽 3 格。
- 耗时只代表本机，tick 和扩展次数可复现。
- "转弯接 3 格空隙"的引导路线是手工给的，正式实现应由表面图规划器提供。
