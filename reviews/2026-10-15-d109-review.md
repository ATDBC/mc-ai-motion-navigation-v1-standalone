# D109 审查：B10 总预算复验与生命周期修复（c2cc1ad）

日期：2026-10-15。审查对象：`origin/main` c2cc1ad “Publish D109 lifecycle hardening”。对照检出是 a9d51a2（D108，也就是 D1 运行所用的生产代码）。

D109 验收文档第 10 节“Linux 补充验收”写的是“待填写”，并把 D3、D5、D7 的 Linux 动态复核和 Linux 全量检查留给三方。本轮就补这一块。B10 的 Fabric 结论只读项目公开的精简证据，没有重跑 Windows 正式结果和 Fabric 实机批次。

## 结论

1. **D109 的生命周期修复在 Linux 最终字节上基本成立。**
   - **D3 zombie：** 项目对抗测试连续 30/30 通过。
   - **全量检查：** Linux 全量 185 个模块的 cleanup 全部为 `passed`。
   - **D4 有界关闭：** `close(1.0)` 在 1.00 s 返回 `incomplete`。sink 卡住或漏调 `close()` 时，解释器都能正常退出。
   - **D7 产品代码：** 关闭自动 GC 后，50 次创建关闭的 fd 增量从 D108 的 +20 降到 +0。3 轮 × 5 场景 × 20 次没有异常。
   - **D5 双 fork：** D108 审查发现的双 fork 守护进程逃逸已经收住。
   - **快照摘要：** 与 D108 逐字节一致。

   因此 D109-N1 可以关闭。D109-N4 的产品代码也成立，但项目自己的 POSIX 门禁测试在 Linux 上失败，原因是测试本身多数了一个 fd（见第 5 节）。

2. **剩下的两项 B10 失败性质不同，不能合并成“计时问题”。**
   - **`complete_time_event_attribution` 不是计时问题，是证据链的确定性缺陷，必须先修。** close_release 的诊断由异步 trace worker 事后去读 `backend.last_diagnostics`。但 `Runtime.close()` 在 trace 封存之前就关闭了后端，`FabricBehaviorBackendV1.close()` 会把诊断置为 `None`。worker 晚到一步就写下 `"diagnostics": null`，归因时读 `row["diagnostics"]["client_tick"]` 便抛出 D8 那条 `'NoneType' object is not subscriptable`。
     - **复现：** 用真实的 `PlayerRuntimeV1`、`BoundedAsyncTraceWriter`、`CloseDiagnosticsTrace` 和归因函数，在 2 个 CPU 上 50/50 复现同一个错误。
     - **对照：** 在调用线程入队前抓取诊断后 50/50 正确。
     - **同一缺陷的三次表现：** D1 是缺行，D8 首次是 `'dict' object has no attribute`，D8 最终是 `None`。
     - **不修的后果：** 下一次 B10 无论运动表现如何，大概率还会在这一项失败。
   - **`b10b_solver_is_bounded` 失败在一个单样本墙钟最大值上，现有证据分不清“求解变慢”还是“被打断”。**
     - **数据对比：** D8 的 P95/P99 是 24.54/26.42 ms，比历史 B10-B 的 27.89/28.42 ms 还低。超门槛的只有一个最大值 41.03 ms。历史上通过时的最大值是 29.586 ms，离 30 ms 只差 0.4 ms。
     - **E46 的发现：** 同进程里有后台 trace 线程和常驻大堆时，一次第 2 代 GC 能让单次求解墙钟比线程 CPU 时间多出 103 ms；只有后台 trace 时，墙钟中位数也会整体抬高约 3.5 ms。
     - **建议：** 先给每次求解补记线程 CPU 时间和 GC 重叠，再用决定文档确定门槛口径。不建议现在去优化求解器。

3. **D5 的 Linux 对抗矩阵是项目第一次真正在 Linux 上运行，10/10 失败。**
   - **测试约束过度（两项）：** `setsid` 和 `ignore_sigterm_holds_output` 断言守护进程“必须经由收养”被清理。实际上它在被收养之前就作为已登记后代被杀掉了，进程确实不在了，清理结果正确。
   - **真实缺口（一项）：** `fork_during_cleanup` 下，settle 阶段每轮都先发 SIGTERM，信号处理器每收到一次就 fork 出新一代，2 s 内约 110 代。分片器返回后仍有进程存活（5/5），报告如实写 `cleanup=failed`。
   - **修法：** settle 阶段改为直接 SIGKILL，11 行。对照 5/5 `passed`、0 个存活，矩阵中该子场景 0/10 失败。

4. **同意 D109“未通过并停止”的判定，也同意不在 D109 里开第三轮修正。** 建议开一个小的后续阶段，全部不涉及运动逻辑，顺序如下：
   1. 修 close 诊断的抓取时点，并补一个用真实关闭顺序的回归测试；
   2. 给求解计时补 CPU 时间和 GC 重叠，用决定文档确定门槛口径；
   3. 只跑一次 B10；
   4. Linux 上做 settle SIGKILL 和两处测试修正。

## 3. B10 time attribution 失败：异步 worker 读到已关闭的后端

### 3.1 代码路径

B10 的 Runtime trace 是：

```
BoundedAsyncTraceWriter(CloseDiagnosticsTrace(directory, backend), capacity=16_384)
```

见 `scripts/probe_fabric_deployment_observation.py:1142-1145` 和 `_runtime_trace`。reset／step 的诊断行由场景在调用线程上同步追加；只有 Runtime 自己多出来的 close neutral，由 `CloseDiagnosticsTrace` 补一行。

`PlayerRuntimeV1.close()` 的顺序（`mc2p/runtime/player_runtime_v1.py:730-739`）：

1. close neutral 成功后，`self._trace.write("close_release", ...)`。对异步 writer 来说这只是入队。
2. `finally`：`self._arbiter.clear()`，然后 `self._close_backend()`。
3. 再 `finally`：`self._trace.close()`，等待 worker 排空并封存。

worker 线程上依次发生：

- `CloseDiagnosticsTrace.write_projected()`（`scripts/fabric_visibility_scenario.py:147-161`）在 worker 处理到 close_release 时，才去读 `self.backend.last_diagnostics`。
- 这时后端多半已经关闭。`FabricBehaviorBackendV1.close()` 执行了 `self._receipt = self._diagnostics = None`（`mc2p/backends/fabric_behavior.py:320`），`last_diagnostics` 返回 `deepcopy(None)`。
- 于是 `diagnostics.jsonl` 最后一行是 `"diagnostics": null`。
- `scripts/client_time_evidence.py:73` 读 `row["diagnostics"]["client_tick"]` 时抛 `TypeError`。它不是该函数预期的 `ValueError`，所以报告只剩一句 `'NoneType' object is not subscriptable`。

D108 之前 B10 用同步 trace，`write()` 在 `_close_backend()` 之前执行，读到的是有效诊断。问题是 D108 把 B10 trace 改为异步后才出现的。

### 3.2 同一缺陷的三次表现

| 运行 | 生产代码 | close 诊断的读取方式 | 表现 |
|---|---|---|---|
| D1（600 s 复验） | a9d51a2 | worker 上按 typed 对象读已投影的 dict，失败 | close 行缺失：5637 次观察只有 5636 个区间，报 `deployment timing samples do not cover one exact Runtime episode`；cleanup 另报 `asynchronous trace worker failed` |
| D8 首次 | D4 第一轮 | 同上 | `AsyncTraceCleanupFailure(stage='sink_write', exception_type='AttributeError', message="'dict' object has …")`，trace 未封存 |
| D8 最终 | c2cc1ad（D4-R2） | worker 上按 dict 读，但事后读 `backend.last_diagnostics` | trace 封存成功（22409/22409），close 行为 `null`，报 `'NoneType' object is not subscriptable` |

D4-R2 修掉的是 dict 与 typed 对象的契约不一致，没有修掉“在 worker 上事后读后端状态”这个时点问题。D109 验收第 11 节说这两项失败“与生命周期修复分开记录”。本审查认为 attribution 这一项恰恰是 close 生命周期顺序的问题，应当记在 D4 名下。

### 3.3 复现（E45）

脚本用真实的 `PlayerRuntimeV1`、`BoundedAsyncTraceWriter`、`CloseDiagnosticsTrace` 和 `export_runtime_time_evidence`。后端沿用项目测试的 V1 Backend，只补上与 `FabricBehaviorBackendV1` 相同的两条语义：`last_diagnostics` 返回副本，`close()` 时清空诊断。“按实测投影成本”一组把 worker 上每条记录的投影时间补足到 D8 实测 P95 0.2201 ms（忙等，持有 GIL）。

| 检出与 CPU | 组别 | close 行的 diagnostics | 归因错误 |
|---|---|---|---|
| c2cc1ad，2 CPU | 项目现状，不加时 | `null` 50/50 | `'NoneType' object is not subscriptable` 50/50 |
| c2cc1ad，2 CPU | 项目现状，按实测投影成本 | `null` 50/50 | 同上 50/50 |
| c2cc1ad，2 CPU | 对照：调用线程入队前抓取 | `{"client_tick": 1001}` 50/50 | 无 |
| c2cc1ad，1 CPU | 项目现状，不加时 | `null` 1/50 | 1/50 |
| c2cc1ad，1 CPU | 项目现状，按实测投影成本 | `null` 2/50 | 2/50 |
| c2cc1ad，1 CPU | 对照 | 正确 50/50 | 无 |
| a9d51a2，2 CPU | 项目现状（两组） | close 行缺失，最后一行是 reset 的 `client_tick 1000` | `do not cover one exact Runtime episode`，cleanup 失败，20/20（与 D1 一致） |

表中每组还都报了 `time events do not cover all formal observations`。这是因为最小夹具没有客户端时间事件文件，与本问题无关。

单 CPU 时 worker 往往在 `_close_backend()` 前就被调度到，所以只偶发；多 CPU 时 worker 与控制线程真正并行，几乎必然晚一步。实机 B10 是多核，worker 前面还排着当轮积压的记录，结果与 2 CPU 一组一致。

### 3.4 修法与回归测试

修法：在调用线程上、入队之前抓取 close 诊断。最小形态是把抓取放到异步 writer 外面一层：

```python
class CloseDiagnosticsCapture:
    def __init__(self, directory, backend, delegate):
        self.directory, self.backend, self.delegate = directory, backend, delegate
    def write(self, kind, payload):
        self.delegate.write(kind, payload)
        if kind == "close_release":
            observation = payload["backend_result"].observation
            append_jsonl(self.directory / "diagnostics.jsonl", dict(
                episode_id=observation.episode_id,
                observation_sequence_id=observation.sequence_id,
                diagnostics=self.backend.last_diagnostics))
    def close(self):
        return self.delegate.close()
```

B10 改为 `CloseDiagnosticsCapture(dir, backend, BoundedAsyncTraceWriter(<只写 trace 的 sink>))`。这条写入只发生在 close 路径上，不进入控制热路径。另一种修法是让 Runtime 在 `_close_backend()` 之前把 close 诊断交给 trace，但那要改 Runtime 的公共契约，范围更大。

项目现有的两项异步 close 诊断测试（`tests/test_fabric_deployment_probe.py:466` 的 `test_async_close_diagnostics_accepts_projected_runtime_records` 和 `:521` 的 `..._preserves_record_when_observation_is_missing`）用的是固定的 `SimpleNamespace(last_diagnostics={"movement_tick": 17})`，而且直接调用 writer，不经过 `Runtime.close()`。这个后端关闭后诊断不会消失，所以测不出这个竞态。回归测试应满足三点：

- 后端的 `close()` 会清空诊断；
- 走真实的 `Runtime.close()` 顺序；
- 断言 close 行不为空，且归因不抛 `TypeError`。

E45 就是这样一个测试，在 2 CPU 上稳定失败、修后稳定通过。另外，`export_runtime_time_evidence` 遇到 `diagnostics` 为 `null` 时，应报出明确的 `ValueError`，而不是让 `TypeError` 穿出去。

### 4.2 同进程负载下的墙钟与 CPU 时间（E46）

E46 在 c2cc1ad 上轮换 R4 的 12 种带速入口（4 个方向 × 0.75/1.5/2.5），每组 150 次求解，同时记录墙钟、`time.thread_time_ns()` 和与求解重叠的第 2 代 GC（经 `gc.callbacks`）。

| 条件 | 墙钟 P50/P95/P99/最大 (ms) | 墙钟−CPU P50/P95/最大 (ms) | 最慢一次 墙钟/CPU (ms) | 重叠的第 2 代 GC |
|---|---|---|---|---|
| A 只求解 | 49.45 / 63.60 / 69.74 / 78.39 | 0.17 / 5.22 / 31.72 | 78.39 / 46.67 | 0 |
| B 后台异步 trace（约 80 条/s，每条约 6 KB） | 52.64 / 71.23 / 76.17 / 84.08 | 3.60 / 8.38 / 12.64 | 84.08 / 77.61 | 0 |
| C 常驻约 9 MB 诊断对象 | 49.79 / 67.74 / 71.88 / 78.89 | 0.25 / 6.40 / 30.17 | 78.89 / 48.72 | 0 |
| D = B + C | 52.39 / 67.80 / 72.56 / **162.00** | 3.64 / 9.53 / **103.26** | **162.00 / 58.74** | 1 次，104.72 ms |

能确定的三点：

- **后台 trace 线程让墙钟中位数整体多出约 3.5 ms**（墙钟−CPU 的 P50 从 0.17 升到 3.6 ms）。这是 GIL 争用，与求解工作量无关。
- **单次离群可以完全来自求解之外。** 条件 A 没有任何同进程负载，仍有一次墙钟比 CPU 多 31.7 ms，这是 OS 调度。条件 D 有一次第 2 代 GC 恰好落在求解中，墙钟 162 ms、CPU 只有 58.7 ms。
- **单样本墙钟最大值对这些干扰没有任何抵抗力。** 历史上通过时只有 0.4 ms 裕量，说明它通过与否本来就接近随机。

不能确定的一点：D8 那次 41 ms 到底是 GC、调度还是某个入口的真实工作量。公开证据只有聚合值，逐样本的 `b10-gap-solver.json` 只在项目本地（公开了 SHA-256），而且原本就没有记录 CPU 时间。

### 4.3 建议

1. **先补测量，不改门槛，不优化求解器。** 每次求解同时记录：
   - `time.thread_time_ns()` 差值；
   - 求解期间是否有 GC（`gc.callbacks` 计数，开销可以忽略）；
   - 入口编号。

   这不改变任何行为，只让下一次 B10 能回答“41 ms 是谁的”。
2. **再用一份决定文档确定门槛口径。** 候选口径：
   - 工作量门槛保留 `candidates ≤ 12`；
   - 时间门槛改为“线程 CPU 时间最大值 < 30 ms，且墙钟 P99 < 30 ms”；
   - 墙钟最大值照常记录；超过 30 ms 的每个样本必须能归因到 GC 或调度，否则仍判失败。

   这是放宽还是改口径，要由项目在决定文档里写明理由。AGENTS.md 不允许为了通过而悄悄改门槛，本审查也不建议跳过这一步。
3. 如果补测后证明离群来自 GC，再考虑在 B10 预热结束后 `gc.freeze()`，把常驻对象移出分代扫描。这要以测量为前提，不预先加。

E46 的绝对值约为 Windows 的两倍（Linux 容器较慢），只能看相对结构，不能拿来和 30 ms 比。

## 5. D7 门禁测试多数了一个 fd

`test_real_worker_lifecycle_matrix_releases_without_cyclic_gc`（`tests/motion_nav/test_d102_registry_lifecycle.py:576-665`）在 Linux 上稳定失败 `AssertionError: 6 != 5`（全量 1 次、E50 3/3）。

原因在测试自己：

- 第 631 行 `saved_stderr_fd = os.dup(2)` 多开了一个 fd，用于临时重定向 stderr；
- 第 643 行 `observed = resource_count()` 在这个 fd 还没关闭时计数；
- 恢复和关闭放在 `finally` 里，晚于计数。

所以 `observed[0]` 比基线多 1。Windows 分支只断言 `>=`，测不出来。

只改测试测量时点的对照见 `e50_lifecycle_test_fd_proposal.diff`：先恢复 stderr 并关闭副本，再计数，`finally` 里只在未恢复时恢复。对照 3/3 通过。

产品代码本身没有问题：E39b 在不做 GC 时每场景 +0 fd，E39 三轮全部干净。修正这处测试后，D109-N4 的 POSIX 门禁就能签署。

## 6. D5 Linux 对抗矩阵

### 6.1 结果

| 子场景 | 项目检出（E48，10 次） | 对照：settle 直接 SIGKILL（10 次） |
|---|---|---|
| `fast_root_exit` | 0/10 失败 | 0/10 |
| `setsid` | 10/10 失败：`did not record daemon as adopted` | 10/10（同一断言） |
| `double_fork` | 0/10 失败 | 0/10 |
| `ignore_sigterm_holds_output` | 10/10 失败：`did not record daemon as adopted` | 10/10（同一断言） |
| `fork_during_cleanup` | 8/10 失败：`'failed' != 'passed'` | 0/10 |

E47 中整个测试 10/10 失败，每次都是 3 个子场景；E48 中 8 次为 3 个、2 次为 2 个（`fork_during_cleanup` 偶尔通过）。全量运行中失败的同样是这 3 个子场景。

### 6.2 `setsid` 与 `ignore_sigterm_holds_output`：断言过度

这两个场景里，守护进程的父进程（模块里的测试进程）在超时时还活着。分片器 25 ms 一次的后代轮询早已把守护进程登记为后代，第一次 `_cleanup_process_tree` 就直接终止了它。它从来没有机会成为孤儿，自然不会被 subreaper 收养。

在同一个子测试里，`assertFalse(psutil.pid_exists(...))` 先于收养断言执行并且通过了，说明进程确实被清理。真正需要收养路径的是 `fast_root_exit` 和 `double_fork`（中间进程先退出），这两项稳定通过。

建议把这两个场景的要求改为“守护进程在 `attempted` 或 `adopted_processes` 中，且已不存在”，只在中间进程先退出的场景要求收养。

### 6.3 `fork_during_cleanup`：真实缺口

场景代码（`tests/motion_nav/test_d107_shard_runner.py:721-738`）里，子进程的 SIGTERM 处理器会 `fork()` 出一个新进程并 `setsid()`。新进程继承同一个处理器，收到 SIGTERM 时会再 fork 一代。

`_settle_linux_subreaper_scope`（`scripts/run_motion_nav_shards.py:913-990`）每发现新 PID 或存活的收养进程，就调用一次 `_cleanup_process_tree(..., grace_seconds=min(.2, remaining))`。这一步先发 SIGTERM、宽限后才 SIGKILL，于是每一轮都给处理器一次 fork 的机会：

- 2 s 的 settle 期限内 fork 出约 110 代；
- 始终达不到“两次稳定扫描”；
- 期限一到，最后一代仍然存活。

E48b 把这个场景直接交给分片器（模块上限 1 s），绕开测试自己 `finally` 里的补杀：

| 检出 | cleanup | 分片器返回后仍存活 | 登记进程数 | 错误 |
|---|---|---|---|---|
| 项目，5 次 | `failed` 5/5 | 5/5 | 114–120 | `Linux subreaper scope did not reach two stable scans`；`not all Linux subreaper-adopted children were reaped` |
| 对照，5 次 | `passed` 5/5 | 0/5 | 3 | 无 |

报告如实写了 `failed`，没有谎报 `passed`，这一点比 D108 的双 fork 问题好。但 D5 的目的正是让模块结束后不留进程，这个场景仍然会留下一个。

对照改动 `e48_settle_sigkill_proposal.diff` 共 11 行：在 settle 每一轮的 `_cleanup_process_tree` 之前，对已登记且身份（PID 与创建时间）仍匹配的非 root 存活进程直接 SIGKILL。第一次清理已经给过 SIGTERM，settle 阶段的进程不应再获得一次运行处理器的机会。Windows 走 Job Object，不受影响。

## 7. 其他观察

### 7.1 漏调 `close()` 会静默丢 trace（设计取舍，不要求改代码）

E49 场景 3：sink 正常、调用方写入 2000 条后不调用 `close()` 就退出。解释器 1.8 s 内正常退出，文件里只有 676 行，也没有 `trace_delivery_summary`。

这是 D4 改成守护线程的直接后果，用来换取“漏调 close 也不会卡住解释器”。目前 Runtime 和 B10 探针都会调用 `close()` 并检查 `sealed`，所以正式路径不受影响。

建议在架构文档的 trace 契约里写明：“异步 writer 只有 `close()` 返回 `sealed` 才算证据完整；没有 `trace_delivery_summary` 的 trace 一律视为不完整”，防止以后的新调用方漏掉。

## 9. 证据边界

- **平台：** 本轮只在 Linux 容器上运行（内核 6.18，Python 3.11.15）。Windows 正式结果与 Fabric B10 结论来自项目公开的精简证据；原始大 trace 和逐样本求解文件只在项目本地，本审查无法核对单个样本。
- **E45 与实机的差别：** E45 的后端是带 Fabric 语义的测试后端，不是真实的 `FabricBehaviorBackendV1`。结论依据三点：
  - 代码路径；
  - 与 D8 完全相同的错误串；
  - 2 CPU 下 50/50 的复现。

  竞态方向依赖调度，单 CPU 时只有 1–2/50。
- **E46 的局限：** 绝对值约为 Windows 的两倍；9 MB 常驻对象是合成的替身。它只证明“同进程干扰可以制造单次墙钟离群”，不证明 D8 那一次就是 GC。
- **E48 首次尝试的事故：** 首次尝试时，残留进程清理的匹配条件过宽，误杀了执行命令的 shell，一个遗留的 `tee` 也写乱了输出文件。最终文件来自之后一次干净的后台重跑。那次误杀可能波及同时进行的全量运行中第 66–80 号左右的模块，因此对其中的非通过模块单独重跑：
  - `test_d102_registry_lifecycle`：40 项，3 项跳过，只复现 `6 != 5`；
  - `test_d107_shard_runner`：复现同样的 3 个子场景。

  结论不受影响。
- **对照改动的位置：** 两个 diff 只在 scratch 检出上应用，没有提交到项目。
