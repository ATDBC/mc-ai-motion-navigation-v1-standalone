# D097 M0 未达标：审查与分析（be38685）

日期：2026-10-10。审查对象：`be38685 Publish D097 M0 stop evidence`，包括 D097、阶段计划、验收文档、`m0_probe.py`、测试和 `evidence/motion_navigation/incremental-motion-m0-v1/`。脚本和输出在 [2026-10-10-d097-m0-review/](2026-10-10-d097-m0-review/)。

## 结论

1. **停止的流程是对的，数字是真的。**
   - 我在 Linux 上复现了失败项：混合动作元反例固定使用 10,056 次 physics step，与三次 Windows 采集完全一致。
   - 项目相关检查 113／113 通过（M0 7 项、TP 94 项、standalone 12 项）。
   - 项目没有删反例、没有改门槛，按预先登记的规则停下。这一点做得对。

2. **但未达标的那一项，量的不是 D097 的在线路径。**
   - 失败门槛是“正例最大耗时 ≤ 400 ms”，量的是 `run_case()`，即在线跑完整参数枚举（地面段 → 起跳 → 空中 → 刹车的全网格）。
   - D097 第 2 节明确规定：在线只在不超过三组离线参数中尝试，完整枚举属于离线生成表的工作，查不到表项就回退 B10。
   - 按 D097 自己的在线路径，混合反例的成本是：
     - 两支 rollout 42 次 step，Windows 实测 2.3—2.9 ms；三组参数的上界 126 次，约 9 ms；
     - 逐次证明估算 32／16 次 step，约 2 ms。

     所有在线门槛都有数倍余量。

   - 所以 M0 没有证明 D097 不可行。它再一次证明了“在线完整枚举不经济”，而这正是 D097 把枚举移到离线的前提。

3. **这条门槛本身还有两处内部矛盾。**
   - **同一笔成本，正例 400 ms 不过，负例 800 ms 能过。** 混合反例的目标是一个点（±1e-9），唯一解排在枚举顺序 51% 的位置。它的成本（10,056 次）与有意义负例的完整耗尽（10,616 次）几乎相同：同一笔钱当负例能过 800 ms，当正例就过不了 400 ms。
   - **负例门槛只因为冻结负例是 A3 网格才通过。** 同一夹具的 A5 网格完整耗尽要 19,752 次 step，按 Windows 实测每次 step 0.058—0.073 ms，折算约 1.1—1.4 s。如果负例里有 A5 不可行用例，800 ms 也会失败。

4. **门槛的来源有我的责任。**
   - 400／800 ms 出自我在 [R2 审查](2026-10-10-tp-5ar-r2-review.md) 第 8 节的判定表，那张表回答的是“要不要重开在线搜索的 TP”。
   - 我在 [方法建议](2026-10-10-tp-next-method.md) 的 M0 里写的门槛只有“单次决策 P95 ≤ 10 ms、rollout P95 ≤ 15 ms”，这两项都已通过。但我在同一行把 `steer_probe.py` 列为 M0 要运行的脚本，没有写明它的耗时属于离线生成表，不能当在线门槛。
   - D097 阶段计划把两份文件的线合在了一起。这个歧义是我留下的。

5. **建议：**
   - 不要在 D097 内部改判。按预先登记的规则，M0 记为未通过。
   - 是否继续，由你决定是否写一份修订决定（例如 D097-A）。修订只做三件事：
     1. 把“完整参数枚举耗时”从 M0 的在线门槛移到 M1，作为预先登记的离线生成预算；
     2. 在线门槛保持不变，并单列混合反例的在线路径耗时；
     3. 修正参数定义：地面、起跳、空中三段的步态独立，空中段带时长。
   - 修订必须在任何新测量之前写好，并保留本次失败记录。这样不算挪门槛，因为改的是与 D097 第 2 节自相矛盾的那一行，在线门槛一项不放宽。
   - 如果你不想再开修订，D097 就此结束，回到 B10 现状。这也是一个干净的结局。

另有一项证据问题需要修：三份 Windows JSON 和 `manifest.json` 的 SHA256 是按 Windows CRLF 字节算的，仓库里存的是 LF，新 checkout 上 `sha256sum -c SHA256SUMS.txt` 有 4 个文件失败。见第 5 节。

证据边界：

- 复现和新增测量在 Linux 上完成（Python 3.11.15），正式平台是 Windows。
- 文中 Windows 毫秒数取自项目 JSON；本文新增的只有 step 计数和据此的折算。

## 2. 失败项量的是什么

`m0_probe.run_case()` 与我在 R2 审查中写的 `steer_probe.py` 是同一个算法。区别在于它固定只在着地时起跳，并把高度截断作为诊断项。算法结构：

- 先试全部不跳的候选；
- 再从最晚起跳点往前，枚举起跳步态 × 空中步态 × 空中时长；
- 每个网格点都刹车到停，并检查目标。

这是一次**完整参数搜索**。D097 对它的定位是：

| D097 条文 | 内容 |
|---|---|
| 第 2 节 | “承诺点之前可以在不超过三组离线参数中有界尝试” |
| 第 3 节 | 表项只推荐方案；查不到表示未求解或未支持 |
| 第 7 节 | 回退到旧 B10 求解只发生在承诺前或落地重锚后 |

也就是说，D097 的在线路径里没有完整枚举。它只在 M1 离线生成表时运行。

M0 的六项检查按“在线路径”和“离线工作”拆开如下：

| 检查 | 属于 | Windows 结果 | 是否通过 |
|---|---|---|---|
| 分类全部正确 | 两者 | 全部符合 | 是 |
| 正例完整枚举最大值 ≤ 400 ms | **离线**（表生成） | 587.9／591.2／736.9 ms | 否 |
| 负例完整枚举最大值 ≤ 800 ms | **离线**（表生成） | 593.8／745.8／744.8 ms | 是 |
| 逐次证明估算 P95 ≤ 10 ms | 在线 | 2.2／2.7／2.7 ms | 是 |
| 已知参数 rollout P95 ≤ 15 ms | 在线 | 4.7／5.8／5.7 ms | 是 |
| 哈希种子不影响结果 | 两者 | 一致 | 是 |

混合反例本身的在线路径（项目 JSON 中的 `known_input_cost`）：

| 项目 | step | Windows |
|---|---:|---:|
| 两支 rollout | 42 | 2.27—2.85 ms |
| 三组参数都试一遍的上界 | 126 | ≈ 9 ms |
| 逐次证明：普通边界／越过承诺点 | 32／16 | ≈ 2 ms／1 ms |
| 完整扫描（只用于离线和验收） | 427 | 40.5—50.8 ms |

除混合反例外，22 个原正例的完整枚举最大值是 flat_sprint 的 256.6 ms，也在 400 ms 内。

## 3. 门槛内部的两处矛盾

### 3.1 正例与负例对同一笔成本给出不同结论

混合反例的目标区域是 ±1e-9 的一个点。它原本是 R2 审查用来证明“绑定 G／J／A 漏掉混合动作”的覆盖反例，只有那一条精确输入能到达。

把同一夹具的目标移到不可达处后，完整耗尽同一网格：

| 口径 | 混合反例找到时 | 同一网格完整耗尽 | 找到时已走过 |
|---|---:|---:|---:|
| 正式（无高度截断） | 10,056 | 19,752 | 50.9% |
| 高度截断诊断 | 6,383 | 13,023 | 49.0% |

在完整枚举里，解排得越靠后，正例的成本就越接近负例耗尽。用不同的毫秒线去卡同一种算法的正例和负例，结论取决于解在枚举顺序中的位置，而不是方法是否可行。

### 3.2 负例门槛只测了 A3 网格

冻结的有意义负例里，唯一需要完整耗尽的大网格是 `gap_start_4_width_3_a3`，即 A3 网格（10,616 次 step）。上表显示，A5 网格完整耗尽要 19,752 次。按三次采集中慢的一次计（0.070—0.073 ms／step），约 1.4 s，超过 800 ms。

如果把“完整枚举耗时”当在线门槛，矩阵里只要有一个 A5 不可行用例就过不了。这再次说明完整枚举只能离线做。这与 R2 审查第 3.3 节的结论一致。

## 6. 如果继续，修订应当怎么写

### 6.1 不变的

- M0 记为未通过，原 JSON 和结论不改写。
- 在线门槛一项不放宽：单次证明 P95 ≤ 10 ms，rollout P95 ≤ 15 ms；M2 的完整控制路径仍为 8／15／30 ms。
- 分类、哈希种子、不得删样本、不得改分箱分母这些规则不变。

### 6.2 要改的

1. **完整枚举不再作为在线门槛。** 改为 M1 的离线生成预算，事先登记。
   - 例如：在项目 Windows 机器上生成全部首版表不超过 8 小时，单个入口点的枚举不超过 40,000 次 step。
   - 按现有数字估算：
     - 每个分箱中心和 8 个角点做完整枚举，每点最多约 20,000 次 step，约 1.4 s；
     - 再用 400 个样本，各做一次 rollout＋完整扫描来验证选出的参数，每个约 0.1 s。
     - 每个分箱约 50 秒。
   - 若 3 个模板共约 450 个分箱，单核约 6 小时，可以并行。

2. **单列混合反例的在线路径耗时：** 两支 rollout，以及最多三组参数时的上界。混合反例同时作为 M1 生成器的覆盖检查：生成器必须能产生 `W → SJ → W×5` 这一组参数。

3. **参数定义拆开：** 地面步态、起跳步态、空中步态、空中时长、起跳触发和落地模式。

4. **负例补一个 A5 不可行用例。** 只用于离线生成预算，同时验证“查不到就回退 B10”的分类。

5. **证据哈希按仓库实际字节计算**（第 5 节 1—3 项）。

修订之后，M0 不需要重跑：在线路径的数字已经在三次 Windows 采集中。新的工作从 M1 开始，M1 的门槛与止损线保持 D097 原文。

### 6.3 什么时候不该继续

- 如果你更看重“按预设规则停就停”的纪律，不想为一项门槛设计失误开修订，那就让 D097 结束。代价只是失去一个在线路径实测良好的方案，正式链不受影响。
- 如果 M1 的离线生成预算在事先登记的上限内做不完，或者分箱一致性达不到 99%，就按 D097 原有止损线结束，不再开第二次修订。
