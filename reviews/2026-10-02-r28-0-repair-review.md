## 一、目标"能解析"不等于"能到达"

### 1. 路线先到方块中心，再折返到目标点

`_surface_action_route` 在路线末尾的方块中心之后，再追加一段"中心 → 目标点"。接纳检查也要求这条连接从中心出发（`connection_from=candidate.path[-1].position`）。

结果是，即使目标点就在去方块中心的路上，机器人也要先走到中心，再掉头回来：
- **墙边：** 目标 x = 1.3、墙面在 x = 2.0 时，路线是 … → (0.5, 6.5) → (1.5, 6.5) → (1.3, 6.5)。方块中心 1.5 离墙太近，控制器走不到，于是在 1.30 处失败；而目标 1.3 本身是可以到达的（`approach_limit.txt`）。
- **开阔地：** 每个非格心目标都多绕一个来回。

原型（[`proto-direct-terminal.diff`](2026-10-02-r28-0-repair-review/proto-direct-terminal.diff)，+14/−1）：在普通步行路线的末尾，如果从倒数第二个路线点到目标点能直线同高行走（复用现有的 `standable_point_in_region(connection_from=...)`），就直接用目标点替换方块中心；否则保留现有做法。有地面证明的路线不受影响。

| 检查 | 41c7d9b | 加原型 |
|---|---|---|
| 完整 v2 清单 1,600 场 | 1,589 | 1,589，没有成功或失败的变化 |
| 指定点两层的到达时间 | — | 170/200 个任务变快，平均 −3.0 / −3.2 tick，最多 −7 tick，最慢 +1 tick |
| 目标修订两层 | — | 66 个任务变快，平均约 −1.3 tick |
| 连续高度层、严格下降层 | — | 指标逐项不变 |
| 运动导航测试 | 870/870 | 870/870 |
| 墙前目标 x = 1.30、1.40、1.45 | 全部失败 | 全部成功 |

### 2. 目标点选择不知道控制器能走到多近

`standable_point_in_region` 用的是静态规则：身体放在这里，不碰撞，支撑比例 ≥ 0.5。但普通步行控制器另有一套更保守的接近限制：墙边有 0.15 格软边界，预测时还要加上制动距离和停止尾迹。

扫描结果（`approach_limit.txt`，平地，完全已知）：

| 接近方式 | 身体最近能到的位置 | 41c7d9b 上的后果 |
|---|---|---|
| 正面接近墙 | 身体正面离墙 0.40 格 | 目标框完全落在这个距离之内时，接纳通过、走过去、然后失败 |
| 沿墙平行接近 | 身体侧面离墙约 0.20 格 | 贴墙站的玩家（身体紧贴墙面）走不到 |
| 走向边缘 | 身体前沿离边缘 0.06 格 | 悬出 0.2 格的目标走不到；悬出 0.1 格可以 |
| 走廊尽头 | 前沿离尽头墙 0.35 格 | 站在尽头的玩家走不到 |

做了一个诊断实验（仅用于定位原因，不是建议的修法）：把软边界设为 0 后，"离墙 0.1"由失败变为成功，但贴墙、平行接近、走廊尽头仍然失败（`player_spots.txt` 最后一组）。所以软边界只是原因之一，制动和停止尾迹也起作用。

这是一个**修复前就存在的**问题，不是本批次引入的。但它直接影响"到我这里来"和跟随：玩家在室内、走廊、平台边缘停下时，正好是这些位置。现有 v2 清单的目标都在开阔地上，所以没有测到。

### 3. 候选点可能落在目标框边界上

当目标框中心不可站立时（例如中心离墙太近），候选点会依次尝试重叠区域的四个角，角点往往正好在目标框边界上：
- 目标 x = 1.75 时，选中的点是 (1.55, 6.3)，裕量为 0（`edge_goals-41c7d9b.txt`）。
- 执行器按"终点到目标框边缘的距离"设置终点容差，结果约为 1e-4。终点几乎无法完成，这正是原 B-1 的失败机制。
- 这类目标对应的玩家位置本身就嵌进了墙里，本来应当直接拒绝。

### 建议

1. **终点直连**：按原型做，属于改变行为的修改，附配对比较。
2. **目标点选择加入可到达条件**，二选一：
   - 由普通步行控制器提供一个"最近可接近距离"查询（墙、边缘分别给出），`standable_point_in_region` 只接受满足它、并且离目标框边界有最小裕量的点；
   - 更简单的做法：给候选点设最小裕量（例如 0.05 格），不满足的直接丢弃。

   两种做法下，没有可接受的点时，都返回有类型的"超出接近范围"，在规划前就结束，不要走过去再失败。
3. **产品清单 v3 加入"玩家常站位置"族**：贴墙（正面、平行）、墙角、1 格宽走廊中间和尽头、边缘悬出 0、0.1、0.2 格，每种都有正常和晚到两个条件。`player_spots.py` 可以作为起点。
4. **R28-2 的第一项行为修改**：低速终端接近。在目标框内、速度很低时，墙面只做硬碰撞检查，不用软边界（在 Minecraft 里贴墙站立是无害的）；边缘仍然保留支撑和停止尾迹检查。这是 R28 里第一条有基线数据支持的 R28-2 修改，可以在 R28-1 之后进行。

## 三、量尺 v2 的分类误差与身体归属空档

`stall_attribution.py` 对 v2 归档的统计（`stall_attribution-41c7d9b.txt`）：

| 层 | 步行停顿 tick | 其中实际是严格下降入口恢复 | 严格准备 | 严格执行 |
|---|---|---|---|---|
| 严格下降，20% 晚到 | 187 | 187（恢复 137、释放 39、稳定 11） | 112 | 132 |
| 目标修订，20% 晚到 | 8 | 0 | 0 | 0 |
| 严格下降，正常 | 0 | 0 | 0 | 76 |

1. **分类误差。** 输入丢失后，严格下降的地面入口恢复由 `MotionRouteCoordinator` 发出输入（在潜行状态下前后挪动），但此时诊断里动作种类为空、控制者列表也为空，于是提取器把它归为"步行"。全部 195 个步行停顿 tick 中，有 187 个是这种情况。
   - 建议：分类优先看"当前路线动作是否为严格动作"，或者由恢复入口登记持有者，而不是只看当帧诊断。
2. **身体归属空档。** 在严格下降晚到层的 64/200 个任务中，有 528 个 tick 导航正在施加非中性输入，诊断中的控制者列表却为空，交接状态为 TRANSFERABLE。
   - 地面恢复本身可能确实允许交接，所以我**没有**把它判为安全缺陷。
   - 但 R28-1 要让统一交接入口依靠监督者和控制者的证据决定身体去向；如果"正在移动身体的一方"不在证据里，交接入口就会在不知情的情况下做决定。
   - 建议在批次 5 中让这段恢复登记为持有者（或由监督者报告实际状态），并把"有非中性输入但没有持有者"加入监视器检查。
3. **自由下落被算作停顿。** "严格执行"类的停顿是在空中自由下落时累计的，因为水平位移很小。建议排除空中帧，或改用三维位移。
4. **比较口径不一致。** `compare_metrics` 对 `net_stall_ticks` 要求完全相等，而验收 5.1 对普通地面允许 ±k tick 的差异。建议两者口径统一。

## 四、较小的意见

1. **同一规则用了两种口径。** 会话里调用 `standable_point_in_region` 时不检查连接，接纳时检查。这可能出现会话接受、接纳拒绝的情况。建议目标点只计算一次，随规划请求一起传递，这样也符合"每类规则只有一个拥有者"。
2. **D049 关于方向不对称的结论成立**：根因在规划器的等价路线选择，不是按键的同分偏向。我在修正方案中的猜测不对，这里更正。
3. **未覆盖的迁移函数是 4 个，不是我上次说的 5 个。** 按项目的门禁报告，`retry_from_current` 已被 1,448 个回归案例中的某些执行到；我没有单独核对是哪一个。门禁按函数入口判断，文档也写明了"执行到一次不能代替关键分支的检查"，口径正确。
