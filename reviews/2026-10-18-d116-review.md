# D115–D116 审查：prepared 交接的两个生命周期缺口（62ec855），以及下一步是否单独处理

日期：2026-10-18。审查对象：`origin/main` 62ec855（“Publish D115-D116 prepared handoff findings”）。

平台说明：本轮只在 Linux 上运行项目函数、项目夹具和项目测试，或只读 D116 公开的时间线证据。对照改动只放在临时工作树里，项目树本身不改。Windows 结论来自 D116 公开证据，本轮没有运行 Fabric。脚本和输出在 [`2026-10-18-d116-review/`](2026-10-18-d116-review/)。

## 结论

1. **方向是对的，D116 的做法值得保留。**
   - **先归因再改：** D116 没有按 D115 的判断去改 Session／监督者／执行器的同帧顺序，而是先做时间线归因，查出真正的第一处阻塞是依赖比较：完整 `CellFact` 比较会把观察时间戳刷新当成依赖变化。
   - **修法只用一个依赖权威：** D116-1 只把这处比较换成 WorldKnowledge 自己的 `dependency_changes()`，没有新增状态，也没有第二套账本。owner 缺失和 `HISTORY_INCOMPLETE` 都保守拒绝。
   - **及时止损：** 出现清单外阻塞后就按止损规则停下，没有继续补 case。
   - **Linux 复核成立：** tick 20 为 `READY_MATCH`，监督者批准，tick 21 第二跳首条输入实际应用（E84）。语义依赖测试在 Linux 上全部通过（E90）。
2. **这两个缺口不是“共享”生命周期缺口，只出现在 prepared 后继链上。**
   - **现行生产链不走 prepared 入口（E86）：** 不加 D116 诊断补丁时，四个方向的单跳场景和 D116 两跳代表场景都走普通 SOLVE，`prepare_upcoming_action`、`prepare_action`、`_seal_snapshot`、`commit_prepared_activation` 的调用次数全是 0。两跳场景本身也能成功，用 2 次普通 SOLVE 提交。
   - **apply 事件缺口：** 全仓只有一处在记录 `APPLIED` 之前不经过 `try_apply()`，就是 prepared 安装分支（`motion_coordination.py:1421–1425`）。普通结果的顺序是 `try_apply → install → 记录 APPLIED（带 accepted_ns）→ 退役`（`motion_coordination.py:1034–1047`），本来就是对的。
   - **tracker 缺口：** 只有 `ActionRouteExecutor.commit_prepared_activation()`（`action_route_executor.py:252–268`）推进 `action_index` 时不经过 `RouteControl.advance()` 里的 `tracker.record_progress()`。
   - **所以：** 修这两项不会改变现行生产行为，也不能说“所有异步结果都缺 apply 事件”。准确的名字是“prepared 后继交接的生命周期缺口”。
3. **只修这两项不够。同一条链上还有三处已知阻塞，其中一处已经出现在 D116 自己公开的 Windows 证据里。**
   - **(c) prepared 状态比较要求精确相等：**
     - 公开时间线 `d116-1-semantic-result-timeline.json` 的 tick 21：预测 z 向速度 `0.22913268755160499`，实际 `0.22913268755160496`，相差约 1 ULP；`prepared_expected_state_matches=false`，控制器进入 `recovering`。
     - D116 把这一 tick 的 `recovering` 归到 tracker STOP 上，但两件事在同一 tick 发生。只修 a、b 之后，路线复核已经不再取消控制器，可凡是第二跳准备登记成功的运行（20/20）仍停在这里，速度差和 Windows 逐位相同（E88、E97）。
     - 普通路径用 `_state_matches_verified_start()` 的 1e-7 容差；prepared 的运行中比较（`motion_candidate.py:548`）和入口比较（`action_route_executor.py:360`）都用 `==`。
   - **(d) receiver 借快照失败后永久拒绝：**
     - `borrow_snapshot_version()` 用非阻塞 `acquire(False)`。观察写入会阻塞式持有同一把锁（`world_model.py:340–341`），两者撞上时借用返回 None。
     - 这次准备随即被记成 `MISSING_INFORMATION`／`WORLD_SNAPSHOT` 拒绝，`missing_cells` 为空，没有重试。
     - 发生率随负载变化：负载未控制时 13–17/30，空闲单核 3/30，同核另有忙循环 5/30（E85、E95）。
   - **(e) 拿不到或用不了 prepared 后继时，没有有界出口：**
     - 执行器只要 `_prepared_action_indices` 里有下一个下标，就停在 `prepared_action_boundary`；这个集合只在换新路线时清空。
     - E96 让快照借用持续失败：协调器 12 次退役这项准备，执行器却从 tick 20 一直等到 80，监视器零违规。
     - prepared 控制器进入 RECOVERING 后也一样：身体在 tick 32 已安全落地，会话仍保持 `BODY_RESPONSIBILITY_UNRESOLVED` 到 80 tick（E84）。
   - **逐项对照（30 次，80 tick）：**

     | 树 | 完成 |
     |---|---|
     | 原样 | 0/30 |
     | 只修 a、b | 0/30 |
     | 修 a、b、c | 17/30 |
     | 修 a、b、c、d | 30/30（`goal_state_satisfied`，零违规） |

     但这里的 d 只是有界重试，持续失败时仍然没有出口，所以 (e) 还要单独修。
4. **回答“下一步是否单独处理”：应该单独做一个阶段，放在扩大矩阵和 Fabric 之前；但范围不能只是这两项。**
   - **范围：** 这个阶段应叫“prepared 后继交接收口”，按已知的五项列清单（a–e），每项单独提交，各自写 RED 和 mutation。
   - **门槛：** 用端到端重复门槛（负载下 N≥30、注入快照失败），不能只看两项各自的单测。
   - **原因：** 如果只修两项就回到矩阵，会再次重复 D115→D116 的模式：修一处，跑代表链，撞上下一处，止损。
   - **“原子更新”的写法：** 不是加锁，而是让 prepared 提交和普通 `_advance()` 共用同一个“完成当前动作”步骤。现在 prepared 提交只复制了其中一部分：tracker 更新漏了，伤害记账和已完成动作候选的丢弃也漏了（§2.4）。
5. **在当前动作集上，连续接续的玩家可见收益很小，排期时应考虑这一点。**
   - **E92：** 同一条两跳路线，现行生产链 57 tick 完成，第二跳在 tick 22；四处修复后的 prepared 链 56 tick，第二跳在 tick 21。两者都零伤害成功，两跳之间分别站 2 帧和 1 帧。
   - **E93：** 第二段间隙宽 2、3 格时，两种模式都是 `no_route_within_complete_scope`。连续接续不会让机器人到达更多地形。
   - **这修正我上一轮的说法：** D114 审查把“同一路线内两次 JumpGap 的连续执行”列为第一个产品能力。实测表明，用现有的一格 JumpGap，它对玩家几乎不可见；它真正的价值在以后需要保持动量的动作链上（疾跑跨多格、连续跑酷），而这件事还没有被证明。
6. **测试与小问题：**
   - **D116 时间线测试在 Linux 上不稳定：** 空闲单核 2/20 失败，同核另有忙循环 5/20 失败；与 14 个相邻模块合跑时也失败 1 次（E94、E90）。根因就是 (d)。测试写死了 tick 20／21 的结果，而验收文档 §7.2 自己写的是“具体 tick 受调度影响，只检查相对顺序和唯一性”。
   - **D115 门槛里的 `L` 需要定义：** 第一跳着地观察在 tick 19，第二跳首条输入在 tick 21。按着地观察算是 L+2，按 proof 出口（tick 20）算是 L+1。
   - **行尾改动淹没了实际改动：** 162 个变化文件里有 128 个只改行尾（126 个 CRLF→LF，2 个 LF→CRLF），实际改动只在 34 个文件。
   - **测试结果：**
     - Linux 全量分片 193 个模块共 2408 项，191 个模块通过。只有两处不通过：只能在 Windows 上运行的 D101；D116 时间线测试，又一次因 (d) 失败。
     - 15 个 prepared 交接直接与相邻的模块共 364 项，原样和两棵对照树各只有 1 项失败（E90）：原样是 (d) 抖动，对照树是 D116 把止损状态写成预期的那一项。

**下一步计划（§7）：**

1. 开一个单独的组件阶段 D117“prepared 后继交接收口”，不跑 Fabric。
2. 修五项：
   - a：apply 事件；
   - b：动作完成与 tracker 同一步提交；
   - c：状态比较复用普通路径的数值规则；
   - d：快照借用忙时归为可重试的瞬时状态，不再记成缺少信息；
   - e：拿不到或用不了 prepared 后继时，回退普通 SOLVE 或有界类型化终止。
3. 门槛是端到端重复：负载下 30/30 完成或在有界 tick 内类型化终止；注入持续快照失败时回退并完成；I18–I22 零违规；监视器新增“边界等待有界”检查；D116 时间线测试改成不依赖线程调度。
4. 给这个阶段设时间盒。五项之外如果再出现新的阻塞，就冻结 prepared 链，保持 D115 撤回自动准备后的状态，转回能力本身。
5. 收口之后，不要只为一格两跳单独跑一批 Fabric。可以把连续接续和第一个需要保持动量的能力（例如疾跑跨两格）放在一起；或者明确这批 Fabric 只验证基础设施，重点看 prepared 入口比较在真实客户端数值下能否成立。

## 2. 两个缺口的真实范围

### 2.1 生产链不走 prepared 入口（E86）

E86 不加任何诊断补丁，用项目夹具跑正式链，只统计调用次数（`output/e86_production_prepared_entry_census.txt`）：

| 场景 | 终态 | 普通 SOLVE 提交 | prepared 链入口（4 个方法） |
|---|---|---:|---:|
| `action-continuity-gap-0..3` | 全部 success | 各 1 | 全 0 |
| D116 两跳代表场景 | success | 2 | 全 0 |

D115 撤回 `prepare_upcoming_action()` 的调用以后，生产中没有任何代码走 prepared 后继链。D116 的时间线和本轮 E84、E85、E88、E91、E95、E96 都是用 D116 脚本的进程内补丁把它恢复的。

### 2.2 apply 事件缺口（a）

motion 协调器里有两处记录 `APPLIED`：

| 路径 | 代码 | 是否先 `try_apply()` |
|---|---|---|
| 普通 SOLVE 结果 | `motion_coordination.py:1034–1047` | 是：`try_apply → install → 记录（accepted_ns）→ 退役` |
| prepared 安装 | `motion_coordination.py:1421–1425` | 否：直接 `install → 记录（无 accepted_ns）→ 退役` |

规划协调器把 `try_apply()` 放在 `_record_admission()` 内部（`planning_coordinator.py:2491–2495`），`world_interaction.py:505` 也先调用了它。所以 a 只是 prepared 分支漏了一步。

**建议修法：** 把“取 accepted_ns → `try_apply()` → 安装 → 记录 APPLIED → 退役”提成 motion 协调器里的一个小函数，普通与 prepared 两条路径都调用它。这正好是两个明确重复点，符合 AGENTS.md 对新抽象的要求。

对照 `e87_prepared_apply_event_control.diff` 只改这一个分支：

- 原样树：每次登记成功的运行都有一次 I19；
- 加上 e87 之后：E88、E91、E95 的全部运行 I19 为 0。

### 2.3 tracker 缺口（b）

| 步骤 | 普通边界 | prepared 边界 |
|---|---|---|
| 推进 `action_index` | `_advance()` | `ActionRouteExecutor.commit_prepared_activation()` |
| 更新 `ActiveRouteTracker` | `RouteControl.advance()` 调 `record_progress()`（`route_body_controller.py:215`） | 没有 |
| 下一帧路线复核 | 通过 | `expected_identity` 用执行器的新下标，tracker 仍是旧下标 → `STOP / route_identity_changed` |

对照 `e88_tracker_atomic_handoff_control.diff`：在 `RouteControl.commit_prepared_activation()` 里，执行器提交成功后立即调用 `record_progress()`。加上它以后，tick 21 激活后的路线复核从 `stop / route_identity_changed` 变为 `unaffected`，不再取消控制器（E97、E90）。

这个对照只用来证明因果，不是正式修法：

- 它读取执行器的私有 `_last_prepared_frame`；
- 它先提交执行器再提交 tracker，tracker 拒绝时会留下半提交状态；
- 进度证据传的是 `None`。

### 2.4 根因：prepared 提交只复制了 `_advance()` 的一部分

普通 `_advance()` 完成一个动作时依次做（`action_route_executor.py:1447–1451`）：

1. 记录已开始动作的伤害（`_commit_action_damage_if_started(..., force=True)`）；
2. 丢弃已完成动作的 prepared 候选；
3. 清除边界标记；
4. `action_index += 1`；
5. 之后由 `RouteControl.advance()` 更新 tracker。

`commit_prepared_activation()` 只做了第 3、4 步，另设了控制器和状态。tracker 缺口只是漏掉的一块：

- 第 1 步目前只影响 ControlledDrop（全仓只有它 `tracks_damage=True`），D116 代表链是 JumpGap→JumpGap，所以今天没有可见后果；
- 第 2 步漏掉以后，已完成动作的候选由谁释放，我没有逐项核实。

所以“原子更新”的正确写法不是加锁：控制线程上本来就是同步调用。应该做的是：

- **共用一步：** 把“完成当前动作”收成一个函数，普通边界和 prepared 边界都调用。
- **顺序：** 先预检 tracker 能否接受“同一路线修订、下标 +1”，再提交执行器，最后在同一个调用里提交 tracker。
- **失败处理：** 任一步失败都返回类型化结果，并且不留下半提交状态。
- **序号来源：** observation sequence 由调用方传入，不读私有字段。
- **进度证据：** 用 prepared 边界的出口状态，也就是上一动作 proof 的出口、下一动作 proof 的入口。

## 3. 同一条链上另外三处阻塞

### 3.1 (c) prepared 状态比较要求精确相等

| 比较 | 代码 | 规则 |
|---|---|---|
| 普通 verified 起点 | `motion_candidate.py:153–167` `_state_matches_verified_start()` | 位置、速度、朝向 ≤1e-7。注释说明依据是对齐普通地面的审计误差 <6e-9。 |
| 物理条件 | `motion_candidate.py:145–148` | float 相差 ≤4 ULP 视为同一表示 |
| prepared 运行中逐 tick | `motion_candidate.py:548` | `anchor.physics_state != branch.trajectory[index]`，精确比较 |
| prepared 入口 | `action_route_executor.py:360` | `branch.trajectory[0] == anchor.physics_state`，精确比较 |

**D116 公开的 Windows 证据里已有这一项。** `d116-1-semantic-result-timeline.json` 的 tick 21：

- 预测速度 `[0.0, 0.3332000064849853, 0.22913268755160499]`，实际 `[0.0, 0.3332000064849853, 0.22913268755160496]`；
- `prepared_expected_state_matches=false`，`prepared_controller_reason=BODY_RESPONSIBILITY_UNRESOLVED`，`prepared_controller_state_after=recovering`。

D116 验收 §7.1 把 `recovering` 归到 tracker STOP 上，但这两件事发生在同一 tick。E97 在只修 a、b 的树上读同一 tick：

- 激活后路线复核已经是 `unaffected`，`route_cancel_after_validation=false`；
- 但 `prepared_expected_state_matches` 仍为 false，控制器照样进入 `recovering`；
- 预测和实际速度与 Windows 公开证据逐位相同。

所以：

- 这 1 ULP 是确定性的：两个平台逐位相同，每次登记成功的运行都会出现。它是 proof 里的预测轨迹和组件后端实际步进之间的差异，不是平台浮点噪声；具体是哪一步运算造成的，我没有继续追；
- 只修 a、b 时（E88），30 次中 20 次登记成功，这 20 次全部从 tick 22 起停在 `BODY_RESPONSIBILITY_UNRESOLVED`；
- (c) 单独就足以阻塞。

**修法：** 对照 `e89_prepared_numeric_tolerance_control.diff` 只把运行中比较换成 `_state_matches_verified_start()`，不新设容差。加上后 E85 对照树 17/30 完成，剩下 13 次都是 (d)。

入口比较（第 360 行）在组件后端上能通过，因为“实际”身体也由同一个计算器算出。到了 Fabric，真实客户端的数值不会和计算器逐位相同。这是推断，没有在 Fabric 上验证：如果不改，prepared 入口很可能每次都是 `ENTRY_MISMATCH`。D117 应让两处比较都复用同一个规则。1e-7 是否也适用于空中落地的状态，需要 Fabric 证据确认。

### 3.2 (d) receiver 借快照失败后永久拒绝

机制：

1. `WorldKnowledge.borrow_snapshot_version()`（`world_model.py:1051–1060`）用 `_snapshot_version_lock.acquire(False)`，拿不到锁就返回 None。
2. 观察写入由 `_snapshot_observation` 包装，在 `with self._snapshot_version_lock:` 里执行（`world_model.py:340–341`），是阻塞式持锁。
3. receiver 的 `_seal_snapshot()`（`motion_worker.py:1322–1335`）只借一次；借不到时租约状态保持 `NOT_READY`。外层还有 `except Exception: pass`，封存时的任何异常也会变成同样的结果。
4. 对 prepared 准备，非 READY 一律记成 `MISSING_INFORMATION` 加 `REJECTED / WORLD_SNAPSHOT`（`motion_worker.py:1385–1393`），`missing_cells` 为空，没有重试。

这违反 AGENTS.md §5 的“缺少信息、计算未完成、明确阻塞和超时必须分别表达”：锁忙既不是缺少信息，也不是世界快照无效。

发生率（“从未登记”的次数，80 tick）：

| 条件 | 原样树 | 来源 |
|---|---:|---|
| 负载未控制（其它核另有测试进程） | 17/30；25 tick 版 15/30 | E85 |
| 空闲单核 | 3/30 | E95 |
| 同核另有忙循环 | 5/30 | E95 |

对照 `e91_receiver_snapshot_retry_control.diff`：receiver 在同一次封存中最多再借 5 次，每次间隔 1 ms。加上它以后，E91 和 E95 全部完成。

**但它只是缓解。** 持续失败时它没有用（§3.3）。正式修法应该是：

- 把“锁忙”表达成可重试的瞬时状态，在 receiver 的下一个周期重试；
- 重试用尽以后，拒绝原因要和“世界快照无效”区分开；
- 拒绝必须通知执行器撤掉 prepared 后继要求（§3.3）。

### 3.3 (e) 拿不到或用不了 prepared 后继时，没有有界出口

| 情况 | 机制 | 证据 |
|---|---|---|
| 准备一直失败 | `_advance()` 只看 `next_index in self._prepared_action_indices`（`action_route_executor.py:1441`）就返回 `prepared_action_boundary`。这个集合由 `require_prepared_action()` 加入，只在换新路线时清空（`action_route_executor.py:293、733`）。`stage_prepared_action()` 没有 handle 时返回 `NOT_READY`，监督者拒绝，下一帧重复。`deadline_tick`／`OVERDUE` 只在 handle 存在时生效。 | E96：快照借用一律返回 None。协调器在 tick 8–19 共 12 次以 `upcoming_motion_selection_rejected` 退役这项准备；执行器从 tick 9 起 `prepared_successor_required=True`，从 tick 20 到 80 都停在 `prepared_action_boundary`。监视器零违规。原样树和四处对照树结果相同。 |
| prepared 控制器进入 RECOVERING | `prepared_decision()` 进入 RECOVERING 后一直返回 `BODY_RESPONSIBILITY_UNRESOLVED`。 | E84 原样树：tick 32 已经安全落地，到 tick 80 会话仍是 `executing / BODY_RESPONSIBILITY_UNRESOLVED`。 |

第一种情况是单一拥有者的问题：

- “这次准备已经失败”的事实在协调器和收件箱里；
- “下一个动作必须用 prepared”的要求在执行器里；
- 两者之间没有事件。

现行生产链用普通 SOLVE 就能完成同一条路线（E86、E92），所以合理的出口是撤掉要求、回退普通 SOLVE。对 RECOVERING：

- 着地静止以后，应交给已有的普通恢复路径；
- 如果没有，就在有界 tick 内以类型化原因终止。

现有监视器没有发现这两种无界等待。D117 应加一条活性检查：边界等待和 RECOVERING 都必须在给定 tick 数内结束或转移。

- 当前动作集上，连续接续每次交接省 1–2 tick，不扩大可达地形。

## 7. 下一步建议

### 7.1 是否单独处理

**应该单独处理，而且应先于扩大矩阵和 Fabric。** 理由：

1. **要改的范围集中：**
   - 五项都在 prepared 后继链上，涉及 `motion_coordination`、`action_route_executor`、`route_body_controller`、`motion_candidate` 和 `motion_worker` 中各一处；
   - 不改 Session 状态、监督者协议或 WorldModel 语义版本。
2. **生产风险低：**
   - 生产链现在不走这条链（E86）；
   - 只有 a 的共用 apply 函数和 b 的共用“完成当前动作”步骤会碰到普通路径，回归集中在 D102、D113、D114、D116、R27 异步接纳和连续性测试。
3. **不修就不能扩矩阵：**
   - 原样时，登记成功的运行 100% 停住；
   - 只修两项时，仍然 100% 停住。

**但不应只处理这两项。** 只修 a、b 的结果是 0/30 完成（E88），下一轮会在 (c) 上再止损一次，接着是 (d)、(e)。

### 7.2 D117“prepared 后继交接收口”的范围与门槛

| 项 | 修法 | RED | mutation |
|---|---|---|---|
| a | 普通与 prepared 共用一个 apply 函数：`try_apply` → 安装 → 记录 APPLIED（带 accepted_ns）→ 退役 | prepared 安装后监视器 I19 | 去掉 `try_apply` 后 I19 重现 |
| b | 普通与 prepared 共用“完成当前动作”步骤：预检 tracker → 提交执行器 → 提交 tracker；失败时类型化、无半提交 | prepared 激活后下一帧 `route_identity_changed` | 跳过 tracker 提交；或让 tracker 预检失败，断言执行器下标不变 |
| c | prepared 入口与运行中比较都复用 `_state_matches_verified_start()` | 1 ULP 速度差进入 RECOVERING | 恢复 `==` 后失败；超出 1e-7 的真实偏差仍被拒绝 |
| d | 锁忙表达为可重试的瞬时状态，在 receiver 下一周期有界重试；用尽后的原因和“快照无效”区分开；去掉 `except Exception: pass` 的吞异常 | 注入一次锁忙后永久 `WORLD_SNAPSHOT` | 去掉重试后失败；封存抛异常时类型为内部错误，不是缺少信息 |
| e | 准备被拒或过期时通知执行器撤掉 prepared 后继要求，回退普通 SOLVE；RECOVERING 在着地静止后交给普通恢复，或有界类型化终止 | E96 持续失败，tick 20–80 一直等待 | 去掉撤销通知后，活性检查失败 |

端到端门槛（组件后端，不跑 Fabric）：

- D116 代表链在“空闲单核”和“同核另有忙循环”两种条件下各 30/30 完成；
- 持续快照失败（E96 注入）时回退普通 SOLVE 并完成；回退后第二跳的起跳 tick 写进验收（现行生产链是 tick 22），并给出上界；
- 第二跳期间注入真实偏差（例如外力）时，在有界 tick 内转入普通恢复或类型化终止；
- I18–I22 零违规；监视器新增一条：边界等待与 RECOVERING 有上界；
- D116 时间线测试改成不依赖调度，在上述两种条件下各 20/20；
- D102、D113、D114、`test_action_continuity_formal` 和全量分片不退步。

时间盒：一个阶段。如果五项之外再出现新的阻塞，就停在“prepared 链保持撤回”的状态，写一份冻结决定，转回能力本身。生产已经能用普通 SOLVE 完成两跳，冻结不会让玩家失去什么。

### 7.3 收口之后

- **不要只为一格两跳单独跑一批 Fabric。** 那一批的玩家可见差异只有 1 tick（E92），主要价值是验证基础设施。
- **建议二选一：**
  1. 把连续接续和第一个需要保持动量的能力放进同一阶段，例如带助跑的两格疾跑跨隙，一次 Fabric 同时看到能力和接续的收益；
  2. 如果先跑基础设施 Fabric，就把它明确写成基础设施验证。重点看三件事：
     - prepared 入口与运行中比较在真实客户端数值下能否成立（§3.1）；
     - 快照锁在真实观察频率下的争用率；
     - 回退路径。

## 8. 证据边界

- 只在 Linux 上运行；没有运行 Windows 或 Fabric。Windows 结论只来自 D116 公开的时间线证据。
- prepared 链的所有运行，都依赖 D116 脚本的进程内补丁恢复自动准备。它们不代表现行生产行为，现行生产行为见 E86、E92 的 production 行。
- 四个对照 diff 只用于因果对照，不是建议提交的代码；e88 读取私有字段，e91 在 receiver 线程里 `sleep`。
- (d) 的发生率随负载变化，表中数字只说明“非零且会随负载升高”，不能当作 Windows 或 Fabric 上的发生率。
- “Fabric 上 prepared 入口精确比较很可能失败”是推断，没有实测。
- E93 只说明当前规划器不生成宽间隙路线；不说明动量动作在接续下一定可行。
- 本轮没有做性能测量；时间线脚本含方法级插桩，不能用来判断 8／15／30 ms 门槛。
