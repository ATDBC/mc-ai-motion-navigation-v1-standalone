# D110 审查：关闭证据链与生命周期修复（f663586）

日期：2026-10-15。审查对象：`origin/main` f663586 “Publish D110 evidence and lifecycle repair”。改前对照是 c2cc1ad（D109）。

D110 验收文档把 Linux settle 与 fd 的最终字节动态复核留给三方。本轮补齐这部分，并单独分析仍未通过的求解墙钟门槛。B10 的 Fabric 结论只读项目公开的精简证据，没有重跑 Windows 正式结果和 Fabric 实机批次。

## 结论

1. **close 诊断修复正确，D110-CLOSE-01 可以关闭。**
   - **B10 入口复测（E51）：** 用 B10 实际使用的 `_runtime_trace(..., capture_close_diagnostics=True, async_delivery=True)`，在 2 个 CPU、单 CPU、worker 前面先积压 200 条记录这三种条件下，close 行都 50/50（积压组 10/10）正确。同一脚本在 D109 上 50/50 得到 `null`。
   - **字节不变：** trace 与诊断文件的字节和 D109 同步路径完全一致。修复没有改变公共 trace 格式。
   - **失败注入：**
     - 诊断为 `null` 时，报出带上下文的 `ValueError`；
     - 队列满拒收 close 记录时，trace 和诊断两边都不出现 close 行，`dropped_records=1` 可见。
   - **项目新增测试质量好：**
     - 走真实的 `Runtime.close()` 顺序；
     - 后端会清空诊断；
     - 断言只在调用线程读取诊断；
     - 覆盖拒收和写失败。
   - D110 正式 B10 的 5253 行诊断，正好等于 1 次 reset、5251 步再加 1 次 close。

2. **Linux 生命周期修复成立。D110-LINUX-01、D109-N2、D109-N4 都可以关闭，但还要补两处只改测试的修正。**
   - **全量检查：** 185 个模块、2309 项，cleanup 185/185 `passed`。D5 矩阵和 D7 fd 门禁都通过。
   - **D5 矩阵：** 在 2 个 CPU 上 20/20 通过（D109 是 10/10 失败）。
   - **fork 链场景（E54b）：** 直接交给分片器时，D110 10/10 `passed`、分片器返回后 0 个存活进程、只登记 3 个进程。D109 是 10/10 `failed`、10 次都有存活、登记 100–107 个进程。
   - **D7 门禁：** 10/10 通过。
   - **新发现：** 单 CPU 时，`fork_during_cleanup` 子场景有约 1/5 失败在测试自己的前置条件上（`did not establish late`）。原因是 settle 现在立刻 SIGKILL，新 fork 的子进程还没来得及写自己的 PID 文件就被收掉了。清理本身是对的。改成由父进程在 fork 后写子进程 PID（只改测试场景的几行），单 CPU 下 20/20 通过。

3. **全量里的另一个错误是 D109 起就存在的不稳定测试，与 D110 无关。**
   - **现象：** `test_d102_action_handoff` 的 `test_same_worker_solve_choice_is_frozen_before_prepare` 在单核下，D110 失败 12/30，D109 失败 8/30。
   - **原因：** 接收线程第一轮只封存快照，下一轮才提交请求，而测试在 `decide()` 后只等一轮。对照显示 13/30 次需要等第二轮。
   - **修法：** 改为“最多等 5 轮，直到出现提交”，单核 30/30 通过。

4. **求解墙钟门槛：同意 D110 不改门槛、不重跑。但证据比“只能说明相关”更强，而且最可能的来源就是 B10 探针自己。**
   - **巧合概率：** 142 个样本里唯一超过 30 ms 的样本，恰好就是唯一与第 2 代 GC 重叠的样本。若两者无关，这种巧合的概率只有 1/142（约 0.7%）。
   - **探针自己的证据缓冲（E55）：** 探针把证据以 `json.loads` 得到的 dict 树常驻内存，`diagnostic()` 还另存一份原始行。按 D110 实际行数填充后：
     - 受 GC 跟踪的对象多出约 3 万个；
     - 本机一次完整 GC 多停 20.7–27.4 ms；
     - 只把已经算好的 JSON 字符串留在内存，增量降到 2.5–3.0 ms。
   - **证据增长也是触发源：** CPython 3.11 只在长寿对象增长超过 1/4 时才做第 2 代 GC，所以持续增长的证据本身就是触发它的原因。
   - **CPU 计时在 Windows 上不可用：** 上一轮本审查建议记线程 CPU 时间。D110 发现它在 Windows 上以 15.625 ms 为步进、无法归因，这个判断正确。
   - **可行的归因办法（E52）：** 用 `gc.callbacks` 记录全程每次 GC 的起止时间，运行结束后再按求解区间统计重叠停顿。42 个与第 2 代 GC 重叠的样本，扣除停顿后与无 GC 样本同分布；项目的 GC 计数判定与停顿计时 0 次不一致。
   - **建议：** 下一步同时做三件事，然后只跑一次 B10：
     1. 记录全程 GC 停顿区间；
     2. 证据缓冲改存字符串；
     3. 写清门槛保护的是哪一种延迟。

   这既不改门槛，也不优化求解器，只是去掉测量装置自己制造的停顿。

5. **小问题。**
   - D110 没有像 D109 那样公开 B10 运行提交 `67f4f1d8` 的生产文件语义哈希，公开读者无法核对 f663586 的脚本就是跑 B10 的那份。
   - close 诊断现在也经过 `trace_projection`。如果诊断里出现非有限浮点或非字符串键，失败的会是整条 close trace 记录，trace 也不再封存；以前只影响诊断行。这是有意的 fail-closed，记录在案即可。

## 2. close 诊断修复

### 2.1 实现

`CloseDiagnosticsTrace.write()`（`scripts/fabric_visibility_scenario.py:134`）在调用线程上处理 close 记录，步骤如下：

1. 遇到 `close_release` 时，当场读 `backend.last_diagnostics`；
2. 把诊断和原 payload 包成 `dict(trace_payload=..., close_diagnostics=...)`，再交给异步 writer；
3. worker 在 `_CloseDiagnosticsSink.write_projected()`（`:178`）里拆开包装：先写 trace 行，trace 写成功后才追加诊断行（`:185`）。

这样有三个性质：

- Runtime 在 `_close_backend()` 之前调用 `write()`，所以读到的一定是关闭前的值；
- 队列满被拒收时，两边都不写；
- trace 写失败时，诊断行也不写，writer 报 `sink_write` 失败，trace 不再封存。

这正是 D110 决定 2.1 要求的“同生同灭”。异步 writer 的 `_snapshot_payload` 在入队时复制可变容器，后端关闭时改写嵌套字段也不会影响已入队的值（项目新测试专门覆盖了这一点）。

D110 的 settle（`scripts/run_motion_nav_shards.py:940`）每轮先收集收养进程，再对身份（PID 与创建时间）匹配、非 root、非 zombie 的已登记进程直接 SIGKILL（`:913` `_kill_registered_linux_descendants`），然后回收并做稳定扫描。第一次正常清理仍先发 SIGTERM，所以正常进程仍有一次体面退出的机会。这与 D109 审查提出的对照改动一致，测试断言的改法也一致：只有中间进程先退出的场景要求收养。

### 3.3 新发现：`fork_during_cleanup` 的前置条件在单 CPU 上依赖调度

E54 在单 CPU 上 3/10、E54c 4/20 失败，断言都是 `fork_during_cleanup did not establish late`。2 个 CPU 时 20/20 通过。项目全量用的也是单核，那一次碰巧通过。

场景代码（`tests/motion_nav/test_d107_shard_runner.py:806`）里，守护进程的 SIGTERM 处理器在子进程中先 `setsid()`，再由子进程自己写 `late.pid`，父进程随即退出。整个过程是：

1. 第一次清理的 SIGTERM 让处理器 fork 出子进程，然后父进程退出；
2. 子进程立刻被 subreaper 收养；
3. settle 第一轮就对它 SIGKILL。

单 CPU 时，子进程可能还没被调度运行就被杀，`late.pid` 从来没写出来。E54b 证明这种情况下分片器的清理完全正确：0 存活、`cleanup=passed`。失败的只是测试的前置条件。

修法（`e54_fork_scenario_pid_test_proposal.diff`，只改测试场景）：由父进程用 `os.fork()` 的返回值写 `late.pid`，子进程只负责 `setsid()` 和等待。这样 `late.pid` 一定先于父进程退出写出，收养断言照常成立。对照在单 CPU 下 20/20 通过，五个子场景全部 0 失败。

## 5. 求解墙钟门槛

### 5.1 D110 的数据说明了什么

| 运行 | P95／P99／最大 (ms) | 超过 30 ms 的样本 |
|---|---|---|
| D109 D1 | 24.59／26.98／46.67 | 1 个 |
| D109 D8 | 24.54／26.42／41.03 | 1 个 |
| D110 | 24.60／27.63／39.25 | 1 个：`r4_validation_2-1-4`，3 个候选；gen0 与 gen2 各 1 次；线程 CPU 记为 31.25 ms |

D110 的 142 个样本中：

- gen0 与求解重叠 95 次，gen1 7 次，gen2 只有 1 次，就是那个离群样本；
- 线程 CPU 只有 0、15.625、31.25 ms 三个值（6／94／42 次），平均约 19.6 ms，与墙钟主体相符。

两点判断：

- **相关性很强。** 如果离群与 gen2 无关，唯一的离群恰好落在唯一的 gen2 样本上，概率是 1/142。D110 说“只能说明相关”是严谨的，但这已经是很强的相关。
- **线程 CPU 在 Windows 上确实帮不上忙。** 31.25 ms 只表示中间跨过了两个 15.625 ms 的计时中断，真实值大约在 16–47 ms 之间。D109 审查建议记 CPU 时间，没有考虑到 Windows 的记账粒度；D110 指出这一点是对的。

### 5.2 停顿从哪里来：探针自己的证据（E55）

B10 探针把六类证据缓冲在内存里，运行结束才落盘（`scripts/b10_gap_solver_runtime.py:131` `_B10EvidenceBuffer`，上限 43 MiB）：

- `append()` 已经算出 `encoded = strict_json_dumps(row)`，却把 `json.loads(encoded)` 得到的 dict／list 树留在内存（`:190`）；
- `diagnostic()` 另外把原始行留在 `rows` 列表里（`:808`）。

这些容器都受循环 GC 跟踪；字符串和整数不受跟踪。

E55 用项目的 `_B10EvidenceBuffer`，按 D110 实际行数填充：diagnostics 5253 行（行结构取自 D110 摘要里的 `last_close_diagnostics`），trials 142 行。每种状态做 15 次完整 `gc.collect()`，取最小值（受干扰最少）。两次运行：

| 状态 | 受跟踪对象 | 完整 GC 最小值增量 |
|---|---|---|
| 0 只有导入和求解夹具 | 39279 | 基线 7.0／6.4 ms |
| 1 项目现状（缓冲 dict 树 + rows 原始行） | +29993 | +20.7／+27.4 ms |
| 2 缓冲只存字符串，rows 仍存原始行 | +10543 | +11.2／+17.7 ms |
| 3 缓冲和 rows 都只存字符串 | +39 | +3.0／+2.5 ms |

还有两点：

- **规模被低估了。** 按字节算，D110 实机每行诊断约 1650 字节（8665157／5253），约为本实验行的 1.75 倍，实际增量只会更大。
- **增长本身在触发 GC。** CPython 3.11 只有在长寿对象新增量超过已有长寿对象的 1/4 时才做第 2 代 GC。探针证据在整个运行中持续增长，正是推动第 2 代 GC 一次次发生的原因。

E55 只覆盖探针证据这一部分。世界模型、观察和 Fabric 编解码的对象不在内，本实验不能说明它们各占多少。

### 5.3 怎样精确归因（E52）

E52 在 Linux 上直接调用项目的 `_measure_gap_solve`，轮换 R4 的 12 种入口求解 200 次。设置是：

- 常驻约 30 MB 对象；
- 后台线程在随机时刻 `gc.collect()`，模拟别的线程触发的第 2 代 GC，求解线程只能等 GIL；
- 同时用 `gc.callbacks` 记录全程每次 GC 的起止时间，运行结束后按求解区间计算重叠停顿。

结果：

- **判定一致：** 项目字段 `solve_gc_overlap=True` 103 次，`gc.callbacks` 测得有重叠停顿 103 次，0 次不一致。
- **扣除停顿后同分布：** 42 个与第 2 代 GC 重叠的样本墙钟最高 262 ms；扣除重叠停顿后 P50 62.9 ms、最大 97.3 ms。无 GC 重叠的 97 个样本 P50 61.5 ms、最大 91.8 ms。
- **粒度量化的 CPU 无法区分：** 按 Windows 粒度量化的线程 CPU 只有 31.25–93.75 ms 五个值，分不出这些样本。

有一个实现细节必须注意：重叠不能在每次求解结束时立即计算。本实验第一版就这样做，结果有 4 个样本漏算：别的线程触发的 GC 结束后，`stop` 回调要等那个线程重新拿到 GIL 才执行，可能晚于求解线程读取结束时间。改为运行结束后统一计算后，漏算消失。

E52 的 GC 频率和停顿长度是人为放大的，只用来验证归因方法，不代表 B10 的实际情况。最后一行 `gc.freeze()` 后完整 GC 为 0 ms，是因为冻结了全部现有对象；实际运行中冻结之后新建的对象仍会被扫描，那个数只能当作上限参考。

### 5.4 建议

下一阶段同时做下面三件事，然后只跑一次 B10：

1. **记录全程 GC 停顿。** 用 `gc.callbacks` 记录每次 GC 的代、起止时间，以及运行首尾的 `gc.get_stats()`。运行结束后，按 E52 的方法给每次求解算重叠停顿，摘要里报告第 2 代 GC 的次数和最长停顿。这在 Windows 上同样精确，不受 15.625 ms 记账粒度影响。
2. **去掉探针自己制造的停顿。**
   - `_B10EvidenceBuffer.append()` 直接保留已经算好的 `encoded` 字符串，`rows()` 在读取时再解析。这样“切断调用方引用、保留控制 tick 时的精确值”的语义不变。
   - `diagnostic()` 的 `rows` 同样只保留摘要需要的字段或字符串。

   这改的是测量装置，不是求解器，也不是生产路径。
3. **在决定文档里写清 30 ms 保护的是哪种延迟。** 两者的处境不同：
   - B10-B 的 142 个计时样本，来自探针在主进程控制线程上的同步调用（`scripts/b10_gap_solver_runtime.py:1093`），会被主进程里任何线程触发的 GC 拖住；
   - 默认后台链在 `MotionSolverWorker` 子进程里求解（`mc2p/motion_nav/motion_worker.py:180`），堆里没有这些探针证据。

   如果门槛要保护“控制线程的真实输入延迟”，它应该覆盖控制 tick 本身，而不只是求解区间；如果要保护“求解工作有界”，就应以扣除 GC 停顿后的墙钟判定，同时单独报告 GC 停顿。

如果做完第 1、2 条后墙钟最大值低于 30 ms，门槛不用改就能通过。如果仍然超过，第 1 条的数据会直接说明是 GC、调度还是求解本身。

## 8. 证据边界

- **平台：** 本轮只在 Linux 容器上运行（内核 6.18，Python 3.11.15）。Windows 正式结果与 Fabric B10 结论来自项目公开的精简证据，逐样本的 `b10-gap-solver-trials.jsonl` 只在项目本地，本审查无法核对单个样本。
- **E51 的夹具：** 后端是带 Fabric 语义的测试后端，不是真实的 `FabricBehaviorBackendV1`。
- **E52 与 E55 的局限：** 都是在 Linux 上测量的绝对毫秒，不能直接和 Windows 的 30 ms 比较。E55 只覆盖探针证据，不覆盖 B10 进程的全部堆；它说明“这部分足以造成十到二十毫秒级的完整 GC 停顿”，不证明 D110 那次 39 ms 就全部来自它。
- **全量与实验的并行：** 全量运行期间有部分实验在其他 CPU 上并行（E51、E52 试跑、E55 试跑），所以全量的模块耗时偏长。`test_d102_action_handoff` 的失败在之后的空闲单核重复中稳定复现（E56），D109 上同样复现，与并行无关。
- **对照改动的位置：** 两个测试 diff 只在 scratch 检出上应用，没有提交到项目。
