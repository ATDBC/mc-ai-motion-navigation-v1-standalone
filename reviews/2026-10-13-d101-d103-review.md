# D101—D103 审查：提前准备与可信注册运动证明（`07fa1d7`）

日期：2026-10-13。审查对象：`origin/main` `07fa1d7`，相对 `5c1485d` 新增 D101、D102、D103 三份决定、提前准备架构、三份阶段计划、三份验收文档，以及对应的生产代码和测试。脚本与输出在 [2026-10-13-d101-d103-review/](2026-10-13-d101-d103-review/)。

## 结论

**产品方向仍然正确，D101 也基本补齐了上一轮指出的协议缺口。但 D102／D103 的实施方向偏了，建议暂停 Task C／D、新的 G2 重跑和 Task 10，先做三件小事再继续。**

1. **D101 合理。**
   - 上一轮建议的八条里，七条已经写进 D101：
     - 0／1 tick 只属于输入流起点；
     - 首条回执立即上报；
     - 一致时只比较；
     - 证明范围与外力阈值分开；
     - 余量放在控制器并在承诺点重新定时；
     - 宽阔地面只用 `FixedRouteController`；
     - 提前计算下一动作，并规定欠载收尾。
   - “必须预排程”暂不冻结，等真实 tick 顺序证据，这个处理也是对的。
   - 只有“连跳落地后 0 tick 衔接”还没有规则。
2. **D101 M0 失败的原因，D102 没有处理，只是把它搬到了后台。**
   - M0 的完整决定 P99 为 48.6 ms，几乎全部来自动作开始时那一次证明：两条起点分支，每个边界都证一条停车尾迹，共 451 物理步。
   - E16：同一动作、同一台机器，只在关键边界（入口、最后可放弃点、着地恢复点、终点）证明尾迹：
     - 物理步从 451 降到 91，耗时降到 17%；
     - 按 M0 的 Windows 实测折算约 8.3 ms，在 15／30 ms 门槛内。
   - D102 没走这条路。它保留整份逐边界证明，并且每条尾迹存完整状态序列：jump_gap_1 的主轨迹只有 48 个状态，尾迹却有 516 个。然后把计算、世界快照和全量复核一起移进后台。
3. **后台链路自己的成本远大于证明本身（E15，Linux，生产代码）。**
   - 物理扫描约 0.1 s；worker 侧合计 0.38—1.79 s；receiver 登记 1.25—2.65 s。
   - 大头是快照逐格复核（120 格要 39 ms，6,496 格要 1.47 s），以及对整份结果重跑所有构造器（约 0.5 s）。
   - 真正防错的身份比对只要 0.8—1.4 ms：请求、输入、generation、ruleset、快照身份。
   - 风险：这条生产链路在 20 Hz 下从未完整计时，realtime 阶段没有运行。
     - 按本机比例粗估，Windows 上从提交到可用可能接近或超过第一跳的空中时间（约 14 tick）。
     - D103 试验只有 72—160 ms，但那是试验脚本，不是现在的生产代码。
4. **G2 的热路径门槛与项目自身设计矛盾。**
   - 量尺把控制线程上任何一次 `physics_1_21.step` 都记为禁止调用。
   - 但 D101 指定的唯一普通地面控制器 `FixedRouteController`，每 tick 都在控制线程逐候选做物理推演，证明“本 tick 输入＋后续中性漂移”安全（`_traversal_movement_safety`）。
   - G3 计划同时要求“地面段走 `FixedRouteController`”和“热调用为 0”，按现定义不可能同时成立。
   - Task C 的止损原因，是 fallback／closeout 现场做了 0+8 tick 的停车检查。E15 实测 Linux 1.18 ms，Windows 约 0.5 ms。这不是性能问题，是门槛把“有界小检查”和“整段重证”算成了同一类。
5. **规模和流程成本已经超过它要解决的问题。**
   - 本次生产代码 +5,887 行（忽略换行变化），测试与脚本 +10,120 行；`motion_worker.py` 从 278 行变为约 1,700 行。
   - 新增内容包括：快照发布、租约、引用计数，三种证明用途登记，激活绑定，以及针对 pickle 对象篡改的零信任复核。
   - G2 两次停止都不是运动问题：一次是量尺没等发布，一次是量尺漏传窗口。止损线又落在一个 0.5 ms 的检查上。到目前为止，运动能力相对 B10 没有新增交付。

**建议的下一步（第 6 节）：**

- 先把证明缩到关键节点；
- receiver 只做身份比对；
- 门槛改成时间预算加每 tick 物理步数上限；
- 先跑只读的 F-TICK。

做完这些，再决定后台准备链还需要保留多少。

## 3. D101 M0 为什么失败，以及本来可以怎样过

M0 的安全和功能项全部通过，只有 P99／最大值失败。验收文档已写明：204 个含初始证明的决定，P50 为 48.35 ms；其余 4,506 个决定的 P99 只有 0.17 ms。

初始证明就是 `scan_commitment`：两条起点分支，每个边界一条停车尾迹，jump_gap_1:A3 共 451 物理步。E16 在同一台机器上比较：

| 口径 | 物理步 | Linux 中位数 | 按 M0 折算的 Windows |
|---|---:|---:|---:|
| 每个边界一条尾迹（M0 实际做法） | 451 | 90.9 ms | 48.35 ms（实测） |
| 只在边界 0、2（最后可放弃）、17（着地恢复）、23（终点）证明尾迹 | 91 | 15.7 ms | **约 8.3 ms** |

- M0 的最大值与 P50 之比约 1.19，所以关键节点口径的最大值估计在 10 ms 左右，P99 15 ms 和最大值 30 ms 都有余量。P95 本来就由廉价决定主导（0.17 ms）。
- 关键节点之间的边界（例如边界 1，以及着地后 18—22）怎样覆盖，取决于欠载语义。D101 生命周期 §4 已允许“明确保持到下一个关键边界”。也可以用保守的支撑范围检查代替逐边界推演。这需要写清并测试；E16 只说明计时，不代表语义已经等价。
- 在已经运行的输入流中开始下一个动作（例如走着进入起跳），起点时序已确定，只需证一条分支，约 45 步，Windows 约 4—5 ms。
- 上一轮 E13 在 28 个样本上得到同样的规律：停车尾迹占证明物理步的 90%。整个动作的中位数，两条分支逐边界证明为 665 步，单分支只证关键节点为 45 步。

所以 M0 失败后最便宜的修正是缩小证明，而不是把它整体搬到后台。D102 架构 §5.2 反而把“逐边界停止／落地依据”写成了 bundle 的冻结内容。

## 4. D102／D103 的方向问题

### 4.1 证明没有变小，反而变大

生产版 `prepare_fixed_motion` 与 `scan_commitment` 的语义逐项一致：两条分支，每个边界一条尾迹。

不同的是，它把每条尾迹都封装成 `PreparedSafetyTail`，保存完整的 `PhysicsState` 序列、依赖事实和版本。对空中不可放弃的边界，它保存“到恢复点为止的后续轨迹＋恢复点尾迹”，因此空中段是平方级存储。

E15，jump_gap_1:A3：

| 内容 | 数量 |
|---|---:|
| 主轨迹状态（两条分支） | 48 |
| 尾迹（两条分支各 24） | 48 条，共 516 个状态 |
| pickle 字节：主轨迹 ／ 尾迹 | 9,192 ／ 95,993 |
| 封存后的消息 | 774,509 bytes |
| 只保留关键边界尾迹 | 每条分支 40 个状态 |

### 4.2 零信任复核：成本远高于证明本身

E15，生产代码，Linux，jump_gap_1:A3：

| 阶段 | 全窗口快照（6,496 格） | 局部快照（依赖包围盒外扩 1 格，120 格） |
|---|---:|---:|
| 对照：`scan_commitment` 物理扫描 | 111 ms | 同左 |
| `validate_sealed_snapshot`（每次构造、准备、登记都会调用） | 1,470 ms | 38.6 ms |
| worker `prepare_fixed_motion` 合计 | 1,793 ms | 381 ms |
| worker `seal_bundle` | 172 ms | 182 ms |
| receiver `_validate_for_registration` 合计 | 2,654 ms | 1,249 ms |
| 其中：重跑全部构造器（`_validate_values`） | 487 ms | 507 ms |
| 其中：规范化 proof 摘要 | 71 ms | 101 ms |
| 其中：不可变对象图检查 | 23 ms | 33 ms |
| 其中：pickle 解包 ／ 消息 SHA-256 | 4.4 ／ 2.0 ms | 5.7 ／ 2.7 ms |
| 其中：**身份比对**（请求、输入、generation、owner、路线、账本、快照、ruleset） | **0.8 ms** | **1.4 ms** |

几点判断：

- **真正拦住 D102／D103 两个反例的，是那 1 ms 的身份比对。**
  - 反例一：重新封存后 ruleset 不一致。
  - 反例二：同一请求换另一条合法输入。
  - 两者都由 `_parent_mismatch` 中的 ruleset 与 expected inputs 比较拦下。重跑构造器、对象图遍历和规范摘要，防的是“自己的 worker 用 pickle 送来被篡改的对象”。
- **这个威胁模型本身不自洽。**
  - 用 pickle 接收数据，本身就意味着完全信任发送方：pickle 能执行任意代码，构造器复核挡不住真正的恶意数据。
  - worker 自己算的 SHA-256 也认证不了什么。D102 自己写了“SHA-256 不认证外部不可信证明”。
  - 架构 §6 也说明不把对抗进程内任意内存修改当作现行能力。
- **超出了 D099“控制开发范围”的必要限度。** D099 要求新增防御对应已授权能力、真实失败或可信复现、已冻结验收或已决定的风险。两个审查反例对应的复现，用 1 ms 的身份比对已经全部覆盖；更重的复核没有对应额外的失败或复现。
- **快照路径也是同样的问题。**
  - 原 B10 正式链给后台求解打包局部物理快照，P99 为 0.725 ms（B12 验收）。
  - D103 试验每场新建 7×58×25＝10,150 格快照，构造 P95 为 39 ms。生产代码又在发布、准备和登记时各做一次逐格复核，每格约 0.2—0.3 ms（Linux）。
  - D102 的应对是在 `WorldKnowledge` 里加版本发布、两把锁、租约、引用计数和字节记账，而不是只取动作需要的小范围。

### 4.3 后台延迟在生产链上没有被测过

- D103 试验从提交到可用为 72—160 ms，第一跳落地前提前 8—10 tick。但那是 `.tmp` 中的试验脚本，receiver 只做了较轻的复核。
- 现在的生产 receiver 加入了重跑构造器和快照复核。G2 只跑到 fast 第 25 项，fast 计时只作诊断；realtime 和 fallback 都没有运行。
- 按 E15 的 Linux 耗时（worker 381 ms＋封存 182 ms＋receiver 1,249 ms）和本机比例粗估，局部快照下生产链在 Windows 上约 0.8—1.0 s。D103 在第一跳起跳那一 tick 提交第二跳；从起跳到着地约 14 tick（0.7 s）。
- 这个估计不精确，但足以说明：继续修 G2 之前，应先在 Windows 上实测生产链“提交 → 发布 → 首次消费”的耗时，不然 realtime 阶段可能因迟交付而失败。

### 4.4 门槛定义：数调用而不是看时间

G2 量尺（`tests/sim/d102_prepared_motion.py` 的 `_ControlMeter`）只要控制线程上出现以下任一调用就计为禁止调用：

- `physics_1_21.step`、`verified_ground_rollout`、`rollout`；
- 任何 `json`／`pickle` 的 dump／load；
- 任何 `sha` 调用；
- 等待超过 1 ms 的锁。

**问题一：与正式地面控制器矛盾。**

- `FixedRouteController._verified_traversal_movement` 每 tick 对候选移动逐个调用 `_traversal_movement_safety`。后者用 `physics_step` 推演“本 tick 输入＋后续中性漂移”，直到停住或越出走廊。
- 这正是 D101 §6 指定的唯一普通地面路径，自 B03 起一直在控制线程运行。
- G3 计划（Task 10）同时要求 `test_ground_segments_use_fixed_route_controller` 和“热调用 0”。按现在的计数，G3 无法通过；或者只能把地面控制改标为豁免，那样门槛就失去意义。

**问题二：把小检查和大工作算成一类。**

E15 实测 `verified_ground_rollout`：

| 调用 | Linux 中位数 | Windows 估算 |
|---|---:|---:|
| fallback／closeout：0+8 tick | 1.18 ms | 约 0.5 ms |
| 中性一步：1+0 tick | 0.15 ms | 约 0.07 ms |
| 落稳检查：1+8 tick | 1.31 ms | 约 0.6 ms |

Task C 因为这些调用存在而止损。而 8／15／30 ms 的预算完全容得下它们。门槛真正要防的，是在控制线程跑无界搜索或整份 451 步证明，而不是一个 8 tick 的停车检查。

**建议的门槛形式：**

- 完整控制决定仍按 8／15／30 ms 计时；
- 另设每 tick 控制线程物理步上限，例如 ≤64 步；
- 只把无界或整份工作列为禁止：搜索、整份证明扫描、整份快照构造。

这样，`FixedRouteController`、fallback 和 closeout 都是合规的有界检查，Task C 的止损条件也随之消失。

此外，`motion_worker.py` 的关闭路径依赖 `multiprocessing.Queue` 的私有属性（`_on_queue_feeder_error`、`_thread`、`_writer`），并按 `win32` 分支处理。在 Linux 上，新增测试 261 项中这一类有 2 项失败（另有 2 项是只允许在 Windows 运行的 M0 runner，3 项跳过）。Windows 是正式平台，这不是阻塞项；但它说明关闭逻辑已经深入到解释器内部细节，维护成本高。

## 5. 哪些部分值得保留

- **D101 的协议规则**：起点时序、首回执、只比较、阈值分离、余量位置、宽地面唯一控制器、生命周期。
- **D102 的基本思路**：
  - 在现有 worker 中提前准备下一动作；
  - 父侧保存 expected inputs 并做身份比对；
  - 准备结果不拥有身体，交接仍由监督者决定；
  - 迟交付时执行已证明的安全前段。
  - D103 试验已经说明热决定可以压到 0.2—0.3 ms，第一跳空中的时间足够准备第二跳。
- **D103 Task A／B 的修正**：执行窗口统一由一个函数生成；观察请求的容量校验移出控制路径。这两项都是真实缺陷，修法也小。

## 6. 建议的方向调整

按顺序做，每一步都小，且可单独验收：

1. **暂停扩张。** Task C／D、新 G1 predecessor、F2 重跑和 Task 10 都先不做。G2 的 FAILED／STOPPED 记录保持原样。
2. **证明瘦身（最关键）。**
   - 尾迹只在关键边界证明：入口、最后可放弃点、着地恢复点、终点。
   - 关键节点之间按 D101 生命周期 §4“保持到下一个关键边界”处理，或用保守支撑范围检查覆盖。
   - 尾迹只存输入和起点索引，真正执行时再在控制线程推演（≤9 步，约 0.5 ms）。
   - 输入流已运行时只证一条分支。
   - 用原 M0 量尺和原 8／15／30 门槛同步重测。按 E16 估计，单跳可以不靠后台直接通过。
3. **信任自己的 worker。**
   - receiver 只做 `_parent_mismatch` 那一类身份比对，加三向 ruleset 和当前依赖版本，约 1 ms。
   - 重跑构造器、对象图遍历和规范摘要移到测试或调试模式。
   - 如果担心传输损坏，保留一次消息摘要即可（约 2 ms）。
4. **快照只取动作需要的范围。**
   - 用现有 `PhysicsWorldView.snapshot(bounds)`，取动作扫掠范围外扩 1 格。B10 正式链已有 P99 0.7 ms 的先例。
   - 不可变元组由 Python 回收，不需要租约和引用计数。
5. **门槛改为时间预算加物理步上限**（4.4 节），恢复 `FixedRouteController` 和有界 fallback 的合法地位。
6. **先跑 F-TICK。** 40 次只读记录，回答“同 tick 命令能否赶上输入采样”。
   - 能赶上，或可以有限预排程：关键节点口径的欠载语义最简单。
   - 赶不上：再决定是否需要更密的尾迹。
   - 这一步不依赖 G2，目前没有技术理由排在 G2／G3 之后。
7. **之后再接正式两跳。**
   - 在 B10 已有的后台求解链上增加“第一跳空中准备第二跳＋着地比较”。
   - 预计改动几百行，而不是重建 worker 和 registry。
   - 同时补上连跳 0 tick 衔接的规则（D101 尚未涉及）。

## 7. 证据边界

- **E15／E16 都是 Linux 计时。** Windows 数字用 D101 M0 的同一证明换算，只代表量级。本机物理扫描比两天前同类测量慢约一倍，所以统一使用同一时刻测得的比例。
- **E15 的夹具：**
  - 来自项目测试；全窗口 6,496 格是测试夹具的世界范围，局部快照只保留证明依赖附近的格子；
  - 正式链的实际快照大小取决于将来的实现，所以表中两列代表上下两端。
- **E16 只是计时口径。**
  - 它复用项目的 `_prove_entry`／`_tail`，并逐个核对关键边界尾迹状态与完整扫描一致；
  - 没有实现新的证明器，也没有证明关键节点之间的欠载语义已经等价。
- **生产链 20 Hz 端到端延迟：** 本审查没有运行（需要 Windows spawn 和完整量尺），第 4.3 节只是风险估计。
- **Linux 测试：** 新增测试 261 项，2 项失败、2 项错误、3 项跳过；失败和错误的原因见 4.5 节。
- **未做的事：** 没有修改项目代码，没有运行 Fabric，也没有复核 G0／G1 的本地原始证据（README 已说明这些原始字节不在公开快照中）。
