## 结论

**1. 证据和工具这一半做得很好。**
- **身体归属：** 最终 2,000 场中，不再有"施加了输入却没有控制者"的 tick，我已核实。原来误计为步行停顿的 187 tick 归入了"入口恢复"；自由下落不再算作停顿。
- **迁移门禁：** 之前一直没被执行到的 4 个迁移函数，补上了正式路径故障场景。
- **查出了模拟器自身的缺陷：** 旧模拟器按诊断名称决定是否注入外力，导致 16 组协调回归实际收到的扰动不同。项目如实保留了旧记录和差异清单。
- **新发现两个修复前就存在的缺陷：** R28-C-01（脚下支撑整体降低半格后无界等待，违反 I4）和 R28-C-02，都已登记。
- **Fabric：** 56 场如实报告为 20 完成、36 未完成。
- 三份归档的校验和都通过，883/883 测试通过。

**2. 但另一半——终点接近筛选——没有达到目的，而且引入了新问题。**

| 检查 | 结果 |
|---|---|
| 筛选的产出 | 2,859 次筛选：2,158 次可行，701 次预算耗尽，**判定"不支持"0 次** |
| 玩家站位失败任务中的筛选状态 | 283 个失败中，282 个是预算耗尽，1 个是筛选判可行但实际失败 |
| 是否提前失败 | 失败时刻与批次 5 之前逐项相同（中位 48 → 48、58.5 → 58.5、47 → 47 tick），所有失败任务仍先移动、后失败 |
| `terminal_approach_control_unsupported` 从哪来 | `action_route_executor.py:823`：最后一段普通步行一旦出现 `fixed_route_has_no_forward_control` 就改成这个名字。这是按原因文案改名，背后没有筛选的判定 |
| 预算是否够用 | 预算耗尽时，688/701 次只检查了 1 个候选位置，中位推演 54 tick；"最多 6 个位置"实际上从未达到。另有 15 次超过 50 ms，最长 96.5 ms |
| 产品结果 | 玩家站位正常层 58 → 59、晚到层 57 → 58 |
| **可复现性** | 在 Linux 上原样复跑 v3：**73/2,000 个任务的行为与归档不同**，其中 1 个成功变成失败。原因是筛选按 50 ms 墙钟截止：在一台机器上算完，在另一台上用尽预算，两者走的路线不同 |

最后一项要特别说明：成功变失败的那个任务正是种子 136，也就是验收第 10.7 节记为"批次 5 新增完成"的那一项。在我的机器上它失败了。

**3. 这个方向偏了，我上一轮的建议有一部分责任。** 上一轮我建议"选目标点时加入控制器能到达的条件，到不了就提前拒绝"，并把真正的控制器修改放到 R28-2。批次 5 把前一条做成了一套基于计算器推演的后台筛选。结果是：
- 为一个可恢复的普通步行动作，加了 216 行的预测机制；
- 它没有产出任何"不支持"的判定；
- 它让机器人的行为依赖机器速度；
- 玩家站位的成功率几乎没有变化。

这正是方向评估中提醒过的模式：精确地刻画失败，而不是减少失败。我当时应该直接建议修控制器。

**4. 问题其实出在控制器上，修起来不复杂。**
- 原因：普通步行每次前进输入至少维持 2 tick（`input_lease_ticks = 2`），预测里还要算上松键后的滑行；预测中一旦碰到墙，就把这个输入判为不可用。所以从静止起步，一次前进至少滑行约 0.35 格，身体永远贴不近墙。而在 Minecraft 里撞墙是无害的，身体只会被挡住。
- 原型（[`proto-terminal-wall-contact.diff`](2026-10-02-r28-batch5-review/proto-terminal-wall-contact.diff)，+6 行）：路线末端 1 格之内，预测碰到墙时在接触点截断，不再判为不可用。
- 在同一台机器上，与未修改版本做完整 v3 配对比较：

|---|---|---|
| 玩家站位，正常 | 58/200 | **117/200** |
| 玩家站位，晚到 | 58/200 | **116/200** |
| 正面贴墙 | 2/50 | 39/50 |
| 沿墙贴墙 | 2/50 | 38/50 |
| 走廊尽头 | 0/50 | 26/50 |
| 墙角 | 0/50 | 20/50 |
| 边缘悬出 0.2 格 | 0/50 | 0/50（需要潜行接近，未处理） |
| 原八层 | 1,589/1,600 | 1,589/1,600 |
| 连续高度层、严格下降层 | — | 指标逐项不变 |
| 失败转成功 / 成功转失败 | — | 119 / 2（走廊中间，种子 187，两个条件各 1 个） |
| 运动导航测试 | 883/883 | 883/883 |

这只是一个草案，不能直接合入，限制见第三节。

**建议：**

| 优先级 | 内容 |
|---|---|
| 立即 | 删除按原因文案改名的逻辑，如实报告 `fixed_route_has_no_forward_control`，并注明筛选已用尽预算 |
| 立即 | 筛选不能让机器人的行为依赖墙钟时间。建议删除筛选，或至少让它只做诊断、不决定路线，把 `terminal_approach.py` 和相关接线一并移除 |
| R28-1 之前 | 修好 R28-C-01 无界等待（属于 S4 安全规则，是阻塞项） |
| 范围决定 | 把"终点接近控制"（墙面允许接触，边缘用潜行接近）排在跟随探针之前。否则跟随探针在室内会被这个已知缺口淹没。它需要占用一个批次，而时间盒已经没有余量，需要你来决定 |

## 一、终点接近筛选的审计

审计脚本 [`screening_audit.py`](2026-10-02-r28-batch5-review/screening_audit.py) 读取 v3 归档中每个任务的 `terminal_screening` 字段（同一结果在每一行轨迹上重复记录，已去重）。

### 1. 筛选状态（玩家站位，正常 + 晚到）

| 站位 | 失败任务的筛选状态 | 成功任务的筛选状态 |
|---|---|---|
| 墙角 | 50 个，全部预算耗尽 | — |
| 走廊尽头 | 50 个，全部预算耗尽 | — |
| 边缘悬出 0.2 | 50 个，全部预算耗尽 | — |
| 正面贴墙 | 46 个预算耗尽，1 个判可行 | 3 个判可行 |
| 沿墙贴墙 | 48 个预算耗尽 | 2 个判可行 |
| 走廊中间 | 22 个预算耗尽 | 26 个判可行，2 个预算耗尽 |
| 边缘悬出 0.1 | 16 个预算耗尽 | 10 个判可行，24 个预算耗尽 |

- **0 次判为"不支持"。** D050 写明"预算耗尽不是不支持的证明"，但这些任务最终都以 `terminal_approach_control_unsupported` 结束。这个名字来自执行器按原因文案改名，与 D050 和 AGENTS.md"不用 reason 字符串暗中决定……"的原则都不一致。
- **筛选判可行，任务却失败了 1 次**（正面贴墙）。说明筛选与实际控制并不完全一致。

### 2. 失败时刻没有提前

批次 5 前后，同一批任务的结束 tick 中位数完全相同，所有失败任务都先移动、后失败（`screening_audit-7348b64.txt` 第 2 节）。验收 10.3 要求"贴墙与边缘不支持的任务可以失败，但要提前、明确、有界"，其中"提前"和"明确"都没有做到。

### 3. 预算结构上不够

- 每推进 1 tick 大约要 0.8–0.9 ms，50 ms 内中位只能推 54 tick。
- 预算耗尽的 701 次中，688 次只检查了 1 个候选位置。架构文档中"最多检查 6 个内部位置"实际上从未达到。
- 有 15 次超过 50 ms 截止，最长 96.5 ms。文档报告了 P95 45.81 ms 和 P99 47.65 ms，但没有报告最大值。

## 二、筛选让行为依赖机器速度

[`determinism_check.py`](2026-10-02-r28-batch5-review/determinism_check.py) 在 Linux 上原样复跑 v3，与 Windows 上的归档逐任务比较（[输出](2026-10-02-r28-batch5-review/determinism-7348b64.txt)）：

| 范围 | 结果 |
|---|---|
| 2,000 个任务 | 1,927 个指标完全一致，**73 个不同** |
| 不同的任务分布 | 指定点 48、目标修订 5、玩家站位 20；连续高度和严格下降层 0 |
| 不同的原因 | 73 个全部是筛选结果翻转：一台机器上判可行，另一台上预算耗尽（或者反过来） |
| 成功数 | 归档 1,706，复跑 1,705；`player-normal-000136` 由成功变为失败 |

此前两轮，未修改的代码跨平台复跑都是 320/320、384/384 完全一致。是批次 5 引入了墙钟依赖。它的后果有三个：
- R28-1 的"行为不变"配对比较要求逐项相等，现在受机器负载影响，会出现假的差异，也可能掩盖真的差异；
- 统计验收中的"同一候选、同一输入"在不同机器上不再是同一实验；
- 机器人在真实服务器上，行为会随负载变化。

D050 写了"Python 不能提供硬实时保证，因此要报告实际耗时"，但问题不在于耗时报得准不准，而在于**一个由墙钟决定的结果被用来选路线**。

## 三、控制器原型

### 根因

`FixedRouteController._prepare_candidate_rollout` 用 `input_lease_ticks = 2` 次相同输入，再加松键后滑到停止，来预测每个候选输入的轨迹；`_evaluate_candidate` 在这段预测中只要碰到墙，就把候选判为不可用。按 1.21 的步行参数，从静止开始，一次前进的总位移约 0.35 格。所以正面接近墙时，身体最近停在离墙约 0.35–0.40 格处，与上一轮扫描到的结果一致。

### 原型与限制

原型只在路线末端 1 格内，把"碰墙"改为在接触点截断预测（同机比较见 [`proto-terminal-wall-contact-v3.txt`](2026-10-02-r28-batch5-review/proto-terminal-wall-contact-v3.txt)，单独场景见 [`player_spots.txt`](2026-10-02-r28-batch5-review/player_spots.txt)）。它不能直接合入，原因有四：

1. **不是所有接触都无害。** 仙人掌之类的方块碰到会受伤。正式实现必须按现有方块运动特征只允许无害的完整方块，其他情况仍判为不可用。
2. **边缘需要另一种做法。** 悬出 0.2 格的情况应改用潜行接近：在 Minecraft 中潜行不会走下边缘。项目已经有潜行模式，探边也在用。
3. **还有遗漏。** 墙角和走廊尽头只修好了约一半；走廊中间种子 187 由成功变为失败，需要单独查原因。
4. **需要实机对照。** 按 R28 的规则，这是改变行为的修改，需要正式配对比较和 Fabric 对照。

与筛选比较：原型 6 行，不依赖墙钟，让玩家站位成功数翻倍，严格层逐项不变；筛选 216 行加接线，玩家站位成功数 +1，而且这 +1 依赖机器速度。

## 四、其他意见

1. **R28-C-01 是安全阻塞项。** 行走中脚下支撑整体降低半格后，任务一直等待路线释放，触发 I4（不终止），在修复前的代码上同样能复现。按 R28 验收，S4 违例阻塞阶段关闭。它正好属于 R28-1 统一偏离路径的范围，建议作为 R28-1 第一个必须通过的场景。
2. **阶段文档里有过时的描述。** `navigation-coordination-convergence-r28-plan.md` 第 9 行仍写"v3 尚未生成"，第 155 行仍写"批次 5 的接口、v3 清单和证据尚未实现"，与同一文件第 3 行和验收 10.7 矛盾。
3. **复杂度在增加。** 从 R28 开始（`403a23f`）到现在，`mc2p/motion_nav` 从 30,891 行增加到 31,398 行（+507），会话从 4,395 行增加到 4,399 行。R28-0 还没有开始迁移，这可以理解；但批次 5 新增的 216 行筛选模块方向相反，删掉它也就收回了这部分增量。
4. **时间盒。** 两天内已用掉 5 个批次，剩下 5 个对应 R28-1、4、3、跟随和 R28-5，没有余量，复核日期 10-15。删除筛选、修 R28-C-01、做终点接近控制，都会挤占这 5 个批次。建议现在就做一次范围决定，见下一节，而不是等到期。

## 五、建议的下一步

1. **小修（可以放进 R28-1 的第一个批次）：** 删除按原因文案改名；删除筛选或改为仅诊断；修正阶段文档。删除筛选后，v3 基线需要在确定性的代码上重新生成。
2. **R28-1：** 以 R28-C-01 为第一个必须通过的场景，按原计划迁移停止和交接的去向。
3. **范围决定（需要你来定）：** 终点接近控制（墙面允许接触，边缘用潜行）要放在跟随探针之前。二选一：
   - 把跟随探针的批次换成终点接近控制，跟随顺延到 R28 之后；
   - 把两者合并成一个批次，跟随探针只用开阔地场景，室内和贴墙场景留到终点接近控制完成后。

   不建议在终点接近控制完成之前，用室内场景评估跟随。

## 六、边界

- 控制器原型只在 sim 中验证，没有跑 Fabric；材质安全限制也还没有实现。
- 复跑在 4 核容器上用 4 个工作进程，比归档机器慢。筛选结果翻转的比例取决于机器和负载，73/2,000 只是这台机器上的一次结果。
- 我没有复核 1,448 个协调回归案例，也没有复核 192 项玩家站位边界和 56 场 Fabric 的原始流。
