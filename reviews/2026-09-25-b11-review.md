## 结论

1. **D024 修好了上一轮发现的伤害与击退拆分。** 修正用公开轨迹中的真实时序（序号 445／446）写成了回归测试。我补测了一个边界：宽限期后紧接着一次“缺世界格”的残差，同一次受击仍会被拆开。这个边界不比修正前更差，但到 B12 部分观察时会更常见（第一节）。
2. **B11 的事务设计是对的，符合 D025“先确认世界变化，再重新规划”。**
   - 一次只放一块；
   - 只有后续观察中目标格出现预期方块、同一槽位数量减 1，才算成功；
   - `pending_confirmation` 不算成功，重试有上限；
   - 失败时不写入假设方块；
   - 站位保证失败时松开潜行也不会掉下去。

   组件检查全部通过。这是项目第一次真正“创造地形”，与总体设想中的“利用地形、创造地形”直接相关（第二节）。
3. **最需要处理的是 B10 跨隙回归两次都失败。** 文档把它归为“既有时序波动”，我认为现有证据更支持“R4 之后出现的回归，C1-R6 嫌疑最大”（第三节）：
   - R4 用同一条会话路径跑了默认协调 10／10、带速 60／60，全部通过；
   - R4 之后又合入了四批改动（C1-R 复审修复、第三轮修复、C1-R6、B11），都没有重跑 B10 Fabric，B11 之后第一次重跑就连续失败两次；
   - 两个失败信息都可以归到同一个触发条件：“输入在许可窗口外生效”。我离线复现了：晚一 tick 的输入会让执行器发送保持落地的中性输入，B10 脚本却把它当作“缺少已验证命令编号”直接抛错；
   - C1-R6 之后，Runtime 每帧写一次世界知识，B10 脚本又用自己的适配器再写一次。B10 每帧约 290 格观察，在本容器上单次写入约 5 ms，两次就在“收到观察到发出下一帧输入”之间多了约 10 ms。

   这是假设，不是定论。要确认，需要看尚未公开的两次失败轨迹。
4. **B11 代码有三处边界，需要在接入跟随或战斗之前处理。** 它们在 B11 的冻结场景里不会触发（第二节）：
   - 连续放置预算在每次目标修订时重置；
   - 放置进行中无法修订目标，会抛 `ContractViolation`；
   - 准备阶段（走位、瞄准、未被仲裁选中）没有代码上限。
5. **公开仓库里的 B11 证据不完整：**
   - 没有 B11 实机归档；
   - 验收文档引用的两个测试模块不在公开仓库；
   - README 仍停在 C1-R6。

## 一、D024 复核

**修正内容：**
- 伤害 tick 的残差如果“覆盖但没有偏差”，不再立即判为无位移，而是保留一个运动 tick（[`external_motion.py:361`][grace]）；
- 下一段残差只要起点正好是伤害 tick、终点是伤害 tick + 1，就可以归因（[`:457`][attribute]）。

**复核结果：**

| 检查 | 结果 |
|---|---|
| 上一轮的拆分脚本（读取公开 C1-C 归档） | 仍打印 445→446 的拆分。归档是修正前的历史记录，没有改写，这是预期结果 |
| 新增回归测试 `test_damage_and_knockback_one_tick_apart_form_one_damage_event` | 通过，合并为一次 `DAMAGE_KNOCKBACK`，事件记在序号 445、tick 448 |
| 上一轮其余四个复现脚本 | 结果与第四轮相同，没有回退 |

**需要注意两点：**

1. **新条件的适用范围比宽限期更广。**
   - 伤害 tick 的残差如果是 `NEEDS_WORLD`，下一段相邻残差现在也会被归因到这次伤害。
   - 为此，已有测试 `test_later_residual_cannot_claim_damage_tick_outside_its_interval` 把输入从 21→22 改成了 22→23，以保持原断言。
   - 这个行为本身与 D024 的语义一致，但没有正向测试覆盖“缺世界格之后的相邻偏差被归因”这条路径。建议补一条。
2. **宽限期后紧接缺世界格，仍会拆开。**
   - 顺序是：
     1. 伤害 tick 448 的残差匹配，进入宽限；
     2. 448→449 的残差 `NEEDS_WORLD`，锚点停在 448；
     3. 世界格补齐后得到 448→450 的偏差。
   - 第三步的起点等于伤害 tick，但终点是 +2，不满足新条件。于是伤害事实被丢弃，这次击退被记成无来源外力。
   - 复现见 [`damage_grace_then_missing_world.py`](2026-09-25-b11-repro/damage_grace_then_missing_world.py)。在 `7827f25` 上，同样的输入第一步就是 `damage_without_motion_residual`，最终结果相同，所以没有变差。
   - 公开 C1-C 通过批次中，1223 段非重复残差里有 31 段跨越多个 tick，其中 24 段是连续的 `NEEDS_WORLD`。这一批恰好没有和受击重叠。
   - 进入 B12 部分观察后，击退把身体推向未观察空间会更常见。建议：残差起点等于伤害 tick 时，只要它是宽限期后第一段完整残差就允许归因，不限定终点 tick。

## 二、B11 实现复核

### 已核对且成立的部分

| 设计要求 | 代码依据 |
|---|---|
| 只有纯移动路线不存在时才搭桥 | 会话在 `NO_KNOWN_ROUTE`（且缺失格已排除）或 `NO_ROUTE_WITHIN_COMPLETE_SCOPE` 后才调用 [`plan_next_bridge_interaction`][bridge-call]；桥规划器以“放置数优先、步数其次”排序 |
| 未知格不当空气 | [`_cell_kind`][cell-kind] 把未知地面、未知身体空间都判为 `blocked` |
| 一次只给出下一块 | 规划器只返回路径上第一个待放格；确认后会话从新世界重新规划 |
| 提交前检查完整 | [`_precondition_failure`][precondition] 检查站位、着地、潜行、静止、支撑格与目标格、主手物品、生存模式和准星 |
| 回执不等于成功 | [`register_dispatch`][dispatch] 在 `pending_confirmation` 时只进入等待；确认要求后续观察中出现预期方块且同一槽位数量减 1；超时重试上限为 2（[`:391`][timeout]） |
| 失败时身体安全 | 站位在支撑中心外 0.62 格（[`bridge_planner.py:153`][work-position]），容差 0.08（[`:181`][tolerance]）。身体中心最多超出支撑边 0.20 格，碰撞箱半宽 0.3，至少还有 0.1 格压在支撑上，失败后松开潜行也不会掉落 |
| 外部方块抢占目标格 | 会话直接核对支撑格和目标格（[`navigation_session.py:727`][invalid]），发现变化就重新规划，不点击。测试覆盖 |
| 材料不足时不开工 | [`_inventory_reason`][inventory] 在第一块之前比较主手数量和整座桥所需块数。测试覆盖 |

有一点值得记录：会话在放置期间不接收帧。恢复时 `session.ingest()` 从共享适配器拿到的只是最近一帧的变化集，期间其他帧的变化不会再交给会话。

B11 通过直接核对支撑格和目标格补上了这一点，所以没有问题。以后如果其他驱动也要长时间暂停导航，需要同样直接核对依赖，或者让适配器累积变化集。

### 边界 1：连续放置预算在每次目标修订时重置

- `start`（仅首个请求）、`start_goal`、`update_goal` 都会把 `_bridge_remaining` 重置为上限（[`navigation_session.py:516`][budget-a]、[`:541`][budget-b]、[`:610`][budget-c]）。内部重新规划不会重置，这一点是对的。
- 复现（[`goal_revision_and_bridge_budget.py`](2026-09-25-b11-repro/goal_revision_and_bridge_budget.py) 第 1 例）：确认两块后剩余 1；做一次目标修订后，剩余变回 3。
- 架构文档写的是“首版最多连续放置三块”。固定目标下两者一致。但接入跟随后，目标每几 tick 修订一次，放置总数就没有上限了。
- **建议：** 把预算放到任务层，或者由世界改变驱动器持有；只在上层明确重新授权时才重置，而不是跟着目标修订走。

### 边界 2：放置进行中无法修订目标

- 放置期间导航驱动器已经释放输入源（[`suspend_for_interaction`][suspend]）。[`replace_goal`][replace-goal] 要求输入源存在，所以直接抛出 `ContractViolation("runtime navigation driver has no active goal")`。
- `RuntimeWorldChangeNavigationDriver` 也没有提供别的修订入口。
- 复现见同一脚本第 2 例。验收中的“目标修订”反例是在 `interaction_required`（放置开始前）触发的，没有覆盖放置进行中的情况。
- **建议：** 明确规则。二选一：
  - 修订排队，等当前这块确认或失败后再生效；
  - 用有类型的原因取消当前事务。

  上层的正常请求不应该得到“编程错误”类型的异常。

### 边界 3：准备阶段没有代码上限

- 事务只限制了已提交的尝试次数和确认等待时间。准备阶段没有次数或时间上限，包括：
  - `work_position_not_reached`
  - `target_not_aligned`
  - 未潜行
  - `operation_not_selected`（[`:261`][not-selected]）
- 两个驱动器也没有上限。当前唯一的上限是 B11 脚本里的循环次数。
- 复现见 [`placement_ready_phase_has_no_limit.py`](2026-09-25-b11-repro/placement_ready_phase_has_no_limit.py)：让客户端始终报告准星落在方块顶面。结果 593 帧都是 `target_not_aligned`，没有进入终态，也没有发出任何操作。
- B11 阶段文档写“重试、候选数和连续放置数都有代码上限”。这对重试成立，对准备阶段不成立。
- **建议：** 给准备阶段加一个运动 tick 预算，超出后返回有类型的 `preparation_timeout`；`operation_not_selected` 也计入这个预算。

## 三、跨阶段回归

### B10 跨隙：两次运行都失败

| 时间点 | 事件 | B10 会话路径的 Fabric 结果 |
|---|---|---|
| 09-24 19:03 UTC | C1-R R4 `20260924T190335141223Z-a31d66d0` | 默认后台协调 10／10，带速 60／60，原跨隙 40／40 |
| `5c600cb`、`7bd1228` | C1-R 复审修复、第三轮修复。执行器改动只涉及取消和缺锚点路径，B10 单目标试次的正常路径不变 | 没有重跑（C1-R 验收第 310 行：“没有新增 Fabric 场景”） |
| `556381a` C1-R6 | Runtime 每次 step 写入世界知识；失败处置生效 | 没有重跑（C1-R6 阶段文档第 4 行、第 73 行） |
| D024、B11 之后 | `…e3a3debb`：第四方向“移动提案缺少已验证命令编号”<br>`…b30b60ce`：10 个协调试次后“一帧输入落在许可窗口外” | 2／2 失败 |

**分析：**

1. **第一个失败信息来自脚本断言，不是执行器本身失败。**
   - [`b10_gap_solver_runtime.py:591`][b10-assert] 要求每个 `submit_input` 决策都带已验证命令编号。
   - 但 [`ActionRouteExecutor`][route-map] 会把所有保持责任的中性输入都映射成 `submit_input=True`、不带编号。这类中性输入包括 `retain_landing_after_input_loss`（[`motion_candidate.py:523`][retain]）、依赖变化后保持落地、等待落地等。
   - 复现见 [`late_input_trips_b10_script_assertion.py`](2026-09-25-b11-repro/late_input_trips_b10_script_assertion.py)：许可窗口 11..12，输入在 13 生效。账本记为 `applied_outside_window`，执行器转为保持落地的中性输入，B10 脚本的判断条件为真。
   - 所以两次失败很可能是同一个触发条件：输入在许可窗口外生效。脚本在记录执行器原因之前就抛错了，所以轨迹里看不出这一点。
2. **C1-R6 之后，关键路径上多了一次写入。** 这是 R4 之后几批改动里，我找到的唯一一处新增每帧耗时。
   - Runtime 在每次 step 后写入自己的适配器（[`player_runtime_v1.py:383`][ingest-step]）。`7bd1228` 及更早的版本没有这一步。
   - B10 脚本仍然用自己的适配器再写一次（[`:99`][b10-adapter]、[`:635`][b10-ingest]）。B11 脚本和放置驱动器则直接读 Runtime 的适配器（[`block_placement_driver.py:101`][placement-frame]）。
   - 我在本容器上测了单次写入耗时：

     | 观察规模 | 中位数 | P95 |
     |---|---:|---:|
     | 294 格（B10 请求体积） | 4.6–4.9 ms | 5.7–8.0 ms |
     | 98 格 | 1.7 ms | 3.2 ms |

   - 所以每帧“收到观察到发出下一帧输入”之间，多出约 10 ms。作为对照，B10 的控制帧预算是 P95 ≤ 8 ms。
   - C1 场景每帧观察只有约 29–104 格（公开 C1-C 轨迹），C1-B 在 R6 之后回归通过。这与“观察规模越大越容易漏 tick”的假设一致。
3. **因此我不同意把它记为“既有时序边界”。** 同一条路径在 R4 全部通过，至少应记为“R4 之后首次出现，原因待查”。

**建议：**
1. B10 脚本改为读取 `runtime.navigation_observation_adapter.latest_frame`，去掉第二次写入；
2. 会话循环遇到保持责任的中性输入时，不直接抛错，而是记录 `reason_code` 和账本状态，按有类型的试次失败计入分母；
3. 每帧记录耗时分解和该帧输入实际生效 tick 与许可窗口的差。耗时分解包括：
   - Runtime 写入；
   - 脚本写入；
   - 会话决策；
   - 后端往返。
4. 重跑 B10；
5. 公开 `e3a3debb` 和 `b30b60ce` 两个失败归档，方便复核这个假设。

## 五、对照总体设想

- **B11 是第一个“创造地形”的能力。**
  - “准备 → 提交 → 观察确认 → 交回规划”的事务模式，可以直接推广到挖掘；
  - 也可以推广到战斗中的造地形，例如挡苦力怕、搭高台、封走廊。
- **目前的放置是“停下、潜行、对准、点击”，输入所有权按顺序交接：** 导航先释放输入，放置再接管。
  - 战斗中造地形往往需要边移动边放置，例如后撤时铺墙、跳起时在脚下放方块。
  - 这就需要同一帧内由不同拥有者分别提供移动、视角和操作，并由仲裁器确认可以同时执行。
  - 这和 B12-B 的“横移攻击”是同一个问题。建议设计 B12-B 时把它当作通用能力来做，不要做成只服务攻击的特例。
- **库存方面目前只检查主手。**
  - 设想中的战斗中切换物品、合成和进食，都需要库存操作事务；
  - 这类事务同样适合“提交后以观察确认”的模式；
  - 可以复用 `BlockPlacementTransaction` 的结构，不必另起一套。
