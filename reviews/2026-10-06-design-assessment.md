# 运动导航整体设计评估：上层设计优秀，中层协调需要重构

- 日期：2026-10-06
- 对象：`main` 上的 [`e108a32`][head]（S0-R 完成后）
- 量尺：[`2026-10-06-redesign/design_metrics.py`](2026-10-06-redesign/design_metrics.py)，基线输出为 `design_metrics-e108a32.txt` / `.json`
- 配套文档：[中层重构总方案](2026-10-06-redesign-master-plan.md)、[下一步方案（M0 + M1）](2026-10-06-redesign-next-step.md)、[D072 草案](2026-10-06-redesign/D072-draft.md)

## 结论

**上层设计是优秀的，中层"协调"的设计还不够好。**

代码多本身不是问题。问题在于：
- 关于"某种动作"的知识没有放在动作自己身上，而是散落在协调代码的各处；
- 同一个问题（异步结果、世界变化、身体交接）被拆给多个模块各自处理；
- Session 成了新规则的默认落点。

结果是两边不对称：
- 顶层容易扩展：跟随层只有 347 行；
- 动作层很难扩展：新增一种动作，要改 4—5 个核心协调文件。

测试和证据很强，但协调代码的理解成本高，而且最近每轮审查都在协调边界上发现新的真实缺陷。

确实存在更简洁的做法，详见总方案：
- 统一动作接口；
- 统一复核机制；
- 统一异步作业生命周期；
- Session 只负责状态转移和事件路由。

S0-R 留下的五组跨平台一致的行为基线，使这项重构可以分步进行，并且每一步都能证明行为没变。

## 一、评估口径

按项目在 AGENTS.md 中的三条要求评估：

| 要求 | 本文的衡量方式 |
|---|---|
| 不要过度工程化 | 同一个问题是否有更简单的统一解法；抽象是否解决了至少两个明确的重复点 |
| 保持可维护 | 长期状态是否只有一个拥有者；名称和类型是否直接表达用途；新人能否理解改动的影响范围 |
| 保持可扩展 | AGENTS.md 写明"新增跳跃主要扩展移动能力和动作执行"，所以要看新增一种动作实际要改哪些文件 |

所有数字都来自 `design_metrics.py` 对 `e108a32` 的静态统计，可以在后续每一步重复测量。

## 二、做得好的部分

这些是长期资产，重构时应保持不变：

1. **安全边界设计正确。**
   - LLM 不参与逐帧控制；
   - 只有 Runtime 仲裁后的唯一出口可以写玩家输入；
   - 动作发出后，必须由客户端的应用回执和后续观测确认；
   - 测试用的全知信息通过 `TEST_ORACLE` 与正式 actor 隔离；
   - 失败带类型，并有处置策略（`FailureDispositionPolicy`）。
2. **确定性基础设施很强。**
   - 运动计算器（`physics_1_21.py`，556 行）是纯函数；
   - 五组行为集合共 3,493 项，在 Windows 两轮、Linux 一轮的运行中逐项一致。

   这使"行为不变的重构"可以被证明，而不只是被相信。
3. **对外接口划分正确。** 正式跟随（`KnownWorldFollowDriver`，347 行）只调用开始、改目标、释放三个接口，没有复制规划、路线或恢复状态。
4. **类型化的中间结果已经存在。** 例如：
   - `ActionPreconditionResult` 区分"就绪"、"需要采集"、"需要信息"和"拒绝"；
   - 失败处置区分"重建运行时"和"结束回合"。

   重构可以直接复用这些类型。
5. **证据与决定记录完整。** 71 项设计决定和缺陷台账记录了每一次取舍，失败证据不被改写。

## 三、问题

### P1 协调层占比过大

| 层 | 行数 | 占比 |
|---|---:|---:|
| 物理、几何、世界知识 | 4,669 | 12% |
| 规划与求解 | 8,142 | 21% |
| 执行与控制 | 7,148 | 19% |
| **协调（异步、接纳、交接、恢复）** | **16,785** | **44%** |
| 其他（子目录） | 1,572 | 4% |

"怎么走"（物理、规划、执行）占 52%；"多个异步结果、世界变化、身体交接如何配合"占 44%。

对一个已知世界里的步行、跳跃、下降系统来说，协调层与"怎么走"几乎一样大。这说明复杂度主要来自模块之间的配合方式，而不是问题本身。

### P2 动作知识散落在协调代码中

在动作实现之外，共有 **70 处**按动作段类型做分支（`type(action) is ...`）：

| 文件 | 分支数 |
|---|---:|
| `action_route_executor.py` | 19 |
| `route_admission.py` | 17 |
| `motion_coordination.py` | 15 |
| `navigation_session.py` | 14 |
| 其余 3 个文件 | 5 |

这 70 处问的其实是同几类问题：

| 类别 | 分支数 | 问的是什么 |
|---|---:|---|
| A 控制器选择 | 17 | 这个动作由哪个控制器执行，什么时候算到达 |
| B 身体承诺与停止安全 | 7 | 中断时身体是否已离地；停下时要不要潜行护边 |
| C 后台动作求解 | 14 | 要不要求解、往哪个方向、在哪里落地 |
| D 前置条件与信息采集 | 6 | 执行前要看见什么、缺什么信息 |
| E 风险与伤害 | 3 | 预计伤害、何时算伤害已提交 |
| F 几何与进度 | 6 | 长度、终点、进度如何计算 |
| G 步行证明与复核 | 15 | 只有步行有几何证明配方，所以接纳和复核要单独判断步行 |
| H 路线类型登记 | 2 | 合法的动作段类型有哪些 |

每种动作段涉及的生产文件（不含定义它的 `action_route.py`）：

| 动作段 | 文件数 |
|---|---:|
| 步行 | 5 |
| 受控下降 | 5 |
| 一格跳 | 4 |
| 跨隙 | 4 |
| 台阶 | 2 |

**后果：** AGENTS.md 说新增跳跃"主要扩展移动能力和动作执行"，但实际上需要修改 Session、接纳、运动协调和执行器 4 个核心文件中的十几处分支。受控下降一项，在 Session 中就有 8 处专门判断，例如："为下降采集信息时要潜行"、"超过 1 格的下降跨过动作边界时，先让 Session 处理一帧"。

**根因：** 没有一个归属于动作本身的接口，回答"这个动作需要什么、会对身体做什么、怎样算完成"。协调代码只能按类型逐一询问。

### P3 两套复核机制

| 动作 | 接纳时的证明 | 世界变化后的复核 |
|---|---|---|
| 步行、台阶 | 表面图上的几何扫掠 | 在控制线程中同步重放步行配方（`route_validation.py`，632 行；`ActiveRouteTracker.validate`） |
| 一格跳、跨隙、下降 | 几何或空中包络查询 | 交给后台动作求解器，用计算器重新求解（运动 worker 的 `REVALIDATE` 作业） |

一套是同步、几何的，另一套是异步、基于计算器的。两套各有自己的配方、身份、预算、失效结论和恢复路径。

D058—D064 两天内连续 7 次修补接纳和复核链，S0 审查找到的接纳入口之间逐字相同的条件，都出在这两套机制的交界处。

### P4 两条异步管线

`PlanningCoordinator`（2,532 行）和 `MotionRouteCoordinator`（1,546 行）各自维护：
- 作业身份和窗口；
- 接纳记录；
- 过期、退场和取消。

两者有 7 个同名方法，例如 `_work_identity`、`_work_window`、`_record_admission`、`cancel_work`。`MotionSolveKind` 在求解器之外还被引用 15 次（执行器 6、运动协调 6、接纳 3）。

同一类竞态（结果迟到、身份过期、世界已变化）要在两处分别处理，R27、R28 的许多缺陷都出在这里。

### P5 身份与版本检查层层重复

逐字相同的条件：
- `admit` 与 `admit_surface` 之间 9 条；
- 两个直走入口之间 6 条；
- `route_admission.py` 与 `route_validation.py` 之间 5 条。

请求 ID、世界会话、目标修订、几何版本、依赖格，会在每个接纳入口、每种记录的构造校验、每个协调器中各检查一次。

本意是"层层防御"，实际变成了"层层重复"：每新增一个需要检查的事实，就要在 N 处补检查；漏了一处，就是一个新缺陷。

### P6 Session 过重

| 指标 | 数值 |
|---|---|
| 行数 | 5,072 |
| 方法数 | 132 |
| 赋值的状态字段 | 63 |
| 超过 100 行的方法 | 12 |
| 最长的方法 | `observe` 195 行、`propose` 187 行、`update_goal` 181 行、`_proposal` 180 行 |

与 R28 收尾时（`b1d43c2`）相比，经过 F1 和 S0-R，Session 又增加了 419 行。Session 同时承担：
- 生命周期；
- 事件路由；
- 目标修订；
- 信息采集；
- 风险预留；
- 各种动作的特殊处理；
- 两个协调器之间的配合。

新规则因此默认落在 Session 里。

### P7 生命周期状态用字符串表达

`RuntimeNavigationDriver` 中有 37 处生命周期字符串字面量，例如 `"stopping"`、`"failed"`。驱动器状态既由 `_sync_report` 从会话状态映射得来，又在多处被直接写入。

S0-R 修复的 I/O 崩溃就出在这里：调用方把"失去控制"覆盖成了"等待交接"。这违背了 AGENTS.md 的要求："不要用 reason 字符串……暗中决定权限和生命周期"。

### P8 测试固化的是历史案例，不是不变量

| 测试 | 规模 |
|---|---|
| 运动导航测试 | 128 个文件、45,587 行，是运动导航生产代码（38,316 行）的 1.2 倍 |
| 全部测试 | 64,203 行 |

很多测试是"某个种子在某个时刻出错"的回归。场景一变，这类测试就会悄悄失效，例子见 S0 审查中的 R28-C-02、补充故障和 seed 163。S0-R 为去掉墙钟删除计时断言时，"后台规划不阻塞控制"的保护也随之消失。

缺少的是按接口约定的测试：每种动作都应满足的不变量，只写一次，新增动作自动获得。

### P9 过程信号

- R28 的结构门槛没有通过；F1 记为"功能通过、结构未通过"；S0 的整理按清单估计只能减少约 1%。
- 最近几轮审查，每轮都在协调边界上发现新的真实问题：
  - 测试污染；
  - 测试前提失效；
  - I/O 失败后抛出未捕获异常；
  - 空中过早判定失败；
  - 测试保护倒退。

这说明在现有结构上继续整理或打补丁，收益在递减。问题需要在设计层面解决。

## 四、根因归纳

1. **动作知识没有归属到动作。** 协调代码按"问什么"组织，而不是按"哪种动作"组织，所以每种动作的规则散落在各处（P2、P6）。
2. **"结果是否仍然有效"没有统一的边界。** 版本和身份在每一层各查一次（P4、P5）。
3. **同一件事有两套实现。** 复核分同步几何和异步计算器两套（P3），异步作业有两条管线（P4）。
4. **生命周期没有显式模型。** Session 和驱动器的状态转移分散在代码中，用字符串表达（P6、P7）。
5. **开发方式是"一个失败、一个补丁、一条测试"。** 这让上面四点越积越多（P8、P9）。

## 五、更简洁的方向（详见总方案）

| 问题 | 方向 |
|---|---|
| P2、P6 | 每种动作实现一个 `ActionSpec`，回答 A—H 八类问题；协调代码只问接口，不判断类型。新增动作 = 新增一个实现并登记 |
| P3 | 接纳和复核统一走 `ActionSpec.revalidate`：用计算器重放输入程序并检查结果范围；步行的几何证明保留为同一接口后面的快速路径 |
| P4、P5 | 规划和动作求解共用一个异步作业生命周期；世界会话、几何版本、依赖集合、目标修订组成一个版本快照，只在接纳边界检查一次 |
| P6、P7 | Session 改为显式的状态转移表加事件路由；驱动器状态改为枚举 |
| P8 | 每个 `ActionSpec` 共用一套约定测试；迁移完成并由约定测试覆盖后，才移除对应的历史回归 |

## 六、边界

- 全部数字来自静态分析。类别 A—H 是按函数归类的近似，未归入的位置会标为 `unclassified`（当前为 0）。
- 没有测量运行时性能。统一复核对控制线程预算的影响，要在 M3 用正式性能门槛验证。
- 没有运行 Fabric。
- "更简洁"指结构和概念数量，不保证总行数立刻下降。迁移的前几步会先增加接口代码。
