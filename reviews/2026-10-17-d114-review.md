# D114 审查：B10 夹具改走正式导航驱动（37ea00b），以及下一步计划

日期：2026-10-17。审查对象：`origin/main` 37ea00b（“Publish D114 formal navigation driver harness”）。

平台说明：本轮只在 Linux 上运行项目函数、项目夹具和项目测试，或只读 D114 公开的原始证据；对照改动只放在临时工作树。Windows 与 Fabric 的结论来自 D114 公开证据。脚本和输出在 [`2026-10-17-d114-review/`](2026-10-17-d114-review/)。

## 结论

1. **D114 把 D113 的根因修对了，修法也是结构性的。** B10 协调器每帧都经过 `RuntimeNavigationDriver` 的 prepare／Runtime control／adopt，组件后端和 Fabric 调用同一个单场函数。我复核了四件事：
   - **Fabric 原始帧（E78）：** 1211 个控制帧中，获胜意图全部是本帧新提议的，没有旧候选，也没有夹具 manual 来源的意图。D113 那种“同一个 intent 连续复用 N 步”的现象没有再出现。
   - **变异对照（E82）：** 把上一轮 E69 的对照（去掉生产驱动里撤销旧租约的那一行）套到 D114 上，D114 组件测试在 10-tick 和 never-return 上 9 个失败、2 个错误，Runtime 报 `TIMED_OUT`。同类缺陷现在能在进入 Fabric 之前暴露。上一轮“夹具缺陷只能在唯一一次正式运行里发现”的问题，就单场控制循环而言已经关闭；外层的 trial 组装仍只在 Fabric 上执行（§4.2）。
   - **性能复算（E80）：** 用项目脚本从原始 trace 重算，1211 个生产帧 P95／P99／最大 2.96／5.4988／5.8878 ms，同步探针最大 27.9042 ms，与验收文档一致。
   - **测试：**
     - D114 直接与相邻的 13 个模块共 248 项通过；
     - Linux 全量分片 191 个模块中 190 个通过，共 2382 项，唯一的 error 是只能在 Windows 上运行的 D101；
     - 上一轮的 D102 竞态测试，以及同文件里另外三个依赖接收周期的测试，在同核争用下各 40/40 通过（E77；上一轮那个测试原样为 5/40 失败）。
2. **只读量尺修正的结论成立，但原因写得不准，而且真正的缺陷在夹具的传送等待。**
   - **修正本身成立：** 我用全部 32 个控制帧复算，3 个被拒的 10-tick 场景位移都是 0（E75）。
   - **但瞬态不是偶发的：** 48 个已执行场景每一个开头都有一次 `on_ground=false`（E79）。其中 45 次落在第 0 帧之前 2 tick，也就是传送到达的那一 tick，被夹具的传送等待吸收了。
   - **只有 3 次落进场景，条件很明确：** 上一场结束时，身体已经在本场起点，朝向也相同。这种情况共 4 次，3 次中招。
   - **机制：** `teleport()` 在“到位、着地、静止、朝向对齐”的第一帧就返回。身体本来就在目标位姿时，第一帧就满足条件，等待在服务器传送真正生效之前就结束了。随后到达的那一 tick 落进了场景。
   - **影响：** 这次只是让量尺误报。但它意味着场景可能在一次尚未生效的传送之后开始。以后加入新动作或带速入口时，迟到的传送可能在助跑中途重置速度。
   - **建议：** 修传送等待，不能只靠放宽量尺。
3. **我怀疑过的两个漏洞，核实后都不成立：**
   - **帧数上限不会被算成安全终态（E76）：** 截断时驱动总是先进入 STOPPING、拒绝立即释放，夹具直接抛错。上限从 3 到 36 都如此。
   - **只读修正的 tick 范围没有漏掉瞬态帧：** 第 0 帧的 grant tick 是 2285，但它的结果观察 tick 是 2286，正好在分析范围内。
4. **上一轮的流程问题已处理：**
   - 三份 TP 5A-R 失败记录按原 Git blob 恢复，并加入导出必需清单；
   - 入口文档已有 D114 条目；
   - 路线内交付估计被明确列为独立问题，不混进 D114。
5. **小问题：**
   - 缺陷台账没有 D114 条目。D110-SOLVE-01 那一行仍停在 D113 的“不满足关闭条件”。
   - README 的“先读什么”仍指向 D113。
   - 组件测试和 Fabric 用两种口径计“等待帧”（§4.2）。
   - 159 个变化文件里有 105 个只改了换行。

**下一步计划（§5）：**

1. 先用半天做 D114 收尾，不跑 Fabric：
   - 修传送等待；
   - 更新台账；
   - 统一“等待帧”口径。
2. 写一份**连续两跳前置条件盘点**决定，逐项给出状态：
   - D110-SOLVE-01：按 D111 计划的条件已可关闭；
   - T1 门槛的归属：取决于证明在控制线程还是 worker 上运行；
   - T2-3 是否仍是前置；
   - T3 能否用 D108／D114 证据关闭。
3. 定下路线内交付估计规则。连续两跳正是多动作路线，这一条必须先定。
4. 然后开始第一个产品能力阶段：**同一路线内两次 JumpGap 的连续执行**。先在组件矩阵上把第二个动作的延迟和失联跑通，再只跑一次 Fabric。

D104 以来连续 11 个决定都在加固 B10 的测量、生命周期和夹具；D114 是这一串里第一次所有登记场景都得到可接受的结果，其中 10-tick 依赖一项公开的只读量尺修正。现在应把精力转回能力本身，同时把“组件后端先执行完全相同的代码路径”作为以后每个阶段的固定前置。

### 1.3 新门槛能抓到 D113 的缺陷（E82）

### 1.4 帧数上限不会被当成安全终态（E76）

审查代码时我担心过一种情况：单场函数撞到 `max_control_frames` 后会调用 `driver.release("b10_formal_scenario_frame_limit")`。如果释放成功，会话以 CANCELLED 结束，原因字符串里没有 `deadline`、`unavailable` 或 `unresolved`，`_b10_coordinator_typed_safe_terminal` 会把它当成合法的 typed 终态。

E76 用项目测试自己的 `_run` 把上限设为 3–36（`output/e76_frame_limit_gate.txt`）。结果是：

- 每一档都抛出 `frame limit left body responsibility unresolved`：活动会话被取消后，驱动先进入 STOPPING，等身体交接证据，不会在同一帧释放；
- 不截断时，10-tick 用 38 帧、never-return 用 48 帧，自然结束，原因分别是 `execution_window_expired` 和 `motion_solver_request_expired`。

所以这个担心不成立。如果以后的驱动改成能立即释放，这条路径就会变成假通过。可以在门槛里显式拒绝 `frame_limit` 原因，成本很低。

## 2. 只读量尺修正与传送等待

### 2.1 修正本身成立（E75）

D114 的只读分析从 trace 中取 `[作业锚点, 最后一次可见或授予]` 范围内的身体状态，用新量尺重算。我直接用全部控制帧复算（`output/e75_ground_flag_frames.txt`）：

| 场景 | 帧数 | 未着地帧 | 32 帧内最大位移 | 原记录 |
|---|---:|---|---:|---|
| 10-0-1、10-1-1、10-2-1 | 32 | 仅第 0 帧，`planning_submitted`，坐标 (-2.5, 0, -6.5) | 0.0000 | 离开支撑 |
| 其余 5 场 | 32 | 无 | 0.0000 | 安全 |

我核对过 tick 的对应关系：第 0 帧的 grant tick 是 2285，它的结果观察是 movement tick 2286，正好在分析范围 [2286, 2316] 内。所以修正分析确实看到了这一帧。新量尺要求“未着地且位移 > 0.01”或“高度下降 > 0.01”，能区分这个瞬态和真正的离边。

### 2.2 瞬态是每场都有的传送到达，不是偶发（E79）

`output/e79_post_teleport_ground_blip.txt` 以每场第 0 帧的结果观察为 0 点，统计前后 4 tick 内 trace 的 `on_ground=false`：

- 48 场中每一场都有一次；
- 45 场落在 −2：这一 tick 有 37 次伴随坐标跳变，也就是传送到达本身。夹具的 `teleport()` 再等到下一帧着地静止才返回，瞬态被吸收；
- 3 场落在 0，就是被误报的那 3 场。

把执行顺序和上一场的终点放在一起看：

| 上一场结束时已在本场起点且朝向相同 | 瞬态位置 | 场景数 |
|---|---|---:|
| 否 | −2 | 44 |
| 是 | −2 | 1（10-3-1） |
| 是 | 0 | 3（10-0-1、10-1-1、10-2-1） |

10-tick 场景不移动，结束时就停在起点；同方向的第二次重复又传送到同一位姿。`teleport()` 的等待条件是“距离 ≤ 0.03、着地、速度 ≤ 0.03、朝向误差 ≤ 1°”，第一帧观察本来就满足，于是在服务器传送生效之前返回。传送到达的那一 tick 就落进了本场第 0 帧。

### 2.3 为什么要修传送等待，而不只是放宽量尺

- 放宽量尺只处理了“误报离开支撑”这个后果。
- 根因是场景可能在传送生效前开始。这次 10-tick 不动，所以没有别的影响。但如果迟到的传送落在助跑或起跳准备中，它会重置位置和速度，并在同一场里制造一次外部运动。到时候量尺很难与真实失败区分。
- 同样的位姿重复也会出现在以后的 typed 失败、never-return 和新动作矩阵里。

建议修法（我没有在 Fabric 上验证）：

1. 传送等待至少推进 2–3 个 tick 之后才接受“已稳定”；
2. 要求连续 2 帧同时满足条件，期间出现 `on_ground=false` 就重新计数；
3. 单场函数在第 0 帧断言起点着地静止，不满足就判为夹具失败，不进入安全统计。

修好后，`_b10_uncommanded_body_departed` 的新口径可以保留，作为第二道检查。

### 2.4 关于事后修改量尺

D114 在看到正式结果后修改量尺，并用同一份原始数据签署。这次可以接受，原因有三点：

- 原始 failed 结果、修正前字段和完整 gzip 都保留了；
- 新口径只放过“坐标完全不变”的帧；
- 我用全部控制帧独立复算，结论相同。

但这次签署只有一次运行，而且带一项事后修正。下一次正式批次应当用修好传送等待和新量尺的同一份代码，作为对 D114 结果的确认。新的量尺也应在正式运行之前，先在上一轮公开的原始帧上回放一遍。

### 4.2 “等待帧”有两个口径

- Fabric 外层把 `submit_input=false` 的帧计为 `waiting_polls`。
- 组件测试组装 trial 时用的是 `result.waiting_frame_count`，即“本帧提议里没有移动意图”。
- 在组件后端上，两种口径数值相同（E83：delay 0／5／10／never-return 分别为 0／2／18／37）。差异只出现在 Fabric 的异步规划帧上：baseline 有 22 帧 `submit_input=false`，但这些帧都有移动意图获胜（E78）。于是 Fabric 的 baseline 会被 `coordinator_validation_success_count` 计成“经历过等待”。
- 门槛只要求 `> 0`，所以目前不影响结论。
- 但这说明 trial 组装在组件测试和 Fabric 外层各写了一份，组件后端又覆盖不到异步规划帧。建议把外层的 trial 组装抽成共享函数，由组件测试调用，并统一用一个等待口径。

- **T1：** 关键是先确定 T1 证明在正式链上的位置。
  - 如果它和 B10 求解一样放在 worker 上，门槛应按 D112 的结构改为“交接期限前准备好、队列有界、晚到有安全尾段”，并记录为门槛归属的变更，而不是放宽；
  - 如果它必须留在控制线程，15 ms 的 P99 就继续有效，T1 需要方案 B 或进一步优化。
  - 这一项是真正的决策点，应由你明确选择。
- **T2-3：** 明确它是不是连续两跳的前置。依我看它只影响载荷大小，可以改为性能跟踪项。
- **T3：** 用 D108 的 40/40 下一 tick 时间线和 D114 的交付链证据做一次正式关闭记录。

**第 2 步：路线内交付估计规则（组件层，小改动）**

在决定里二选一：路线内保守，或者“新的 SOLVE 重新建立估计，REVALIDATE 只上调”。然后用三层台阶这类多动作路线冻结。上一轮 E73 已经在组件层验证后一种规则：三层台阶从 205 tick 回到 201 tick，180 个抖动场景全部完成。连续两跳就是多动作路线，这一条不定，第二跳的等待时间就没有确定口径。

**第 3 步：第一个能力阶段——同一路线内两次 JumpGap**

建议的最小范围：

- 已知地形，同一方向两个间隙，固定种子；
- 第一跳在空中时，后台准备第二跳；
- 第二跳按时交付时，不停顿接上；
- 第二跳晚到或失联时，必须安全停在中间平台，并以 typed 失败结束。

验收建议：

- **组件矩阵：** 复用 D114 的单场函数，扩展为多动作。第二个动作的延迟取 0／2／5／10 tick 和 never-return，四个方向。检查以下各项：
  - 不复用旧租约；
  - 两次着地都在支撑上；
  - 零伤害；
  - 来源释放；
  - 控制准备 8／15／30 ms；
  - 第二跳的接续停顿 tick 数，作为玩家可见指标报告。
- **一次 Fabric 批次：** 组件全绿、Windows 完整检查通过后再跑，只跑一次。

停止条件：

- 需要新增 Session 状态，或需要放宽安全条件，就停止并另立决定；
- 中间平台的安全尾段证明不了，就停止。

### 5.3 以后每个阶段的固定前置

D108 以来，每一轮的停止原因几乎都只在唯一一次 Fabric 运行里才暴露：

- D108：命令缺超时参数；
- D112：字段名错误；
- D113：旧租约；
- D114：传送等待。

D114 已经把单场循环放到组件上执行，这是关键的一步。建议再固定三条：

1. 正式命令用到的 trial 组装、汇总和门槛函数，都必须先在组件后端执行过一次；
2. 新增或修改的量尺，先在上一轮公开的原始帧上回放；
3. 夹具对起点状态做硬断言，例如传送已生效、着地静止，不满足时记为夹具失败，不能进入行为统计。
