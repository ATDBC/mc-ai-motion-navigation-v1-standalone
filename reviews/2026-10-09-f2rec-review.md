# 分析：F2-REC 的 R2 性能止损与柱顶 Walk→JumpUp 交接（02bc4c4）

日期：2026-10-09。对象：`main` 上的 `02bc4c4`（F2-REC R1 签署快照），以及 R2 的停止记录。复现脚本与输出在 [2026-10-09-f2rec-review/](2026-10-09-f2rec-review/)。

## 1. 结论

**恢复方向是对的。** R0 和 R1 已经签署，Windows 完整正序、逆序各 1661/1661，公开 `main` 重新回到全绿。

**R2 的止损是门槛设错了，不是 R2 本身退步。**

- **R2 其实比基线更好。** 在没有任何改动的 F2-R 基线上，R0 测得 19 个目标修订帧的 production P95 为 11.42 ms；R2 是 9.49 ms，反而更快。
- **19 个样本算不出可信的 P95。** R2 的 P95、P99 和最大值都是 9.49 ms，正说明样本太少，三个统计量落在同一帧上。
- **超出的时间不在选面。** 纯选面的 P95 只有 1.19 ms；修订帧的大部分时间花在跟随更新和导航准备上。
- **这个门槛是我写进恢复方案的。** 我要求“跟随修订帧满足 8/15/30 ms”，却没有要求先与基线比较。这是我的错误。
- **建议**：R2 的门槛改为“不劣于 R0 基线”，并且用足够多的修订帧测量；8 ms 绝对值按 D089 登记为性能债。照这个口径，R2 可以签署。

**柱顶 24 项的失败与 R1 无关，是两个早就存在的交接缺陷。** 在 `5124bd7`、`1ee76b6` 和 `02bc4c4` 上，结果完全相同。

1. **D1：走路不会转头，跳跃却要求朝向精确。**
   - JumpUp 的入口窗口要求身体朝向与跳跃方向的误差不超过 **2°**（`jump-up-v1.json` 的 `maximum_yaw_error_degrees`）。
   - `FixedRouteController` 从不输出视角，代码里没有任何 look。
   - 所以只有机器人出发时恰好已经面对跳跃方向，才可能交接成功。
   - v9 柱顶的路线先沿 +z 走，再转 90° 朝 +x 跳，所以 24 项全部失败。
   - 这就是缺陷台账里一直开着的 R28-P-04（“步行不会自动转身”）。
2. **D2：朝向对上了，路线却被整体取消。**
   - 机器人还在接近时，后台已经按预计的入口状态求解 JumpUp。
   - 求解结果被判为 `motion_negative_basis_changed` 而拒绝，3 次本地重试很快用完，`MotionRouteCoordinator` 就取消了整条路线。
   - 代码注释原本写着要“保留仍然有效的地面段，下一帧再试”。

**两个缺陷都与终点几何无关，影响也比 v9 这 24 项大得多。** 实际地形里，“转个弯再上一格台阶”非常常见。现有量尺没有发现它们，是因为既有的 JumpUp 用例都是直线接近，而且起始朝向恰好就是跳跃方向。

**修复建议**：两处都是局部修改，不需要动 Session 或规划器，适合开一个独立的“动作衔接”小阶段（见第 4 节）。D091 把柱顶推迟到后续阶段是对的。

## 2. R2 性能

| 来源 | 测量 | P95 |
|---|---|---:|
| R0：F2-R 基线，生产代码未改 | D061 的 19 个目标修订帧 | **11.4178 ms** |
| R2 第一轮 | D061 跟随修订层 | 9.4895 ms（P99 和最大值都是 9.4895） |
| R2 限定修正后 | 纯选面，600 个杂乱跟随目标 | 1.1873 ms |
| R2 限定修正后 | 正式 Runtime 桥，修订加准备，60 帧 | 8.8542 ms |

几点说明：

- **以前的 7.02 ms 不能拿来比。** F2-SP 当时测得的修订层 7.02 ms，用的是漏计了 Runtime 外壳的旧量尺（F2S-T-01），而且 F2-SP 早已整体撤出主线。
- **修订帧的时间分布。** D077 的分段显示，修订帧中跟随更新约 3 ms，导航准备约 5 ms。所以修订帧要压到 8 ms 以下，需要优化的是这两段，而不是选面。
- **硬期限没有失败。** D061 的完整路径最大值低于 50 ms，deadline miss 为 0。按 D089，这属于性能债，不是硬停止。

**建议的 R2 门槛：**

1. 修订帧至少采集 200 个样本，使用同一个量尺和同一台机器，与 R0 交错复跑；
2. 门槛为 R2 的 P95 和 P99 都不高于 R0；
3. 整体 production 仍需满足 8/15/30 ms，full 最大值 < 50 ms，deadline miss 为 0；
4. 8 ms 修订帧目标登记为性能债，以后单独处理。

## 3. 柱顶交接

### 3.1 现象

v9 柱顶场景：floor y=63，x 3..4、z 9..10 有一个 2×2 的一格高方块，起点 (0.5, 64, 0.5)。规划器给出的路线是：

```text
[0] Walk (0.5,0.5) → … → (0.5,9.5) → (1.5,9.5) → (2.5,9.5)
[1] JumpUp (2,64,9) → (3,65,9)
```

[jumpup_handoff_trace.py](2026-10-09-f2rec-review/jumpup_handoff_trace.py) 记录的最后几帧（[输出](2026-10-09-f2rec-review/jumpup-handoff-output.txt)）：

- 身体停在 x=2.439，与入口点 (2.5, 9.5) 的距离在 0.18 的入口容差以内；
- z 在 9.43 和 9.52 之间来回，速度 0.36—0.87 b/s，形成 4 tick 一个周期的左右平移；
- 速度始终没有降到入口要求的 0.1 b/s 以下，止步检测触发制动后，以 `fixed_route_stalled` 结束；
- JumpUp 始终没有激活。

原因是入口窗口里有一项永远满足不了：朝向。控制器能调整的只有位置和速度，所以它在入口点附近反复微调，直到被判定为停滞。

### 3.2 D1：朝向（主因）

[jumpup_direction_yaw.py](2026-10-09-f2rec-review/jumpup_direction_yaw.py) 在一条很宽的一格台阶前直线行走 3 格，测试四个方向和两种起始朝向。[jumpup_yaw_confirm.py](2026-10-09-f2rec-review/jumpup_yaw_confirm.py) 使用 v9 柱顶场景，只改变起始朝向：

| 场景 | 起始朝向 | 结果 |
|---|---|---|
| 直线，−z、+x、−x | 0（不对准跳跃方向） | 全部 `fixed_route_has_no_forward_control` |
| 直线，四个方向，3 格助跑 | 对准跳跃方向 | 不再卡在入口；全部转为 D2 取消（同条件下 5 格助跑能成功） |
| v9 柱顶，冻结的外角目标 (4.7, 65, 10.7) | 0 | `fixed_route_stalled` |
| v9 柱顶，同一目标 | −90°（对准 +x） | **成功**：Walk → JumpUp → Walk |

`1ee76b6` 和 `02bc4c4` 的结果逐项相同；在 `1ee76b6` 上，外角目标更早以“目标站立点不可用”结束。我在调查中也用 `5124bd7` 跑过同一柱顶场景，同样卡在入口，但没有单独保存这次输出。

代码依据：

- `known_map_planner._action_entry_window()` 为 JumpUp 入口设置了 `required_yaw_radians = atan2(-dx, dz)`，允许误差来自校准配置，为 2°；
- 执行器把这个窗口作为前一段 Walk 的 `handoff_entry_window`；
- `segment_entry._fits()` 检查朝向误差；
- `fixed_route.py` 中不存在任何视角输出。JumpUp 控制器自己会先转头再起跳（`jump_up.py` 约第 472—478 行），但它只有在入口通过之后才会被激活。

### 3.3 D2：预计入口的求解被拒，路线被取消

[jumpup_cancel_reason.py](2026-10-09-f2rec-review/jumpup_cancel_reason.py) 截获了取消路线的调用（[输出](2026-10-09-f2rec-review/jumpup-cancel-output.txt)）：

```text
cancel from MotionRouteCoordinator._accept_result (line 807):
  motion_retry_exhausted:motion_negative_basis_changed; prepared=admission_rejected;
  upcoming action 1, executor at 0
```

过程是这样的：

1. 身体还在接近时，后台按预计的入口状态求解 JumpUp，得到一个否定结果；
2. 由于身体仍在移动，这个否定结果的依据随即“改变”，于是被拒绝并重新提交；
3. 每次拒绝都计入 `LocalAttemptChain(maximum_failures=3)`；
4. 三次之后，执行器取消整条路线，任务以 `cancelled` 结束。

问题在于，这条分支的注释明确写着：上游动作的预计入口可能与下一帧观察不同，应该保留仍然有效的地面段，等下一个实际状态再试。但重试预算被“身体还在走”这种正常情况耗光，一个本来无害的状态变化就变成了取消路线。

### 3.4 为什么现有量尺没发现

- 连续高度矩阵里的 `jump_up_1` 是直线车道，而且场景会按方向旋转，起始朝向随之对准行进方向，所以 D1 不会出现；
- v7、v8、F2 528 都没有“转弯后再上一格”的组合；
- v9 第一次在行进中加入了 90° 转弯，所以 24 项全部失败；
- 这只说明以前的覆盖不足，不是 R1 引入了新问题。

## 4. 修复建议

两处都在动作执行和运动协调层，不需要修改 Session、规划器或生命周期。

**D1：在接近入口时转向。** 当下一段动作的入口窗口带有 `required_yaw_radians` 时，执行器在 Walk 的最后一段输出视角，把朝向转到要求的角度。

- 最小做法：剩余距离小于约一格，或已在入口容差内且速度很低时，发出指向所需朝向的视角请求。
- 地面移动本来就按“本帧最终视角”计算世界坐标下的移动（B12-B），所以转头不会改变行走轨迹。
- 视角可能被战斗占用，这时应该等待，而不是放宽 2° 的要求。这一点需要单独做一次仲裁检查。
- 不建议的做法：在入口检查中忽略朝向，交给 JumpUp 控制器原地转头。后台的验证求解是按入口朝向算的，入口不检查朝向，就可能用一个不匹配的解。

**D2：接近期间的否定结果不计入取消预算。** 下一段动作还没开始时（`action_index > executor.action_index`），`motion_negative_basis_changed` 不计入本地失败次数，或者在身体进入入口窗口之前不提交求解。

- 两种做法都不改变求解与证明的语义，只改变重试的计数方式。
- 必须保留的上限是：身体已经进入入口窗口后的真实失败。

**建议的验收：**

- RED 场景族：
  - 直线四个方向，起始朝向不对准跳跃方向；
  - 转弯后跳跃，转弯分别在入口前 1、2、3 格；
  - 3 格以内的短助跑；
  - v9 柱顶 24 项。
  每族都覆盖正常和首条晚一 tick 两种时序。
- 门槛：
  - 上述正例全部完成；
  - v7、F2 528、v8 的旧成功退步为 0；
  - 战斗占用视角时，交接有界等待而不是放宽；
  - JumpUp 起跳前的朝向误差不超过 2°；
  - Fabric 抽查转弯后跳跃，四个方向。
