## 结论

1. **上一轮的四个高优先级问题，在当时报告的具体场景下都已修复，并有对应测试。**
   - 战斗导航桥现在传入锚点和 Runtime 账本；
   - 目标修订保留旧执行器，复现脚本测得的中性帧从 1 帧降到 0 帧；
   - 残差不支持时形成 `DAMAGE_WITH_UNVERIFIED_MOTION`；
   - 攻击等目标无敌帧结束后再出手，命中可由生命下降或死亡确认，未确认时有界重试。
2. **D019 遗留项大多补齐：**
   - 世界知识上移到 Runtime；
   - 观察缺口不再终止任务；
   - 第 5 次外力事件交给任务决策；
   - 父驱动改用有类型的结果；
   - 攻击被拒绝时保留同帧移动；
   - 直线接近时可以边走边打；
   - 公开仓库新增 140 项控制与战斗测试。
3. **仍有四个问题，都出现在“已验证的空中动作或带速动作”与“外力或世界变化”的交叉处。** 平地验收覆盖不到它们，四个都已用脚本复现：
   1. 已验证跨隙执行途中，只要有一帧拿不到状态锚点，导航就会**抛出异常**，而不是继续负责落地；
   2. 空中发生**路线依赖变化**时，会话仍会丢弃执行器；
   3. 地面接管新路线时，**不检查旧执行器是否有在途的已验证命令**；
   4. 受击后残差如果长时间缺世界格或缺输入，伤害事实会在 8 tick 后被**静默丢弃**。

   其中 1 和 4 会叠加：空中被击退到未观察的空间时，残差缺世界格，既不产生外力事件，也拿不到锚点，导航会直接抛异常。
4. **其他需要注意的地方：**
   - 失败处置现在会被记录，但 Runtime 遇到任何异常仍然封存；
   - 世界知识虽归 Runtime 所有，但只有导航会话在读取观察时才写入，而且会话仍默认新建自己的世界；
   - 5° 容差只支持朝目标直线接近时边走边打；
   - 用生命下降确认命中，可能把火焰等其他伤害算成本次命中。

## 二、剩余问题

### 1. 已验证跨隙途中缺锚点会抛异常

- `execution_anchor()` 只在残差追踪器把锚点推进到当前观察时才返回锚点，否则返回 `None`（[`navigation_session.py:362-376`][exec-anchor]）。残差为 `NEEDS_WORLD` 或 `NEEDS_INPUT` 时，追踪器会保留旧锚点，于是返回 `None`。
- `propose()` 在锚点为 `None` 时绕过协调器（[`navigation_session.py:730`][propose]），直接调用执行器。执行器若正持有 `VerifiedMotionExecutor`，会抛出 `ContractViolation`（[`action_route_executor.py:419-424`][exec-raise]）。
- 复现 [`verified_motion_without_anchor.py`](2026-09-25-c1r-rereview-2-repro/verified_motion_without_anchor.py)：已验证跳跃命令提交后的下一帧不传锚点，结果抛出 `ContractViolation`。
- 可能触发的情况：
  - 空中被击退到未知格子，残差报 `NEEDS_WORLD`，这也是 R3 失败记录里出现过的情况；
  - 客户端输入缓冲溢出后淘汰了旧采样，残差报 `NEEDS_INPUT`。

**建议：** 已验证命令在途时，缺锚点的帧应让执行器继续执行已证明的命令序列，或进入它自己的恢复分支，同时请求所需证据，不能抛出异常。补上“已验证命令途中锚点缺失一帧”的测试。

### 2. 空中路线依赖变化仍会丢弃执行器

- `observe()` 发现活动路线的依赖格发生变化时，调用 `_replan_from_current()`（[`navigation_session.py:699`][dep-change]）。后者使用 `_replace_request()` 的默认参数 `preserve_active_route=False`（[`:902`][replan]），立刻退役执行器。
- 复现 [`airborne_dependency_change.py`](2026-09-25-c1r-rereview-2-repro/airborne_dependency_change.py)：已验证跳跃中，身体离地时报告一个依赖格变化，结果执行器被丢弃，会话回到 `snapshotting`。
- D020 第 3 条只覆盖了“取消或替换”，这条重新规划路径没有纳入。

**建议：** 这条路径也保留执行器，交给执行器自己的空中恢复逻辑，落地后再换新路线。补上“空中依赖变化”的会话测试。

### 3. 地面接管不检查在途的已验证命令

- 新路线被接纳时，只要身体着地，会话就立即清除旧执行器（[`navigation_session.py:1064-1075`][handoff]）。路线接纳只检查位置在 0.8 格内，不检查速度（[`route_admission.py:337`][connection]）。
- 复现 [`ground_handoff_during_verified_command.py`](2026-09-25-c1r-rereview-2-repro/ground_handoff_during_verified_command.py)：已验证的“前进＋跳跃＋疾跑”命令已经提交，身体还在地面，此时修订目标。下一帧旧执行器被替换，新执行器处于 `awaiting_verified_motion`，不提交任何输入。
- 如果那条命令已经生效，下一帧身体会离地，走的是安全的空中分支。所以风险集中在仍着地的已验证 tick：助跑模板，或首条命令晚一 tick 生效。R4 的带速入口可达 3 格/秒，此时放弃输入，身体可能滑向缺口边缘。

**建议：** 旧执行器有在途的已验证命令，或正处于非 Walk 段时，推迟地面接管，与空中分支采用同一规则。

### 4. 残差长时间不可用时，伤害被静默丢弃

- `NEEDS_WORLD` 和 `NEEDS_INPUT` 不属于“永久不可用”，伤害事实只会挂起。超过 8 个运动 tick 后，检测器把它清除，且不产生任何事件（[`external_motion.py:384-389`][detector-drop]）。
- 复现 [`damage_with_missing_world_residual.py`](2026-09-25-c1r-rereview-2-repro/damage_with_missing_world_residual.py)：受到 3 点伤害并离地，残差连续 12 tick 缺世界格，结果 0 个事件。
- 击退方向背离攻击者，通常把身体推向身后。身后多在 120° 视野之外，格子常常未知，所以这正是最需要恢复的情况。
- D020 第 5 条要求“缺少世界格或输入回执时继续等待必要证据”。等待本身合理，但超时后应该升级为 `DAMAGE_WITH_UNVERIFIED_MOTION`，而不是丢弃。

**建议：** 挂起的伤害事实超时后，转为保守恢复事件。补上“伤害＋持续缺世界格”的检测器测试。

## 三、其他观察

1. **失败处置只记录，不改变结果。** `step()` 遇到任何异常，都会先计算处置结果，然后照样封存（[`player_runtime_v1.py:407-408`][seal]）。D019 第 9 条要求的“只有身份错乱、输入所有权破坏和无法安全收尾才关闭会话”，仍由调用方在 Runtime 被封存之后自行处理。
2. **世界知识归 Runtime 所有，但写入仍依赖导航会话。**
   - Runtime 自己不把观察写入适配器。攻击和恢复期间如果没有会话调用 `ingest()`，这些帧看到的方块不会进入世界知识。
   - `NavigationSession` 仍默认新建适配器（[`navigation_session.py:265`][adapter-default]），B10 正式协调脚本也没有传入 Runtime 的适配器（[`b10_gap_solver_runtime.py:512`][b10-session]）。
   - 建议由 Runtime 在每次 `step()` 后写入，正式路径把适配器改为必填参数。
3. **边走边打目前只适用于直线接近。** 仲裁只在战斗视角与导航朝向相差不超过 5° 时保留移动（[`arbiter_v1.py:30`][heading]、[`navigation_session.py:1156`][tolerance]）。横移、后撤、绕圈仍会被压成静止。下一步需要导航输出世界坐标下的移动方向，由最终合成器按瞄准视角换算按键。
4. **用生命下降确认命中，可能归因错误。** 攻击后 1 秒内只要生命下降就算命中（[`fixed_melee.py:248`][health-confirm]）。着火、中毒或队友攻击造成的扣血也会被计入，而这次确认又会授予交战许可。建议要求降幅不低于当前武器的最低伤害，或者把“确认命中”和“授予交战许可”分开处理。
5. **重试上限是整个任务累计，而且合并计算两类情况。** `_unconfirmed_strikes` 只在任务开始时清零（[`moving_melee_driver.py:105`][unconfirmed-init]），“未确认”和“攻击被拒绝”共用这一个计数（[`:585-600`][unconfirmed-limit]），累计到 2 次就进入 `NEEDS_TASK_DECISION`。现在边走边打，准星偏移造成的攻击拒绝本身就是正常、廉价、可重试的。长时间战斗里，两次分散发生的拒绝就会把任务交给上层。建议改为按连续次数计数，命中确认后清零，并把两类情况分开计数。

## 五、建议的修复顺序

1. **已验证动作在途时的缺证据处理：** 缺锚点时不抛异常，执行器继续负责（第二节第 1 条）；伤害挂起超时后转为保守恢复（第二节第 4 条）。两者合在一起，覆盖“空中被击退进未知空间”这一种最危险的情况。
2. **统一“替换路线”的交接规则：** 目标修订、依赖变化、地面接管都走同一个判断。旧执行器处于空中、有在途的已验证命令或处于非 Walk 段时，都等它安全结束再替换（第二节第 2、3 条）。
3. **补一个战斗路径的跨隙集成测试：** 通过 `RuntimeNavigationDriver` 驱动真实会话执行跨隙，并在途中注入一帧缺锚点和一次依赖变化。
4. **然后再处理第三节的四项。**
