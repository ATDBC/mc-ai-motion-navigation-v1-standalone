# R28 v7 量尺与 R28-1 前两个切片审查

- 日期：2026-10-03
- 审查对象：`main` 上的 [`3c15744`][new]（对照 [`7260f42`][old]），包括 v7 交付延迟量尺、R28-C-06 修正、R28-1 共同恢复和持续目标两个切片
- 复现材料：[`2026-10-03-r28-v7-review/`](2026-10-03-r28-v7-review/)

## 结论

**1. 上轮建议已全部落实，有几处做得比建议更好，结果在 Linux 上可以复现。**

- 延迟估计的修正用一个共用采样函数替代了两处重复代码，同一工作身份只采样一次，并先写了能在旧实现上失败的检查。
- v7 按运动 tick 计时，而不是按 poll 次数（我的探针用的是后者）；延迟按动作区分，参数冻结在清单里。
- 平视二格下降在 Fabric 上复验 2/2，回到 R28-1，批次按 7/10 如实折算，证据在 Git 中只保留索引和哈希。

我在 Linux 上做了以下复现：

| 检查 | 结果 |
|---|---|
| v7 产品清单 2,000 项，与归档逐项比对 | 完成情况、原因、指标、运动作业记录和实际输入哈希都是 2,000/2,000 一致，1,705 项完成 |
| 运动导航检查 | 984/984 通过 |
| 4 个补充迁移故障 | 4/4 通过 |
| 完整协调集合 1,448 项 | 1,448/1,448 通过，没有异常，逐项通过情况与归档一致 |

**2. R28-1 两个切片的方向是对的：在删重复决定，没有加平行状态。**

- `cancel()` 从约 30 行分支缩成一次 `_request_ending` 调用，`close()` 同样处理。
- `_task_stop_requested` 原来要看 4 个散落的字段，现在只看交接协调器的一个状态。
- 两处原本各自为取消、失败、关闭、探边终态拼装结果的终态分支，合并成同一个出口。
- `GoalReachPolicy` 只是任务开始时固定的一个枚举，没有引入新的生命周期状态，也没有跟随专用的等待。
- Session +186／−174 行，净增 12 行，增加的内容主要是持续目标。

**3. 有三个小问题需要处理。**

1. **轨迹哈希不能跨平台比对。** 92/2,000 个下降任务的 `trajectory_sha256` 在 Linux 上与归档不同。完整轨迹已不在 Git 中，外部审查无法判断这是浮点尾差还是行为变化。在哈希前把浮点数取整到 1e-9：v6 的 400 个下降任务，原样哈希只有 308/400 一致，取整后 400/400 一致。
2. **"结束后再修订"只修了一半。** 结束请求被接受、身体还在停止时，`update_goal` 按新契约返回 False；但任务一旦进入终态，同样的迟到修订仍会抛 `ContractViolation`。跟随层每 tick 都会修订目标，持续任务一旦失败就会碰到这种情况。
3. **"三个迁移函数没有入口覆盖"已经过时。** `handle_internal_contract_failure`、`_wait_for_active_terminal`、`_resolve_pending_retry` 在当前代码上都能被 4 个补充故障覆盖，只是本切片的证据没有包含故障运行。

**4. 解读晚到下降层时要考虑它本身的噪声。**

只改第一个后台作业的延迟（冷启动 7 tick 改为暖态 2–3 tick），200 个晚到下降中就有 12 个完成情况翻转：7 个由失败变成功，5 个相反。v5 的 −4、v7 的 −7 都在这个范围内。今后比较晚到层时，应同时报告双向翻转数，并使用已有的配对检验，不要只看净差。

**5. 方向：第十批值得重新考虑。**

剩余三批排的是 R28-1、R28-4、R28-3。v7 的 295 个未完成中，286 个（97%）是玩家常站位置，台账中却没有任何打开的失败用例属于 R28-3。建议在 10-15 复核时比较两种选择：第十批做 R28-3，还是做终点接近。

## 二、R28-1 切片

### 1. 做对了的地方

| 原来 | 现在 |
|---|---|
| `cancel()`、`close()`、`handle_internal_contract_failure`、风险拒绝、依赖变化各自调用 `request_stop` 和 `_transition`，并分别写 `_cancel_reason`、`_risk_failure_reason`、`_pending_probe_terminal*` | 都通过 `_request_ending(destination, cause, reason)` 交给 `NavigationHandoffCoordinator`，先接受的结束请求保持不变 |
| 终态分支按"取消／完成"和"失败／阻塞／失联"分两段，各自嵌套判断关闭、探边、风险和取消原因 | 一个出口：`finish_ending()` 给出去向，再映射到终态 |
| `_pending_retry` 是 Session 里的独立元组 | 改为从交接协调器的停止请求读出，不再另存一份 |
| 规划截止只在 `propose` 中检查，观察到截止边界后工作仍可能活动（R28-C-02） | `expire_at_observation` 在接收观察时退场，同一帧不重复推进 |

这些修改正是 R28-1 要做的事：把决定移交给拥有者，同时删除原来的分支。14 项协调签名变化都属于多个结束原因竞争，现在保留先接受的结果，规则明确。

### 2. 完整协调集合

在 Linux 上重跑全新的 1,448 项（4 进程，32 分钟）：

- 全部通过，没有异常；逐项通过情况与 `r28-1-slice-v1/coordination-summary.json` 一致。
- 归档列出的 14 项签名变化，重跑得到的终态与归档的"之后"终态 14/14 相同。
- 这个集合本身确实不进入三个函数，但补充故障进入了（见第一节第 2 条）。

### 3. 迟到修订的契约

`late_revision_check.py` 运行一个普通任务，在 tick 12 取消，然后在之后每个 tick 提交更新的修订：

| 会话状态 | 结果 |
|---|---|
| `stopping`（结束请求已接受，身体在停） | 返回 False（符合 R28-C-07 的修正） |
| `cancelled`（终态） | 抛出 `ContractViolation: navigation lifecycle event revise_goal is reject in cancelled` |

协调集合中没有出现第二种情况，是因为模拟运行器只在会话和 driver 都不处于终态时才派发事件，相当于由测试替调用方做了检查。真实的跟随层每 tick 修订目标，持续任务因重试耗尽等原因失败的那一 tick，就会碰到同样的竞态。

两种修法任选其一：

- 终态下的 `update_goal`，以及来源已释放后的 `replace_goal`，同样返回 False（身份错误、修订号不递增仍然抛异常）；
- 或者在架构第 17.11 节写明"终态后调用属于契约错误，调用方必须先检查 `report.terminal`"，并给跟随层补一条正式链检查。

前一种与 17.11 的现有表述（"返回是否接受，不抛程序异常"）一致，我倾向于前一种。

### 4. 两处命名

- `_finish_pending_probe_terminal` 现在是所有结束请求的共同出口，不再只与探边有关。
- `request_recovery` 同时处理重新规划和取消、关闭、失败等结束去向。

AGENTS.md 要求名称直接表达用途。建议分别改为 `_finish_ending` 和 `request_stop`（或拆成 `request_replan` 与 `request_ending`），趁调用点还不多时一起改。

### 5. 代码量

| 文件 | 变化 |
|---|---|
| `navigation_session.py` | +186／−174 |
| `navigation_handoff.py` | +99 |
| 生产代码合计 | +378／−193 |

R28 的退出条件之一是协调代码净减少。前两个切片是先把新的拥有者建起来，净增可以理解，但剩下的迁移（`_restart_after_active_terminal`、探边去向、替代规划失败、`propose` 拆分）需要开始带来净减少。建议在每个切片的记录中报告这一项。

## 三、轨迹哈希应在取整后计算

`trace_signatures` 对 `strict_trace` 的 JSON 直接做 SHA-256。上轮已经确认，Windows 和 Linux 在下降轨迹上存在 ≤2.3e-15 的浮点尾差，所以同一行为会得到不同的哈希。

`rounded_signature.py` 用 v6 的 Windows 归档轨迹，对比 `7260f42` 在 Linux 上重跑的 400 个下降任务：

| 哈希方式 | 一致 |
|---|---:|
| 原样（与 `trace_signatures` 相同） | 308/400 |
| 每个浮点数先取整到 1e-9 | **400/400** |

完整轨迹现在不进 Git，`trajectory_sha256` 是外部核对行为的唯一依据。建议把取整写进 `trace_signatures`，或者另加一个 `trajectory_rounded_sha256`。

- 取整只作用于证据哈希，不改变运行行为。
- 跨平台尾差在 1e-15 量级，行为差异远大于 1e-9，取整到 1e-9 能把两者分开。
- 恰好落在取整边界上的值仍可能得到不同哈希，但实测 400/400 没有出现。

## 四、v7 量尺的两个特性

`v7_warm_probe.py` 直接复用项目的 `DeterministicMotionWorker` 和控制步，只把每个任务第一个作业的 7 tick 冷启动换成对应动作的暖延迟。实际运行时 worker 会通过 `spawn_successor` 跨任务复用，冷启动通常只发生一次。

| 分组 | 模型 | 完成 | 每任务作业数 | 到达中位数 |
|---|---|---:|---:|---:|
| 正常下降 | v7（首个作业冷启动 7 tick） | 200/200 | 2.02 | 71 |
| 正常下降 | 仅暖延迟 | 200/200 | 2.02 | 66 |
| 晚到下降 | v7 | 191/200 | 2.30 | 78 |
| 晚到下降 | 仅暖延迟 | 193/200 | 2.27 | 72 |

从这张表可以看出三点：

1. **完成数基本不受冷启动假设影响。** 到达时间偏保守 5–6 tick，作为量尺可以接受，但读到达指标时要知道这一点。
2. **每个下降仍然要两轮后台作业。** 原因是每条路线的延迟估计都从 1 tick 开始，而下降的暖延迟就有 2–3 tick，所以第一次求解总是晚到，要靠一次复核才能起步，并占用一次执行重试。阶段第 12.1 节决定等 v7 证明有收益再处理，现在 v7 已经可以用来评价这个问题。这不是缺陷，是一个已知的效率缺口。
3. **晚到层有固有噪声。** 两个模型在 200 个晚到下降中有 12 个完成情况翻转，7 个变好、5 个变坏。原因是每个种子的晚到 tick 是固定的，起步时刻一移动，被延迟的输入就换了一批。D055 的根因报告已经说明过这一机制。

   所以几个任务的净差不能单独作为结论。建议比较晚到层时报告双向翻转数（b、c），用已有的 Tango 配对检验；需要更稳的结论时，对同一种子换两三组晚到序列。

## 五、方向与第十批

- 批次：已折算 7/10。第八批 R28-1 正在进行，第九、第十批分别是 R28-4 和 R28-3；终点接近与跟随、R28-5 留到 10-15 复核再定。
- v7 的未完成共 295 项：玩家常站位置 286 项，晚到下降 9 项。
- 台账中仍打开的产品项：
  - R28-P-04：普通步行不转身；
  - R28-P-05：贴墙、走廊尽头和边缘目标失败；
  - R28-C-03：撤回筛选后三项悬出站位失败。

  这些都不属于 R28-3，也没有任何打开的失败用例指向 R28-3。

R28-3（异步失效与结果关联的简化）是纯结构性工作，R28-4（统一预算）则是持续跟随的前提，这两者的性质不同。建议在 10-15 复核时比较两种安排，用数据决定第十批：

- 按原计划做 R28-3；
- 改做终点接近（贴墙接触）。前者减少代码重复，后者直接面向 97% 的产品失败。批次 5 审查中的 6 行贴墙原型就能让玩家常站位置的完成数翻倍。

## 六、建议（按优先级）

1. `trace_signatures` 在哈希前取整（第三节）。改动小，但决定了瘦身后的证据能否被外部核对。
2. 终态下的迟到修订统一返回 False，补跟随层的正式链检查（第二节第 3 条）。
3. 切片证据加入补充故障运行，并更正"三个函数未覆盖"（第一节第 2 条）。
4. 比较晚到层时报告双向翻转数和配对检验（第四节第 3 条）。
5. 剩余迁移带来净减少，并在每个切片记录中报告（第二节第 5 条）。
6. 10-15 复核时，比较第十批做 R28-3 还是终点接近（第五节）。
