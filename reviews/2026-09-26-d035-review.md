## 结论

1. **切换方向正确，主干已经到位。**
   - **不能退回旧射线：**
     - 缺少表面深度提供器时，客户端在启动前失败；
     - Python 后端和导航证据入口都拒绝 profile 3 和 `first_hit_ray`；
     - 构建门禁检查旧采集器没有进入正式 JAR。
   - **实测新传感器：** 我用仓库内固定的原生源码在 Linux 上编译（只替换了导出宏），通过正式的 `CacheBridge` JNI 驱动一块平地。结果：
     - 站立平视时，视野内 16 格以内的地面全部可见；上一轮指出的 z=1、z=2 两排也在其中；
     - 不透明的墙会挡住墙后的地面，标为透明的墙不会遮挡。
     - 上一轮“竖直射线空隙导致等待 1.4 秒”的根因，在新传感器下不再成立。
   - **旧逻辑删除干净：** 按 9 个俯仰行对齐的转头候选已经删掉。
   - **检查与证据：** README 的全部检查都通过。历史归档只改了外层清单，成员文件的哈希不变。
2. **高优先级问题：容量上限会让正式传感器在地下直接失败（第二节）。**
   - 传感器把附近 4³ 瓦片里的全部非空气方块都打包，上限 25,000。
   - 地下 1×2 隧道周围约有 33,000 个方块，超过上限就抛异常；而任何传感器异常都会结束整个正式会话。
   - 修法已验证：打包前剔除“六个面都被不透明完整方块包住”的方块。
     - 在 220 个随机世界和岩层世界里，剔除前后的可见结果逐块一致；
     - 地下打包数降到 6,392（保留存储边缘），或 240（为边缘多读一圈邻居）。
3. **中等问题一：每帧重发全部可见方块，这是射线时代协议的遗留（第三节）。**
   - 旧射线每帧约 33 个方块。表面深度下，平地一眼就有约 300 个，复杂地形会上千。
   - 实测 Python 侧解码加写入世界：300 个方块约 7–12 ms，1,500 个约 38–60 ms，而一个 tick 只有 50 ms。
   - 客户端线程还会把整份观察解析后再序列化一次。
   - 这很可能是 B10 偶发错过严格 tick 的原因之一，建议先测一下。
   - 解码时间里 JSON 解析只占约 15%，其余是逐块建对象和校验。所以有效的做法是不重发未变化的方块，而不是换 JSON 库。
4. **中等问题二：透明规则会让机器人看穿不透明方块（第四节）。**
   - 熔岩、浮冰、蓝冰和所有含水方块，都被当作不遮挡视线，所以机器人能看到它们后面的方块。这违反“合法观察”。
   - 实体可见性仍是 5 个采样点的射线，而且遮挡规则与方块深度不一致：玻璃后的实体看不见，熔岩后的实体却看得见。
   - 修法：16 格内的实体改用与空气确认相同的可见区域判定；16 格外改用同一张遮挡表逐格判断视线。
5. **射线时代的遗留逻辑（第五节，你关心的部分）：**
   - **空气确认没有视线约束：** 按需空气确认（D004）对 32 格内任意位置作答，不看遮挡。射线时代它是“看不见空气”的补丁；有了深度传感器，它既不再必要，又超出了合法观察。
     - 可以改为精确判定“看得见的空”：整格落在可见区域内，且本帧这一格没有可见方块，才确认为空气。
     - 原型结果：500 个随机世界零误判，每帧 128 格约 0.2 ms。
     - 中心连线两个方向都会出错：误收了 29 格其实有方块的格子，又拒绝了一个 71% 可见的格子。
   - **D034 的旧口径：** D034 和 B12-B 验收仍写“被遮挡的实体地面”，首动 0.5 秒门槛的豁免也是按射线证据定的。B12-B 夹具的四向扫描同理，重跑 B12 时应重新评估。
   - **失效模块：** 4 个仍在仓库里的模块引用了本次已删除的文件，已经无法导入。其中 `point_goal_driver.py` 还在导出清单和 C1-B 的溯源源码清单里。
   - **缺少自动测试：** 旧射线的遮挡测试删掉后没有替代。独立仓库里，正式表面深度的遮挡和透明规则没有任何自动测试。
   - **文档仍写“已完成”：** README 首段，以及 B03、B11、B12、C1 的阶段与验收文档，都没有注明 profile 3。
6. **另外一处改动：** B10 执行器现在不再逐 tick 核对跳跃末尾的中性输入（第六节）。
   - 代码注释说“客户端采样已经报告了中性输入”，但执行器和 B10 探针都没有读取这些样本。
   - 在物理上，这个放宽大概率成立，建议补一行核对，让注释属实。

## 二、容量上限让正式传感器在地下失败

**代码：**
- `TileGeometryStore` 保留离眼睛 17 格内的 4³ 瓦片；瓦片离开 21 格才删除（[`TileGeometryStore.java:36`][tiles]）。
- `SurfaceSensor.pack()` 把这些瓦片里所有带外形的非空气方块都送进原生缓存，超过 25,000 个就抛出 `surface geometry capacity exceeded`（[`SurfaceSensor.java:60`][capacity]）。
- 原生端和 JNI 也各自限制 25,000。
- 任何传感器异常都会结束整个会话。

**估算（[`sensor_capacity_estimate.py`](2026-09-26-d035-repro/sensor_capacity_estimate.py)，完全按上述瓦片规则计算）：**

| 场景 | 打包方块数 |
|---|---|
| 平地站立（17 格瓦片） | 14,720 |
| 平地，21 格保留上限 | 25,664（超限；按我的绕圈行走模拟，实际峰值约 19,000） |
| 地下 1×2 隧道（17 格瓦片） | **33,264，超限** |
| 地下，只计带外露面的方块 | 198 |

**影响：**
- 挖矿、洞穴、隧道这类四周大多是实心方块的环境，一进入就会导致正式会话失败。
- 山坡和峡谷也会压缩余量。
- 挖矿是总体设想中的核心能力，所以这是切换后最先要修的问题。

**建议：**
- 打包前剔除六个方向都被不透明完整方块包住的方块。
  - 为什么不会造成透视：视线进入岩体之前，必须先穿过一个与空气相邻的方块面，而这种方块永远不会被剔除。
- 已验证（[`EnclosedCullingProperty.java`](2026-09-26-d035-plan-repro/com/mc2p/surface/EnclosedCullingProperty.java)，正式 `CacheBridge`）：
  - 200 个随机世界加 20 个岩层隧道，剔除前后的可见方块集合完全一致；
  - 没有一例被剔除的方块本应可见。
- 容量（[`culling_capacity_estimate.py`](2026-09-26-d035-plan-repro/culling_capacity_estimate.py)）：地下打包数从 33,264 降到 6,392（存储边缘的方块邻居不在存储里，只能保留）；为边缘多读一圈邻居，可降到 240。
- 同时补一个地下场景的感知验收。详细做法见整改方案包 1。

## 三、每帧重发全部可见方块

**旧协议的前提已经变了：**
- 旧射线最多 1,431 条，而且大量射线打在同一格上。公开的 B12-B 轨迹里，每帧约 33 个方块。
- 协议和适配器是按这个量级设计的：每帧重发全部可见方块及完整碰撞形状，Python 每帧逐个解码、逐个比较、写入世界。
- 表面深度是连续的。上面的平地实验一帧就有 300 块地面，有地形、树木和建筑时会上千。

**实测（[`observation_payload_cost.py`](2026-09-26-d035-repro/observation_payload_cost.py)，本容器，正式解码＋profile 4 门禁＋`NavigationObservationAdapter.ingest`；每帧内容相同）：**

| 每帧方块 | 载荷 | 解码 P50／P95 | 写入世界 P50／P95 |
|---|---|---|---|
| 33 | 12 KiB | 0.6／0.7 ms | 0.5／0.6 ms |
| 300 | 52 KiB | 2.7／4.9 ms | 4.5／6.8 ms |
| 1,500 | 234 KiB | 14.0／25.4 ms | 24.2／35.8 ms |
| 5,000 | 766 KiB | 50.0／80.0 ms | 87.6／104.6 ms |

**额外的客户端开销：** 部署探针在客户端线程上，把整份观察 JSON 先解析成树，嵌进样本，再整体序列化一次（[`DeploymentObservationProbe.java:159`][reparse]）。方块越多，客户端 tick 也越容易被拖慢。

**和 B10 的关系：**
- D035 记录的 B10 控制往返是 P50 约 38 ms、P95 约 60 ms；P95 已经超过一个 tick。
- 修正计划认为原因不能简单归为表面计算；但载荷、客户端二次序列化和 Python 解码都随可见方块数增长，还没有单独测过。

**成本拆分（[`decode_cost_split.py`](2026-09-26-d035-plan-repro/decode_cost_split.py)）：** 1,500 个方块时，解码约 12 ms，其中 JSON 解析只占约 1.9 ms，其余都花在逐块建对象和校验上。

**建议（与整改方案包 4 一致）：**
1. 先在 B10 轨迹里逐帧记录：可见方块数、载荷字节数、客户端序列化时间、Python 解码与写入时间。
2. 再做两项不改契约的修正：
   - 去掉客户端的“解析后再序列化”；
   - Python 适配器跳过未变化的格子。
3. 只有实测仍超预算时，才改为增量协议：已知方块只传可见位置，新出现或变化的方块才传完整记录。

## 四、透明规则与实体可见性

**方块（[`SurfaceWorldSource.java:12`][transparent]）：**
- 透明名单包括 `packed_ice`、`blue_ice`，另外把所有 `fluid` 不为空的方块都当作透明（[`:32`][fluid-rule]）。

| 被当作透明 | 游戏里的实际情况 | 后果 |
|---|---|---|
| 熔岩 | 不透明 | 看穿熔岩湖和熔岩瀑布，下界里尤其常见 |
| 浮冰（`packed_ice`）、蓝冰（`blue_ice`） | 不透明，只有普通冰半透明 | 看穿冰墙 |
| 含水台阶、半砖、墙、活板门、树叶等 | 实体部分不透明 | 整格失去遮挡 |

- 反方向的偏差（该透明却被当作不透明）只会让机器人少看，是保守的；上面这三类则是多看，违反“正式机器人使用合法的结构化观察”。
- 修正计划第四步要求“可见外形和是否遮挡后方分开记录”，目前实现的仍是一个硬编码名单，而且没有任何测试。

**实体（[`ClientObservationCollector.java:542`][entity-visible]）：**
- 实体仍用 5 个采样点的原版射线判断是否被挡住：`OUTLINE` 形状加 `FluidHandling.NONE`。
- 结果与方块深度的规则相反：
  - 玻璃、蜘蛛网、草丛挡住射线，所以玻璃后的僵尸不可见，但它身后的方块可见；
  - 射线忽略流体，所以熔岩后的实体可见。
- 5 个点也是稀疏采样：目标只露出头顶一小块时，可能一个点都没打中。
- D035 把它列为“保留”（[L72][d035-entity]）。但表面深度已经有每帧的遮挡面，可以直接把实体包围盒投影进去，用同一套规则判定。
- **建议：**
  - **16 格内：** 用与空气确认相同的可见区域计算，但判定改为“包围盒任一部分可见即可见”。先做点测试，任一点可见就直接判为可见，只有全部点都被挡时才做精确计算。
  - **16 格外：** 表面缓存不覆盖这么远，改用同一张遮挡表逐格判断视线（整改方案包 2.2）。

## 五、射线时代的其他遗留

1. **空气确认没有视线约束。**
   - 客户端对请求的任意位置，只检查 32 格距离和 `isAir()`，不管是否被遮挡（[`ClientBlockObservationV3.java:79`][air-query]）。
   - Python 端对任何“未知”格都可以发起请求（[`runtime_adapter.py:146`][air-request]）。
   - 结果：墙后、地下的空洞，只要在 32 格内，都能被确认为空气。这比视觉范围的 16 格还远。
   - D004 当时的前提是“没有看到方块不能证明是空气”，在稀疏射线下成立。
   - 有了表面深度，眼睛到可见表面之间的空间本身就是观察到的空气。
   - **建议的判定**（论证和数据见[空气确认设计](2026-09-26-air-visibility-design.md)）：
     - **原理：** 空格子里没有东西，所以它哪部分可见，只取决于它前面的遮挡。格子的可见部分，等于它的投影减去更近的不透明面，可以复用本帧已经投影好的面精确算出。
     - **规则 (a)：** 整格（或八分之一块）完整落在视野和 16 格内，并且投影全部处在可见区域里；
     - **规则 (b)：** 本帧传感器没有在这一格报告可见方块。
   - **原型结果：**

     | 做法 | 单帧确认 | 错误确认 | 每帧 128 格耗时 |
     |---|---|---|---|
     | 中心连线 | 21,560 格 | 29 格 | 很低 |
     | 中心＋8 个内缩角点 | 3,854 格 | 0（仅限测试形状，不能证明） | 0.04 ms |
     | 精确可见区域（九点预筛） | 3,036 整格／64,437 个八分块 | 0 | 0.2 ms（整格）／1.2 ms（八分块） |

   - 去掉规则 (b) 后，会出现 7,488 次错误确认，所以两条规则缺一不可。
   - 单帧看不全的格子，比如柱子后面那格，可以跨帧累积：眼睛左右各挪约 0.8 格，八分块就从 0/8 累积到 8/8。
   - 同一判定也能撤销已经消失的方块：已知方块格本帧整格可见、却没有报告方块，说明方块已经不在了。
   - D035 目前明确保留了原样（[L35][d035-air]）。
2. **D034 的口径和 B12-B 夹具。**
   - B12-B 验收仍写“缺失位置是一排被遮挡的实体地面”（[L198][acc-l198]）。
   - 首动 0.5 秒门槛在出现 `_requires_information` 时整体豁免（[`b12b_partial_combat_runtime.py:324`][waiver]）。
   - 夹具每场开始前还做四向扫描。
   - 这三点都是在射线证据下定的。在 profile 4 下，那场诱发转向应该不再需要等待信息。

## 六、B10 执行器：中性尾段不再核对

**改动：**
- 跳跃证明末尾全是中性命令时，执行器直接跳到末尾，改为“滑行到落地”（[`motion_candidate.py:574`][coast]）。
- 到达证明的出口 tick 后，再核对最终状态。
- B10 探针对滑行帧既不提交账本，也不调用 `observe_sample`（[`b10_gap_solver_runtime.py:500`][probe-coast]）。

**评价：**
- 验证过的动作命令租约只有 1 tick。最后一条有效命令仍要逐条确认生效窗口，确认之后才进入滑行。所以滑行期间“客户端自动回到中性”在物理上大概率成立。
- 但注释说“客户端采样已经报告了中性输入”，而代码并不读取这些样本。
- 如果滑行期间有别的非中性输入被应用，只能等落地时由最终状态核对间接发现。
- **建议：** 滑行帧仍把实际应用样本记入账本，并要求它们是中性的。成本很低，也能让注释属实。

**早落地：** 早落地不算完成，要等到出口 tick 再核对，这比旧逻辑更严格，是对的。

## 八、对照总体设想

**这次切换让机器人的“看”第一次接近真人玩家：**
- 视野内连续可见，被挡住的看不到，未知就是未知。
- 上一轮查到的平地等待，正是稀疏射线造成的，现在从根上消失了。

**但“接近真人”也意味着数据量从每帧几十个方块涨到几百上千个。** 下一步要让三件事跟上这个量级：
- **传感器只保留可能被看到的表面：** 解决地下容量问题。
- **协议只传变化：** 解决每帧的解码和写入成本。
- **世界知识能用“看到了空”来更新：** 替代没有视线约束的空气确认，让合法性和效率同时成立。原型已经验证可行：零误判，每帧 128 格约 0.2 ms。

这三件事都属于“观察层”，不需要改规划、控制或战斗。建议先完成它们，再恢复 B10 和后续验收。

## 九、建议（按优先级）

逐项步骤、通过条件和顺序见[整改方案](2026-09-26-d035-remediation-plan.md)。

1. **地下容量：** 打包前剔除被完全包住的方块（已验证零差异）；补地下和洞穴的感知场景。
2. **每帧成本：**
   - 先逐帧测量；
   - 再去掉客户端二次序列化、让 Python 跳过未变化的格子；
   - 实测仍超预算时，才改为增量协议。
3. **透明规则：**
   - 熔岩、浮冰、蓝冰改为遮挡，含水方块按方块本身判断；规则做成数据表并加测试；
   - 实体可见性：16 格内用可见区域判定，16 格外用同一张遮挡表判断视线。
4. **空气确认：**
   - 改用表面深度的精确可见区域：整格可见，且本帧没有报告方块；
   - 同一判定也用于撤销消失的方块；
   - 更新 D004 和 D035 的相关表述；
   - 不要用中心连线或固定几条射线作判定。
5. **清理遗留：**
   - 删除或移走 4 个失效模块，并从导出清单和 C1-B 溯源清单中去掉；
   - 修正 D034 和 B12-B 的“遮挡”说法；
   - 重跑 B12-B 前恢复 0.5 秒门槛、去掉四向扫描；
   - 给正式表面代码补门禁测试；
   - 统一 README 与各阶段、验收文档的状态。
6. **B10 执行器：** 滑行帧记入账本并核对为中性。
