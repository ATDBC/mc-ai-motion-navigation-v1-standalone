## 结论

**结束结构整理，用 6 个阶段重构运动导航的中层。** 物理、几何、规划和对外接口都不动，只重组协调层。

| 阶段 | 内容 | 主要解决 | 时间盒 |
|---|---|---|---|
| M0 | 收尾与安全网 | 终止 S1—S4，补回测试保护，固定量尺 | 1 个批次 |
| M1 | 动作接口验证：迁移受控下降 | P2 的一部分；验证接口是否成立 | ≤ 2 个批次，**结束时判定是否继续** |
| M2 | 迁移其余 4 种动作 | P2、P6 的一部分 | ≤ 4 个批次 |
| M3 | 统一复核机制，并与终点接近一起交付 | P3、P5 的一部分 | ≤ 3 个批次 |
| M4 | 统一异步作业生命周期和接纳边界 | P4、P5 | ≤ 3 个批次 |
| M5 | Session 改为状态转移表，驱动器状态改为枚举 | P6、P7 | ≤ 3 个批次 |

全程最多 16 个批次。规则：
- 每一步都必须让五组行为集合逐项一致；
- 每个阶段都有可测的量尺目标和止损条件；
- 不允许连续两个重构阶段没有产品增量。

**终点目标（M5 结束时）：**

| 量尺 | 当前 | 目标 |
|---|---:|---:|
| 动作实现之外的动作类型分支 | 70 | ≤ 6 |
| 新增一种动作需要修改的生产文件 | 4—5 个核心文件 | ≤ 3（含动作实现本身） |
| 复核机制 | 2 套 | 1 套 |
| 异步管线 | 2 条 | 1 条 |
| Session | 5,072 行 | ≤ 3,000 行，无超过 100 行的方法 |
| 驱动器生命周期字符串 | 37 处 | 0 |
| 协调层占比 | 44% | ≤ 30% |

## 一、目标结构

```
Runtime ── RuntimeNavigationDriver（生命周期为枚举）
             └─ NavigationSession：状态转移表 + 事件路由
                  ├─ GoalRequestLedger / RetryLedger              （已有，保留）
                  ├─ AsyncJobs：规划与动作求解共用一个作业生命周期    （M4）
                  │    └─ AdmissionBoundary：版本快照只在这里检查一次  （M4）
                  ├─ RouteAdmitter：只负责路线级接纳                 （M3 起收窄）
                  │    （组装、资源、终点；动作级证明交给 ActionSpec）
                  ├─ ExecutionSupervisor：身体 owner                 （交接规则来自 ActionSpec）
                  └─ ActionRegistry ── ActionSpec × 5               （M1—M2）
                       Walk / Step / JumpUp / JumpGap / ControlledDrop
                       ├─ 接纳与复核：计算器重放 + 步行几何快速路径    （M3）
                       └─ 控制器：沿用现有的 fixed_route、空中和跳跃控制器
世界知识 / 运动计算器 / 表面规划器 / 观测与动作契约                    （不改）
```

### 1. ActionSpec：动作知识归属到动作

`ActionSpec` 回答评估中 A—H 八类问题，即现在 70 处类型分支在问的问题。接口草图见 [`action_spec_sketch.py`](2026-10-06-redesign/action_spec_sketch.py)。

| 类别 | 接口成员（草图） |
|---|---|
| A 控制器选择 | `controller()`、`arrived()` |
| B 身体承诺与停止安全 | `body_commitment()`、`requires_safe_handoff()`、`stop_hold()`、`requires_verified_motion()` |
| C 后台动作求解 | `solve_kind()`、`solve_request()`、`accept_solution()` |
| D 前置条件与信息 | `precondition()`（复用 `ActionPreconditionResult`）、`observation_needs()` |
| E 风险与伤害 | `expected_damage_points()`、`damage_committed()` |
| F 几何与进度 | `start_surface()`、`end_surface()`、`route_length_blocks()`、`progress_key()` |
| G 证明与复核（M3） | `dependencies()`、`revalidate()` |
| H 类型登记 | `ActionRegistry`，唯一一处由类型映射到实现 |

**规则：**

1. **无状态。** `ActionSpec` 只读取动作段和观测，不保存运行状态。每次执行的状态仍在控制器实例中，保持"每类长期状态只有一个拥有者"。
2. **不按类型分支。** 协调代码可以问接口，但不能再写 `type(action) is ...`。唯一的例外是 `ActionRegistry`。
3. **有默认值。** 不适用的成员由 `ActionSpecBase` 提供带类型的中性默认值。新增动作只实现与默认不同的部分。
4. **防止接口膨胀。** 新增接口成员，必须替代至少两处分支，或者服务至少两种动作。只为一种动作开的成员，说明抽象漏了，要回头检查。

### 2. 一套复核

M3 把"世界变化后，路线中的动作是否仍然成立"统一成 `ActionSpec.revalidate(segment, world, changed_cells)`：

- **默认实现：** 在当前已知世界中，用计算器重放这个动作的输入程序，检查落点、扫掠体积和伤害是否仍在范围内。
- **步行和台阶：** 保留现有的几何配方，作为同一接口背后的快速路径。D058 规定每次复核 P95 不超过 1 ms，几何路径可以满足这个预算。快速路径给出"无法判断"时，退回计算器重放。
- **空中动作：** 现在走后台 `REVALIDATE` 作业，改为同一个 `revalidate`。是否需要后台执行，由动作自己声明。

### 3. 一个异步作业生命周期和一个接纳边界

M4 把规划作业和动作求解作业统一成：

```
提交 → 身份 → 交付 → 接纳 → 安装或退场
```

身份和窗口只定义一次。版本快照只在接纳边界检查一次，包括：
- 世界会话；
- 几何版本；
- 依赖集合；
- 目标修订；
- 请求 ID。

通过之后，下游模块不再重复检查同一个事实。

### 4. Session 与驱动器

M5 把 Session 的生命周期写成显式的状态转移表：状态 × 事件 → 动作。Session 只负责路由，不再承载各种动作的特殊处理；这些处理在 M1—M2 中已经移入 `ActionSpec`。驱动器状态改为枚举，并且只有一个写入者。

## 二、全局原则

| 编号 | 原则 |
|---|---|
| G1 | **行为不变。** 每一步都必须让五组集合逐项一致。有意改变行为，必须先列出条目并写决定，不能在比较时再解释差异 |
| G2 | **逐步替换。** 新旧两种方式只能在一个阶段内短暂共存。阶段验收前，旧分支必须删除。等价比对写在测试侧，生产代码不增加开关 |
| G3 | **一个迁移单元一次提交。** 依次运行直接测试、正序与逆序完整检查、五组集合、量尺。任一失败就回退该单元 |
| G4 | **不顺带加功能。** 重构提交只搬移和统一，不修行为、不加能力。产品工作走独立的产品轨道 |
| G5 | **保持安全不变量。** 唯一输入出口、观测确认、落地责任、类型化失败、未知不当空气，都不能因重构弱化 |
| G6 | **单元测试不依赖墙钟。** 性能只由 Windows 的正式性能门槛判定 |
| G7 | **按量尺推进。** 每个阶段结束时用 `design_metrics.py` 报告。达不到计划改善量的一半，就停下重新评估，不能延长 |

## 三、各阶段方案与验收

所有阶段都必须满足第四节的全局验收 V1—V7，下表只列各阶段特有的内容。

### M0 收尾与安全网（1 个批次）

范围：
- 采纳 D072，终止 S1—S4；
- 补回"后台规划不阻塞控制"的确定性检查；
- 按断言替换流程删除 3 个死路径；
- 把 `design_metrics.py` 收进 `scripts/`，并冻结基线；
- 补回 R28-C-05 被删的种子；
- 在缺陷台账登记待查项。

验收见下一步方案第一节。

### M1 动作接口验证：迁移受控下降（≤ 2 个批次）

范围：
- 引入 `ActionSpec`、`ActionSpecBase` 和 `ActionRegistry`；
- 5 种动作都先提供组合判断（跨隙 + 下降）所需的分类成员；
- 受控下降完整迁移基线中提到它的 21 处分支，其中 13 处只涉及下降，8 处与跨隙组合；
- 建立 `ActionSpec` 约定测试。

验收（详见下一步方案）：

| 编号 | 标准 |
|---|---|
| M1-a | 提到受控下降的类型分支：21 → 0（不计动作实现） |
| M1-b | 类型分支总数：70 → ≤ 49 |
| M1-c | Session 不再引用 `ControlledDropSegment` |
| M1-d | 提到受控下降的生产文件：5 → ≤ 1（不计动作实现） |
| M1-e | 协调层行数净减少；Session 至少减少 100 行；运动导航总行数增加不超过 300 行（接口的一次性投入） |
| M1-f | 受控下降通过 `ActionSpec` 约定测试 |
| M1-g | 实现 DropSpec 没有新增"只服务下降"的接口成员，或至多 1 个，并写明理由 |

**是否继续的判定：**

- 满足 M1-a 至 M1-g 和 V1—V7：继续 M2；
- Session 没有缩小、需要 2 个或更多只服务下降的成员，或性能门槛失败：停止重构，在决定中记录原因。M1 的改动是保留还是回退，看行为是否一致、量尺是否改善。

### M2 迁移其余 4 种动作（≤ 4 个批次）

顺序：跨隙 → 一格跳 → 台阶 → 步行。步行最后迁移，因为它牵涉的接纳和复核分支最多（类别 G 的 15 处）。

每迁移一种动作就是一个检查点，量尺必须单调改善。

| 编号 | 标准 |
|---|---|
| M2-a | 动作实现之外的类型分支：≤ 6，只允许保留 G 类中暂时依赖步行配方的位置，它们在 M3 中清零 |
| M2-b | 每种动作在动作实现之外最多出现在 2 个生产文件中（规划边转换为动作段的位置，以及登记） |
| M2-c | `MotionSolveKind` 在求解器和动作实现之外的引用：15 → ≤ 3 |
| M2-d | **新增动作演练：** 在一次性分支上新增一个测试用动作（例如"原地等待一拍"），只能修改 ≤ 3 个生产文件，并通过约定测试。演练分支不合并，结果写入验收 |
| M2-e | Session ≤ 4,500 行；协调层占比 ≤ 40%；运动导航总行数不超过基线 |

### M3 统一复核，并与终点接近一起交付（≤ 3 个批次）

范围：
- `ActionSpec.revalidate` 成为唯一的复核入口，步行几何配方成为快速路径；
- 空中动作的 `REVALIDATE` 作业改走同一入口；
- `route_validation.py` 与 `route_admission.py` 中重复的记录和校验合并到动作实现中；
- `RouteAdmitter` 收窄为路线级接纳。

与产品结合：终点接近（贴墙、走廊尽头、悬出 0.1—0.2 格）的失败，本质是"格心几何证明不能表达连续的精确停靠"。计算器重放天然支持这一点。所以 M3 的产品验收加入一个终点接近集合（从 v7 中"玩家常站位置"的未完成项提取），这部分允许有意的行为改善，但必须按 G1 先列出条目、写决定。

| 编号 | 标准 |
|---|---|
| M3-a | 复核机制只剩 1 套；`route_admission.py` 与 `route_validation.py` 之间逐字相同的条件：5 → 0 |
| M3-b | Windows 性能门槛：复核 P95 ≤ 1 ms；完整控制准备 P95 ≤ 8 ms、P99 ≤ 15 ms、最大值 < 30 ms |
| M3-c | 五组集合中，除登记的终点接近改善条目外逐项一致；终点接近集合的完成数提高，且没有成功转失败 |
| M3-d | 复核机制改变了真实输入的依据，所以必须在 Fabric 上复跑已签署的 5 个产品目录，以及终点接近的实机样例 |

### M4 统一异步作业与接纳边界（≤ 3 个批次）

范围：
- 规划作业和动作求解作业共用一个生命周期类；
- 版本快照只在接纳边界检查一次；
- `PlanningCoordinator` 与 `MotionRouteCoordinator` 合并其中重复的部分。

| 编号 | 标准 |
|---|---|
| M4-a | 两个协调器的同名方法：7 → 0（重复部分合并到共用作业类） |
| M4-b | 接纳入口之间逐字相同的条件：9 / 6 → 0 |
| M4-c | 每个版本事实（世界会话、几何版本、目标修订、请求 ID）在协调层只有 1 处校验，用静态统计确认 |
| M4-d | 协调集合 1,448 项和故障 16 项逐项一致，这两组最依赖竞态与过期行为；随机事件序列测试全部通过 |
| M4-e | 协调层占比 ≤ 35% |

### M5 Session 状态转移表与驱动器枚举（≤ 3 个批次）

| 编号 | 标准 |
|---|---|
| M5-a | Session 生命周期由一张状态转移表定义；非法转移有类型化结果，不再靠散落的条件判断 |
| M5-b | Session ≤ 3,000 行，没有超过 100 行的方法，赋值的状态字段 ≤ 40 |
| M5-c | 驱动器生命周期字符串：37 → 0；驱动器状态只有一个写入者 |
| M5-d | 协调层占比 ≤ 30% |
| M5-e | 用一次性分支复做新增动作演练，仍然 ≤ 3 个生产文件 |
| M5-f | Fabric 复跑已签署的 5 个产品目录 |

## 六、测试策略

1. **约定测试。** 每个 `ActionSpec` 都要通过同一套测试：
   - 前置条件只返回类型化结果，并覆盖每个原因码；
   - 身体承诺的分类与执行器的实际阶段一致，在五组集合的全部动作实例上逐一比对；
   - 依赖格覆盖扫掠体积；
   - 任意一拍中断后，身体都处于某个已声明的承诺状态；
   - 预计伤害不低于实际提交的伤害。

   新增动作自动获得这些测试。
2. **等价比对。** 迁移某种动作时，在测试侧用旧分支的逻辑作为对照，与新接口在五组集合的动作实例上逐一比较。迁移完成后，把对照结果冻结为小型回归语料（≤ 1 MB），删除旧逻辑的副本。
3. **历史回归只在被覆盖后移除。** 某个按种子写的回归测试，只有在约定测试或行为集合确实覆盖它要保护的路径之后，才能移除，并且要用变异检查证明。不允许为了减少测试数量而删除。

## 七、产品轨道

- M1 期间可以并行做产品分析：从 v7 中提取终点接近的失败集合，并分类。
- M2 完成后，终点接近作为 M3 的产品交付。
- M3 之后，如果 M4、M5 要连续进行，中间至少交付一个产品增量。候选：
  - 地面跟踪自动转身（R28-P-04）；
  - 跟随在室内终点的停靠。

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 大重构停滞，重演 R28 | 每个阶段有时间盒和量尺，M1 结束时强制判定；达不到计划改善量的一半就停 |
| 计算器重放拖慢控制线程 | 步行保留几何快速路径；M3 用 Windows 正式性能门槛把关；需要后台执行的动作由自己声明 |
| 五组集合没覆盖的路径悄悄变了行为 | 每阶段更新路径矩阵；对只有直接测试保护的目标做变异检查（V4）；不受保护的目标先补场景 |
| 新旧两种方式长期并存 | G2：等价比对放在测试侧，旧分支在阶段验收前删除 |
| `ActionSpec` 变成"上帝接口" | 新增成员必须替代至少两处分支或服务至少两种动作（M1-g） |
| 真实游戏与模拟器有差异 | M3、M5 必须复跑 Fabric |
| 产品停滞 | 第七节的规则：不允许连续两个重构阶段没有产品增量 |
