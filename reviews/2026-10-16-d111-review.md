# D111 审查：B10 GC 归因与证据缓冲（cf101b4），以及下一阶段性能门槛提案

日期：2026-10-16。审查对象：`origin/main` cf101b4 “Publish D111 B10 GC attribution outcome”，改前对照为 f663586（D110）。同时评估用户提出的下一阶段性能决定草案（控制线程与后台求解分开设门槛）。本轮只在 Linux 上复核，没有重跑 Windows 正式结果和 Fabric 实机批次。

## 结论

1. **D111 的实现正确，测量可信。** 在 Linux 上逐项复核：
   - **GC 时间线：** 项目的 `_GCPauseTimeline` 和 `_attribute_solve_gc_pauses` 在真实的跨线程 GC 下完整（217 个区间，零丢弃、零未配对、零测量错误），第三方回调被保留，旧的次数判定与区间判定 200 次中 0 次不一致（E59）。
   - **字符串缓冲：** 追加 5401 行诊断只新增 11 个受 GC 跟踪的对象，D110 写法是 10815 个。
   - **两处测试修正：** 单核下都稳定通过。D5 矩阵 20/20（D110 时单核 4/20 失败），动作交接测试 30/30（D110 时 12/30 失败）（E61）。
   - **相关测试与全量：** 三个根目录测试模块全部通过（E57）。Linux 全量 185 个模块中 184 个通过，唯一的错误是平台限定的 D101，cleanup 185/185 通过。

2. **D111 的 B10 结果不能支持“求解耗时稳定在 30 ms 左右”。这次整轮比 D110 慢了约三成，而且慢的不只是求解。**

   | 运行 | 墙钟 P95／P99／最大 | 线程 CPU 平均 | 同进程 trace 投影 平均／P95／P99 |
   |---|---|---|---|
   | D109 D8 | 24.54／26.42／41.03 ms | — | 72.1／220.1／255.2 µs |
   | D110 | 24.60／27.63／39.25 ms | 19.6 ms | 71.2／203.8／241.8 µs |
   | D111 | 31.89／33.44／39.96 ms | 26.5 ms | 83.7／267.3／341.1 µs |

   - **代码和输入都没变：** 计时区间内的代码与 D110 相同（只多记了起止时间戳）；B10 用的是超平坦世界，seed 不改变求解面对的地形。
   - **机器在同样的工作上跑得更慢：** 线程 CPU 平均值从 19.6 ms 升到 26.5 ms。Windows 以 15.625 ms 记账，但 142 个样本的平均值标准误只有约 0.4 ms，所以这个差异是真实的。同一进程里与求解无关的 trace 投影也慢了 17%（平均）到 41%（P99）。
   - **剩下的时间是求解线程自己的计算，不是等待：** D111 的墙钟平均 27.4 ms，CPU 平均 26.5 ms。

   因此 D111 的墙钟超限，最可能来自那次运行时整台机器或整个进程偏慢，而不是求解变了、也不是 GC。“GC 不是主要原因”对 D111 成立：扣除 GC 停顿后仍有 17 个样本超限。但更准确的总结是：**单次求解大约 20–27 ms CPU，运行之间会因机器状态波动约三成，而 30 ms 门槛的余量小于这个波动。**

3. **求解时间主要花在安全证明上，不在搜索上（E60）。**
   - 一次跨隙求解约 95% 的时间在物理步进上，每次约 395 步。
   - 其中约 87% 来自 `_release_recovery_evidence`：对轨迹上每个时刻证明“此刻松开全部输入，仍能安全落到支撑面”。
   - 延迟起跳变体又把这部分证明做一遍。真正的候选搜索只占约 9%。

   这正是你提案第 2 条“晚到时当前动作有安全尾段”所依赖的证明。继续压缩几毫秒，只能削减这份证明或去优化物理步进与世界查询，两者都不会改善玩家看到的效果。这一点支持你的判断。

4. **提案的方向正确，建议先写这份新决定。它实际上是回到 B10 自己的验收计划。** B10 验收计划第 5–6 节本来就分别规定了：
   - 控制帧 P95≤8、P99≤15、最大值<30 ms；
   - 50 ms 提交期限；
   - 采样到输入生效 P99≤100 ms；
   - “后台求解阻塞 500 ms 时，已有安全前段足够则不新增无谓停车”。

   单次求解墙钟 <30 ms 是 B10-B 探针后加的检查。设立时求解只要 2.7 ms（B10-B／B10-C，9 月 21–23 日），9 月 25 日涨到约 28 ms 后，这个门槛没有按任何交接期限重新推导过。

   但要真正做到“把门槛放到影响体验的位置”，而不是“换个地方放松”，决定里必须补上五点：
   1. **第 4 条与现有探针冲突，必须明说怎么处理。** 当前在控制线程上同步求解的只有 B10-B 探针本身，外加一个目前没有调用方的内联回退（`prepare_planned_gap_motion`／`prepare_planned_air_transition` 在 `precomputed` 为空时就地求解）。
      - 按第 4 条原文，探针的 142 个样本仍受 30 ms 约束，B10 会继续失败。
      - 决定要写明：探针是测量装置，生产路径在 `MotionSolverWorker` 子进程中求解，因此这 142 个样本改为报告项。这是门槛范围的改变，要如实记录。
      - 同时把那条内联回退删掉，或在控制线程上直接拒绝。
   2. **“准备好”要按端到端定义。** 应以“控制线程能取用，且输入在候选执行窗口内实际生效”为准，用客户端回执的 tick 衡量，而不是以 worker 返回为准。门槛建议为：冻结矩阵中 0 次错过；按 tick 报告余量分布；设一个最小余量，用来吸收约三成的机器波动。
   3. **迟到路径要有 Fabric 故障注入证据。** B04 对后台规划做过 500 ms 阻塞注入（注入期间固定路线连续执行 12 帧，没有新增中性输入）。对动作求解，我在公开验收记录里没有找到同类的 Fabric 结果，B10-C 只说明迟到结果不会取得输入权限。证明里已有 `release_safe_command_indices`，可以先做确定性检查：在期限 tick，当前命令序号必须在安全集合里。然后再在实机上注入延迟验证。
   4. **第 1 条要先测，余量可能很薄。** 现在的 B10 正式运行不检查、也不公开控制帧指标。9 月 25 日回归记录的“本地非后端控制耗时”P95 是 7.939 ms，离 8 ms 只差 0.06 ms；按 D111 那种慢三成的机器状态，P95 会到约 10 ms。应先用现有本地原始数据（如 `b10-coordinator-control-frames.jsonl`）算出当前值，再冻结门槛，否则新决定可能马上在第 1 条上失败。
   5. **正式性能运行要做机器状态校准。** 每次正式性能运行前后，跑一个固定的离线基准（同一组 R4 求解），并记录电源计划和同时运行的重负载进程。基准偏差超过阈值的运行，不用来下性能结论（功能结论照常有效）。否则第 1、2 条同样会随机器状态时过时不过。

   另外两点：
   - **对第 3 条：** 单次求解耗时可以不阻断，但建议保留一个不阻断的回归警戒（用校准基准换算后，比冻结基线涨超过约定比例就标记）。计算量上限（≤12 个候选、每个候选 ≤20 tick、队列和字节上限）是确定性的，继续阻断。
   - **对第 5 条：** 同意 D111 保持 FAILED／STOPPED。D110-SOLVE-01 不应由新决定直接关闭，要等新门槛在一次正式运行中通过后，才按新口径关闭；旧记录保留。

### 2.2 GC 时间线

实现与 D110 审查 E52 的结论一致：

- 回调只追加 `(代, 阶段, perf_counter_ns)` 小元组，有事件上限；
- 全部试次结束后才配对、算交集；
- 交集取并集，所以重叠区间不会重复扣除；
- 移除时按对象身份，只删自己的回调。

E59 在 Linux 上用这两个函数做真实负载复核：常驻约 30 MB 对象，后台线程随机 `gc.collect()`，用项目 `_measure_gap_solve` 求解 R4 的 12 种入口 200 次。

| 检查 | 结果 |
|---|---|
| 时间线 | 434 个事件、217 个区间，`complete=True`，丢弃／未配对／测量错误均为 0 |
| 第三方回调 | 项目回调移除后仍登记，期间被调用 444 次 |
| 旧次数判定与区间判定 | 200 次中 0 次不一致 |
| 无 GC 重叠样本（105 个） | 墙钟 P50 41.89、P95 53.02、最大 60.20 ms |
| 与第 2 代 GC 重叠样本（44 个） | 墙钟 P50 179.19、最大 269.57 ms；项目扣除停顿后 P50 37.73、最大 70.27 ms |

扣除后的分布回到无 GC 样本附近。P50 略低（37.7 vs 41.9 ms），说明跨线程时停顿可能被多算几毫秒：别的线程的回调在取时间戳前后都可能让出 GIL。这个偏差只会让“扣除后仍超限”的结论更保守，不影响 D111 的判断。

## 3. D111 的 B10 结果应该怎么读

### 3.1 整轮偏慢，不只是求解

E58 只读公开证据，结果见结论第 2 条的表。要点：

- **代码和输入不变：**
  - 计时区间里的代码与 D110 相同。D111 只在 `_measure_gap_solve` 里多记了 `solve_started_ns`／`solve_ended_ns`，其余改动都在区间外。
  - B10 的服务器使用 `level-type: minecraft:flat`、不生成结构（`scripts/fabric_deployment_sandbox.py:58`）。D111 把 seed 从 21001 换成 21002，不改变求解面对的地形。
- **CPU 工作量确实变多：** 线程 CPU 平均值从 19.6 ms 升到 26.5 ms。单个 Windows 样本只能是 15.625 ms 的整数倍，但起点相位随机时量化误差均值为 0。142 个样本的平均值标准误约 0.4 ms（按最坏情况算也不到 0.8 ms），所以 +6.9 ms（+35%）是真实的。
- **与求解无关的工作也变慢：** 同一进程里 trace 投影是 worker 线程上的纯 Python 工作，与求解无关。它的平均值慢了 17%，P95 慢了 31%，P99 慢了 41%，最大值从 0.67 ms 变成 14.9 ms。

三者合起来，最可能的解释是那次运行的整台机器或整个进程偏慢，例如 CPU 频率或电源状态不同、同时有其他重负载、超线程同核争用。公开证据无法区分具体是哪一种。

### 3.2 剩余时间是求解线程自己的计算

D111 墙钟平均 27.41 ms，CPU 平均 26.52 ms，两者只差约 0.9 ms。所以 D111 验收文档里“不能把剩余墙钟进一步归因为求解工作或调度”可以说得更明确：**从总体平均看，剩余时间基本是求解线程自己的 CPU 时间，不是排队或等待。** 只是这台机器在这次运行里，同样的工作要多花三成时间。

### 3.3 GC 的作用

D111 全程有 3 次第 2 代 GC，合计 42.4 ms，单次最长 16.7 ms。扣除 GC 停顿后，最大值从 39.96 ms 降到 33.18 ms，但 P95 只从 31.89 ms 降到 31.50 ms。所以：

- GC 造成个别离群，D110 那次唯一的超限样本也属于这种；
- GC 决定不了整体水平。

对提案第 1 条有一个提醒：16.7 ms 的第 2 代停顿发生在控制线程上，就会单独超过 P99≤15 ms 的单帧预算。好在 3 次相对约 5400 个控制步不到 0.1%，不影响 P99，也低于最大值 30 ms。

### 3.4 求解时间的构成（E60）

在 Linux 上用 cProfile 剖析 16 种入口（4 方向 × 静止对正与三档带速），共 80 次求解：

| 函数 | 累计占比 | 含义 |
|---|---:|---|
| `physics_1_21.step` | 95% | 物理步进，31620 次，约 395 次／求解 |
| `_release_recovery_evidence` | 87% | 对轨迹每个时刻证明“松开全部输入仍能安全落到支撑面”，每次求解调用 2 次 |
| `_prove_delayed_starts` → `_replay_verified_commands` | 48% | 延迟一 tick 起跳的变体，重放并再做一遍恢复证明（与上一行嵌套） |
| `_ranked_air_rollouts`／`_rollout_air_template` | 9% | 候选搜索本身 |

静止对正和低速入口只需 1 个候选，墙钟中位 37 ms（Linux）；2.5 格/秒入口需 4 个候选，中位 44 ms。候选数从 1 增到 4，耗时只增加约 18%，因为主要成本不在搜索。

这份证明给每个时刻都标出了“可以安全松手”的命令序号（`release_safe_command_indices`），也就是提案第 2 条要检查的“安全尾段”。把求解放在后台、给足提前量，正是为了让这份昂贵但必要的证明不占用控制帧。

## 4. 对下一阶段性能决定草案的逐条意见

| 草案条目 | 意见 |
|---|---|
| 1. 控制线程和动作激活帧继续 P95≤8、P99≤15、最大<30 ms | 同意，这是玩家直接感受到的延迟。要求：测的是控制线程完整本帧，包括 GC 和证据写入；先用现有数据确认当前余量（9 月 25 日“本地非后端控制耗时”P95 7.939 ms），并纳入机器状态校准 |
| 2. 后台求解检查交接期限、剩余 tick、上限、安全尾段 | 同意，这是正确的抽象。要求：期限按“输入在候选执行窗口内实际生效”定义；冻结矩阵 0 次错过；按 tick 报告余量并设最小余量；迟到路径用证明里的 `release_safe_command_indices` 做确定性检查，再做 Fabric 延迟注入 |
| 3. 单次后台求解耗时继续报告，不单独阻止连续运动 | 同意，但加一个不阻断的回归警戒；计算量上限继续阻断 |
| 4. 仍在控制线程同步运行的求解继续受 30 ms 约束 | 同意原则，但要附清单：目前只有 B10-B 探针和一条无调用方的内联回退。决定要写明探针样本改为报告项（理由：生产路径在子进程），并删除或封住内联回退 |
| 5. D111 保持 FAILED／STOPPED | 同意；D110-SOLVE-01 等新门槛在正式运行中通过后再按新口径关闭 |

是否算“降低要求”，取决于第 2 条怎么测：

- **算降低：** 只看 worker 是否在交接前返回；不做迟到注入；第 1 条不实测。
- **不算降低：** 按输入实际生效计期限，有余量下限，有迟到注入，第 1 条有实测余量。这比现在的单样本 30 ms 更严格，也更接近玩家体验。
