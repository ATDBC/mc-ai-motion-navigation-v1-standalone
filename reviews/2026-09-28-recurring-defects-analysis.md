# 为什么每次推进都出现 P0／P1：原因分析与代码组织建议

日期：2026-09-28
对象：
- 实施 agent 对“反复出现高优先级问题”的解释；
- `origin/main` 提交 [`8898cf9`][base] 的代码结构；
- 2026-09-24 至 09-28 的 21 份审查记录（本目录）。

性质：外部审查意见。不属于 `docs/motion_navigation/` 四类正式文档。

## 结论

1. **实施 agent 的解释基本属实，但停在现象层面。**
   - 它说的三点都有证据支持：检查不够严密、`NavigationSession` 职责过多、新阶段打破旧阶段的隐含前提。
   - 但它没有指出两个更根本的原因，而这两个才决定问题会不会继续出现：
     - **同一类缺陷在不同模块里反复出现。** 以下三类在 21 份审查里各出现 5 到 11 次，分布在战斗、放置、跨隙、连续高度等不同功能里：
       - 身体控制权在中断时的交接；
       - 重试和额度的上限；
       - 安全门槛放在错误的层。
       原因是没有一个共享机制来保证这些不变量，每个新能力都在会话里重新手写一遍。这就是“打地鼠”的来源。
     - **缺少走正式路径的闭环测试工具。** 16 个使用 `NavigationSession` 的测试文件中，没有一个接入 1.21 运动计算器让身体真正动起来。最近三轮的全部 P0，都是我用“规划器／会话 + 计算器”闭环脚本发现的；而项目里没有这种测试。所以“检查不够严密”主要不是态度问题，而是严密检查在现有工具下太贵。
2. **还有两个它没有提到的因素：**
   - **修法针对复现脚本，而不是针对缺陷类。** 修复通常恰好让审查脚本通过，同类问题换个条件又出现。例如：
     - 落点门槛：第十六轮修掉旧问题，第十七轮发现新分支过宽，第十八轮又发现新探边不安全；
     - 后续地面段重搜：修了空中动作之后的那一段，首个地面段的同一机制仍在；
     - “两种失败交替就绕过计数”：B12-A 出现过，第十八轮在重规划计数里又出现。
   - **单次交付范围过宽。** 连续高度一次改了规划、代价、控制器、接纳、执行器、会话和伤害额度（59c45bb：73 个文件，+8.6k 行）。项目原则写的是“一次修改围绕一个可验收行为”。
3. **架构方向不需要推翻，同意它的判断。**
   - 以下核心资产都站得住，多数修复都能在局部完成：
     - 感知 → 世界知识 → 规划 → 动作证明 → 执行 → 唯一输入出口的分层；
     - 运动计算器、状态锚点、输入账本、动作证明。
   - 债务集中在两处：
     - **协调层：**`NavigationSession` 有 47 个字段，涉及约 8 类关注点；`_state` 在 14 个方法里被赋值 43 次。
     - **验证基础设施：**没有正式路径闭环、没有扰动注入、没有不变量监视器。
4. **运行效率不是问题，开发效率的主要损耗是返工。**
   - 闭环控制 P95 约 2 ms，规划在预算内。
   - 但每个功能平均要经过 3 到 4 轮“交付 → 外部审查 → 补丁”。发布历史里 `fix:` 提交 13 个，`feat:` 提交 15 个。
5. **建议分三步走，每步都小，都能单独验收：**
   - **先建工具：**正式路径闭环模拟、扰动注入、不变量监视器。
   - **再补三个共享机制：**
     - 身体控制权协议；
     - 动作边界前置条件；
     - 统一的重试与额度账本。
   - **最后按状态归属拆分会话。**
   目标不是减少代码行数，而是让“新增一种控制身体的能力”或“新增一种中断”时，只需要实现一个接口，不必修改会话里的多条路径。

## 二、21 份审查中的缺陷分布

下面按缺陷类型归类中等及以上的问题。分类是我根据各轮结论做的，数量是约数。

| 类型 | 约数 | 例子（审查记录） |
|---|---|---|
| **A. 中断时的身体控制权交接** | 11 | 目标修订或取消时丢弃执行器，空中失去落地责任（C1-R 复审）；缺锚点时空中抛异常、依赖变化丢执行器、交接不看在途命令（C1-R 二次复审）；放置中改目标失败（B11）；边缘改目标任务失败（D026）；空中多一个 tick 重建 Runtime（D027）；视角与台阶输入同帧（D034）；探边潜行保持不解除（第十七轮）；探边结束松开潜行导致坠落（第十八轮） |
| **B. 重试、额度和期限的上限** | 9 | 目标修订重置搭桥额度、准备阶段无上限（B11）；两类攻击失败交替时都不耗尽（B12）；追击到期抛异常（B12 追击）；伤害额度按动作不按任务（第十六轮）；重规划无上限、额度接纳不复核（第十七轮）；交替原因绕过重规划上限（第十八轮） |
| **C. 正式路径与被测路径不一致** | 5 | C1 战斗没走 B01–B10 主线（架构审查）；生效窗口只有 B10 探针传给 Runtime（最终复审）；B03 回归不经过会话（B12 加固）；起点总在格子中心（第十六轮）；代表场景避开了远处落点与多道坎（第十八轮） |
| **D. 文档契约与代码不一致，或门槛放在错误的层** | 6 | 中性帧原因覆盖（D033）；B10 结论写得过满（D034）；任务额度语义（第十六轮）；落点门槛文档与代码（第十七轮）；落点证据放在整条路线接纳时、下落参照口径（第十八轮） |
| **E. 感知与传感器的领域问题** | 约 8 | 射线竖直间隙、容量上限、透明规则、空气确认合法性、范围泄漏（D034 至第十五轮） |

**观察：**

1. **E 类问题基本是一次性的。** 修好后没有反复出现，说明感知模块的边界是清楚的。
2. **A、B 两类贯穿所有功能，而且几乎都落在同一个地方。** 每引入一种控制身体的方式（空中动作、放置站位、探边），或一种计数（搭桥额度、攻击失败、重规划次数），就要在会话或驱动里再写一遍中断处理和计数逻辑，也就再出一次同类错误。这正是“打地鼠”。
3. **C、D 两类说明验证与契约之间缺少机器检查。** 文档写得认真，也很诚实，但不变量没有变成能自动运行的检查，所以会与代码悄悄分离。

## 三、代码结构的量化事实

由 [`code_metrics.py`](2026-09-28-recurring-defects-data/code_metrics.py) 在 8898cf9 上得出，输出见 [`code_metrics-8898cf9.txt`](2026-09-28-recurring-defects-data/code_metrics-8898cf9.txt)。

**`NavigationSession`：**

- 类体 1,840 行，43 个方法，47 个实例字段。按关注点分：
  - 目标与请求 4；
  - 规划与快照 8；
  - 执行与交接 8；
  - 信息获取与探边 8；
  - 任务伤害 3；
  - 恢复计数 2；
  - 世界交互与搭桥 4；
  - 世界、残差与接纳 4；
  - 生命周期 3。
- `_state` 在 14 个方法中被赋值 43 次，`_reason` 在 14 个方法中被赋值 42 次。任何一个新状态或新中断，都要在这些位置里找齐所有相关路径。
- 最大的方法：
  - `_advance_planning` 278 行；
  - `propose` 215 行；
  - `observe` 144 行；
  - `_proposal` 140 行。
- 文件由 1,142 行（09-25）增长到 2,167 行（09-28）。19 个相关发布中，每个新功能和每次修复都让它变长。

**测试：**

- 共 1,004 个测试函数。使用 `NavigationSession` 的测试文件有 16 个，**其中接入 1.21 运动计算器的为 0**。
- 会话测试都在静止帧上检查单帧决定，或者用 `Mock` 执行器，或者直接改私有字段（这 16 个文件中有 61 处 `session._xxx`）。

**原因字符串仍参与控制流：** 19 处，分布在 `motion_coordination`、`external_motion`、`moving_melee_driver`、`block_placement_driver` 等模块。项目最初的 AGENTS.md 第 4 节明确写了“不要用 `reason` 字符串、散落布尔开关或全局变量暗中决定权限和生命周期”（本审查分支保留的版本，第 112 行）。

- `fixed_route.py` 1,425 行，同时包含普通路线和证明走廊闭环两套控制。

它们还没有到必须拆的程度，但会是下一个会话。

## 四、根因

1. **不变量没有落到机制上，只落在文档和人的注意力上。**
   - 典型的是“身体离开支撑时必须有空中动作负责”和“任何重试都有上限”。每个新功能都要重新记住它们，漏一次就是一个 P0 或 P1。
2. **会话同时是状态机、调度器和很多长期状态的所有者。**
   - 状态迁移没有显式的转移表，而是分散在 14 个方法的条件分支里。
   - 新增一种中断，需要人工推演所有组合，容易漏；实施 agent 所说的“只改到其中一条路径”就发生在这里。
3. **没有便宜的正式路径闭环测试，于是验证退化成两种：**
   - 单帧组件测试，身体不动；
   - 少量理想化的 Fabric 代表场景。
   两者之间，恰好是所有交叉缺陷所在的区域。
4. **修复流程以“让审查复现变绿”为终点。**
   - 复现脚本天然只覆盖一个实例。如果修复后不做“同类搜索”（其他模块、其他路径有没有同样的写法），也不把实例扩展成性质测试，同类问题就会在下一轮换个位置出现。
5. **交付粒度过大，而且由同一个 agent 设计、实现并写验收。**
   - 一次交付跨越多层时，审查面和交叉组合数会迅速增长。
   - 自己写的测试倾向于证明“功能能工作”，不倾向于寻找它在什么条件下失败。

## 五、代码组织建议：按状态归属，而不是按行数

目标是：**新增一种控制身体的能力、一种中断或一种计数时，只实现一个接口，不必修改会话里的多条路径。**

下面三个共享机制，每个都对应第二节中至少 5 次重复出现的缺陷类型。按 AGENTS.md“新抽象至少解决两个明确重复点”的标准，它们都符合条件。

### 1. 身体控制权协议（消除 A 类）

所有会产生移动输入的对象，都实现同一个小接口：

```
class BodyController(Protocol):
    def decide(self, frame, anchor, ledger) -> ControlDecision   # 本帧输入和状态
    def request_stop(self, cause: StopCause) -> None             # 中断请求，不是立刻丢弃
    def safe_to_release(self, frame) -> bool                     # 身体在支撑上、速度小、没有在途命令
    def release_decision(self, frame) -> ControlDecision         # 未达到安全前每帧怎样收尾
```

- 路线执行器、已验证空中动作、探边、外力恢复、放置站位都实现这个接口。
- 会话只持有一个 `current_controller`，交接规则只写一次：
  - 目标修订、取消、路线替换、超时，一律变成 `request_stop`；
  - 只有 `safe_to_release` 为真时，才换成新控制者；
  - 在此之前，每帧使用旧控制者的 `release_decision`。
- 第十八轮的坠落，就是探边没有 `release_decision`。C1-R 复审中“改目标丢弃空中执行器”，是会话绕过了这条规则。
- 一个通用性质测试可以覆盖全部组合：每种控制者 × 每种中断 × 若干时刻，身体不会在没有空中控制者的情况下离开支撑。

### 2. 动作边界前置条件（消除 D 类中的层级错误）

- 规划与整条路线的接纳，只检查“静态可行”：地形已知、证明段存在、额度总量足够。
- 与时效或当前身体状态有关的条件，由每种动作自己声明，在它接管身体之前检查：
  - 落点近距离证据；
  - 离边时的额度承诺；
  - 入口窗口。
- 这样，第十八轮“两道坎的路线无法接纳”这类问题，在结构上就不会出现。
- 探边成为一种前置条件未满足时的获取动作，也只能在该动作的起始支撑面上启动。

### 3. 统一的重试与额度账本（消除 B 类）

一个小组件，供重规划、攻击重试、搭桥额度、信息等待、探边次数共同使用：

- 以“进度状态”为键，例如（起始支撑面，世界几何修订，目标版本），对所有原因分别计数，同时设总上限；
- 只在测得真实进度时清零，不在原因变化或目标修订时清零；
- 返回有类型的“已耗尽”结果，交给任务层处理。

B12-A 中“两类失败交替”的修法（设跨类别总上限）已经证明了这种形状，只是当时只用在了攻击上。

### 4. 然后再拆会话

有了前三个机制，会话里的字段自然分成若干明确的所有者：

| 所有者 | 负责的状态 |
|---|---|
| `GoalRequestLedger` | 目标、请求序号、待定目标 |
| `PlanningPipeline` | 快照、规划进程、候选 |
| `ExecutionSupervisor` | 当前控制者、交接、安全终态 |
| `InformationAcquisition` | 缺失格、观察状态、等待上限、探边作为其中一种动作 |
| `TaskRiskLedger` | 伤害额度、承诺记录 |
| `RecoveryLedger` | 重试与重规划计数 |

- 会话本身只剩一个显式的状态机：状态 × 事件 → 转移，并写成表。
- 对这张表做穷举测试：每个状态下收到每种事件，结果都有定义。
- `reason` 只用于报告，不参与任何判断。

`known_map_planner.py` 中的证明回路也可以按同样原则抽出，成为独立的“路线证明”步骤，并把“与路线无关的证明失败”写成类型（第十八轮第四节的问题）。

## 六、验证方法：把交叉矩阵变成代码

1. **正式路径闭环模拟器，作为一等测试基础设施：**
   - 组成：`RuntimeNavigationDriver` 或 `NavigationSession`、同步规划器、同步动作求解、1.21 运动计算器、可配置的观察模型（空气查询按几何给出可见／遮挡／下部可见）。
   - 前几轮审查中的脚本，就是它的雏形：`traversal_robustness`、`probe_far_landing`、`two_drop_terrace`、`stale_request_budget` 等。
2. **扰动注入，冻结种子：**
   - 起点偏移、每条命令迟到、随机迟到、朝向偏差、入口速度；
   - 在任意 tick 改目标、取消、缺锚点；
   - 世界变化（方块出现或消失）、击退冲量、额度变化。
3. **地形族生成器：**
   - 宽场地加小高差；
   - 阶梯山坡（多道坎）；
   - 路线旁有坑；
   - 平台旁有墙；
   - L 形走道；
   - 半砖、土径、积雪混合地面。
4. **不变量监视器，每 tick 检查，在模拟和实机诊断中共用。** 例如：
   - 身体离开支撑时，必须有空中控制者；
   - 每一帧的移动输入都有明确的控制者；
   - 同一进度状态下的重试次数不超过上限；
   - 已承诺的伤害不超过任务额度；
   - 接纳的路线里，每条需证明的边都有证明；
   - 失败分类不能是“无路”，除非后备搜索也失败。
5. **验收分五级，文档中逐项标注：**已实现 → 组件通过 → 正式路径闭环矩阵通过 → Fabric 代表场景 → 完整矩阵关闭。前一级不通过，不进入下一级。
6. **修复规则：**
   - 每个审查发现都要附一个**性质测试**，覆盖这类缺陷，而不只是这个实例；
   - 附一次**同类搜索**记录：其他控制者、其他计数、其他门槛有没有同样的写法。
7. **角色分离：**实现完成后，由另一个会话或另一个 agent 只做一件事：用上面的模拟器找反例，然后才交外部审查。外部审查应当主要看设计取舍，而不是充当唯一的反例生成器。

## 七、推进顺序

每一步都小，都有可运行的验收，不做一次性重写。

| 步骤 | 内容 | 完成条件 |
|---|---|---|
| 0 | 闭环模拟器、扰动注入、不变量监视器；把前几轮审查脚本迁入测试 | 第十八轮的三个问题以失败测试形式出现 |
| 1 | 身体控制权协议；迁移路线执行器、空中动作、探边 | 第十八轮 P0 在“控制者 × 中断 × 时刻”矩阵下为 0 |
| 2 | 动作边界前置条件；落点证据与额度承诺移到动作开始前 | 多道坎、远处落点场景闭环通过 |
| 3 | 统一重试与额度账本；替换会话重规划、攻击、搭桥三处计数 | 交替原因、交替失败类型都能在上限内结束 |
| 4 | 拆分会话，建立显式状态转移表，`reason` 只用于报告 | 转移表穷举测试通过；会话主体明显变小，但以职责为准，不设行数指标 |
| 5 | 在新的验收分级下，补完连续高度的完整矩阵 | 按第六节第 5 点逐级关闭 |

步骤 0 到 3 完成之前，建议暂停新增能力，例如新的动作类型或新的地形。

## 八、不建议的做法

- **推翻重写：**分层和核心资产都是对的，重写只会丢掉已经验证过的部分。
- **引入通用状态机框架或插件系统：**三个接口加一张转移表就够了，与 AGENTS.md 的“不过度工程化”一致。
- **只加长文档或人工检查清单：**文档已经很认真，问题在于它不能自动执行。
- **继续以“代表场景通过”作为阶段推进条件：**这正是 C、D 两类问题的来源。
- **把行数作为目标：**拆分的依据是状态所有权和测试边界，不是文件长度。
