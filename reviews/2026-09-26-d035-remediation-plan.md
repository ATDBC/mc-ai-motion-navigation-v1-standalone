# 表面深度切换后的整改方案

日期：2026-09-26
对应审查：[第十三轮（D035）](2026-09-26-d035-review.md)，并收尾[第十二轮](2026-09-26-d034-review.md)的遗留项
基线：`origin/main` 提交 [`3e0c64b`][base]
性质：外部审查给出的方案建议，不属于 `docs/motion_navigation/` 四类正式文档。采纳时请按仓库规则写成正式的阶段计划和决定记录。

## 结论

1. **按“先不崩溃、再合法、然后降成本、最后补证据”的顺序，拆成 7 个改动包。**
   - 每个包只改一类可验收的行为，符合 AGENTS.md“一次修改围绕一个可验收行为，不同时改感知权限、路径评分和底层控制”。
2. **两项关键做法已经用正式代码验证可行：**
   - **剔除被完全包住的方块（修地下容量）：**
     - 200 个随机世界加 20 个实心岩层隧道，剔除前后的可见方块集合逐块一致，没有一例被剔除的方块本应可见。
     - 地下场景的打包数从 33,264 降到 6,392；再多读一圈邻居，可降到 240。
   - **降低观察成本：** 1,500 个方块时，JSON 解析只占解码时间的约 15%，其余都是逐块建对象和校验。所以真正有效的是“不重复发送未变化的方块”，换更快的 JSON 库没有用。
3. **恢复 B10 及后续实机验收前，必须先完成包 1、包 2、包 3。**
   - 否则新的 profile 4 证据会在“能看穿熔岩、能隔墙确认空气”的规则下产生，之后还得全部重跑。
   - 包 4 先做不改契约的两项修正，是否改协议按包 0 的实测结果决定。
4. **不建议的做法：**
   - 放宽动作窗口来掩盖 B10 晚到；
   - 把未知当空气来缩短首动时间；
   - 保留射线作为回退；
   - 在测量之前引入线程、缓存框架或配置开关。

## 包 0：先测量（不改行为）

**目的：** B10 仍会偶发晚 1 tick，D035 的数据是控制往返 P50 约 38 ms、P95 约 60 ms。在改协议或调度之前，先知道时间花在哪里。

**逐帧写入正式轨迹（只作诊断，不参与决策）：**
- 本帧导出的方块数，其中 `surface_depth` 来源各多少；
- 载荷字节数；
- 客户端各段耗时：表面计算、方块读取、JSON 构建、样本序列化；
- Python 端各段耗时：接收、解码、profile 4 门禁、快照构建、`NavigationObservationAdapter.ingest`；
- 观察年龄、请求的 tick 与实际生效 tick 之差。

**自然地形感知探针（新增场景，只采集，不移动）：**
- 场景：森林、山坡、峡谷边、洞穴入口、1×2 地下隧道、水面、熔岩湖旁；
- 每个场景采 200 帧，记录上面的数据，外加 `TileGeometryStore` 的记录数和每帧重读数；
- 在诊断模式下调用现有的 `SurfaceWorldSource.audit()`，确认事件驱动刷新没有漏掉变化（包 1 会用到）。

**产出：**
- 一张“场景 × 每帧方块数 × 各段耗时”的表；
- 与 B10 的晚到帧做对齐，看晚到是否集中在方块多或载荷大的帧。

## 包 1：传感器容量与刷新

### 1.1 剔除被完全包住的方块

**规则：** 一个方块同时满足下面三条时，不送入原生缓存：
- 它本身是不透明的完整方块；
- 六个面方向的邻居都是不透明的完整方块；
- 这些邻居都在当前存储里。邻居不在存储里（存储边缘、未加载区块）时，保留该方块。

**为什么不会产生“透视”：**
- 眼睛位于非实心格。任何视线进入实心区域之前，必须先穿过一个“实心格与非实心格之间的面”。
- 这个面属于一个与空气或透明方块相邻的方块，而这种方块永远不会被剔除。
- 所以，被剔除的方块本来就不可能被看见，也不可能是唯一的遮挡物。
- 剔除后，保留方块朝向被剔除邻居的那些面会重新进入场景。但只有从这个方块自己的外露面进入的视线才能看到这些面，而此时该方块本来就可见，结论不变。

**已验证（[`EnclosedCullingProperty.java`](2026-09-26-d035-plan-repro/com/mc2p/surface/EnclosedCullingProperty.java)，正式 `CacheBridge` 加仓库固定的原生源码）：**

| 场景 | 平均方块数 | 剔除后 | 可见集合差异 | 被剔除却可见 |
|---|---|---|---|---|
| 200 个随机世界（密度 0.35–0.95，含玻璃和半砖） | 2,949 | 2,718 | 0 | 0 |
| 20 个实心岩层中的 1×2 隧道 | 4,282 | 1,552（其中大部分是测试区域边缘） | 0 | 0 |

**容量（[`culling_capacity_estimate.py`](2026-09-26-d035-plan-repro/culling_capacity_estimate.py)，按 `TileGeometryStore` 规则）：**

| 地下 1×2 隧道 | 打包方块 |
|---|---|
| 现状 | 33,264（超过 25,000） |
| 剔除，存储边缘保留 | 6,392 |
| 剔除，并为边缘多读一圈邻居 | 240 |

**实现位置：**
- 在 `SurfaceSensor.pack()` 里先建一个 `HashMap<Pos, Record>`，每个记录查 6 个邻居后再决定是否打包。
- 只在 `store.changed` 时执行，挖掉一块方块会触发一次，所以需要在包 0 的探针里量一下耗时。
- 第一版保留存储边缘即可，6,392 已经远低于上限。只有测量显示 `pack()` 过慢时，再加“边缘多读一圈”。

**门禁测试：** 把上面的等价性检查改写成正式 Java 门禁：随机世界若干个，要求零差异。

### 1.2 刷新改为默认事件驱动

**现状：**
- 只有 6 个方块 ID（石头、泥土、草方块、基岩、金块、红石块）只在收到事件时刷新，其余方块每帧重读外形并比较。
- 在深板岩、安山岩、沙子、原木、树叶这类自然地形里，几乎所有方块都会每帧重读。

**改为：**
- 所有方块默认只在 `WorldChunk.setBlockState` 事件和区块加载／卸载事件时刷新。
- 只有外形依赖玩家上下文或方块实体、不经过 `setBlockState` 就会变化的方块，才每帧重读：`moving_piston`、各色潜影盒、`light`、`scaffolding`（后两者的外形取决于玩家手持物品）。
- 名单写成数据，并附上测试。

**验证：**
- 在包 0 的自然地形探针里，每隔 N 帧调用一次 `audit()`，要求零差异。
- 再做一个活塞推动和潜影盒开合的场景。

### 1.3 仍然超限时

- 保持明确失败，但失败原因要区分“存储方块超限”和“可见方块超限”，并写进会话失败记录。
- 只有自然地形实测仍会超限时，再考虑自适应半径。
  - 做法：按距离截断，同时把本帧的有效视距缩到截断距离，并写入元数据。
  - 这样被截掉的遮挡物一定比截断距离远，不会造成透视。
  - 本轮不需要做。

### 1.4 原生代码可跨平台编译

- 只需把 `__declspec(dllexport)` 换成一个导出宏：Windows 用 `__declspec(dllexport)`，其他平台用 `__attribute__((visibility("default")))`。
- 这样，原生逻辑测试可以在 Linux 上作为门禁运行。正式运行平台仍只验收 Windows，不改启动器的平台判断。
- 第十三轮的 `FlatFloorHarness` 和上面的等价性检查，都已经证明在 Linux 上只需改这个宏就能编译和运行。

## 包 2：遮挡规则与实体可见性

### 2.1 冻结遮挡表

**原则：** 每个方块有两个独立属性。
- “是否可见”：玩家能否看到它；
- “是否遮挡后方”：能否透过它看到后面的东西。

表格由原版数据一次性生成，提交到仓库，并记录版本哈希。

| 类别 | 可见 | 遮挡 | 说明 |
|---|---|---|---|
| 原版渲染层为 solid 的方块 | 是 | 是 | 默认情况 |
| cutout／translucent 层（玻璃、染色玻璃、玻璃板、遮光玻璃、冰、霜冰、史莱姆块、蜂蜜块、植物、蜘蛛网、铁栏杆等） | 是 | 否 | |
| 树叶 | 是 | **是**（固定策略） | 原版的树叶渲染层随“图像品质”设置变化，不能在运行时读取 |
| `packed_ice`、`blue_ice` | 是 | **是** | 现状错误地当作透明 |
| 流体本身（水） | 是 | 否 | 水下能见度留到 B13 |
| 流体本身（熔岩） | 是 | **是** | 现状错误地当作透明 |
| 含水方块 | 按方块本身决定 | 按方块本身决定 | 不再用“有流体就透明”一刀切 |
| `BlockRenderType.INVISIBLE`（屏障、光源方块、结构空位） | **否** | **否** | 不导出也不遮挡；`moving_piston` 例外，由方块实体渲染 |
| 表中没有的方块 | 是 | 是 | 默认按遮挡处理，偏保守 |

**实现与测试：**
- `SurfaceWorldSource` 改为查表，不再使用硬编码名单和 `!fluid.isEmpty()`。
- 门禁测试覆盖上表每一类的代表方块状态，包括含水台阶和含水半砖。
- 感知元数据和启动清单增加 `visibility_rules_id`（表格哈希），让以后的证据能说明自己用的是哪版规则。

### 2.2 统一视线判定

**新增一个小工具 `SightLine.clear(eye, point)`：**
- 在客户端线程上沿线段逐格遍历；
- 对每一格读取方块状态，按遮挡表判断是否遮挡；只有遮挡的方块，才用它的外形与线段求交。
- 不依赖表面缓存，所以 16 格以外同样适用。

**只用于以下两处：**

| 用途 | 现状 | 改为 |
|---|---|---|
| 实体可见性 | 5 个采样点，原版射线（`OUTLINE`＋`FluidHandling.NONE`）：玻璃挡住实体，熔岩不挡 | 保留 5 个采样点，改用 `SightLine`：玻璃后的实体可见，熔岩后的不可见 |
| 空气确认 | 不检查视线 | 见包 3 |

**准星命中仍用原版射线。** 它只回答“这次攻击或交互能不能打中”，不属于观察。

**先统一规则，再考虑采样精度。** 如果以后的战斗证据里出现“目标只露头却没被识别”，再改用原生面投影判断实体包围盒。

**测试场景：**
- 熔岩墙后的僵尸和方块；
- 浮冰墙后的方块；
- 含水台阶墙后的方块；
- 玻璃墙后的僵尸；
- 屏障墙后的方块，屏障本身不应出现在观察里。

## 包 3：空气确认加视线约束

### 3.1 客户端只回答“看得见的空气”

> 2026-09-26 修订：本节原先用“格心连线不被遮挡”作判定。后续原型证明中心连线规则两个方向都会出错，已改为下面的精确判定。完整论证、测试和耗时见[空气确认设计](2026-09-26-air-visibility-design.md)。

`discoverRequestedAir` 不再直接读取 `isAir()`，改由表面深度提供器回答。同时满足下面两条，才确认一格是空气：

1. **整格可见。** 这一格完全位于当前 120° 视锥和 16 格范围内，并且它在屏幕上的轮廓完全落在“可见区域”内。可见区域是指这一格的投影减去比它更近的不透明面。
2. **本帧没有报告方块。** 传感器本帧没有在这一格报告任何可见方块。

**实现要点：**
- 复用同一帧已经投影好的面，不另外发射线；
- 先用“中心加 8 个内缩角点”的快速点测试预筛，只有通过的格子才做精确的多边形判定；
- 预筛只会拒绝、不会误收，因为空格若整格可见，这 9 个点必然可见。

**测试：**
- 墙后、熔岩后、身后的空气不确认；
- 玻璃后的空气、正前方的空气可以确认；
- 脚下和身体占据的格子，仍由身体接触直接确认；
- 随机世界正确性测试：确认的格子里不得有任何方块外形。

### 3.2 允许用同一条件撤销过时的方块

**现状：** 视觉只会写入方块，从不会撤销，而导航的空气请求只针对未知格。所以路线上的支撑方块被别人挖掉后，世界知识里仍是“实心”。

**改为：**
- 导航可以把“当前路线依赖、且在视野内的已知方块”，以较低的配额加入空气请求。
- 客户端按 3.1 的条件判定：已知方块格若本帧整格可见，且没有报告方块，说明方块已经消失，确认为空气。
- 适配器随后用 `confirm_air` 覆盖旧方块，路线依赖变化会触发重新规划。
- 这与 B10 探针里已有的“已知方块也重查”思路一致，只是改成在视线约束下正式化。

**契约：**
- 修订 D004：空气确认要求当帧可见，范围与视觉一致。
- 修订 D035“空气与未知”一节。

### 3b 信息视角（单独一个包，避免同时改感知权限和控制）

**条件：** 只有同时满足以下三点，导航才提出一个低优先级的视角提案：
- 会话处于“等待信息”；
- 缺失格不在当前视野内；
- 本帧没有更高优先级的视角（战斗瞄准、路线动作）。

**视角怎么算：** 复用 `perception_candidates` 里已经改成连续区域的计算。

**优先级写进 D034 的视角归属：** 战斗瞄准 ＞ 路线动作 ＞ 信息视角。

**验收：** 在 B03、B10、B12 场景里，“等待信息”的帧数和首动时间不高于包 3 之前。

## 包 4：观察传输成本

### 4.1 不改契约的两项修正（先做）

**客户端不再二次序列化。**
- 部署探针现在把 `collectV3` 生成的 JSON 字节先解析成树，再和回执等拼成样本，整体再序列化一次。
- 改为按字节拼接：`{"schema_version":…,"observation":` ＋ 原始字节 ＋ `,"receipt":…}`。
- 另一种做法：在传输帧里把观察和元数据作为两个字段分开发送。

**Python 适配器跳过未变化的格。**
- 在 `NavigationObservationAdapter` 里保存每个位置上次写入的 `(block_id, collision, fluid_id)`。
- 与上次相同的位置，不再写入世界、不参与前后比较。写入成本从“每帧全部可见方块”降到“本帧变化的方块”。
- 解码成本不变：1,500 个方块时约 12 ms，其中 JSON 解析只占约 1.9 ms（[`decode_cost_split.py`](2026-09-26-d035-plan-repro/decode_cost_split.py)）。

### 4.2 增量协议（仅当包 0 显示仍有需要时才做）

**触发条件（满足任一）：**
- 自然地形场景的每帧可见方块 P95 超过约 800；
- 做完 4.1 后，端到端控制往返 P95 仍 ≥ 50 ms。

**协议改动（Observation V3 的 perception 段）：**
- `visible_positions`：本帧所有表面深度可见方块的位置，用排序后的扁平整数数组（x₀,y₀,z₀,x₁,…），解码成本很低；
- `blocks`：只放两类记录：
  - 相对上次已确认发送的内容，新出现或状态变化的可见方块；
  - 身体接触、空气查询、准星目标这几类来源的记录，照常每帧发送。
- **已发送状态的确认方式：** 沿用 `ClientDamageEventBuffer` 已经验证过的“下一代确认”。
  - 第 g 代发出的记录，要等收到代数大于 g 的请求才算已确认；
  - 未确认的记录下次重发；
  - 世界或会话变化时，全部清空重来。

**需要迁移的消费者**（它们现在把“出现在本帧 `blocks` 里”当作“当前可见”）：
- `interaction_aim` 的目标方块检查；
- `perception_confirmation`；
- `active_perception` 的前后比较；
- `navigation_memory`；
- `NavigationObservationAdapter`。

**等价性门禁：** 用已录制的轨迹，分别按全量帧和增量帧回放，要求：
- 每帧重建的世界知识逐格一致；
- `visible_positions` 与全量帧的可见位置集合一致。

**这是一次跨消费者的契约变更。** 需要单独写决定记录，并在它之前完成包 1–3，避免同时改规则和协议。
