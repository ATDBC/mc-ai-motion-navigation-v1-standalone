# 审查：F2-S 至 F2-RH 系列与复杂度分析（2bad9bf）

日期：2026-10-08。对象：`main` 上的 `2bad9bf`，对照 `9a8dfd6`（F2-S 方案）和 `1ee76b6`（F2-R）。复现脚本与输出在 [2026-10-08-f2s-chain-review/](2026-10-08-f2s-chain-review/)。

## 1. 结论

**是的，用了不必要的复杂思路，代价已经实际体现出来。**

原计划是一个“支撑区域收敛”小批次。一天之内，它扩展成 13 个子阶段和 13 条决定（D076—D088），共 108 个提交。运动导航生产代码从 39,551 行增加到 46,568 行（+7,017，+18%）。13 个子阶段中只有 F2-SP 通过，F2-S 本身也没有关闭。

现在的 `main` 处于以下状态：

1. **完整检查不是全绿。** Windows 1812 项中 56 项失败、4 项错误，项目在 README 中如实写明了这一点。我在 Linux 上得到 58 项失败、5 项错误，失败的测试方法与 Windows 基本相同。F2-R 时这套检查是 1647/1647 全绿。
2. **原有回归量尺跑不起来。**
   - F2 的 528 项冻结清单中，400 个玩家站位和 16 个参照任务全部以 `driver_failed/ready, not_started` 结束。原因是证据脚本里的运动 worker 替身不满足新的 Runtime 就绪接口，驱动器根本没有启动。
   - v7 产品证据在第一项就中止：`v7 stopped at invalid evidence: drop-normal-000000`。
   - 也就是说，这一串改动对历史产品行为的影响，目前没有任何量尺能测出来。
3. **普通地面控制慢了约 8 倍。** 用同一条开阔直线路线、同一台机器、同一个闭环，`FixedRouteController.decide` 的中位耗时从 1.06 ms 涨到 8.39 ms，P95 从 1.60 ms 涨到 13.25 ms（[输出](2026-10-08-f2s-chain-review/controller-hotpath-output.txt)）。这次性能没过门槛，根因就在这里：每个普通地面帧都对 9×2 共 18 个候选做完整的 1.21 物理验证，F2 设计中“开阔地走快速路径、最多复核 3 个候选”的结构被拿掉了。
4. **安全分类开始依赖墙钟。** 验证器用 `started + 30 ms` 的墙钟预算；超时后，候选被标为预算耗尽，控制器随即请求重规划。同一组输入下，只要模拟一个慢 31 ms 的时钟，原本第 50 tick 成功的路线就在第 2 tick 变成 `needs_replan`（[输出](2026-10-08-f2s-chain-review/wallclock-budget-output.txt)）。这违反了 F2 架构的不变量“行为不依赖墙钟”：在较慢或负载较高的机器上，机器人会频繁停下重规划。
5. **一组冻结的安全负例改变了结果，没有决定说明。** F2 清单中“未声明边缘”的 8 项，原来按设计被拒绝；现在全部 `succeeded`。仿真中没有掉落，所以不一定是安全缺陷，但这是对冻结负例的未解释改变，需要明确判断：是原负例过严，还是新验证器过宽。

D089 已经识别出“任务自动扩张”这个问题，并加了两轮修正上限和停止边界，这是对的。但 D089 只管以后，没有处理已经进入 `main` 的结果。

**建议：**

1. 先把 `main` 恢复到可验证的状态，再讨论下一步。
2. 普通地面控制回到 F2-R 的结构，只保留已经独立通过门槛的部分：F2-S 的区域几何、F2-SP 的有界选面，以及可以单独拆出来的 Runtime worker 生命周期修复。
3. F2S-C-04 改用“偏好面优先、无路时退回目标集合”的小修复，见第 4 节。

这条链的规律是：每一步都用一个更通用、更“可证明”的机制，回应一个很小的局部失败。新机制又带来新的回归，回归再成为下一步的理由。

- F2S-C-04 只有 1 项。它是 F2-S 自己改变了 Session 的选面结果造成的。
- 为它引入的多终点 A* 造成 51 项退步。
- 最后剩下的 3 项，机器人只停在目标外 0.006—0.023 格，为此引入了宽度 512 的 beam search、后台 worker 和 Runtime 生命周期改造。

每一步单独看都有道理，例如“唯一真值”“一次搜索”“共享策略”“完整候选族”“不用启发式代替证明”。但没有一步问过：为了这几个用例，值不值得改变公共结构？

## 3. 哪些复杂度是不必要的

### 3.1 用“完整候选族”取代 F2 的快速路径

D083 的理由是：前 3 个候选的上限“改变了安全集合”。这把两件事混在了一起：

- **安全性**：F2 中任何被执行的候选都经过了计算器完整验证，上限不会让不安全的输入被执行；
- **完备性**：上限只影响“能不能找到一个安全输入”。

为 4 项完备性失败，D083 让每个普通地面帧都验证 18 个候选。开阔直线路线的控制耗时因此涨了约 8 倍，这次性能失败的根因就在这里。

更简单的做法：保留 F2 的两级结构，只有当前 3 个候选全部失败时，才继续验证剩下的候选。代价只落在少数困难帧上。

### 3.2 用 beam search 处理 0.006—0.023 格的误差

D086 的 3 个用例，机器人都已经安全停稳，只是离窄完成区域差不到 3 厘米。更合适的处理有几种：

- 停稳后再给一次低速的单 tick 修正；
- 检查这些完成区域为什么这么窄。它们是目标与可站区域相交的结果，可能根本不适合作为终点；
- 接受一个明确的失败分类。

宽度 512 的 beam search 需要后台 worker、11 tick 的提前量、取消和世代作废，又进一步要求改造 Runtime 的 worker 生命周期。这个代价与问题的规模不成比例。

### 3.3 墙钟预算进入安全分类

F2 曾明确规定“候选数量固定，不能用墙钟决定是否继续检查”。现在为了让 18 个候选在帧内算完，加了 30 ms 的墙钟预算。用“预算耗尽”这个分类保证不会被当作安全，是对的；但它让行为取决于机器速度和负载。

如果需要一个上限，应该按物理步数或候选数这类确定的量来设，而不是用墙钟。

### 3.4 状态机没有生产者，却仍在维护

D075 规定：如果下一阶段不是路线优化器，就删除潜行状态机。下一阶段已经变了，状态机却没有删，现在 36 项失败来自它的组件测试。

## 4. 当初更简单的路线

F2S-C-04 出现时（第 2 节第 4 行），有两个小得多的选择：

1. **偏好面优先，无路时退回目标集合。** 在同一个规划作业里，先按 Session 的偏好面搜索；找不到路线时，再用已有的 `goal_test` 搜索目标里所有可行的面。不需要 Session 重试状态，也不改通用 A*。偏好面可达时，行为和以前完全一样，所以不可能产生 51 项退步。它也能处理 41 项“无已知路线”中的 39 项可达任务。

   D078 拒绝这个做法的理由是“可能先接受一条更差路线”。这是一个最优性上的顾虑，不是产品问题：被拒绝的方案能保住所有旧成功。

2. **如果坚持多终点搜索**，终点仍用节点到达判定，再加一个便宜的代价项，比如节点到完成区域参考点的距离。最后一段继续交给 F2 原有的控制器，F2 中 400/400 证明它能完成这些终点。不需要终点搜索边、共享跟踪策略、完整候选族或 beam search。

这两条路线的预计改动都在几百行以内，而且都能用现有的 v7、v8、F2 528 量尺直接验证。

我也有责任。F2-S 让 Session 改用区域查询选面，是我上一轮建议的。这项统一改变了 1 个杂乱场景的选面结果，链条就从这里开始。我当时应该同时建议：统一查询时保持原有的选面结果，或者给无路情况留一个回退。

## 5. 应该保留的部分

- **F2-S 的区域几何**：统一网格、绑定矩形复核、只跟踪选定矩形的依赖。它独立有效，并且解决了 F2S-C-01。
- **F2-SP 的有界选面**：它通过了 D061，耗时 5.17/5.36/7.02 ms。
- **D087 的三段时间量尺**（生产、模拟后端、完整夹具）：它纠正了量尺本身。
- **Runtime 持有 worker 以及几处 typed 修正**：READY 之后死亡、取消队列满时的背压、发布前最后一次检查。这些缺陷对空中动作求解同样存在。如果能从 TS/TP 中拆出来单独验证，就值得保留。
- **D089 的风险分级和任务扩张边界。**

## 6. 建议的恢复顺序

1. **恢复可验证的 `main`。** 普通地面控制、规划终点和接纳回到 `1ee76b6` 的结构，叠加上面第 5 节的几项。以下内容先撤出主线，保留在分支上：F2-SG/ST 的终点搜索边、GP/PC/SC 的跟踪策略、CV/WR/SS 的帧内完整验证、TS/TP 的 beam search 交付。
2. **立一条硬规则：公开 `main` 的完整检查必须全绿**，或者失败集合与上一个签署版本逐项相同。这次已知红着的 `main` 被发布了，这本身就是一个流程问题。
3. **修复回归量尺。** 证据脚本使用的运动 worker 替身必须满足新的就绪接口。在 v7、F2 528、v8 都能跑通之前，不接受任何普通地面控制的行为变更。
4. **F2S-C-04 用第 4 节方案 1 修复**，一个小批次。门槛：F2S-C-04 恢复；v7、v8、F2 528 的旧成功退步为 0；控制耗时回到 F2-SP 水平。
5. **删除潜行状态机**（按 D075），并为“未声明边缘”负例写明期望。
6. 之后如果还要追求完备性，例如 F2-CV 想解决的 4 项，就按 3.1 的“回退式完整验证”来做，并使用确定的预算。

## 7. 证据边界

- Linux 只是补充复核：完整检查、F2 528 项、控制耗时的同机对比、注入时钟的检查，都在这台机器上完成。
- 控制耗时只比较同一台机器上两个提交的相对差别，不能代替 Windows 实测数值。
- “未声明边缘”的结果来自仿真，没有在 Fabric 上验证。
- 第 4 节的替代方案没有实现或测试，只是设计判断。
