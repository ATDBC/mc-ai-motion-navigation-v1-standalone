# D105 三轨止损审查：T1 卡在证明摘要，T2-2 的门槛超出安全需要，T3 的 B10 失败尚未归因（`eec26af`）

日期：2026-10-13。审查对象：`origin/main` `eec26af`，包括 D105、阶段计划、验收、可靠稀疏证明架构、`sound_sparse_proof.py`、T2 receiver 改动、F-TICK sidecar 和三条轨道的证据。脚本与输出在 [2026-10-13-d105-review/](2026-10-13-d105-review/)。

## 结论

**三条止损都按预登记规则执行，失败证据保存完整，三轨互不拖累的结构也起了作用。但三处止损的直接原因，都不是各自要验证的核心问题：**

- **T1**：方案 A 已把推演成本降了六成。卡住它的是对整份证明做两次规范 JSON＋SHA-256，占扫描时间的 59%。
- **T2-2**：要求的“最大可达包络”只影响命中率，不影响安全。
- **T3**：实测到的 22 个试次全部落在下一 movement tick。失败来自一条近三周没有正式实机运行的 B10 旧路径，目前无法区分是旧缺陷还是 sidecar 的时序干扰。

**建议下一步不做方案 B。** 先去掉证明身份摘要的重复计算，再按第 5 节分别处理三件小事。

1. **T1：P99 就是首决定的成本，而首决定的大头是证明摘要。**
   - 204 个首决定只占 4,710 个决定的 4.33%，所以 P95 落在普通决定上（0.13 ms），P99 落在首决定上。
   - 首决定中位 23.61 ms，最小 23.25 ms。最大值 30.46 ms 是单个离群点，前五大值在 29.2—30.5 ms。
   - Linux 不插桩拆分一次 D105 扫描（E19），共 42.9 ms：
     - 推演、尾迹和组装 17.8 ms，占 41%；
     - 整份证明摘要每次 11.8 ms，算了两次：生成时一次，`validate_sound_sparse_proof` 紧接着又算一次；
     - 结构检查只要 1.1 ms。
   - 方案 A 本身达到了目的：物理步 407→143（−65%），推演与组装 45.2→17.8 ms（−61%）。
   - 摘要对象是 202,752 字节的规范 JSON，包含每个已算尾迹的逐 tick 状态。其中 8.2 ms 花在 Python 递归的 `_canonical` 上，JSON 编码和 SHA-256 本身只占约 3 ms。
2. **只改摘要算法、不改证明内容，就能过线；单做方案 B 过不了线。**（Windows 首决定估算，按 Windows 实测 23.61 ms 等比例换算）

   | 做法 | Windows 首决定 | 15 ms 门槛 |
   |---|---:|---|
   | 现状：整份摘要算两次 | 23.6 ms | 失败 |
   | V1：只算一次 | 16.9 ms | 失败 |
   | V1′：只算一次，规范化按类型缓存字段表（摘要逐字节相同） | 13.8 ms | 通过，余量小 |
   | V2：只摘要紧凑证明 | 13.2 ms | 通过 |
   | V3：控制线程不算内容摘要 | 10.4 ms | 通过 |
   | 方案 B（E17 包络），摘要不改 | 约 21—22 ms | 失败 |
   | 方案 B＋V3 | 约 8—9 ms | 通过 |

3. **我上一轮的估计漏掉了这个常数，需要更正。**
   - D104 审查估计方案 A 的 Windows 首决定约 7—10 ms，实际是 23.6 ms。
   - 我当时只计时了主轨迹回放和尾迹推演。这部分本轮在同一工作量上实测约 7.7 ms（Windows 换算）；D105 实现的推演加组装约 9.8 ms。这部分估计本身没错。
   - 但我没有把证明组装、摘要和复验算进去，也没有指出 D101 旧扫描器里摘要已占 35%。“方案 A 能过线”的判断因此错了。
4. **T2：receiver 精简真实有效，但 T2-2 的止损条件比安全需要更严。时间线也漏报了两处数字。**
   - **可信投影与完整构造结果一致。** 在 6,496 格夹具上，`_trusted_hot_view`／`_trusted_handle` 与完整构造逐字段相同；构造耗时从 24.7 ms 降到 0.008 ms（E21）。项目测试没有这条等价断言，建议补上。
   - **T2-2 的止损条件不是安全需要。** 快照外的格子由 `SealedSnapshot.cell` 返回 UNKNOWN，物理计算随之返回需要信息，不会当成空气。包络取小了只会降低命中率，不会产生假 SAFE。安全性已经由“越界即需要世界信息＋实际依赖复核”保证，T2-2 不需要先证明多模板的最大可达包络。
   - **从请求到首次消费是 451 ms，不是文档中的 330 ms。**
     - 提交前还有 117 ms 的快照封存（1,176 格），文档没有报告。
     - worker 的 300 ms 没有分项，`worker_solve_ns` 为空。
     - 451 ms 约合 9 个 tick。它是连续两跳能否衔接的关键数字。
   - **同一份 probe 中，控制线程的交接 tick 为 43.4 ms，收尾 tick 为 58.4 ms。**
     - 时间线生成时用了 `check_performance=False`。打开后这份 probe 会报 4 项性能错误。
     - E20 表明，这主要是 G2 量尺的 `sys.setprofile` 造成的：在 Linux 上，量尺把普通 tick 从 1.65 ms 放大到 8.6 ms，交接 tick 从 9.7 ms 放大到 102 ms，收尾 tick 从 15 ms 放大到 101 ms。
     - 去掉量尺后，按约 0.5 的比例换算，Windows 的交接 tick 约 5 ms，收尾 tick 约 6—9 ms。
     - 结论：这把量尺可以用来数调用次数，不能用来计时。
5. **T3：F-TICK 本身得到的是正面结果，失败的是被借用的 B10 旧路径，原因还没查清。**
   - 18 个 INCOMPLETE 全部是 `trial_missing`，即 B10 中止后根本没有运行的试次。实际运行的 22 个试次全部是 `NEXT_MOVEMENT_TICK`，没有一个 LATER，也没有一个时间线残缺。西向一个样本也没有。
   - `coast_input_unobserved_retain_landing` 的含义是：滑行段内某个 movement tick 在输入账本里没有样本。
     - 原始 trace（8.9 MB）不在导出仓库内，现有证据无法定位根因。
     - 候选原因之一是旧路径回归。文档记录的 `b10_gap_solver_runtime.py` 最后一次正式 Fabric 通过是 2026-09-25（`a059bdc6`）。此后导出仓库里有 13 个提交改过 `motion_candidate.py`，5 个提交改过该脚本，而这个失败原因从未出现在任何已提交证据中。
     - 另一个候选原因是 sidecar 的时序干扰。sidecar 在客户端线程的 `tickMovement` 内同步写盘：每个事件重新解析一次 JSON，再写入并 flush，每 tick 约 4 个事件。它不改数据，但改变时序。
   - “ordered source 未注销”很可能是 B10 抛错中止后的连带结果，应查中止路径的清理逻辑，不宜单独当作一项能力退步。

## 2. T1：方案 A 做对了，卡在证明摘要

### 2.1 P99 量的是什么

三份 Windows 正式证据使用同一工作量（204 场、4,710 个决定），首决定都包含完整证明（E19 §1）：

| 证据 | 首决定中位 | 最小／最大 | 物理步 | 全体 P99 |
|---|---:|---:|---:|---:|
| D101 M0 旧扫描器 | 48.35 ms | 38.35／57.56 | 408 | 48.61 ms |
| D104 K2（无效候选诊断） | 18.12 ms | 17.93／18.53 | 178 | 18.25 ms |
| D105 T1 方案 A | 23.61 ms | 23.25／30.46 | 144 | 23.71 ms |

- 首决定只占 4.33%，P99 的位置正好落在首决定里。因此在这个工作量下，“P99 ≤15 ms”实际上就是“首决定 ≤15 ms”。
- 普通决定最大只有 0.154 ms。逐 tick 比较的开销已经很小，这一点 D105 没有退步。
- D104 的失败候选物理步更多（178 对 144），耗时却更短（18.1 对 23.6 ms）。这说明决定 D105 耗时的不是物理步。

### 2.2 耗时拆分（Linux，40 轮交错，取最小值）

| 部分 | D105 方案 A | D101 旧扫描器 |
|---|---:|---:|
| 主轨迹＋尾迹推演＋组装 | 17.78 ms（143 步，约 124 µs／步） | 45.21 ms（407 步，约 111 µs／步） |
| 整份证明摘要 | 11.79 ms × 2 次 | 24.82 ms × 1 次 |
| 结构与紧凑尾迹检查 | 1.13 ms | — |
| 合计 | 42.91 ms | 70.03 ms |
| 摘要占比 | 59% | 35% |
| 规范 JSON 大小 | 202,752 字节 | 452,611 字节 |

代码位置：

- `scan_sound_sparse_commitment` 先执行 `proof = replace(proof, trajectory_hash=trajectory_digest(proof))`，随即调用 `validate_sound_sparse_proof(proof)`。后者第一步又是 `trajectory_digest(replace(proof, trajectory_hash=""))`。
- 同一调用内、同一个不可变对象、同一个确定性函数，第二次只可能得到相同结果。这次复验不防任何错误。
- 摘要覆盖 `boundary_decisions[*].tail` 的全部逐 tick 状态。架构文档 §6 只要求保存“输入和主轨迹摘要”和关键边界的可执行尾迹。逐 tick 尾迹还要随证明一起做规范化，这超出了文档的要求。
- 一次整份摘要 11.8 ms，其中 `_canonical` 递归占 8.2 ms，主要花在逐值调用 `is_dataclass`、`fields` 和 `isinstance`。改为按类型缓存字段名后，输出逐字节相同，摘要降到 6.2 ms（E19 已核对摘要值相同）。

### 2.3 变体估算

换算方法是：Linux 上各部分占现状扫描的比例 × Windows 实测首决定中位 23.61 ms。前提是各部分在两个平台上按同一比例变化。同一份代码在两个平台上实测的 Windows/Linux 比为 0.49（D105）和 0.63（D101）。比例并不完全一致，表中数字只能作为量级参考。

| 做法 | 改动 | 证明内容 | Linux 扫描 | Windows 首决定 |
|---|---|---|---:|---:|
| 现状 | — | — | 42.9 ms | 23.6 ms |
| V1 | 删掉 validate 里的整份复算 | 不变 | 30.7 ms | 16.9 ms |
| V1′ | V1＋按类型缓存字段表的规范化 | 不变，摘要逐字节相同 | 25.1 ms | 13.8 ms |
| V2 | V1＋摘要只覆盖紧凑证明 | 不变，但逐 tick 尾迹不再受摘要覆盖 | 24.0 ms | 13.2 ms |
| V3 | 控制线程不算内容摘要，由 worker 或进程边界计算 | 不变 | 18.9 ms | 10.4 ms |

- V1′ 是最小改动：只去掉冗余，语义不变，T1-A0—A2 的完整性结论不受影响。缺点是离 15 ms 只有约 1 ms 余量。
- V3 与 T2 的信任模型一致：worker 产出证明并计算摘要；同一发行物内的本地 worker 结果不在热路径复算。在 D101 这个同步探针里，V3 意味着摘要不在决定计时窗口内计算。必须在决定文档里写明这一点，否则会被看成挪开计时。
- V2 改变了摘要覆盖的范围。中段晚到时，`saved_executable_tail` 仍会读取非关键边界的完整尾迹，所以 V2 需要额外论证这些尾迹不必受摘要保护。不建议优先采用。

### 2.4 方案 B 的上限

E19 §5 在同一工作量上运行上一轮 E17 的保守停车包络：

- 方案 B 把物理步从 141 降到 107，风险区间仍为 `(3, 4, 17)`，与旧扫描器一致；
- 推演时间按 B/A 耗时比缩放（两次运行分别为 0.73 和 0.82）后，加上各种摘要做法：

| 组合 | Windows 首决定 |
|---|---:|
| 方案 B＋现状两次摘要 | 约 21—22 ms |
| 方案 B＋V1 | 约 14—15 ms |
| 方案 B＋V3 | 约 8—9 ms |

B 被包络证明的边界不保存可执行尾迹，真实实现还要补上这部分，所以上表是下界。**单做方案 B 过不了门槛；修好摘要后，不做方案 B 也能过。** 方案 B 应搁置，等更难的场景实测出推演瓶颈后再议。

### 2.5 对我上一轮估计的更正

D104 审查第 4 点写“方案 A 约 7—10 ms，Windows 估算”，这个数字只计时了 E17 的 `sparse_scan`：主轨迹回放、尾迹推演和区间判定，不含证明对象组装、摘要和复验。本轮同一部分实测为 15.9 ms（Linux），换算后约 7.7 ms（Windows），与当时的估计一致。错误在于漏掉了常数项：

- 我在 D101—D103 审查中已经测过 receiver 侧规范化和构造器重放的成本，却没有想到扫描器自身也在做整份规范化；
- 因此没有提醒“过线还要看摘要”。

这是我连续第二轮的性能估计出错（上一轮是 E16 用了答案区间）。今后的估计会以项目的完整入口函数为计时边界。

### 2.6 其他代码观察

- `validate_sound_sparse_proof` 的结构检查（1.1 ms）覆盖了逐边界决定、风险开闭、空中省略的条件和紧凑尾迹的契约，有实际价值，应保留。
- 第一阶段的 `_RiskCertainty.UNRESOLVED` 只在支撑探测遇到 UNKNOWN 时出现。之后第二阶段一定会在同一边界抛出需要信息的错误，所以 UNRESOLVED 只会让后续多算尾迹，不会少算。这一点是保守的。
- 方案 A 在本工作量上省略了 48 个边界中的 24 个，全部是风险打开后的空中边界。这与 E17 的统计一致。

## 3. T2：receiver 精简成立，T2-2 止损条件过严，时间线漏报两处数字

### 3.1 receiver 可信路径

- 信任条件是 `type(worker) is MotionSolverWorker`。结果经由父子进程之间的私有管道传回，这个边界合理。
- 可信路径跳过了以下检查：
  - 整图不可变遍历；
  - 构造器重放；
  - 整份规范 bytes 与摘要复算；
  - 父侧自己封存的快照复核。
- 可信路径保留了以下检查：
  - job token、计数预算、ruleset 和证明形状；
  - request、generation、owner、路线、账本、世界、输入、窗口和伤害；
  - 依赖事实与快照的比对。
- 拒绝矩阵测试覆盖了这些保留项。
- `_trusted_projection` 用 `object.__new__` 加 `object.__setattr__` 绕过构造器。测试检查了字段名是否漂移，但没有检查“同一 bundle 两条路径得到的结果相同”。E21 补做了这项检查：19 个 hot view 字段、8 个 handle 字段（不含随机 token）全部相同。建议把这项检查加入项目测试，否则以后 `from_bundle` 改变派生方式时，可信路径会悄悄偏离。
- 可信路径下 `bundle.proof_digest` 不再复算，却仍写入 `registered_digest`。在信任前提下这没有问题，但它只是一个标签，不能再被当作“已核对的内容身份”使用。

### 3.2 T2-2 止损的前提

`t2-2-stop.json` 的止损理由是：请求里没有动作模板的最大可达包络，因此无法证明 detached 快照的边界足够大。

这个要求把命中率当成了安全条件：

- `SealedSnapshot.cell` 对快照外的格子返回 `UNKNOWN_CELL`（E21 §2），物理计算遇到 UNKNOWN 时返回需要信息，不当空气；
- 父侧还会用快照核对证明的实际依赖，执行前再用正式世界复核；
- 所以快照取小了，结果是 NEEDS_WORLD、重取、多花时间，不会接纳错误的证明。

建议把 T2-2 改成两条：

1. **安全条件：** 越界读一律得到需要信息；实际依赖全部在快照内并与正式世界一致；
2. **效率指标：** 用“已选轨迹扫过的包围盒＋尾迹最大滑行距离＋1 格”等简单包络取快照，实测 NEEDS_WORLD 比例。

这样做不需要新的多模板包络算法，也符合 AGENTS.md“不提前建设”的要求。

### 3.3 生产链路时间线

| 段 | 耗时（Windows） | 文档是否报告 |
|---|---:|---|
| 请求准备到快照封存完成（`_seal_snapshot`，1,176 格） | 117.1 ms | 否 |
| 提交 | 2.6 ms | 否 |
| 提交 → 父侧收到 worker 结果 | 300.4 ms | 是 |
| 收到 → receiver 发布 | 29.6 ms | 是 |
| 发布 → 首次消费 | 0.35 ms | 是 |
| **请求 → 首次消费** | **450.9 ms ≈ 9 tick** | 否（文档写的是提交 → 消费 330 ms） |

- worker 的 300 ms 没有分项，`worker_solve_ns` 为空。其中可能包括请求反序列化、证明搜索、规范化与摘要，以及 688 KB 结果的序列化。
- 第 2 节已经表明，规范化和摘要在 worker 侧同样昂贵。这 300 ms 是下一个需要量清楚的瓶颈。
- 连续两跳的第二跳若要在第一跳空中准备好，需要在起跳时就提交请求，并保留约 9 tick 的准备时间。一格跨隙的空中时间约 12—14 tick，余量很小。

### 3.4 控制线程的交接与收尾 tick

同一份 spawn probe 中，控制线程的样本如下（Windows，量尺开启）：

- 普通 tick 中位 4.40 ms；
- 交接 tick（24）43.44 ms，其中 arbitration 34.4 ms；
- 收尾 tick（41）58.42 ms，其中 handle 38.8 ms、handoff 12.8 ms。

时间线是在 `validate_probe(raw, check_performance=False)` 下生成的。若打开性能检查，这份 probe 会报 `control percentile exceeded: complete／handoff` 和 `control maximum exceeded: complete／handoff` 共 4 项错误。验收文档只写了“时间线完整”，没有提到这些样本。

E20 在 Linux 上用同一夹具和坐标重跑（inline worker），并把量尺的 `sys.setprofile` 换成空操作再跑 5 次：

| tick | Linux 量尺开启 | Linux 无量尺（5 次中位） | 放大倍数 |
|---|---:|---:|---:|
| 普通控制 tick（中位） | 8.63 ms | 1.65 ms | 5.2× |
| start | 10.14 ms | 2.06 ms | 4.9× |
| handoff | 101.71 ms | 9.74 ms | 10.4× |
| closeout | 100.76 ms | 15.04 ms | 6.7× |

- 量尺通过 `sys.setprofile` 记录每一次 Python 调用，调用越密集的代码被放大得越多。整图不可变遍历的递归调用就属于这一类：我对一次 inline probe 做剖析时，`visit` 共被调用约 18 万次。
- 两个平台在量尺开启时的比例约为 0.43—0.58。按这个比例粗估，Windows 无量尺时交接 tick 约 4—6 ms，收尾 tick 约 6—9 ms。均未超过 30 ms 的最大值门槛，但交接 tick 接近 P95 的 8 ms。
- 收尾 tick 在无量尺时，44% 的时间花在构造 `ProofReleaseEvidence` 等对象时的整图遍历上，其中 `ProofReleaseEvidence` 两次共 4.9 ms。这和 T2 在 receiver 上去掉的是同一类开销，只是发生在控制线程上。
- 我在 D101—D103 审查中说 closeout 的 8 tick 停车检查只有约 0.5 ms，这个数字对检查本身仍然成立。但我当时没有发现 closeout 里还有构造器整图遍历这项更大的成本。

**结论：** G2 量尺适合数调用，不适合计时。性能门槛应在关闭 `setprofile` 的运行中计时，调用计数放到另一次运行里统计。否则任何后续的 G2／realtime 性能判定都会被量尺本身放大 5—10 倍。

## 4. T3：F-TICK 得到正面结果，失败的是 B10 旧路径

### 4.1 22 个完整时间线证明了什么

- 22 个完整时间线：南 10、东 10、北 2。每个都是 `movement_tick_offset = 1`，即决定发出后，首条命令在下一 movement tick 生效。没有 LATER，也没有身份错配或重复。
- 18 个 INCOMPLETE 全部是 `trial_missing`：B10 在第 23 个试次中止后，剩下的试次没有运行。它们不代表 sidecar 丢事件或时间线残缺；sidecar 封存了 1,818 个事件，丢弃为 0。
- 这与既有实机证据一致：
  - D053 批次 `e6db26f5` 的四次起跳都是观察与应用相邻 tick；
  - `action-entry-handoff-repair` 批次 `a3e39991` 中，四次故意晚一 tick 的试次都在请求后的第二个运动 tick 生效，与设计一致。
- 局限：西向没有样本；样本只来自单机本地服务器，没有覆盖高负载或网络延迟。

### 4.2 B10 失败：已知与未知

已知：

- 失败发生在 command 16，B10 已进入滑行段（剩余命令全为中性）；
- `_coast_input_changed` 发现从 `_coast_checked_through_tick + 1` 到当前锚点之间，有 tick 在输入账本里没有样本，于是返回 `missing`，执行器转入 RECOVERING，终态为 INPUT_LOST；
- 文档记录的 `b10_gap_solver_runtime.py` 最后一次正式 Fabric 通过是 2026-09-25 的 `20260925T134940922188Z-a059bdc6`。此后导出仓库里有 13 个提交改过 `motion_candidate.py`（包括连续高度、S0—S5、连续跨隙入口、D053、D055、D103），5 个提交改过该脚本；

未知：

- 哪个 tick 缺样本、缺失发生在客户端回执还是 Python 账本合并环节。原始 trace 和 `b10-gap-solver-trials.jsonl` 不在导出仓库内，只有哈希。

### 4.3 sidecar 不改数据，但改时序

`ClientFtickDiagnostics.event` 在客户端线程上同步执行：

- 同步锁；
- 构造 `JsonObject`；
- `ClientTimeSegmentWriter.accept` 中的 `JsonParser.parseString` 再解析一次；
- `stream.write`、`stream.flush`，以及每秒一次的磁盘余量检查。

每个 tick 至少触发 `INPUT_SAMPLED`、`MOVEMENT_APPLIED`、`CLIENT_FRAME_RECEIVED`、`CLIENT_OBSERVATION_SENT` 四个事件，其中两个就在 `tickMovement` 内部。它们不改写任何输入或账本字段，所以“只读”在数据上成立；但每个 tick 都多了同步 I/O，所以对时序不是零影响。

在 Windows 上，杀毒软件或磁盘缓存偶尔会让一次 flush 变慢。这能否让某个 tick 的样本赶不上观察，现有证据既不能证实，也不能排除。

### 4.4 其他

- `ordered_source_not_released` 由 `_ordered_source_release` 根据 trace 中缺少 `ordered_source_unregistered` 判定。B10 以 RuntimeError 中止，这一项很可能是中止路径没有走到注销逻辑。建议作为探针清理缺陷单独检查。
- T3 index 的命令是 `--run-dir … --output .tmp\d105-t3-replay-fix2-20261013`，说明正式结果来自对同一不可变原始批次的第三次分析（replay 模式）。这符合“不重跑 Fabric”，但验收文档没有说明分析脚本改过两次、改了什么。分类依赖分析器，建议补记。
- 预检失败（缺 `JAVA_HOME`）单独保存为 `t3-preflight-no-java-home/`，与正式批次分开。这样处理是对的。

## 5. 建议的下一步

D105 的三轨结构值得保留。这一轮三处止损都落在测量或附带成本上：

- T1 是摘要常数；
- T2-2 是把命中率写成了安全条件；
- T3 是借用的旧路径。

之前 D101 M0（摘要占 35%）和 D103 G2（量尺计数）也是这样。建议先清理这类常数和量尺问题，再动算法。下面每一项都可以单独立项、单独止损：

1. **T1-R：证明身份摘要只算一次。**
   - 删掉 `validate_sound_sparse_proof` 里对整份证明的复算，结构检查保留；规范化改为按类型缓存字段表，输出逐字节相同（V1′）。
   - 证明内容不变，T1-A0—A2 的结论继续有效，只需重跑 Windows M0。预期约 14 ms。
   - 若余量不够，再决定是否采用 V3（摘要归 worker 或进程边界），并在决定文档中写明计时窗口。
   - 方案 B 搁置。
2. **T2-2-R：改写快照门槛。**
   - 安全条件改为“越界即需要信息，实际依赖复核”，包络改为效率指标并实测命中率。
   - 补上可信投影与完整构造的等价测试。
   - 时间线补报快照封存时间和 worker 分项（反序列化、求解、规范化、序列化）。
3. **G2 量尺拆分：** 计时在关闭 `setprofile` 的运行中进行，调用计数另跑一次。之前凡是用这把量尺得出的耗时结论，都应注明“含量尺放大”。
4. **T3-R：先归因，再重测。**
   - 在同一源码上关闭 sidecar，跑一次 B10 对照批次。这次运行作为诊断单列，不计入 T3。
   - 对照也失败：属于 B10 旧路径回归，按 B10 缺陷单独修复。
   - 对照通过：把 sidecar 改为内存有界缓冲，收尾时再写盘，然后重做 T3。
   - 另一个选择是让 F-TICK 改走现行的正式导航驱动路径（C1R 之后的 `NavigationSession`），不再依赖 B10 旧脚本。这一点由项目决定。
5. **连续两跳的前置条件：** 以上各项完成后，真正决定能否衔接的是第 3.3 节的 451 ms 准备链延迟。应先把 worker 的 300 ms 拆清楚，再讨论零等待交接。
