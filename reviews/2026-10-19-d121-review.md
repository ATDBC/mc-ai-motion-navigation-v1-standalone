# D118–D121 审查，以及联合事实是否需要另写决定（3889d10）

日期：2026-10-19。审查对象：`origin/main` 3889d10（“Publish D118-D121 momentum handoff work”），对照上一轮的 dce230f。

平台说明：

- 本轮只在 Linux 上运行项目函数、项目夹具、项目脚本和项目测试，项目树本身不改。
- 脚本和输出在 [`2026-10-19-d121-review/`](2026-10-19-d121-review/)。
- 体积和耗时都是 Linux 上的数值。消息字节与平台无关：S2 探针在 Linux 上复现的字节数与公开证据逐字节相同。

## 结论

1. **D118–D120 方向对，结果站得住。**
   - **D118-0 停得对：** 实机发现计算器漏了原版的 0 高度 step 候选。D119 只改了 18 行（行尾变化之外），条件与原版 1.21 收集 step 高度的规则一致：按 float 取差、`>= 0`、不等于基础 Y 位移、不超过台阶高度。
   - **D120 离线校准在 Linux 上复现（E120）：** 四方向 972 个入口、2916 个后缀全部通过，清单哈希与公开证据一致，用时 6.6 s。
   - **D117 代表链没有退步（E115）：** 正常情况仍是 tick 21 起第二跳、tick 36 完成。快照持续 BUSY 时回退普通求解，两个提交各 20/20，tick 完全相同。
2. **D121-S1 的通用 fallback 是对的，但它把证明放大了一个数量级。现在还不阻塞，以后长动作链的体积就来自这里。**
   - **体积与耗时（E114、E116）：** 同一个一格跨隙，当前证明的规范字节从 41,684 变成 413,586（pickle 从 9,913 变成 90,096）。单次求解中位耗时从 33 ms 变成 69 ms，规范摘要从 3.8 ms 变成 31 ms。
   - **原因：** 每个命令边界都保存一条完整尾段，两个起点分支各一套。尾段状态（186 个／分支）是主轨迹（17 个）的 11 倍，占证明字节的 90%（E112）。
   - **可去掉的冗余（E117）：** D121 真实场景的第二跳，尾段状态里 75% 与主轨迹逐值相同。
3. **S2 的止损不是消息容量问题，是表示方式问题。我认为这里出现了过度防御。**
   - **不复制时离上限很远（E114、E117）：**

     | 消息 | 字节 | 占 2 MiB |
     |---|---:|---:|
     | 同一 gap→gap 夹具，现行正式后继消息 | 695,487 | 33% |
     | D121 四格场景，第二跳 | 469,369 | 22% |
     | D121 四格场景，第一跳（同一 fallback 规则） | 613,205 | 29% |

   - **超限来自测试侧 direct-copy 的重复（E112、E113）：** 它把当前证明放了两份、后继证明放了两份，pickle 里又带了一份规范 JSON，所以达到 2,137,317 bytes。
   - **按你提的“引用＋摘要＋出口 fallback”：** 只多约 4–14 KB。即使两条完整证明各带一次，也只有约 1.1 MB（52%–56%）。
   - **体积止损不是登记过的条件：** D121 决定 §6 的停止条件里没有消息体积。第一次试做把对象图重复了一遍，属于两轮限定修正内就能改掉的实现错误，不该升级为阶段止损。
   - **新测试把这次失败锁死了：** `test_d121_joint_worker_stop` 断言 direct-copy 必须超过 2 MiB，断言 `PreparedJointMotionProof` 等名字不存在，还断言证据与复现逐项相同。以后证明一旦变小，或按计划实现联合类型，这些测试都会失败。
4. **下一步需要写下来，但只写一页 D121 修订，不必再开一轮“重新冻结防伪、生命周期和消息体积门槛”的阶段（§4）。**
   - **表示：** 同意“已有证明引用＋摘要＋精确出口 fallback 身份”。每份完整证明只出现在它自己的现有消息里一次。
   - **防伪：** 以现有身份和 revision 比较为主；摘要只在 worker 或 receiver 线程计算，并随结果封存。控制线程上算一次摘要要 31 ms，不能放在 L 帧。
   - **生命周期：** 直接沿用 D117 的 registry 和异步 apply／retire。
   - **体积：** 2 MiB 不动，门槛写成实测数字。
   - **本轮发现、必须写进修订的前提：** 四格后继只能用单 tick 窗口 [L+1, L+1]。窗口放到 L+2 时，晚一拍分支会被现行 0.15 标准支撑规则拒绝（E117：hold 那一拍正是走出边缘仍着地的那一拍，支撑为 0）。所以：
     - L+1 的默认输入必须是出口 fallback（潜行）；
     - 后继首条输入一旦错过 L+1，就作废，不能晚一拍再起跳。
   - **还可以更小：** 安全只依赖当前证明里已经证明过的出口 fallback（S1 已有）。“承诺前后继可证”是活性要求，不是安全要求。它可以这样满足：
     - 第一跳求解时，从候选出口重放一次后继固定输入（约 20 步），结果记进现有的 `continuation`；
     - 完整后继证明照旧走 D117 路径在空中准备；
     - L 帧还没 READY 就潜行。

     这样联合事实不必成为新消息。修订里应在这两种做法中选一种，并写明理由；我倾向后者。
5. **收敛性：D118–D120 的防御是必要的；D121 之后开始只防不收。**
   - **产品能力没有变化：** 自 D115 起 7 个决定里有 4 个以 STOPPED 结束（D115、D116、D118、D121）。生产链在 1-1-4 地形上仍然找不到路线（E118），prepared 自动后继仍默认关闭。
   - **改动以测试、脚本和文档为主：** 这次提交在行尾变化之外：
     - 生产代码 +700／−127；
     - 测试 +3172；
     - 脚本 +3879；
     - 文档 +1299；
     - 87 个证据文件。
   - **建议把 D121 的完成定义收窄成一个可演示的结果**（§5）：组件链在 1-1-4 地形上，后继按时就跨过；后继被拒、过期或迟到就潜行停在中间平台。
6. **小问题：**
   - 7 个文件又整文件从 CRLF 换成 LF（E119），包括 `motion_solver.py`（实际改动 376 行，diff 显示 3564 行）和 `physics_1_21.py`（实际 18 行，diff 显示 1122 行），违反 D118 决定 §8 自己写的规则。
   - D121 决定头部状态仍是 “AUTHORIZED／IN PROGRESS”，计划和验收是 “PARTIAL／STOPPED”。

### 2.3 晚一拍分支被拒的原因

晚一拍分支先按 hold 输入（前进＋疾跑）走一拍，证明器要求这一拍仍满足标准支撑（`_safe_support`，0.15）。

| 状态 | z | 着地 | 标准支撑 |
|---|---:|---|---|
| L（D120 名义落地） | 2.050 | 是 | 是 |
| L+1 hold 之后 | 2.437 | 是 | 否 |

身体已经整个越过平台边缘，但按原版碰撞仍报告着地，也就是上一轮说的“走出边缘那一 tick 仍可起跳”。D120 把 `landing-immediate-late1` 当正例校准过，但现行 prepared 证明器不会接受这条分支，而且不接受是对的：这一拍没有支撑，不能当作“等待”。

所以 D121 的后继只能是单 tick 窗口，这正好与 D121 §2(3)“`L` 决定，`L+1` 生效”一致。但这个前提现在只是碰巧成立，没有写进任何文档，应在下一份修订里写明。

## 3. S2 的止损复核

### 3.1 复现（E113）

在 Linux 上运行 `scripts/d121_joint_worker_stop_probe.py`，结果与公开的 `s2/stop.json` 逐项相同：

- 规范内容 1,941,363 bytes，pickle 2,137,317 bytes；
- 各部分字节相同；
- 注入的预算异常映射为 `BUDGET_EXHAUSTED -> STALE`，没有 READY。

### 3.2 字节从哪里来

`DiagnosticJointEnvelope` 由以下几部分组成：

| 组成部分 | 内含 | 规范字节 |
|---|---|---:|
| `request` | 含当前证明的绑定，418,160 | 428,348 |
| `proof` | 后继证明 | 544,471 |
| `joint_fact` | 再放一次当前证明和后继证明 | 966,102 |
| `sealed_bytes` | 上面三者的规范 JSON | — |

再加上 pickle 里的对象本身：

- 当前证明出现 2 次，后继证明出现 2 次；
- 规范 JSON 又把整体再带一遍。

现行 `seal_bundle()` 也是“对象＋规范 JSON”两份，所以正式后继消息里 `sealed_bytes` 就占 83%–89%。

| D121 场景：第一跳和第二跳各一条完整正式消息 | 1,082,574 | 52% |

### 3.4 为什么说是过度防御

- **D121 §6 没有登记体积止损。** 它的停止条件是：
  - 有限样本升级为连续包络；
  - 承诺前无法证明 fallback；
  - L→L+1 不稳；
  - 需要新的 Session 状态、owner、账本或输入出口；
  - 需要改规划器或 profile；
  - 需要放宽规则；
  - 特判扩散到 3 个以上模块；
  - 两轮修正后仍有新的跨层阻塞；
  - 旧成功退步。

  “消息超限”不在其中。S2 文本里说“预登记的消息体积止损”，指的只能是代码里的 2 MiB 上限。不提高上限是对的，但改掉重复的表达本来就在 S2 的设计里（“联合结果使用现有异步身份、snapshot lease、预算和 registry”）。
- **停止依据的是一个刻意复制两份完整图的测试侧对象。** 第一次生产试做已撤回，而且不可复现。
- **S2 新增的 5 个测试里，3 个把失败固定下来：**
  - `assertGreater(direct_copy_pickle_bytes, MAXIMUM_MESSAGE_BYTES)`：证明一旦变小，测试就失败；
  - `assertFalse(hasattr(prepared_motion, "PreparedJointMotionProof"))`：实现联合类型就失败；
  - 证据与复现逐项相等：任何证明字段变化都会失败。

  AGENTS.md 要求测试验证行为、接口或失败边界。这几项只是复述一次历史测量，应改为只读的历史记录（文档和冻结 JSON 已经保存了它），或者删除。

## 4. 下一步决定该写什么

需要写，因为 D121 计划自己规定“继续前要另行决定”，而且这确实改变了 S2 的表达方式。但它应是 D121 的一页修订，不是新的阶段，也不需要新的 S0。下面是建议的内容。

### 4.1 表示

- 每份完整证明只在它自己的现有消息里出现一次：
  - 当前证明随普通 SOLVE 结果；
  - 后继证明随 prepared bundle。
- 联合事实只含引用，不含任何完整证明：
  - 当前证明的异步身份和候选 revision；
  - 当前证明的摘要；
  - 出口边界序号；
  - 出口 fallback 的候选 id 和尾段摘要；
  - 后继请求 id 和期望输入摘要；
  - 后继证明摘要。

  约 4–14 KB（§3.3）。

### 4.2 防伪

沿用现有原语，不新建框架：

- **身份与 revision 比较为主：** 控制进程持有当前证明对象，后继请求已经绑定：
  - 精确入口状态（等于当前证明的出口状态）；
  - generation、owner、route 和 action；
  - route／action／goal revision；
  - 继承的依赖版本。

  当前证明一旦被替换，它的出口状态或 revision 就不再匹配：现有 prepared 校验比较 route／action revision，执行器在交接时还用 `verified_start_state_matches()` 比较后继入口，都会拒绝这个后继。
- **摘要只在后台算：** 用现有的 `canonical_motion_digest()`，在 worker 或 receiver 线程计算，并封存在结果里。S1 之后，一格跨隙当前证明的摘要在 Linux 上中位要 31 ms（E116），绝不能在控制线程或 L 帧计算。
- **出口 fallback 的身份要与当前证明里那一条完全相同**，包括 candidate、owner、generation、route、action 和首效 tick。

### 4.3 生命周期

- 沿用 D117 的 registry、原子完成和异步 apply／retire。
- 唯一新增的是 S3 本来就要做的一条：选择 fallback 后，当前 owner 持有身体，直到 fallback 终态，并且 release witness 成立。

### 4.4 消息体积

- 不改 2 MiB 上限。
- 门槛写成可复核的数字：D121 代表场景每条正式消息不超过上限的 50%。现值分别是 22% 和 29%。
- 报告证明规范字节，供后续长动作链参考。
- 删除或改写 §3.4 的三项锁定测试。

### 4.5 本轮发现的前提

- **后继窗口只能是 [L+1, L+1]（§2.3）。**
- **L+1 的默认输入必须是出口 fallback（潜行）：** 由当前动作在出口处预先排好，被批准的后继在 L+1 精确覆盖它。后继首条输入错过 L+1 就作废，不能在 L+2 起跳。
- **输入流起点晚一拍不再由“晚一拍仍可接续”吸收：** 这是 D118 §3 的第二类时序。在这个设计里，它只会导致安全的潜行停车。后台交付抖动（第一类，D113 的 D/D+1）只影响后继能否在 L 前 READY。这比上一轮我估计的更保守，但仍然安全，应在验收里单列一行“后继首条输入迟到 → 潜行停在中间平台”。

### 4.6 更小的选项：不新增联合消息

- **为什么可以不要联合消息：** 安全只依赖当前证明里的出口 fallback。S1 已要求每个边界、包括出口，都有经过证明的尾段。“第一跳承诺前后继可证”只是避免做无用功的活性要求。
- **怎样满足活性要求：**
  - 第一跳求解时，从每个候选出口重放后继固定输入。S0 测到第二跳加潜行合计 28 步，在 Windows 上 P95 为 2.5 ms。
  - 重放通过的结果记进现有的 `VerifiedMotionResult.continuation`。现行 `_accept_upcoming_selection()` 已经比较 `proof.continuation == request.continuation`。
- **完整后继证明** 仍走 D117 现有路径，在第一跳空中准备。D121 第一跳有 26 tick，时间足够。
- **L 帧：** 后继 READY 且有效就接续，否则执行出口潜行。
- **代价：** 不需要新的联合类型，也不需要新的消息、门槛或测试族。修订里应在这一选项和 §4.1 之间选一种，并写明理由；我倾向这一个。
