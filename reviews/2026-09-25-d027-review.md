## 结论

1. **上一轮的三个实现问题和两处记录偏差都已处理，复现结果符合预期。**
   - 正式导航驱动在首条命令晚一个 tick 生效时，账本仍判为窗口内，由新增的 Runtime 集成测试覆盖。
   - 起点选择在“整格方块边缘、旁边是半砖”时，选中的是整格方块。
   - 跨多个 tick 的偏差不再标成击退。
   - D024 的文字与代码一致了。

   - 我用新的相邻规则回放公开 C1-C 批次：33 次击退中有 32 次仍判为击退，唯一跨 3 个 tick 的那次转为“运动未验证”，与文档描述一致。
2. **新发现一个中等问题，是 D027 引入的：空中多出一个客户端 tick，会让整个 Runtime 失败并重建**（第二节）。
   - Runtime 要求窗口的最早 tick 恰好等于“当前观察 tick + 1”，但执行器计算下一条命令的 tick 时不看当前锚点。
   - 一旦观察比预期晚一个 tick 才采样，Runtime 就在发送前报出 `observation_invariant`，处置为 `recreate_runtime`。与此同时，导航驱动释放了输入源，而已验证的执行器仍处于 `RUNNING`（人在空中）。
   - 这种情况原本的设计出路是 `INPUT_LOST`，然后保持落地。
   - 触发概率不高（公开轨迹的控制过程中几乎没有跳过 tick），但后果重，而且以前只影响 B10 探针，现在覆盖了战斗和 B11 的正式路径。
3. **证据边界写得如实。**
   - 本轮的两个新实机批次（B10 `a059bdc6`、C1-C `ab9ef883`）没有公开。
   - 公开包仍是上一轮的 7 个批次，文档也写明了这一点。
   - “首条命令晚一个 tick”没有写成实机证据。

## 二、新问题：空中多一个客户端 tick，会让 Runtime 重建

**机制：**
- D027 让每条已验证的移动意图都带上窗口。
- Runtime 在发送前检查“窗口最早 tick == 当前观察的运动 tick + 1”，不满足就抛出 `ContractViolation`（[`player_runtime_v1.py:543-547`][detached]）。这个异常被归类为 `observation_invariant`，处置是 `recreate_runtime`。
- 执行器提交下一条命令时，tick 只按 `start_tick + command_index` 计算（[`motion_candidate.py:360-362`][expected]、[`:540`][next-command]），不和当前锚点比较。

**复现**：[`extra_client_tick_recreates_runtime.py`](2026-09-25-d027-repro/extra_client_tick_recreates_runtime.py)。
- 使用 D027 自己那条晚 tick 测试所用的正式路径夹具。
- 改动只有一处：第二条空中命令按时在 tick 3 生效后，客户端又跑了一个 `lease_exhausted` 的 tick，然后才采样观察。这正是真实客户端卡顿后补跑 tick 时会出现的情况，而且真实客户端在租约用尽的 tick 上会保留上一请求的身份。

| 帧 | 结果 |
|---|---|
| 0 | 正常提交第二条已验证命令 |
| 1 | Runtime 失败：`observation_invariant`（“input execution window is detached from the current movement tick”）；Runtime 状态 `failed`，处置 `recreate_runtime`；导航驱动 `failed/runtime_failure`，输入源释放；已验证执行器仍是 `running` |

**说明：**
- 对照上一提交的尝试不能说明问题，因为这个夹具只在非中性命令时推进 tick，旧代码会卡在中性空中命令上等待生效。所以我不拿夹具去证明“旧代码行为更好”，只看设计意图。
- 按设计，“命令无法在证明的 tick 生效”应当由执行器判为 `INPUT_LOST`，然后发中性输入、保持落地（`_consume_pending` 和 `retain_landing_after_input_loss` 就是为此写的）。
- 现在 Runtime 在执行器看到这个情况之前就让整条控制链失败了。

**触发概率：**
- 我统计了公开的 C1-B 和 C1-C 批次中同一任务相邻两次观察的运动 tick 间隔：C1-C 的 1207 次全是 1；C1-B 的 1801 次里，有 4 次间隔为 6，其余都是 1。
- 所以正常运行时很少发生。但卡顿后补跑 tick 是 Minecraft 客户端的常见行为，一旦恰好发生在跨隙途中，代价是整个 Runtime 被重建。

**建议：**
1. 执行器在提交下一条已验证命令之前，先比较 `anchor.movement_tick_id + 1` 与 `_expected_tick()`。如果当前 tick 已经越过了证明允许的 tick，就进入 `INPUT_LOST` 和保持落地。这样过期检查由拥有证明的一方完成，Runtime 的检查只作为最后防线。
2. Runtime 发现窗口已过期时，改为返回有类型的“本帧未发送”结果，而不是契约错误。窗口过期是时序事实，不是观察不变量被破坏，不应导致重建 Runtime。
3. 把复现中的场景加进 `test_runtime_navigation_verified_handoff.py`。

## 五、对照总体设想

D027 定下的规则是“约束挂在意图上，仲裁后只采用赢家的约束”。这正是 B12-B 同帧组合（移动、视角、放置或攻击来自不同拥有者）需要的基础，方向对。

第二节的问题补充了一条同样适用于 B12-B 的规则：
- 每个拥有者在提交意图前，要先用当前观察检查自己的约束是否还成立；过期了就走自己的有类型恢复。
- Runtime 的检查只作为最后防线；发现过期时，给出“这一帧不发送”的结果，而不是把整个控制链判为不可恢复。
- 否则组合的来源越多，一个来源的时序偏差就越容易把其他来源一起拖垮。

## 六、建议（按优先级）

1. **执行器：** 提交已验证命令之前核对当前锚点 tick，越过证明允许的 tick 时进入 `INPUT_LOST` 并保持落地；补“空中多一个 tick”的正式路径测试。
2. **Runtime：** 窗口过期改为有类型的“本帧未发送”，不要触发 `recreate_runtime`。
3. **证据：** 下次更新公开包时，考虑用本轮的 B10 批次（`a059bdc6`）替换 B10-C 通过批次，因为它对应的是 D027 之后的代码。
